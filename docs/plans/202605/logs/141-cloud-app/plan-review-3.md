## CRITICAL

**C1 — `claude.yml` auth-model incoherence + no consumer-shipped template (design-coverage gap, success criterion unsatisfiable).**
FINAL SCOPE decision 6 + Success Criterion 10 require design/plan/build + manual ship/debug to launch via `@claude /bkit-<phase>`, wired in `claude.yml`. Two problems the plan understates:
(a) **Auth divergence.** `claude.yml:37` authenticates with `claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}` (Claude subscription OAuth), while `bkit-cloud.yml` is being rebuilt on `ANTHROPIC_API_KEY` + `id-token: write` (OIDC App). These are two different auth mechanisms and two different required secrets. The plan's T4.1 "Done when: auth model coherent with `bkit-cloud.yml`" is unsatisfiable as written — they do not share an auth path or a secret. The plan must explicitly decide whether `claude.yml` moves to `ANTHROPIC_API_KEY` (consumer would then need both secrets, or one) or whether the "appear as the App" claim only applies to `bkit-cloud.yml`. This is the core "rewrites the auth model" risk and is left ambiguous.
(b) **No template.** Glob confirms `claude.yml` exists only at `.github/workflows/claude.yml` (this repo's live file) — there is NO `.agents/templates/.../claude.yml`. The plan (Arch §Block 4) flags "verify whether a template copy exists" but adds NO task to ship one. Without a shipped `claude.yml`, consumers on GitHub-tracker repos cannot use the `@claude /bkit-<phase>` primary trigger surface at all — Success Criterion 10 + the Concrete Example Step 1 are unreachable for any consumer. Either add an explicit task to ship a consumer `claude.yml` template (with its own auth wiring + `ANTHROPIC_API_KEY`/App requirement) under the `cloud=claude` module, or add an explicit out-of-scope note that `@claude` triggering is bkit-repo-only this cycle. As written this is an uncovered touched surface.

**C2 — Bare `Auto` survives in `bkit-modules.ts` advisory text after the label migration (re-entry into the migrated-away pattern).**
The Labels success criterion and Supersession Inventory migrate bare `Auto` → `bkit:auto` only in the two preflight hooks. But `runCloudModule`'s `bkit-cloud-setup` advisory still emits bare `Auto` at `bkit-modules.ts:2051` ("reads the `Auto` opt-in label"), `:2054` ("labelled `Auto` in Linear"), and `:2055` ("carries the `Auto` label"). These are consumer-facing strings shipped by bkit describing the exact gate label the migration renames. Leaving them ships inconsistent label guidance (advisory says `Auto`, hooks check `bkit:auto`) — the precise inconsistency FINAL SCOPE's "consistency required" clause exists to prevent. Add these three lines to the migration task (T4.2 or T1.7). Also note: those lines live in the `isLinearCloud` branch, which the cloud-split (cursor=linear) may delete wholesale — reconcile the migration with the split so the strings are fixed-or-removed, not stranded.

**C3 — `bkit-postinstall.ts` cloud advisories assume `LINEAR_API_KEY` in `bkit-cloud.yml` (uncovered consumer of the deleted Linear branch).**
`buildCloudSetupAdvisory` (803), `buildCloudDashboardsAdvisory` (849) and `buildCloudSecretsAdvisory` (895) all branch on `tracker==="linear"` to add `LINEAR_API_KEY` to the `bkit-cloud.yml` secret set and to phrase "post-CI auto-routing" around a Linear-flavoured workflow. Decision 1 + criterion "Vestigial Linear branch removed; bkit-cloud.yml is GitHub-only" makes a Linear `bkit-cloud.yml` impossible — so these advisories now describe a state that can never exist, and `buildCloudSecretsAdvisory` would tell a (mis-recorded) consumer to set a secret the GitHub-only workflow never reads. These are direct downstream readers of the surface being deleted, yet `bkit-postinstall.ts` is absent from the plan's in-scope surfaces, Architecture section, and Derived Test Matrix. Add a task to reconcile these three advisory builders with the GitHub-only model (and the cloud=claude/cursor split), and a test row. This is the classic "schema column dropped, downstream reader not updated" regression.

**C4 — Two-tier YAML gate has no defined branch→issue derivation for the in-job `bkit:auto` re-check (kill-switch unimplementable as specified).**
Decision 7 / T2.7 specify the cheap tier as `gh issue view {ISSUE} --json labels`. But on the `workflow_run` (CI-completion) path, `bkit-cloud.yml` only resolves a **PR number** (`gh pr list --head "$BRANCH"`, line 123) — it never resolves the linked **issue**. There is no established branch/PR→issue mapping in the workflow. As written, `{ISSUE}` is undefined on the auto-route path, so the live kill switch (the entire cheap tier, Edge Case row "issue lost `bkit:auto`", and Concrete Example Step 3) cannot be implemented. The plan must specify how the YAML derives the issue number from a `workflow_run` event (FID-from-branch → issue, or PR-body cross-ref) — this is the same FID-derivation that D3's concurrency key (T3.1) needs, so the two should be specified once and reused. Additionally, T2.6 moves the orchestrator's kill-switch _propagation_ (which removes the `bkit:auto` PR label, per `trackers.md:169`/`bkit-cloud.md:193-196`) into YAML; the plan only ports the _check_, not the propagation — a behavioural regression in the kill switch unless explicitly re-homed or dropped by decision.
