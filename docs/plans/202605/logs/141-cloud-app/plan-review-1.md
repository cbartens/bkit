## CRITICAL

### C1 — `claude.yml` auth-model coherence is asserted but unverifiable as written (Block 4 / Decision 1 / checklist item 1, 10)

The plan repeatedly states both workflows "authenticate as the App" and that `claude.yml`'s auth is "coherent with `bkit-cloud.yml`" (T4.1 Done-when, Success Criteria, Edge Cases, Security & Privacy). But the live `.github/workflows/claude.yml:37` authenticates via `claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}` — a different mechanism than `bkit-cloud.yml`'s intended `ANTHROPIC_API_KEY` + `id-token: write` OIDC path. These are NOT the same auth model. The plan does not reconcile them:

- The FINAL SCOPE never says `claude.yml` and `bkit-cloud.yml` share one auth mechanism — it says both surface as "the App". `claude.yml` is the App-generated workflow (from `/install-github-app`); `bkit-cloud.yml` is bkit-shipped and must add `id-token: write` to reach the App via OIDC. The plan conflates "both appear as the App" with "both use the same token input".
- T4.1's Done-when ("auth model coherent with `bkit-cloud.yml`") is not codebase-verifiable as phrased — there is no test or grep that proves "coherence" of two different auth inputs. **Restate the criterion** to something testable, e.g.: "`claude.yml` retains `claude_code_oauth_token` + `id-token: write`; `bkit-cloud.yml` gains `id-token: write` + keeps `ANTHROPIC_API_KEY`; both run as the Claude App." Remove the implication that they share an input.

This blocks because Block 4 is the trigger-wiring foundation for checklist items 1 and 10 (live dispatch reaches a Claude turn; `@claude /bkit-<phase>` launches phases) and the current Done-when cannot be checked off honestly.

### C2 — `claude.yml` is not bkit-shipped; the plan must decide whether T4.1 edits a non-managed file (Block 4 scope)

`Glob **/claude.yml` returns ONLY `.github/workflows/claude.yml` — there is no template copy under `.agents/templates/`. `claude.yml` is generated by the Claude GitHub App's `/install-github-app`, not by `bkit install`. The plan flags this as an open question (Block 4 note line 335: "verify whether a template copy exists") but then T4.1 still lists `.github/workflows/claude.yml` as a `[MODIFY]` target with a Done-when that asserts routing changes.

This is a scope-discipline gap: if `claude.yml` is App-owned, bkit editing this repo's copy is dogfooding-only and does NOT ship to consumers — meaning the consumer-facing `@claude /bkit-<phase>` behaviour (checklist items 6/10) is governed by the App's default `claude.yml`, not by anything bkit writes. The plan must explicitly resolve: (a) does `@claude /bkit-<phase>` work with the stock App `claude.yml` (the `if:` at lines 16-19 already fires on any `@claude` comment, and the typed command is passed through as the prompt) so T4.1 reduces to a verification + doc task, or (b) does bkit need to ship/template a `claude.yml`? As written, T4.1 risks editing a file that is overwritten by the App and never reaches consumers. **Decide and rewrite T4.1's scope before execution.**

### C3 — Two-tier CI gate omits how the in-job re-check resolves `{ISSUE}` from a `workflow_run` event (T2.7 / Decision 7 / checklist item 6)

T2.7 and the Architecture block specify the cheap-tier kill switch as `gh issue view {ISSUE} --json labels`, but neither the plan nor the current `bkit-cloud.yml` establishes how `{ISSUE}` (the linked tracker issue) is derived inside the `workflow_run` job. The live `bkit-cloud.yml:117-129` CI path resolves a **PR number** from the head branch (`gh pr list --head "$BRANCH"`), not an issue number; the FID/issue linkage is not currently extracted in that job. The `bkit:auto` label lives on the issue, not the PR. Without a concrete derivation step (branch → FID → issue, or PR → linked issue), the kill switch cannot be implemented and T2.7's Done-when ("exits no-op when `bkit:auto` is gone") is not verifiable.

This is the live kill switch — the security/trust boundary called out in Security & Privacy and checklist item 6. **Add an explicit `{ISSUE}` resolution sub-step** (e.g. derive FID from `head_branch` `feat/{FID}`, map FID→issue) to T2.7 / the Architecture Block-2 YAML task, and make the Done-when reference it. Note this couples with D3's "FID-derived token" (T3.1) — the same branch→FID derivation feeds both, which the plan should state once and reuse.

### O3 — Manifest split vs. variant-gated emission left as an in-task choice (T1.5)

T1.5 / Architecture offers two implementations ("split the manifest… or keep one manifest but gate file emission by variant"). The deciding constraint is uninstall correctness: `.cursor/Dockerfile` is `markered-text` and `bkit-cloud.yml` is `byte-equal-text` (verified `bkit-manifest.ts:212-214`), and uninstall walks the manifest. A single manifest with variant-gated _emission_ but unconditional _uninstall listing_ would orphan files on `uninstall --cloud` for the unused variant. Recommend stating that uninstall must remove only the recorded variant's files, and pick the manifest-split approach to make that mechanical. T1.5's Done-when already tests "uninstall removes the variant's files" — promote that constraint into the design note so the agent does not pick the lossy option.
