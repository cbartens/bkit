# Design Brainstorm & Ideas

Lens: Optimal-tradeoff — best long-term shape ignoring legacy constraints.

Pass: 3 (extension of the PASS'd 10-step / 16-agent design). Approaches focus on the five pass-3 delta surfaces: UI/UX lens; reference-repo signal + down-weighting contract; supply-chain/CI-CD security split decision; conditional data-layer/DB + AI/LLM lenses; the KEYSTONE conditional-lens model (applicability flags + "N/A" coverage state + minimal-here-vs-full-#207 boundary).

## Approach A — Minimal Conditional-Lens Model + Strict Signal Tier Separation ⭐ Recommended

Summary: Extend `audit-stack.md` with a boolean applicability-flag block (`hasWebSurface`, `hasDb`, `hasLLM`), add "N/A — not applicable" as a first-class coverage state in `## Missing Lenses`, gate UI/UX and data-layer/DB and AI/LLM on those flags in the orchestrator fan-out (Step 5), and introduce a hard signal-tier contract — `confidence: low` + an `externalSignal: true` marker on all reference-repo findings — so every downstream agent (synthesise, organise, summary) can mechanically enforce "never top/critical" without ad-hoc prose instructions. Supply-chain/CI-CD security becomes a separate 13th lens (not merged into `security`) because pipeline hardening and app-level auth are orthogonal disciplines with distinct probe sets.

- **Complexity:** MEDIUM. The applicability-flag block adds three boolean fields to `audit-stack.md` (already owned by `bkit-audit-stack-detect`); the orchestrator adds a conditional branch per flag in Step 5; synthesise and organise get a two-tier rank rule keyed on `externalSignal: true`. The new conditional logic lives in one place each (stack-detect produces flags; orchestrator reads flags; synthesise/organise/summary enforce tier). No new agent archetypes; the same read-only-reviewer skeleton applies to UI/UX, supply-chain, data-layer, and AI/LLM lenses.
- **Extensibility:** HIGH. Adding a future conditional lens (e.g. mobile, WebAssembly) means: (a) add one boolean to `audit-stack.md` schema, (b) wire one detection heuristic in `bkit-audit-stack-detect`, (c) author one lens prompt, (d) add one fan-out conditional in Step 5. The signal-tier contract is field-keyed so a third signal source (e.g. CVE database) would add a new marker value, not new rank logic. The "N/A" coverage state is extensible by definition — any new conditional lens that does not apply just records "N/A", and the coverage manifest remains a complete picture.
- **Risk:** The applicability-flag detection heuristics in `bkit-audit-stack-detect` are the load-bearing piece: a false-negative `hasWebSurface: false` on a repo that does have a frontend surface causes the UI/UX lens to silently skip a real surface. Mitigation: detection heuristics are evidence-based (presence of HTML/CSS/JSX/template files + `frameworks[]` list), not binary config flags, so a partial frontend shows up as `hasWebSurface: true`; the `confidence` scalar already covers ambiguous cases (low-confidence = CONCERNS on the step). False-positive `hasWebSurface: true` on a repo without a web surface causes a lens to run and find nothing — a correct null result, not a false-all-clear. The `externalSignal: true` marker thread risks being forgotten by a new lens author; mitigated by making it a required field in the reference-signal agent's output contract, asserted by the synthesiser's `awk` parser.
- **Maintenance:** LOW-MEDIUM. Three new boolean fields in `audit-stack.md` schema — low churn once stable. The signal-tier contract in synthesise/organise/summary is a grep-assertable rule (`externalSignal: true` findings drop one severity bucket and are excluded from the top-N ranked list); once implemented it is self-enforcing. The "minimal here vs full #207" boundary is explicit: this approach ships ONLY the three flags needed for THIS issue's conditional lenses (`hasWebSurface`, `hasDb`, `hasLLM`) and the N/A coverage state; #207 generalises the model to an arbitrary applicability-tier schema. The boundary is stated in the design doc and the `audit-stack.md` schema comment so future #207 work knows exactly what to extend rather than replace.
- **Friction vs ideal:** LOW. The existing `audit-stack.md` schema already permits extension (it has a `schemaVersion` field for exactly this reason). Adding three booleans is additive. The "N/A" coverage state requires updating the `## Missing Lenses` format in the synthesiser and the Step 6 orchestrator grep-assertion — both are localised changes. The reference-signal agent is a new prompt (not a modification of any existing lens), so it does not disturb the 12 universal lens prompts. The orchestrator Step 5 fan-out grows from "invoke 11 lenses" to "invoke 12 universal lenses + invoke reference-signal agent + conditionally invoke 0-3 conditional lenses based on flags" — the conditional branch is the largest new orchestrator surface.

## Approach B — Flat Fan-Out with Post-Hoc Filtering (No Applicability Flags)

Summary: All new lenses (UI/UX, supply-chain, data-layer, AI/LLM) run unconditionally in the Step 5 fan-out. Each lens is responsible for detecting whether its surface is present and gracefully emitting zero findings if not. The `## Missing Lenses` coverage manifest records "ran, zero findings" for lenses that self-determined no surface was present. No applicability flags added to `audit-stack.md`; no conditional orchestrator branching; no "N/A" coverage state.

- **Complexity:** LOW. The orchestrator Step 5 fan-out remains a flat list — invoke all lenses, await all results. No conditional logic in the orchestrator. Each lens carries its own surface-detection heuristic in its probe block. The reference-signal agent also runs unconditionally; it emits `confidence: low` on all findings but no separate marker field.
- **Extensibility:** MEDIUM. Adding a new conditional lens means adding one prompt and one fan-out slot — the same steps as Approach A. But the lens must now encode both its surface-detection heuristic AND its probes, coupling two concerns in one prompt. If the detection heuristic changes (e.g. detecting a DB by ORM package vs by migration file presence), all consumers of that heuristic (the single lens prompt) update in one place, which is actually simpler than the two-place update in Approach A (stack-detect + lens). However, if two future lenses share the same detection heuristic (e.g. both data-layer and AI/LLM need to know "is there a DB?"), the heuristic is duplicated across two prompts.
- **Risk:** The critical problem: a conditional lens that runs on bkit's own repo (no UI, no DB, no LLM usage) will produce zero findings. The `## Missing Lenses` manifest records "ran, zero findings" — which is indistinguishable from "ran, genuinely clean." A human reading the audit report cannot tell whether the UI/UX lens found nothing because the repo is clean or because there is no UI surface to audit. This is the "false all-clear" problem the design-input explicitly identifies as the keystone risk. Without a distinct "N/A" state, every conditional lens produces misleading signal when it runs on an inapplicable surface.
- **Maintenance:** MEDIUM. Detection heuristics duplicated across lens prompts create drift — the UI/UX lens and a hypothetical layout-shift lens could diverge in their definition of "has a web surface." The synthesiser has no way to assert that all lenses agreed on surface presence. The `externalSignal` marker is absent from this approach; the reference-signal down-weighting is a prose instruction in the synthesiser and organise prompts ("treat findings without internal evidence lower"), which is unenforceable by the `awk` parser and cannot be asserted at Step 6.
- **Friction vs ideal:** MEDIUM-HIGH. The false-all-clear problem is a correctness gap, not a future-extensibility concern. Fixing it later requires adding applicability flags (Approach A's model) retroactively, which touches `audit-stack.md` schema, all conditional lens prompts (to remove their self-detection), the synthesiser, organise, summary, and the Step 6 gate — a larger migration than doing it correctly in this pass. The reference-signal down-weighting without a machine-readable marker is the second correctness gap: the rule "never top/critical" is only as strong as the prose instruction in each downstream agent, and prose drifts.

## Approach C — Separate Reference-Signal Agent with Hardened Tier Fence + Deferred Conditional-Lens Model

Summary: Treat the reference-repo signal as a structurally distinct tier by making it a non-lens agent with its own output file (`audit-reference-signal.md`) and a hard schema barrier — all findings are emitted with `tier: external` (not `tier: internal`), and the synthesiser uses `tier` as the primary rank key before `severity`. The "N/A" coverage state and applicability flags land as a pass-3 minimal model (same as Approach A), but the supply-chain/CI-CD lens is merged INTO the existing `security` lens as a new probe section rather than a separate lens, keeping the universal fan-out count lower. Conditional lenses (data-layer, AI/LLM) are explicitly deferred to #207.

- **Complexity:** MEDIUM. The `tier: external|internal` field on findings is a single-field addition to the `finding` block schema — the awk parser gains one rule: external-tier findings rank after all internal findings regardless of severity. The synthesiser's rank algorithm becomes two-phase (internal by severity, then external by severity). Supply-chain merging into `security` avoids a new prompt file but adds probe scope to an existing one. Deferring data-layer and AI/LLM removes two conditional lenses from this cycle.
- **Extensibility:** MEDIUM-HIGH. The `tier: external|internal` field is a clean extension point — a future "org-policy" tier or "compliance-database" tier adds one new enum value and one sort key. The security lens merge works until the probe block gets too large (>25 findings ceiling means supply-chain probes compete with app-security probes for slots — a real tension in large repos with both surfaces). Deferring conditional lenses to #207 means #207 inherits both the minimal conditional-lens model from this pass AND the two new lenses — less scope divergence than landing a partial model here and a full model in #207.
- **Risk:** Merging supply-chain into `security` creates a probe-competition risk: each lens caps at 25 findings, and app-security findings (auth holes, input validation, secret-in-code) and pipeline findings (unpinned Action SHAs, over-broad token perms) compete for slots in one lens. A repo with many app-security issues will crowd out supply-chain findings even when both are important — a severity-ranking artefact, not a real severity judgment. The `tier: external|internal` approach is cleaner than the `externalSignal: true` boolean marker in Approach A (it expresses a richer concept), but it requires a schema change to the canonical `finding` block — all 12 (or 15) existing lens prompts need a `tier:` field added, which is a larger migration surface than adding a top-level marker.
- **Maintenance:** MEDIUM. The `tier` field in the `finding` schema is low churn once stable. The security lens with merged supply-chain probe block is a larger prompt with mixed concerns — supply-chain probes (Bash for git history scan, lockfile integrity) conflict with the security lens's read-only tool surface (`Read, Grep, Glob, Write`). Adding `Bash` to the security lens to support git-history scanning makes it no longer a read-only auditor, breaking the clean lens tool-surface invariant. Deferring the conditional lenses defers the "N/A" state's value proposition: the minimal conditional model ships with only `hasWebSurface` for the UI/UX lens, which is a thinner implementation than the three-flag model in Approach A.
- **Friction vs ideal:** MEDIUM. The `tier` field migration across all existing lens prompts is non-trivial (12+ files). The security lens tool-surface conflict is a real constraint — if supply-chain probes need `Bash` (git-history scan, lockfile integrity), the lens cannot stay read-only, which violates the lens skeleton invariant. Splitting supply-chain as a separate lens (Approach A) resolves this cleanly: the supply-chain lens carries `Bash` in its tool surface independently of the `security` lens. Deferring data-layer/AI/LLM to #207 is defensible on scope grounds but means the conditional-lens model shipped here is tested against only one conditional lens (UI/UX), reducing confidence before #207 lands the full model.
