# Design Brainstorm & Ideas

Lens: Optimal-tradeoff — best long-term shape ignoring legacy constraints.

## Approach A — Linear Pipeline with Strict Step Isolation ⭐ Recommended

Each workflow step is a discrete, atomic unit: stack-detect runs first and writes `audit-stack.md`; skill-install runs next and conditionally installs matching skills; then 11 lens subagents fan out in parallel, each reading `audit-stack.md` and any installed skill overlays but never each other; synthesise and organise are sequential reducers. The orchestrator owns all git/tracker ceremony; subagents are pure leaf writers.

- **Complexity:** MEDIUM. Two new steps (stack-detect, skill-install) before the fan-out; each is a single-subagent invocation with a clear input/output contract. The orchestrator step-numbering shifts by +2 relative to the superseded design (Steps 3+2 = fan-out now at Step 5). No new concurrency model needed.
- **Extensibility:** HIGH. Adding a new lens means adding one prompt file and one fan-out slot in Step 5 — zero changes to the stack-detect or skill-install steps. Adding a new skill type (e.g. `audit-python`) means authoring the skill and potentially extending the `npx skills find` query in Step 4 — the orchestrator logic is unchanged. Phase 3 WebSearch lands as a Step 6 conditional inserted between lens fan-out and synthesise.
- **Risk:** The skill-install step is conditional and potentially a no-op (no matching skills found). If `npx skills find audit-{stack}` returns nothing, the pipeline must continue gracefully rather than stalling at the gate. The gate needs a `skills found: 0 → SKIP` branch or the Failure Path gets triggered spuriously. A second risk: if `audit-stack.md` is malformed or omits a key field (e.g. package manager), lens prompts that read it may silently use empty values and miss stack-specific probes covered by installed skills.
- **Maintenance:** LOW. Each step has a single responsibility. Lens prompts are purely universal-pattern text with no library names; the only file that changes when the ecosystem evolves is the matching skill. Drift between `audit-stack.md` schema and what lens prompts expect is the main ongoing maintenance concern — mitigated by keeping the schema minimal and documented once in `bkit-audit-stack-detect.md`.
- **Friction vs ideal:** LOW. The existing bkit-design step-ceremony (gate, status.json append, tracker comment, commit) is reused verbatim for each new step. The only novel pattern is the conditional skill-install: the orchestrator needs a `SKILLS_INSTALLED` count captured after Step 4 to populate the gate checklist. The `bkit-build-install-skills` agent already exists and sets a pattern. The superseded design's lens prompts will need full rewrites to strip stack-specific lists — this is the largest migration surface (11 prompt files) but is bounded work.

## Approach B — Inline Stack Context (No Skill-Install Step)

Stack-detect runs before the lens fan-out and writes `audit-stack.md`, but there is no separate skill-install step. Instead, each lens subagent reads `audit-stack.md` and, within its own process, calls `npx skills find` to discover and load any matching skill overlay before running its probes. The skill discovery is co-located with the lens execution, not a pipeline step.

- **Complexity:** MEDIUM. The orchestrator is simpler (one fewer pipeline step), but each lens subagent becomes more complex: it must conditionally invoke a shell command, parse its output, read an additional file if found, and then run its probes. The lens prompt frontmatter needs `Bash` in the tools list for all 11 agents, adding a mutating surface to what should be a read-only auditor.
- **Extensibility:** MEDIUM. Adding a skill still requires no orchestrator changes, which is good. But the skill-discovery logic is duplicated across 11 lens prompts — if the `npx skills find` API changes, all 11 need updating. Phase 3 WebSearch integration is similarly scattered.
- **Risk:** Per-lens skill discovery creates 11 independent shell invocations; if the skills registry is unavailable or slow, 11 agents each stall or fail. Any one failure means re-running the full fan-out. With the linear pipeline (Approach A), a single skill-install failure at Step 4 aborts before any lens work is done — cheaper and clearer.
- **Maintenance:** MEDIUM-HIGH. Skill-resolution logic lives in 11 files, not one. The lens prompts are longer and mixed-concern (skill loading + universal probing). Reviewing whether skills are being applied correctly requires inspecting each lens rather than a single install step.
- **Friction vs ideal:** MEDIUM. The Two-Layer Separation rule (`subagents NEVER call tracker MCP`) does not directly prohibit subagents running `npx skills`, but the existing pattern in `bkit-build-install-skills` places all skill tooling in a dedicated agent rather than distributing it. Moving skill-install into every lens agent deviates from that established pattern and makes the lens prompts non-portable standalone (they now depend on the `npx` environment).

## Approach C — Merged Stack-Detect + Skill-Install Agent

The stack-detect and skill-install steps are merged into a single pre-lens subagent (`bkit-audit-prepare`) that reads manifests, emits `audit-stack.md`, and immediately installs matching skills, writing a combined `audit-prepare.md` with both the stack report and the list of installed skills. The orchestrator invokes one subagent instead of two before the fan-out.

- **Complexity:** LOW. One fewer orchestrator step, one fewer prompt file, one fewer gate checklist, one fewer tracker comment, one fewer status.json entry.
- **Extensibility:** LOW-MEDIUM. The prepare agent has two concerns: stack detection and skill installation. If the skill-install logic needs to evolve (e.g. new skills CLI flags, Phase 3 WebSearch signal injected at install time), the detection logic is in the same file. Future Phase 3 augmentation would require unpacking the merged agent anyway.
- **Risk:** The merged agent's output (`audit-prepare.md`) combines two conceptually distinct artifacts. If skill-install fails partway through (skills CLI unavailable), the stack report may still be valid and the lenses could run with just `audit-stack.md`. A merged agent either fully succeeds or fully fails — there is no recovery path where the orchestrator retries only skill-install using the already-written stack report. This is a hard failure mode with no partial-progress recoverability.
- **Maintenance:** LOW initially, but the merged agent grows over time as both stack-detection heuristics and skill-install patterns evolve. Separating them later requires splitting the prompt, the gate, and the status.json entry — a non-trivial refactor that risks breaking in-flight runs.
- **Friction vs ideal:** LOW initially. The merged step keeps the orchestrator shorter and matches the cognitive model ("prepare the audit environment, then run lenses"). The downside is that the ideal long-term shape (Approach A's clear step isolation) must be reached by a later split, creating two migration events instead of one upfront design decision.
