# Design Brainstorm & Ideas

Lens: Risk premortem — failure modes, scale, time, handover.

> Scope: pass 3 extends the PASS'd 10-step / 16-agent design at `docs/plans/202605/80-audit-workflow-design.md`. NONE of these approaches re-derives the orchestrator shape, two-layer separation, enrichment-never-gates contract, `audit-stack.md` schema, or YAML-`finding` block. All three fold in the pass-3 delta (UI/UX lens, reference-repo signal, supply-chain/CI-CD, conditional data-layer + AI/LLM, the keystone conditional-lens model). They differ on **how applicability + fan-out + the new network surface are organised** — i.e. the load-bearing pass-3 architectural choices.

> Common to all three (do not re-litigate): all lenses `model: claude-opus-4-7` / `effort: high` (comment 4539759063 §2); skill machinery reused incl. uninstall/prune (§1); version not pinned, resolved at build/ship (§3); `--with-websearch` opt-in only; reference-signal capped at `confidence: low` and ranked strictly below internal-evidence everywhere; `## Missing Lenses` gains an `N/A — not applicable` coverage state distinct from "ran clean" and "crashed"; UI/UX prompt carries zero framework names (framework _how_ rides in via `audit-stack.md frameworks` + installed `audit-{framework}` skill); no `gh api`/raw HTTP in workflows (tracker MCP only); ASCII operators only in workflow/prompt files.

## Approach A — Applicability-Gated Fan-Out With Dedicated `audit-applicability.md` Sidecar (Keystone-First, Minimal Conditional Model) ⭐ Recommended

**Summary (one sentence):** `bkit-audit-stack-detect` emits a small, append-only `audit-applicability.md` sidecar carrying the boolean gating flags (`hasFrontend`, `hasDb`, `hasLLM`, `hasCI`, `hasPipeline`, `hasSupplyChain`) alongside `audit-stack.md`; the Step 5 fan-out reads the sidecar and resolves each lens to one of three outcomes — `run`, `skip-na`, or `skip-flag` — written into a fixed-slot artifacts manifest so `## Missing Lenses` can render the third "N/A — not applicable" state without re-deriving applicability at synthesise time.

**Pass-3 fold-in (how the delta lands here):**

- 14 lenses total: 11 baseline + **UI/UX** (gated `hasFrontend`) + **supply-chain/CI-CD** as a **new lens** (gated `hasCI || hasPipeline`, near-always-true — see Decisions) + **data-layer** (gated `hasDb`) + **AI/LLM safety** (gated `hasLLM`). 15th non-lens agent = **reference-signal** (gated `--with-websearch`).
- Fixed-slot manifest: Step 5 always declares all 14 lens slots in `status.json#steps[].artifacts`; gated-out lenses get a zero-byte sentinel + a `skip-reason` line so the synthesiser doesn't have to redo gating logic.
- Step 6 synthesiser reads the sidecar + sentinels and renders `## Missing Lenses` with three explicit states per lens row: `ran`, `N/A — not applicable (flag={flagName}=false)`, `crashed`.
- Reference-signal is a separate agent in Step 5 (not a lens), with its own slot; synthesiser/organise/summary apply the `confidence: low` cap + the strict-below-internal ranking gate (greppable assertion).

**Premortems:**

- **10× scale (the fan-out grows past 14):** Step 5 width = 14 today, plausibly 18–22 within a year (web-perf, DX from #207; runtime probe from #83; per-language sub-lenses). With Opus/high on every slot, p95 step duration is bounded by the slowest lens, not the count — but the orchestrator now ships a 14-row `status.json#steps[5].artifacts` array per run. **What breaks:** the gate that asserts "all declared slot artifacts non-empty" becomes a long boolean AND; one slow lens stalls the whole fan-out toward the 3600s ceiling. **Observability:** per-slot start/end timestamps in the orchestrator's Step-5 progress comment make the slow lens identifiable from the tracker comment alone. **Recovery:** the sidecar's applicability flags double as a re-invocation filter — re-run only the failed slot with `[lenses=slug1,slug2]` (a new input escape worth landing in this pass since it directly mitigates the fan-out width risk).
- **6 months later:** the sidecar fields drift (a new conditional lens adds `hasMobileApp` without bumping the schema; old runs lack the field; readers crash). **What breaks:** any reader that does `applicability.hasMobileApp` without a default. **Observability:** sidecar carries `schemaVersion: 1` (mirrors `audit-stack.md` discipline); readers MUST default-false on missing keys; a CI test asserts every documented flag has a default. **Recovery:** schema bump = N+1, never mutate v1 fields; old logs render as `unknown` not `crash`. The fixed-slot manifest insulates `status.json` shape from sidecar drift — slot count is owned by the workflow file, not the sidecar.
- **On-call at 3am:** a user reports "the UI/UX lens didn't find anything on our Next.js app." **Page shape:** zero — audit is read-only / ad-hoc, no automated paging. **Diagnosability:** the operator pulls `audit-applicability.md` (one screen), greps `hasFrontend`; if `false` on a clear frontend repo, they look at `audit-stack.md#Detection Coverage` for the `frameworks: []` miss → that's a stack-detect bug, not a lens bug. **Recovery path:** `[skills=false] [lenses=uiux] [applicability-override=hasFrontend=true]` re-runs only the UI/UX lens forcing the flag, takes ~3 min, no full re-audit. The applicability override is an explicit escape hatch landed in this pass — without it, the on-call has to hand-edit the sidecar to retry, which is a 3am footgun.
- **Author leaves:** the keystone (sidecar + three-state coverage) is the load-bearing concept. **Knowledge concentration:** the design doc + the `audit-applicability.md` schema in the producing agent's prompt = two co-located documentation sites; the third (the synthesiser's `## Missing Lenses` renderer) reads the sidecar verbatim — no derivation logic to forget. **Bus factor:** medium — anyone who has read the prompt understands the contract. **Tribal knowledge:** the rule "gated-out != clean bill" is encoded in the rendered `## Missing Lenses` table, not in commentary; a successor reading a real audit cannot mistake an `N/A` row for a `ran clean` row.

**Risk-mitigation guidance (additive to this approach):**

- Land the `[lenses=slug,...]` and `[applicability-override=flag=bool]` input escapes in this pass — without them, partial re-runs and false-negative gating recovery require hand-editing artifacts. Cheap (input parsing only); mitigates both 10× scale and 3am scenarios above.
- Make the `## Missing Lenses` three-state row a fixed visual format (e.g. `- {slug}: ran | N/A ({reason}) | crashed ({reason})`); add a Step 6 grep-assert that every declared slot appears exactly once with one of three states (extends the review-2 C-3 gate).
- Cap the supply-chain/CI-CD lens's `Bash` tool surface to a fixed allowlist (`git log`, `git rev-parse`, `git cat-file`, `cat`, `jq`, `grep`); the existing lens family is `Read, Grep, Glob, Write` (sibling-blind, provably non-mutating) — the new `Bash` surface needs explicit fencing in the prompt + a `prompts.md` § Tool set row noting "read-only Bash, no fs writes, no network."
- Cross-check `audit-stack.md frameworks: []` AND `hasFrontend: true` (i.e. flag set but no framework detected) → CONCERNS at stack-detect (the inverse plausible-but-wrong guard; mirrors the existing `confidence: low → CONCERNS` rule).
- Document the network-surface count explicitly: pre-pass-3 = 1 (`npx skills`); pass-3 = 2 (`npx skills` + `--with-websearch` reference-signal). The doubling is intentional and opt-in but should be called out in § Risks so a reader doesn't read "exactly one network surface" prose elsewhere and trip.

## Approach B — Conditional Lenses As Self-Gating Leaves (No Sidecar, Lenses Read `audit-stack.md` Directly)

**Summary (one sentence):** Skip the `audit-applicability.md` sidecar entirely; each conditional lens reads `audit-stack.md` itself, decides applicability in the first ~50 lines of its run, and either proceeds or writes a fixed `# Not Applicable` artifact with a structured `## Reason` block — the synthesiser parses presence-of-`# Not Applicable`-header to render the third coverage state.

**Pass-3 fold-in:**

- Same 14 lenses + reference-signal as Approach A.
- Stack-detect emits ONLY `audit-stack.md` (one artifact, no sidecar). Conditional lenses encode their gate in-prompt (e.g. UI/UX checks `frameworks` ∩ {web-framework family} OR presence of `public/`, `src/app/`, etc. — the actual probe is universal, the gating is a small grep).
- Coverage state is inferred at synthesise time: file present + has `finding` blocks = ran; file present + `# Not Applicable` header = N/A; file absent / empty / verdict-missing = crashed.
- Reference-signal is still a separate agent in Step 5, with the same `confidence: low` discipline.

**Premortems:**

- **10× scale:** Same fan-out width as A; per-lens gating decisions are duplicated across N conditional lens prompts (4 today, more later). **What breaks:** when a new gating signal appears (e.g. `hasGraphQL`), every conditional lens that cares about it must be re-edited in lockstep; lens prompts grow gating boilerplate. **Observability:** worse than A — the gate decision is buried in the lens output; to see "did the UI/UX lens N/A or run-empty?" you have to open the lens artifact, not glance at a sidecar. **Recovery:** the partial-re-run knob (`[lenses=slug]`) still works, but applicability override requires touching `audit-stack.md` itself, which is the contract feeding all 14 lenses — high blast-radius edit.
- **6 months later:** gating logic in each lens prompt drifts independently — UI/UX considers `next` a web framework, data-layer's "needs DB" check uses a different list of ORM tokens, supply-chain treats `bitbucket-pipelines.yml` as CI but CI-CD lens doesn't. **What breaks:** silent disagreement on what's "applicable" with no single source of truth. **Observability:** none — each lens's gate is private. **Recovery:** painful — requires reading each lens prompt to reconstruct the implicit applicability matrix.
- **On-call at 3am:** "UI/UX lens marked itself N/A on our app" → operator opens `audit-lens-uiux.md`, reads the prompt-embedded gate description, decides whether to override. **Diagnosability:** OK if the lens's `## Reason` block is rich; bad if it's terse. **Recovery:** force-rerun is awkward without an applicability override; user can `[skills=false] [lenses=uiux]` but the lens will N/A itself again unless the user edits `audit-stack.md` or the lens prompt has its own override flag — N escape hatches, one per conditional lens.
- **Author leaves:** the keystone is distributed across N lens prompts instead of one sidecar. **Bus factor:** lower than A — a successor must read every conditional lens to understand the applicability matrix. **Tribal knowledge:** "this lens's gating logic considers X but not Y" is exactly the kind of detail that gets forgotten.

**Risk-mitigation guidance (additive to this approach):**

- Standardise the in-prompt gate block to a fixed structure (a `## Applicability` H2 with bulleted "trigger if" conditions citing `audit-stack.md` fields by name) so the matrix is at least mechanically reconstructible by `grep -A 20 '## Applicability' .agents/prompts/bkit-audit-lens-*.md`.
- Land a per-lens `[applicability-override=lens-slug=bool]` flag (still 1 escape, but operator must know which lens — friction vs A's flag-name approach).
- Add a doc-test that diffs the gating logic across conditional lenses for shared signals (e.g. all DB-conditional lenses must consult the same `audit-stack.md#db` list); fails CI on drift.
- Same `Bash` allowlist as A for the supply-chain/CI-CD lens.
- Strictest hedge: require every conditional lens to emit `# Not Applicable` with a `triggered-by-flag: {name}` line even though there is no central flag — gives the synthesiser a key to dedup applicability disagreements between lenses.

## Approach C — Single Mega-Step Conditional Bundle (Three Step-5 "Tracks": Universal / Conditional / External-Signal)

**Summary (one sentence):** Restructure Step 5 from a flat 14-way fan-out into three named tracks — **universal** (10 always-on lenses including the new supply-chain/CI-CD lens), **conditional** (UI/UX, data-layer, AI/LLM, gated by sidecar flags), and **external-signal** (reference-repo agent, gated by `--with-websearch`) — each track ships its own coverage manifest and gate; the `status.json#steps[5]` entry carries three sub-arrays instead of one.

**Pass-3 fold-in:**

- Same 14 lenses + reference-signal as A/B but organised by failure-mode class, not by lens identity.
- Three coverage manifests at synthesise time, merged into one `## Missing Lenses` section but with three sub-headings (`### Universal`, `### Conditional`, `### External Signal`).
- Reference-signal's "strict-below-internal-evidence" ranking is structurally enforced by being in a different track (organise/summary iterate universal → conditional → external in fixed order; the renderer cannot accidentally promote external above universal because the loop order forbids it).

**Premortems:**

- **10× scale:** width per track is smaller (10 / 3 / 1 today) but the orchestrator's Step-5 gate logic triples — now three artifact arrays to validate, three sub-verdicts to merge. **What breaks:** the workflow file grows three near-identical gate blocks (DRY violation; pattern-match with `bkit-design.md` weakens — the file no longer reads like a peer). **Observability:** better-categorised (an operator scanning the Step-5 progress comment sees "universal: 10/10 OK; conditional: 2/3 N/A, 1 OK; external: skipped" — useful at a glance). **Recovery:** track-level re-run (`[track=conditional]`) is a natural escape, smaller blast radius than full Step 5.
- **6 months later:** the track boundaries blur — supply-chain/CI-CD is "universal" today but a future repo with no CI/CD config flips it conditional; lenses migrate between tracks; the workflow file diff churns. **What breaks:** the universality of a lens is a judgement call frozen into the workflow file's structure. **Observability:** track migrations need a release-note entry; otherwise old audits read inconsistently. **Recovery:** flat fan-out (A or B) doesn't have this — adding/removing a flag is a sidecar/prompt edit, not a structural workflow edit.
- **On-call at 3am:** Three tracks = three places to look. **Diagnosability:** good if operator knows the track taxonomy; bad if they don't (extra concept to learn vs A). **Recovery:** same as A/B at lens-level, plus track-level shortcut.
- **Author leaves:** the track taxonomy is novel — diverges from `bkit-design.md`'s flat fan-out pattern, so a successor cannot rely on the design-workflow analogy. **Bus factor:** lower — the categorisation rationale lives in the workflow file's prose, not in a code structure.

**Risk-mitigation guidance (additive to this approach):**

- Pattern-match `bkit-design.md` by extracting the per-track gate into a single repeated snippet block in the workflow file (DRY); annotate explicitly "three tracks, one shape" so the divergence from the flat design pattern is documented.
- Lock the track membership in a one-line table at the top of `bkit-audit.md` so migrations are visible in diffs.
- Use the track ordering to enforce the reference-signal ranking constraint structurally (organise iterates universal → conditional → external; renderer cannot reorder).
- Same `Bash` allowlist + `[lenses=slug,...]` escape as A; add `[track=name]` as the track-level escape.

## Cross-Approach Risks

Surface in the final design's `Risks & Open Questions` regardless of which approach is picked:

- **Fan-out width vs Opus cost.** Pass-3 takes Step 5 from 11 to ~14 lens slots + 1 non-lens agent. With Opus/high pinned, per-run token cost grows ~30–45%; with growth from #207 / #83, the trajectory is ~1.5–2× baseline within a year. The Sonnet-downgrade lever is the acknowledged escape but is NOT exercised in this pass — open question for the next minor.
- **Conditional-lens false-N/A is silent by construction.** A mis-detected `hasFrontend=false` on a real frontend repo renders as `N/A — not applicable` in `## Missing Lenses`, which by design is NOT a finding. The only signal is the operator noticing the N/A on a repo they know has the surface. Mitigations: (a) `confidence: low → CONCERNS` already catches thin stack detection; (b) inverse-guard "flag=true but no matching `audit-stack.md` evidence" → CONCERNS (Approach A risk-mitigation); (c) operator-visible flag table in the Step-3 tracker comment so a wrong flag is one glance away. None of these eliminate the risk; document explicitly.
- **Conditional-lens false-applicable (running on absent surface).** Opposite failure: lens runs against a repo with no real surface, emits noise findings. Lower blast radius (findings have explicit `location:` lines; a noise finding pointing at a non-existent file is identifiable; reviewer drops it). But the 25-finding cap means noise can crowd out real signal from sibling lenses.
- **Reference-signal network reproducibility.** Even with `confidence: low` capped + ranked-below-internal, two `--with-websearch` runs on the same commit can return different reference repos and therefore different divergence callouts. The `bkit-audit-reference-signal` agent must capture (a) which repos it consulted + their commit/tag and (b) the search query — same provenance discipline as `audit-install-skills.md` carries today. Without this, an audit is non-reproducible even given the same input commit.
- **`--with-websearch` opens a second network surface.** The baseline design's § Risks line "the only network surface in the pipeline, isolated to Step 4" no longer holds when reference-signal is opt-in. Update that line; do not let the design doc's prose lag the new posture.
- **UI/UX no-op on bkit's own repo.** bkit has no UI → UI/UX lens MUST N/A cleanly (this is the whole point of the keystone). Validate at build time by running `/bkit-audit` on bkit itself and asserting the UI/UX row in `## Missing Lenses` shows `N/A — not applicable (hasFrontend=false)`, not `ran clean`. If it shows `ran clean` the keystone is broken. (Comment 4580555629: "bkit has no UI → must no-op cleanly (drives the keystone below)" — this is the acceptance test.)
- **Supply-chain/CI-CD lens is "near-universal" but technically conditional.** A repo with no `.github/workflows/` and no `package-lock.json|pnpm-lock.yaml|yarn.lock` legitimately has nothing to scan. The `hasCI || hasPipeline || hasSupplyChain` gate must be permissive (any one signal triggers run) — over-strict gating silently skips real surfaces.
- **`status.json#steps[].artifacts` array shape.** Pass-3 grows the Step-5 artifacts array from 11 to 14 (+ 1 for reference-signal when on). Downstream readers (status.json parsers, `bkit-trackers` outside-worktree progress, cloud orchestration) must not assume a fixed length; verify the array is treated as a list everywhere (`steps[5].artifacts.length` not hard-compared to 11).
- **Auto-installed `audit-*` skills are still ship-pruned.** Per baseline design Risk + memory: `.agents/skills.md` is curated manually and `/bkit-ship` Step 10 prunes unlisted skills; the reproducibility log is the durable record. Pass-3 expands the surface (more potential `audit-*` skill matches per repo across frontend / DB / LLM / supply-chain tokens) — restate the prune posture so a reader doesn't assume installed audit skills survive across ship cycles.
- **AI/LLM lens has a self-reference risk.** Running an LLM-safety lens on a codebase that integrates LLMs, using an LLM, with prompts shipped as files in the repo — the lens MAY find its own prompt files as "unvalidated model I/O" surfaces. Either scope the lens to exclude `.agents/prompts/**` + `.cursor/**` + `.claude/**` or accept the false-positive and document the exclusion expectation in the prompt.
- **Authoring-rule lock-in.** Every workflow/prompt edit in pass-3 lands under `.agents/workflows.md` § Workflow Authoring Rules + `.agents/prompts.md` § Prompt Authoring Rules (comment 4552784986). ASCII operators only (`!=`, `>=`, `<=`) in those files. Tracker MCP only (no `gh api` / no raw HTTP). These are existing rules but the volume of new prompts in pass-3 (4+ new lens prompts, 1 new non-lens agent, sidecar producer changes) amplifies the lint surface — call out in build readiness.
