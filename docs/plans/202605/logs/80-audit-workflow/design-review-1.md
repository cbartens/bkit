# Design Review

Lens: Buildability — stack feasibility, library fit, integration risk.

This repo IS the bkit tooling repo. Pass 3 is a doc-authoring delta over an already-PASS'd Pass-2 design: one workflow file extension, five new prompt files, one frontmatter-key addition across 16 lens prompts, one schema bump on `audit-stack.md`, and a registry-block extension in `.agents/workflows.md` / `.agents/prompts.md`. "Stack" = `.agents/rules.md` + `.agents/workflows.md` § Workflow Authoring Rules + `.agents/prompts.md` § Prompt Authoring Rules + existing skills/agent machinery. Buildability is judged against those, not a runtime library stack. Pass-3 is **incrementally** buildable on the PASS'd Pass-2 design — every new mechanism has a precedent or a credible adaptation path — but four under-specified items need tightening before `/bkit-plan` can act on it cleanly.

## Stack Feasibility

Buildable with the approved authoring stack. Four specific points need tightening:

(a) **Keystone conditional-lens mechanism — internally consistent, one under-spec gap.** The `## Applicability` block in `audit-stack.md` (v1 → v2) + per-lens `requires:` frontmatter + launch-and-self-no-op + three-state `## Missing Lenses` form a clean closed loop:

- Producer: stack-detect emits the block (5 named booleans + `## Applicability — Flag Inventory` + `## Applicability Overrides` + `## Applicability Disagreement`).
- Consumer: each conditional lens reads its flag → if false, writes `# Not Applicable\n\nReason: {flag}=false` and exits PASS.
- Verifier: synthesiser reads all 16 lens artifacts, classifies each as `ran` / `N/A — not applicable ({flag}=false)` / `crashed (reason)`, renders one row per slot in `## Missing Lenses`.
- Gate: orchestrator Step 6 grep-asserts every of the 16 known slugs appears exactly once with one of three state-token prefixes.

This is mechanically sound and faithful to Pass-2's "never silently lose findings" posture (the launch-and-self-no-op is belt-and-braces — a stack-detect flag bug still leaves a launch artifact AND a `## Missing Lenses` row). The schema-bump cadence (v1 → v2) absorbs the change cleanly per the Pass-2 contract ("lenses assert `schemaVersion` and degrade on mismatch").

**Under-spec gap (CRITICAL #1):** the Step 6 orchestrator grep-assert is described as "every of the 16 declared slot slugs MUST appear exactly once in `## Missing Lenses`, with one of `ran` | `N/A — not applicable (` | `crashed (` as its state token. Missing row OR unknown state token ⇒ first absence re-issues synthesiser with tightening prompt; second absence ⇒ Failure Path." But it does NOT specify **where the orchestrator gets the canonical 16-slug list at gate time**. Options: (i) hardcoded in `bkit-audit.md` Step 6 (drift surface — gets out of sync with `## Applicability — Flag Inventory`); (ii) read from `audit-stack.md ## Applicability — Flag Inventory` + a hardcoded 11-universal list (two-source); (iii) read from the synthesiser's own prompt enum (the design says the synthesiser hardcodes this — § Data Model line "The synthesiser reads (a) the list of 16 lens slots from its own prompt body (a hardcoded enum…)"). Picking (i) is simplest but most drift-prone; picking (iii) means the orchestrator reads the synthesiser prompt to know the gate list, which couples gate logic to prompt content. Plan must commit explicitly. Recommend the workflow file inline the 16-slug list verbatim in Step 6 (matches `.agents/workflows.md` § Workflow Authoring Rules "Self-contained: inline the rule") and add a plan-time grep-assert that the list matches the synthesiser prompt + the lens-prompt requires-value union.

(b) **Supply-chain lens needs allowlisted `Bash` — buildable, but allowlist is prompt-body discipline only.** The design correctly admits "the lens prompt body documents the allowlist; the host tool surface still grants raw `Bash`. The allowlist is a discipline, not a sandbox." This is honest and matches how Pass-2 handles `bkit-audit-install-skills` (no allowlist there — `Bash` is fully open for `npx skills`). The allowlist (`git log`, `git rev-parse`, `git cat-file`, `cat`, `jq`, `grep`, `awk`; NEVER `git checkout` / `reset` / `push` / `commit`) is enumerable, readable, and matches what the lens probes need (git-history secret-scan + lockfile walks). **Buildable.** But two gaps:

- The "read-only invariant" is **not** cleanly preserved — the lens family advertises "Read-only reviewer" (`Read, Grep, Glob, Write`) for 14 of 16 slots; `supply-chain` breaks the uniformity. The design absorbs this by adding a `Read-only reviewer with allowlisted Bash` sub-row in `.agents/prompts.md` § Tool set patterns. That sub-row is the right place; recommend the row also explicitly state "the host does not enforce the allowlist — review the prompt body on every audit edit" (so a future author doesn't silently add `git push` to the allowlist).
- The allowlist as written includes `awk` and `cat` which are full-Turing utilities (e.g. `cat | sh` is feasible). For an audit lens that is read-only by intent, `awk -v cmd=...` and `cat $UNTRUSTED_PATH | sh` are escape hatches. Plan should either tighten further (drop `awk` — `grep` + `jq` covers the parsing surface) OR explicitly note that the allowlist is a guidance-to-author tool, not a security boundary (which is what the design already says — but make sure the prompt body says it too, not just the registry).

(c) **Reference-signal `--with-websearch` + down-rank grep-assert — mostly buildable, one phrasing fix.** The mechanism: reference-signal lens reads `audit-stack.md ## Applicability hasNetwork`; on true, runs WebSearch-bounded probe (top-3 popular reference repos, structure/config/README only); emits findings with `source: reference-repo` + `confidence: low` on every block; organise's self-verify checks the rendered matrix top row + ranked-list top-3 + executive summary block for any line containing `source: reference-repo` OR `confidence: low` → FAIL on match.

**The "machine-enforceable grep-assert" is actually checkable** — the rendered organise output is a markdown file; greppable by `awk` / `grep` over the heading-bounded sections. Implementation precedent: `bkit-design-organise` Step 9 self-verify (orphan / DAG-cycle), which is **in-agent prompt logic**, not an orchestrator post-step grep. The Pass-3 design says "Organise self-verify grep-assert: after rendering `audit-v2-ranked.md`, grep the matrix top row + ranked-list top-3 + per-class appendix top entries + executive summary; any `source: reference-repo` OR `confidence: low` line in those blocks ⇒ FAIL the organise step." This phrasing leaves it ambiguous whether the grep runs **inside the organise agent's self-verify** (in-prompt `Bash` — needs `Bash` on organise's tool surface, which Pass-2 already grants) OR **outside in the orchestrator Step 7 gate** (orchestrator runs `grep` on the artifact and routes FAIL). Both are buildable; the in-agent path matches the existing organise self-verify pattern; the orchestrator-gate path mirrors the Step 6 `## Parse Errors` / `## Missing Lenses` greps. Plan must pick one explicitly.

**Down-rank assertion fragility:** the grep matches the literal strings `source: reference-repo` and `confidence: low`. If the renderer prefixes findings with quoting / indentation / different field naming (`source = reference-repo`, or wraps in a code fence), the assertion silently passes (false negative). Plan should pin the renderer's output format (verbatim YAML fence echo, or a documented `- source: reference-repo` indented-list shape) so the grep pattern stays bound to a stable surface.

(d) **21-agent / wider Step 5 fan-out + gate counts + fixed-array `status.json`.** Subagent count grows 16 → 21 (1 stack-detect + 1 skill-install + 16 lenses + synthesise + organise + summary) per design line 7; the **Step 5 fan-out is 16**, not 21. Mechanism unchanged from Pass-2 — orchestrator launches all 16 in one fan-out block (precedent: Pass-2 11-wide). The "fixed-length 16-entry array" claim for `status.json#steps[5].artifacts` is workable: every lens slot emits a real artifact (real findings OR `# Not Applicable` body), so the artifact count is 16-by-construction. **Buildable.** But:

- The `status.json` field semantics row (`workflows.md` line 205) calls `artifacts` "absolute `docs/plans/{YYYYMM}/logs/{FID}/...` paths (or PR URL for create-pr)" — a list, no fixed-length constraint. Pass-3 introduces a per-workflow per-step fixed-length invariant that lives entirely inside `bkit-audit.md` Step 5 + downstream-reader notes; **do NOT change the universal `status.json` schema**. The design says this correctly ("downstream readers MUST treat as a list, NOT hard-compare length to 11 or 16"). The plan must make sure no `bkit-trackers.ts` / cloud-orchestration code introduces a `===16` check.
- 16-wide Opus/high fan-out cost: ~4.5× design-triplet (Pass-2's review-1 already flagged 11-wide is 3.6× — this grows it further). Acknowledged in design § Risks; Sonnet-downgrade lever stays the documented future escape. No correctness blocker; cost/throughput is a build-time empirical validation.
- Context-window pressure on the synthesiser: synthesiser ingests 16 × up-to-25 findings (4 of which will likely be `# Not Applicable` 2-line bodies on bkit's own repo) + `audit-stack.md` + 16-row coverage manifest. Within `claude-opus-4-7` 200K context. No blocker.

(e) **Lens universality (zero library names, grep-gated) holding for the 5 new lenses incl. UI/UX.** This is the harder universality question. Pass-2's grep-gate (success criterion #3: `grep -iE 'pino|winston|zod|joi|pnpm|vitest|next|esbuild' bkit-audit-lens-*.md returns zero`) is buildable but is **only as strong as the regex enumeration**. The 5 new lenses introduce new lexical surfaces with library-shaped tokens that the existing regex won't catch:

- `ui-ux` — probes "viewport meta, rem-based base, line-height, semantic landmarks, ARIA, alt text, focus order, WCAG ratios, design tokens, layout-shift" — these are **standards-domain tokens**, not library names. Buildable as written. But "design-system adherence" probing risks naming popular design systems (Material, Chakra, shadcn) if the author lapses — extend the grep-gate regex.
- `supply-chain` — probes "unpinned Action SHAs, `pull_request_target` misuse" — `pull_request_target` is a GitHub-Actions-specific token. Borderline: it's a CI-platform feature, not a library, but it IS GitHub-specific. The brief's universality principle (no library names) is **slightly bent** here because pipeline hardening is intrinsically platform-specific. Acceptable for this lens family; extend the grep-gate to allow `pull_request_target` / GHA tokens as documented exceptions OR rephrase as "auto-merge-write workflow trigger" (less specific, more universal).
- `data-layer` — probes "N+1, indexes, LIMIT, transactions, migration safety" — universal DB concepts. Buildable.
- `ai-llm` — probes "prompt-injection, model I/O, PII/secrets to providers, token-cost, model-version pinning, eval coverage" — universal. The `.agents/**` / `.cursor/**` / `.claude/**` exclusion is correct (bkit dogfood self-reference quirk caught).
- `reference-signal` — by construction reads other repos' structure/config/README and reports divergence; library names will appear in findings (the divergence target), but the lens **prompt** stays universal — findings emit library names from the target repos consulted, not from the prompt. Buildable.

Recommend Pass-3 extend the grep-gate regex used to validate universality to cover the new lens surfaces (add `Material|Chakra|shadcn|tailwind|bootstrap|MUI|Radix` for UI/UX; add `Actions|gha|workflow_dispatch` for supply-chain only if the lens body uses them; etc.). The plan-time universality grep-gate IS the only enforcement surface for the universality invariant — extend it.

- **`WebSearch` tool maturity / availability**: documented in `.agents/prompts.md` line 70 as an allowed `tools:` value, and used in production by `bkit-design-review-1/2`. Frontmatter passthrough proven on both Claude (native) and Cursor (2.4+ honours `tools:` allowlist). No new dependency.
- **Reproducibility / provenance**: `## Reference Repos Used` block captures repo names + commit/tag + search query — mirrors `audit-install-skills.md`'s "Stack Tokens Queried" / "Newly Installed" shape. Solid precedent.
- **Bundle / types / license**: N/A — tool, not a code dep.
- **Gap — search-result instability**: `WebSearch` results drift over time (popular-repos list, ranking) — the design correctly calls this out ("Reproducibility is 'explainable', not 'identical'"). No mitigation needed beyond provenance capture.
- **`npx skills` for the new conditional skills (`audit-{ui,db,llm,supply-chain}-*`)**: the design's CRITICAL #2 from the Pass-2 review-1 (`audit-*` skills likely don't exist in the registry yet) **widens** in Pass-3 — now 4 new token classes that probably also don't exist. Acknowledged in design § Risks. Non-gating posture absorbs it; enrichment value is latent until skills ship. Buildable, value-deferred.

7. **`bkit install` mirror regen** picks up 1 workflow edit + 5 new prompts + 11 frontmatter additions + registry edits → regenerates `.claude/` + `.cursor/`. Batch-at-session-end per project memory. Standard.

## Verdict Reasoning

**CONCERNS** (feasible with caveats — design proceeds, findings are addressable).

Every Pass-3 mechanism is buildable. The keystone (`## Applicability` block + `requires:` frontmatter + launch-and-self-no-op + three-state coverage) is internally consistent, follows the schema-bump cadence Pass-2 explicitly enables, and uses the belt-and-braces gating posture that's already the bkit pattern ("never silently lose findings"). The two new tool-surface exceptions (`supply-chain` Bash, `reference-signal` WebSearch) reuse precedented tool surfaces and are scoped to one lens each; the `Read-only reviewer` pattern remains dominant. The 16-wide fan-out is a 1.45× scale-up over Pass-2's already-stress-tested 11-wide. The new prompts are clones of the existing read-only-reviewer skeleton with a one-key frontmatter addition + one prompt-body clause. No FAIL-level infeasibility.

It is not a PASS because four under-specified items need explicit choice before `/bkit-plan` can act on them cleanly: (1) where the Step-6 gate reads the canonical 16-slug list; (2) where the down-rank grep runs (in-agent self-verify vs orchestrator post-step); (3) the renderer output format the down-rank grep is bound to; (4) the universality grep-gate regex extension for the new lens lexical surfaces. All four are addressable in plan; none break buildability.

## CRITICAL

- **Pin the Step-6 gate's canonical 16-slug source.** Inline the list verbatim in `bkit-audit.md` Step 6 (matches the Self-contained workflow-authoring rule) + add a plan-time grep-assert that the three lists (workflow Step 6, synthesiser prompt enum, lens-prompt `requires:` value union with `always` mapped to the universal 11) agree. Without this the keystone gate has an underdetermined contract surface and will drift the first time a lens is added.
- **Pick the down-rank grep's execution site.** In-agent organise self-verify (matches existing `bkit-design-organise` orphan/DAG self-verify pattern; needs no orchestrator change) OR orchestrator Step 7 post-step gate (mirrors Step 6 `## Parse Errors` / `## Missing Lenses` grep). Plan must commit to one and rephrase the design's "organise self-verify grep-assert" wording accordingly.
- **Pin the rendered finding format the down-rank grep binds to.** The grep pattern (`source: reference-repo` / `confidence: low` literal-string match) is only sound if the renderer emits those tokens verbatim and indelibly.
