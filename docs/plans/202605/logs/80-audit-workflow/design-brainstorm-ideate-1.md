# Design Brainstorm & Ideas

Lens: Pragmatic — existing code, minimal new infra, ship fastest.

Scope anchor: re-design `/bkit-audit` as a 6th peer workflow cloned from `bkit-design.md`. New direction = stack-detect step + skill-install step BEFORE an 11-lens parallel fan-out, then synthesise → organise → summary → close. Lens prompts carry universal patterns only (no library names); they read `audit-stack.md` + target `.agents/docs.md` + `docs/knowledge.md`; installed skills supply stack-specific depth. v1 = Phases 1+2; Phase 3 (WebSearch) deferred. Audit is read-only, ad-hoc only, Linear-bound, terminal at `In Review`. The brainstorm here picks the _orchestrator/prompt decomposition shape_ — downstream design-generate + organise produce the canonical doc and workstreams.

---

## Approach A — Clone-and-Extend (maximal reuse of `bkit-design` skeleton + existing skill agents) ⭐ Recommended

**Summary (one sentence):** Build `bkit-audit.md` by lifting `bkit-design.md` Steps 1/2/close verbatim (swap `design-`→`audit-` slug, drop nothing structural), insert a stack-detect step and a skill-install step modelled respectively on a new `bkit-audit-stack-detect` agent and the _existing_ `bkit-build-install-skills` agent (re-parameterised), then a `bkit-design-brainstorm-ideate`-shaped parallel fan-out of 11 lens agents, then `bkit-audit-synthesise`/`-organise`/`-summary` cloned from `bkit-design-generate`/`-organise`/`-summary`.

- **Pipeline shape (9 steps):** 1 Start Workflow · 2 Worktree Setup (drop `pnpm install --frozen-lockfile` — read-only audit; keep env/vale copy) · 3 Stack Detect (`@bkit-audit-stack-detect` → `audit-stack.md`) · 4 Skill Install (`@bkit-audit-skill-install` → augments `.agents/skills/`, writes `audit-skills.md`) · 5 Lens Audits (11× `@bkit-audit-lens-{slug}` parallel → `audit-lens-{slug}.md`) · 6 Synthesise (`@bkit-audit-synthesise` → `audit-v1-synthesis.md`) · 7 Organise (`@bkit-audit-organise` → `audit-v2-ranked.md`) · 8 Summary (`@bkit-audit-summary` → `audit-summary.md`, push) · 9 Close Workflow (`cp` v2 → `docs/audits/{FID}-audit.md`, hard stop). Steps 6–8 reuse the design fan-in → verdict-extract → status-commit → comment-append ceremony 1:1.
- **Stack-detect agent:** new `bkit-audit-stack-detect` (`Read, Grep, Glob, Write`; `medium`/sonnet; tier M). Reads `package.json`, `tsconfig.json`, `*.config.*`, lockfiles, `.github/workflows/`, container/IaC manifests; emits a fixed-schema `audit-stack.md` (language / runtime / package manager / frameworks / build tools / test runner / CI / deploy / db / orm) — emphatically _generic field names_, no Node-only assumptions baked into the schema (e.g. "package manager" not "is-pnpm"). 2-way `PASS|FAIL` (atomic detect — either it produced a report or it didn't).
- **Skill-install step:** re-use `bkit-build-install-skills` _verbatim as the pattern_, but invoke a thin audit-specific sibling `bkit-audit-skill-install` whose Process reads `audit-stack.md` and runs `npx skills find audit-{stack-token}` / `npx skills add` per detected token (next→`audit-nextjs`, vitest→`audit-vitest`, pnpm→`audit-pnpm`). Cap at 10; "not found → note, do not block". Identical tool surface (`Read, Grep, Glob, Bash`), effort, maxTurns as the build sibling. The `find-skills` skill is already a Universal skill (`vercel-labs/skills`) — leaned on, not re-built.
- **Lens agents:** 11 prompts forked from the `bkit-design-brainstorm-ideate-1` skeleton (read-only-reviewer pattern `Read, Grep, Glob, Write`; `high`/opus; tier M; sibling-blind). Each INLINES its own universal-pattern probe block (Standalone-runnable rule forbids cross-file cites). Reuse the 11-lens charter unchanged (architecture/hotpath/config/reliability/observability/debt/dead-code/deps/security/tests/docs-drift). Each reads `audit-stack.md` + target `.agents/docs.md` + `docs/knowledge.md` + any installed `.agents/skills/audit-*`. Cap 25 findings, severity-sorted. Verdict-bearing.
- **Synthesise/Organise/Summary:** clone `bkit-design-generate` (xhigh, dedup across lenses), `bkit-design-organise` (high, severity×class matrix + ranked list + per-class appendix + workstream decomposition with `Requires` DAG + self-verify), `bkit-design-summary` (low/haiku, 500-token Linear-bound). Step 9-equivalent workstream-issue spawning reuses `bkit-design`'s Step 9 `design-workstream-issues` machinery so the old WS-1..WS-13 (#103–#107) get re-cut by the organise output.
- **Complexity:** MEDIUM. Two genuinely new agents (`stack-detect`, lens-charter-bearing lens prompts); everything else is a slug-swap clone.
- **Extensibility:** HIGH. New framework support = author a community/bkit `audit-{stack}` skill + (maybe) add a detection token — zero lens-prompt edits. Schema-generic stack report tolerates non-Node stacks. The deferred Phase 3 WebSearch slots in as an optional augment to the lens step without reshaping the pipeline.
- **Risk:** Lens-prompt purity erosion — an author re-introduces a library name "just this once", silently re-leaking the stack. Mitigation: a grep-gate acceptance criterion (`grep -r` for library-name tokens in `bkit-audit-lens-*.md` returns zero) carried into the plan, mirroring the superseded design's §Success-Criteria #4. Secondary risk: skill-install is a network step inside an otherwise hermetic read-only flow — must be non-blocking ("not found → continue").
- **Maintenance:** LOW–MEDIUM. Shares ceremony with five other workflows, so cross-workflow invariant changes propagate by the existing "change shared lines in ALL workflows" rule. New surface = 1 orchestrator + ~14 prompts + registry rows; the lens charter centralises the only audit-specific knowledge that drifts.
- **Reuse vs new:** ~80% reuse (design skeleton + build-install-skills pattern + find-skills skill + organise/summary shapes). Net-new: stack-detect agent, audit skill-install sibling, 11 universal-pattern lens prompts, synthesise/organise/summary audit variants, registry edits.

## Approach B — Merged Detect+Install Preflight (one preflight agent instead of two steps)

**Summary:** Collapse stack-detect and skill-install into a single `bkit-audit-preflight` agent (one step) that both emits `audit-stack.md` AND installs matching skills in the same run, shrinking the pipeline to 8 steps; lens fan-out + synthesise/organise/summary identical to Approach A.

- **Pipeline shape (8 steps):** Start · Worktree · Preflight (detect + install, one agent) · Lens Audits · Synthesise · Organise · Summary · Close.
- **Why consider it:** Fewer steps = less orchestrator ceremony, one fewer subagent dispatch, one fewer status entry + comment. Detection output feeds installation directly inside one agent's memory — no intermediate file hand-off.
- **Complexity:** MEDIUM (one composite agent vs two simple ones — roughly even on total LOC, fewer orchestrator steps).
- **Extensibility:** MEDIUM. The composite agent mixes two tool surfaces (read-only detection + `Bash`/network install) into one sandbox, so it can no longer be marked provably non-mutating; harder to reason about and to reuse the detector standalone (e.g. a future "stack report only" mode).
- **Risk:** Conflation breaks the Session-Brief layering model — the brief explicitly separates "stack-detect output (bkit)" from "skills (community/bkit)" as distinct knowledge layers; merging them muddies that boundary and the `audit-stack.md` artifact (which lenses depend on) becomes a side-effect of an install step rather than a first-class deliverable. A network/install failure now also risks the detection artifact.
- **Maintenance:** MEDIUM. Diverges from the `bkit-build-install-skills` precedent (which is a dedicated install agent), so the audit install logic can no longer track the build sibling's wording verbatim — violates "change shared lines in ALL prompts".
- **Reuse vs new:** ~75% reuse. Loses the clean re-use of the existing install-agent shape; gains nothing structural the two-step version doesn't already have.

## Approach C — Charter-Doc-Driven Lenses (shared lens-charter doc as cited dependency, thin lens prompts)

**Summary:** Same 9-step pipeline as Approach A, but lens prompts are made _thin_ — each cites a single shared `bkit-audit-lens-charter.md` for its universal-pattern probe table rather than inlining its own row, so the 11 prompts shrink to a stub + charter pointer.

- **Pipeline shape:** Identical to Approach A; the only delta is where the probe knowledge lives (one shared doc vs inlined per prompt).
- **Why consider it:** A single charter is easier to keep internally consistent and easier to audit for library-name leakage (one grep target instead of 11). Future probe edits touch one file.
- **Complexity:** MEDIUM. Charter authoring is straightforward, but wiring 11 prompts to read it adds a load-bearing cross-file dependency.
- **Extensibility:** MEDIUM–HIGH for probe edits (one file) but the cross-reference fights the prompt model.
- **Risk:** **Direct violation of the Standalone-runnable rule** (`.agents/prompts.md`: "Each prompt works invoked outside any workflow … NO cross-references"). A lens agent invoked ad-hoc (`@bkit-audit-lens-security path/`) would fail to find its probes if the charter isn't passed as a Read path. The superseded design already hit this exact CRITICAL (review-1 #2) and resolved it by _inlining_ probes and demoting the charter to a passive human-facing index — so Approach C re-litigates a settled decision.
- **Maintenance:** MEDIUM. One probe source is nice, but the broken standalone contract means every ad-hoc invocation must remember to wire the charter path — a recurring foot-gun.
- **Reuse vs new:** ~80% reuse (same as A), but spends its novelty budget on an anti-pattern the codebase already rejected.

## Decisions

| Decided                                                                                                                                 | Alternatives                                                  | Why                                                                                                                                                                                                                              |
| --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Approach A — clone `bkit-design` skeleton, two distinct preflight agents, inlined-probe lenses**                                      | B (merged preflight), C (charter-cited thin lenses)           | Maximises reuse of the proven multi-lens-then-synthesise pattern; honours the Session-Brief knowledge-layering separation; keeps every prompt standalone-runnable per `.agents/prompts.md`.                                      |
| **Two preflight steps (detect, then install)**                                                                                          | One merged preflight agent (B)                                | Keeps `audit-stack.md` a first-class deliverable lenses depend on; lets stack-detect stay provably non-mutating (`Read, Grep, Glob, Write`); lets skill-install track the existing `bkit-build-install-skills` wording verbatim. |
| **Skill-install reuses the `bkit-build-install-skills` pattern via an audit sibling**                                                   | New bespoke install agent; inline install in the orchestrator | Existing agent already wraps `npx skills find/add`, caps at 10, treats "not found" as non-blocking; the audit sibling only changes the query seed (stack tokens → `audit-{stack}`).                                              |
| **Lenses INLINE their own universal-pattern probe block; charter doc is a passive human index (or omitted)**                            | Charter as cited runtime dependency (C)                       | Standalone-runnable rule forbids cross-file cites; the superseded design's review-1 CRITICAL #2 already settled this — inline + passive index.                                                                                   |
| **Stack report uses generic field names (no `IS_PNPM`/logger-list leakage)**                                                            | Carry forward the superseded per-lens `STACK_FLAGS` blocks    | The whole point of the new direction: detection mechanism moves upstream into a stack-agnostic schema; lens prompts stay library-name-free (grep-gate enforces).                                                                 |
| **9-step pipeline (design's 10 minus workstream-vs-close re-numbering, plus 2 preflight steps)**                                        | 7-step superseded shape; 8-step merged (B)                    | Two new preflight steps shift numbering vs the issue-body table; reuse design's fan-out/synthesise/organise/summary/workstream/close ceremony so the workstream re-cut (#103–#107) is mechanical.                                |
| **Drop `pnpm install --frozen-lockfile` in Worktree Setup; keep env + vale copy**                                                       | Keep full design Step 2 verbatim                              | Audit is read-only; lenses + stack-detect operate on source/manifests, not a built tree. (Carried from superseded design.)                                                                                                       |
| **Audit stays read-only, ad-hoc-only, Linear-bound, terminal at `In Review`; deprecation header only on legacy `bkit-utility-audit-*`** | Auto-route PASS to Done; delete legacy prompts now            | Session Brief carry-forwards; uniform terminal state matches design/plan/build.                                                                                                                                                  |
| **Phase 3 (WebSearch) noted as a follow-up slot on the lens step, not designed**                                                        | Design `--with-websearch` now                                 | Explicitly deferred by the Session Brief; pipeline is shaped so it drops in without restructuring.                                                                                                                               |

> Out-of-lens (noted, not designed here): per-finding schema details, INDEX.md pruning policy, re-audit FID suffixing, smoke-test attestation, exact deprecation-header version strings — these belong to design-generate/organise, not brainstorm.
