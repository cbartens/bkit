# Design Brainstorm & Ideas

Lens: Pragmatic — existing code, minimal new infra, ship fastest.

Scope: pass-3 delta over the PASS'd 10-step / 16-agent baseline (`docs/plans/202605/80-audit-workflow-design.md`). All three approaches PRESERVE that backbone — orchestrator owns tracker/git/lock/status.json, 16 leaf agents, fan-out at Step 5, synthesise/organise/summary at Steps 6/7/8, `## Missing Lenses` coverage manifest gate at Step 6, `## Parse Errors` gate, Failure Path, the YAML `finding`-block schema, the `audit-stack.md` versioned schema, and the `bkit-build-install-skills` parity for skill-install — and differ only in HOW the five new surfaces (UI/UX, reference-signal, supply-chain/CI-CD, data-layer, AI/LLM) and the **keystone conditional-lens model** (applicability flags + conditional gating + "N/A — not applicable" third coverage state) fold in.

Open-question constraints (frozen by comment 4539759063 — apply to all approaches): every lens `opus`/`high`; reuse build/ship skill install + uninstall machinery verbatim (10-skill cap, ship-prune cleans `audit-*` too); do NOT pin versions (resolve `Deprecated since` at build/ship vs `package.json#version`); ASCII operators only in `.agents/workflows/*` and `.agents/prompts/*`; reference-signal MUST emit `confidence: low` and never rank top/critical; tracker-agnostic phrasing (no Linear-direct verbs); MCP-only for tracker writes.

## Approach A — Flag-Stamped Lens Roster (minimal keystone, one tier of lenses) ⭐ Recommended

**Summary (one sentence):** Add all new lenses to the same Step-5 fan-out roster the baseline already runs (11→16: +`ui-ux`, +`supply-chain`, +`data-layer`, +`ai-llm`, +`reference-signal`); each lens declares its own `requires:` applicability key, `bkit-audit-stack-detect` emits a single new `## Applicability` flag block in `audit-stack.md`, the orchestrator gates launch on the flags, and lenses not launched are recorded as `N/A — not applicable ({reason})` in `## Missing Lenses` — a third coverage state distinct from `ran-empty` and the existing implicit `crashed`.

- **Pipeline shape (still 10 steps, no new step type):** Steps 1, 2, 3 (stack-detect now emits an extra `## Applicability` block), 4, **5 fans out 16 lens slots** with conditional gating, 6 (synthesise adds the third coverage state + reference-signal down-rank), 7 (organise: ranking honours `source == reference-repo → never top/critical`), 8, 9, 10. New orchestrator input flag `--with-websearch` flips the `network` applicability flag.
- **Conditional gating mechanism:** lenses ALWAYS launch and self-no-op when their `requires:` flag is false — the lens prompt opens `**If** required flag is false → write empty body + 'N/A — not applicable ({flag-name}=false)' marker, exit.` Belt-and-braces: a stack-detect flag bug cannot silently lose a lens because the launch artifact + N/A marker still appear in `## Missing Lenses`. Cost = one trivial-no-op subagent (<1s, low token).
- **Stack-detect change:** add a `## Applicability` block to `audit-stack.md` (schema bumps to `schemaVersion: 2`):

  ```markdown
  ## Applicability

  hasWebSurface: true # frontend/UI present (drives ui-ux)
  hasDb: true # database present (drives data-layer)
  hasLLM: false # LLM/model integration present (drives ai-llm)
  hasCi: true # CI workflows present (drives supply-chain — defaults true)
  hasNetwork: false # orchestrator-set from --with-websearch (drives reference-signal)
  ```

  Plus a `## Applicability — Flag Inventory` enum block (the canonical list of flag names) so a plan-level grep-gate can assert every lens's `requires:` key appears in the inventory (mirrors the existing zero-library-names grep-gate).

- **Per-lens `requires:` frontmatter key:** one-line addition to the existing frontmatter (`name`, `model`, `effort`, `tools`, `requires`). Values: `always` | `hasWebSurface` | `hasDb` | `hasLLM` | `hasCi` | `hasNetwork`. Existing 11 lenses set `requires: always`. New lenses set their flag.
- **Supply-chain ships as a NEW lens (not extending `security`):** own slug `supply-chain` (class: security), own tool surface `Read, Grep, Glob, Bash` (only lens needing Bash — for git-history secret-scan + lockfile integrity scan). Pin to a read-only Bash allowlist in the prompt body (`git log`, `git cat-file`, `grep`, `awk`; explicitly no `git checkout`/`reset`/`push`). `requires: hasCi` defaults true (most repos have CI + deps).
- **Reference-signal as a LENS (not a non-lens sibling agent):** slug `reference-signal`, `requires: hasNetwork`, emits findings via the same YAML `finding`-block schema with the constraint `confidence: low` always + a new `source: reference-repo` field. Bounded to top-3 reference repos, structure/config/README only. Captured repo identities go in the lens output's `## Reference Repos Used` section for reproducibility.
- **Down-rank rule:** synthesise/organise/summary apply `source == reference-repo OR confidence == low → never matrix top-row / never ranked-list top-3 / never executive summary`. Single grep target across the three downstream prompts.
- **Third coverage state in `## Missing Lenses`:** synthesiser distinguishes `ran` (returned non-empty) / `ran-empty` (returned empty body) / `N/A — not applicable ({reason})`. `crashed` (no artifact) stays caught by the existing artifact-exists+non-empty universal gate. Step-6 gate adds one grep-assertion: every roster entry resolves to one of the three states.
- **Skill-install:** unchanged — reuses `bkit-build-install-skills` pattern via `bkit-audit-install-skills` (frozen by 4539759063). Ship-prune of `audit-*` skills coverage is a one-line addition to `bkit-ship`'s Prune Skills step's allowlist (parity with the `bkit-build-install-skills` lifecycle).
- **Complexity:** LOW. ~95% reuse of the PASS'd baseline. 5 new lens prompts + one new block in `audit-stack.md` + one new frontmatter key + one new coverage state + one orchestrator input flag + one down-rank filter in 3 downstream prompts. No new pipeline step, no new agent class.
- **Extensibility:** HIGH for new conditional lenses (add prompt + applicability flag + a stack-detect signal, done). MEDIUM for fundamentally new agent shapes (would still need their own step). The `--with-websearch` slot generalises to any future network-tier lens without re-plumbing.
- **Risk:** (1) Applicability flags become hidden coupling between `bkit-audit-stack-detect` and every lens — a renamed flag breaks gating silently. Mitigation: `## Applicability — Flag Inventory` block + plan-level grep-gate. (2) A mis-set `true` flag pollutes findings — caught by each conditional lens's own `**Lens discipline:**` clause requiring a sanity probe before emitting findings ("if probe finds no UI files, emit empty + N/A note even if flag is true"). (3) Supply-chain's Bash surface is the only mutating-class tool in a read-only fan-out — pinned to a documented read-only allowlist in the prompt.
- **Maintenance:** LOW. Adding a 13th universal or a 6th conditional lens follows the same edit pattern. Cost ceiling rises with roster size (16 opus lenses ~4.5× design triplet) — Sonnet-downgrade lever stays available unchanged.
- **Reuse vs new:** Reuse — fan-out shape, all gate ceremony, finding-block schema, dedup, `## Missing Lenses`, `## Parse Errors`, build-skill-install pattern + uninstall, the deprecation-header convention, `bkit-design.md` 10-step skeleton. New — 5 lens prompts, `## Applicability` block + flag inventory, `requires:` frontmatter key, third coverage state, `--with-websearch` orchestrator flag, down-rank rule.

## Approach B — Two-Tier Fan-Out (always-on lenses vs conditional-lens tier)

**Summary:** Split Step 5 into **Step 5a (always-on lenses, parallel)** and **Step 5b (conditional lenses, parallel)** — two distinct fan-outs each with their own gate count, their own status.json artifact, their own tracker comment. Pipeline grows from 10 to 11 steps; pre-launch filter (no launch-and-self-skip). Supply-chain extends `security` rather than a new lens.

- **Pipeline shape (11 steps):** 1 Start · 2 Worktree · 3 Stack Detect (emits `## Applicability` block) · 4 Skill Install · **5a Always-On Lenses (parallel, 13 lenses)** · **5b Conditional Lenses (parallel, 1-4 lenses)** · 6 Synthesise · 7 Organise · 8 Summary · 9 Workstream Issues · 10 Close. Reference-signal sits in 5b gated by `--with-websearch`.
- **Pre-launch selection:** orchestrator reads `## Applicability` flags BEFORE dispatching 5b and only launches lenses whose flag is true. The 5b tracker comment loudly logs the selection (`Conditional lenses launched: data-layer; skipped: ai-llm (hasLLM=false), ui-ux (hasWebSurface=false), reference-signal (hasNetwork=false)`).
- **Supply-chain extends `security` (one prompt, two probe blocks):** the `security` lens prompt gains a second `### Supply-chain / CI-CD probes` section after the existing app-level probes; tool surface escalates to `Read, Grep, Glob, Bash` (with the same allowlist constraint as Approach A's supply-chain). Lens count stays at 12 in 5a (11 baseline + ui-ux).
- **UI/UX moved to 5a as a near-universal:** accepts that no-UI repos will emit `N/A — not applicable` via the same conditional-lens-self-no-op machinery (so the keystone still lands), but the lens lives in the always-on tier because most consumer repos have UI.
- **Third coverage state and N/A** still need to exist (5b lenses skipped pre-launch must be marked N/A in `## Missing Lenses`); same down-rank rule for reference-signal.
- **Complexity:** MEDIUM. Adds a second fan-out step + step renumbering (10→11) + extra gate ceremony + a second tracker comment per run + larger registry-block rewrite. Extending `security` is one prompt with two probe sections but the lens-class boundary blurs.
- **Extensibility:** HIGH for the conditional family (5b grows freely without touching 5a's count or gate); changing tier assignment (moving a lens from 5a to 5b) requires an orchestrator edit. The two-tier shape signals to future authors where new lenses belong, reducing taxonomy bikeshedding.
- **Risk:** (1) Bigger deviation from the `bkit-design.md` 10-step pattern — the very registry-rewrite risk the baseline risk register #1 flags. (2) Two fan-outs = two status.json artifacts to gate + two failure-isolation surfaces. (3) Pre-launch filter means a flag bug silently SKIPS a lens with no launch artifact telltale — only the 5b comment text is the safety net. (4) Extending `security` blurs the class boundary — one lens emitting `class: security` findings of two very different shapes (auth/validation vs unpinned-action-SHA); synthesiser dedup still works `(class, normalized_location)` but workstream-cut readability suffers, and supply-chain-specific authors must touch the security prompt.
- **Maintenance:** MEDIUM. Two-tier shape is more code to maintain (two fan-outs, two gates) and a deeper deviation from the design skeleton. The `security` lens grows in length; all future security-domain additions land in one prompt (could become a multi-thousand-line mega-prompt).
- **Reuse vs new:** Reuse — fan-out skeleton (twice), gate ceremony, finding schema, dedup, build-skill-install. New — second fan-out step + its status.json/comment artifacts, step renumbering, extended `security` prompt with two probe sections + Bash surface, applicability flags + pre-launch selection logic, N/A coverage state, down-rank rule.

## Approach C — Stack-Detect Gating Plan (lens roster as artifact, single fan-out)

**Summary:** Push the conditional decision entirely upstream — `bkit-audit-stack-detect` produces, alongside `audit-stack.md`, a **`audit-lens-roster.md`** flat list of slugs to launch on this repo plus reasons for the excluded ones. The orchestrator's Step 5 fan-out reads the roster and launches exactly that set (data-driven loop, no per-lens applicability checks, no launch-and-self-skip). The synthesiser cross-references the roster against the full known lens inventory (compiled into its prompt) to compute the three `## Missing Lenses` states.

- **Pipeline shape (still 10 steps):** Step 3 grows a second output artifact (`audit-lens-roster.md`); Step 5's fan-out becomes data-driven (read roster → loop launch). Reference-signal is the only lens NOT driven by the roster — it's a parallel sibling agent (`@bkit-audit-reference-signal`) gated by `--with-websearch`, mirroring the baseline's "non-lens agent" treatment of stack-detect / skill-install.
- **Roster artifact schema:**

  ```markdown
  # Audit Lens Roster

  schemaVersion: 1

  ## Launch

  architecture, hotpath, config, reliability, observability, debt, dead-code, deps, security, tests, docs-drift, ui-ux, supply-chain, data-layer

  ## Skip

  ai-llm: N/A — not applicable (hasLLM=false)
  ```

- **Synthesiser cross-check:** lens inventory enum lives in the synthesiser's prompt (`KNOWN_LENSES = [architecture, hotpath, ..., ai-llm, reference-signal]`); cross-check launched roster ∪ skip-list ∪ reference-signal-presence against the enum to compute the three coverage states + flag any unknown lens emissions.
- **Complexity:** MEDIUM. New artifact (`audit-lens-roster.md`) with its own schema + its own Step-3 gate. Data-driven fan-out loop in the orchestrator (was a fixed 11-slot fan-out, becomes `for lens in roster`). Reference-signal as a non-lens agent means a new step or a folded-into-Step-3/4 placement.
- **Extensibility:** HIGHEST for changing applicability logic (rewrite roster-computation prose in one prompt; no orchestrator edit). Lens roster becomes a first-class human-readable artifact — useful for explainability ("why didn't lens X run?"). LOW for net-new lens slots — adding a new lens requires editing both the lens prompt AND the stack-detect prompt's inventory (two-file edit vs A's one).
- **Risk:** (1) Single point of decision = single point of failure. A stack-detect bug that drops a lens from the roster makes that lens invisible (no launch artifact, no per-lens N/A entry from the lens itself — only from the synthesiser's roster cross-check). (2) Two contracts (`audit-stack.md` + `audit-lens-roster.md`) feeding 16 readers vs A's one — more contract surface, but each small. (3) Lens inventory enum in the synthesiser prompt drifts from the actual lens count — silent shrinkage of the safety net (no compile-time check on Markdown). (4) Reference-signal as a non-lens agent breaks the "all signals are lenses" mental model the baseline established and adds another agent-class to the registry.
- **Maintenance:** MEDIUM-HIGH. Two contracts to keep in sync. Adding a lens is a two-file edit; the lens-inventory enum lives in stack-detect's prompt — easy to forget. Roster file is a nice debugging surface but is a regression risk for the documented-vs-implemented gap the baseline explicitly warns against (review-1 C2).
- **Reuse vs new:** Reuse — fan-out shape, gate, finding schema, dedup, build-skill-install, baseline non-lens-agent pattern (stack-detect / skill-install). New — `audit-lens-roster.md` artifact + schema + gate, data-driven fan-out loop in orchestrator, lens inventory enum in stack-detect AND synthesiser prompts, reference-signal as separate agent class, third coverage state via roster cross-check.
