# Design Brainstorm & Ideas

Lens: Risk premortem — operability, failure modes, on-call ergonomics. Scope: how the outcome gate behaves when it times out / when re-trigger is itself suppressed, how it stays observable and actionable, how it composes with the existing ship-side regression gate (#81 Change B/C), the no-CI consumer discriminator, EC-1 idempotency blast radius, EC-2 abort semantics, and the documentation + authoring constraints.

> Grounding refs (this worktree): the loud push + inline HEAD-Subject Assertion at build close-workflow `.bkit/workflows/bkit-build.md:1179-1189`; the create-pr `[skip ci]` commit at `:1128`; build's blind `gh pr create` at `:1092` with retry→Failure-Path at `:1108`; the EC-2 abort push at `:95-96` (force-with-lease to feat); the shared assertion source `.bkit/workflows.md:938-986`; ship's pre-merge fail-fast on empty rollup `.bkit/workflows/bkit-ship.md:291`; #81 regression gate `:355-387`; ship post-merge dispatch gate `:543-546` and squash-SHA gate `:930-938`; KN-11 `docs/deployments.md:317-319`.

## Approach A — "Bounded poll + single capped self-heal, with a typed no-op verdict" (the outcome gate as a diagnosable state machine) ⭐ Recommended

**Summary:** Implement the D2-safe kernel as an explicit 4-outcome state machine inlined after every final loud push — `DISPATCHED` (pass) / `SUPPRESSED→re-trigger→DISPATCHED` (self-healed) / `NO-CI` (re-trigger also dispatched nothing → typed no-op, log and pass) / `UNRESOLVED` (re-trigger errored or budget exhausted → Failure Path) — so every terminal state is named, logged to `status.jsonl`, and maps to exactly one operator action.

The operability thesis: a gate that can silently pass on "no run" is the bug we are fixing (KN-11). A gate that can silently _fail_ on "consumer has no CI" is the _next_ incident. The discriminator (re-trigger dispatches nothing → no-op) is load-bearing precisely so the gate never pages a no-CI consumer. Make the four outcomes a closed set with a verdict field on the `step-done` status record (`ciDispatch: dispatched|self-healed|no-ci|unresolved`), so on-call can read the verdict instead of reconstructing it from poll logs.

**Premortems:**

- **10x scale (high build throughput / busy Actions queue):** The failure mode is _queue latency mistaken for suppression_. At fleet scale, GitHub may not surface a `bkit-decide` check in `statusCheckRollup` within 60s even though the push _did_ trigger — the run is queued, not suppressed. The gate then pushes a spurious `re-trigger` empty commit, which fires a **second** `pull_request: synchronize`. Two runs now race on the same branch; the first (real) run is the one we wanted, the second is wasted CI and — critically — if the issue carried `bkit:auto`, the re-trigger commit carries `bkit [auto route]` (per `.bkit/workflows.md:534`) and can fan a **second auto-route** dispatch. Blast radius: doubled CI minutes per false-positive + a redundant auto-route event. _Observability:_ poll-loop should log each attempt (`attempt N/6: rollup has K checks`) so a queued-vs-suppressed call is reconstructable. _Recovery:_ the self-heal cap of 1 bounds the waste to exactly one extra run; the re-trigger is `--allow-empty` so it never changes tree state. Mitigation below tightens the discriminator so queue latency does not read as suppression.
- **6 months later (drift / magic numbers):** `~60s (6×10s)` is a tuned constant with no derivation in the workflow file (authoring rules forbid rationale inline). In 6 months a maintainer bumping CI cold-start, or a consumer on a slower runner, silently converts "queued" into "suppressed" → chronic spurious re-triggers that look like flakiness. The undocumented invariant "poll budget > p99 dispatch-surfacing latency" lives only in tribal memory. _Observability:_ the constant must be a single named symbol (`POLL_BUDGET_S` / `POLL_INTERVAL_S`) so a grep finds every copy across the 3 workflows — not three bare `6` literals. _Recovery:_ the rationale + the derivation ("budget must exceed observed dispatch-surfacing latency, not run _completion_") goes in `deployments.md` KN-11 update so the magic number has a documented home.
- **On-call at 3am (page shape / diagnosability):** The page we _want_ is "build aborted: CI dispatch UNRESOLVED on `feat/{FID}` after re-trigger — HEAD is `<sha>`, last rollup empty, re-trigger run errored: `<gh error>`." The anti-page is the status quo (KN-11): no page at all, silent green, discovered days later at ship. The risk in _this_ approach is the `NO-CI` no-op being **indistinguishable** from a genuine suppression that the re-trigger also failed to clear (e.g. a _second_ skip token leaked onto the re-trigger commit). If both "no CI configured" and "re-trigger itself suppressed" collapse to `no-op`, on-call gets a false all-clear. _Observability:_ before concluding `no-ci`, the gate must re-assert the re-trigger HEAD is clean (reuse the inline HEAD-Subject Assertion on the empty commit) — a suppressed re-trigger is `unresolved`, only a _clean_ re-trigger that dispatches nothing is `no-ci`. _Recovery path:_ `unresolved` → Failure Path with the abort-handover comment naming HEAD SHA + the manual `gh workflow run ci.yml --ref feat/{FID}` recovery (already documented `deployments.md:351`).
- **Author leaves (bus factor):** The entire correctness of this gate rests on one non-obvious fact — `PUSH_MODE=LOCAL` is _not_ "no CI" (it creates a PR, `bkit-debug.md:172`), so the _only_ legitimate no-op is "repo has no CI workflow for this event," and the _self-heal is the discriminator_. That reasoning is in the issue body, not the codebase. If the author leaves, the next maintainer "simplifies" the gate by re-adding a `PUSH_MODE`-based no-op branch and silently reintroduces the blindness. _Mitigation:_ the `deployments.md` D2 record must state the discriminator-by-construction invariant explicitly ("no mode branch; the clean-re-trigger-dispatches-nothing probe is the sole no-CI signal"), and `workflows.md` § HEAD-Subject Assertion must be renamed/expanded to § "CI-Dispatch Gate" covering both the typed-string _and_ the outcome clause as one contract.

**Risk-mitigation guidance (fold onto whichever approach is picked):**

- Tighten the discriminator: between the two polls, re-run the inline HEAD clause on the re-trigger commit so a _suppressed_ re-trigger is `unresolved`, never `no-ci`. This is the single highest-value safety add — it closes the 3am false-all-clear.
- Record a `ciDispatch` verdict enum on the `build-close-workflow` / `debug-close-workflow` / `ship-merge-pr` `step-done` record so the four outcomes are queryable from `status.jsonl` (composes with #209's NDJSON model; `merge=union`-safe, append-only).
- Make the re-trigger commit inherit the _exact_ marker treatment of close-workflow: it MUST carry `bkit [auto route]` iff `bkit:auto` was read (reuse `AUTO_ROUTE_SUFFIX` from `bkit-build.md:1168`), and MUST NOT introduce a fresh suppressor. Open question from the issue ("does the re-trigger interact with the auto-route marker?") resolves to: same suffix, sourced from the same pre-commit label read.
- Promote the poll budget + interval to named symbols and document the derivation in KN-11 (budget bounds _dispatch surfacing_, not run completion — the gate must never wait for `bkit-tests` to _finish_, only to _appear_).

## Approach B — "Verify-only gate, no self-heal; suppression always routes to Failure Path with a one-command fix" (push the auto-recovery cost onto the human, buy a smaller blast radius)

**Summary:** Keep the outcome probe (poll `statusCheckRollup` / post-merge `gh run list` for a `bkit-decide` run) but drop the automatic `re-trigger` empty-commit self-heal entirely: an empty rollup after the bounded poll is _always_ a loud Failure Path that names the HEAD SHA and prints the exact `gh workflow run ci.yml --ref feat/{FID}` (or re-push) recovery — except the _no-CI consumer_ case, which is detected up-front by a cheap "does this repo define a CI workflow for this event?" probe rather than by an empty-commit discriminator.

The operability thesis: self-heal hides the signal. Every auto-re-trigger that "fixes" a suppression also erases the evidence that something is constructing suppressed HEADs in the first place — so the _root_ defect (e.g. a workflow step that leaks a skip token) never gets seen. A verify-only gate trades a small amount of human toil (one command at abort time) for a much smaller blast radius and a much louder signal.

**Premortems:**

- **10x scale:** This approach _removes_ the doubled-CI-on-queue-latency failure mode of Approach A — no empty commit is ever pushed automatically, so queue latency just extends the poll, never fires a second run. The cost shows up as **alert volume**: at fleet scale, every transient queue-latency false-positive becomes a Failure Path / page. If dispatch-surfacing p99 ever creeps past the poll budget, a verify-only gate pages the whole fleet where Approach A would have (wastefully but silently) self-healed. _Observability:_ same per-attempt poll logging. _Recovery:_ the page is self-describing (one command), but the _rate_ of false pages is the risk — needs the poll budget tuned conservatively (longer than A's, since there is no self-heal backstop).
- **6 months later:** The up-front "does a CI workflow exist for this event?" probe is the new brittle integration. Detecting "no CI configured" _without_ an empty-commit experiment means parsing `.github/workflows/*.yml` for trigger events (or `gh api` for workflow definitions) — both of which drift as GitHub's schema / event model evolves, and the latter violates the MCP-only workflow rule (memory: workflows are MCP-only for GitHub). A statically-parsed "has CI" check is exactly the kind of typed-string assumption (does my YAML _look like_ it triggers?) that #261 is fixing — it re-introduces "check what we typed, not what GitHub did." _This is the approach's core weakness._ _Recovery:_ would have to fall back to the empty-commit discriminator anyway, collapsing B into A.
- **On-call at 3am:** Best-in-class page shape — every suppression is a loud, named, one-command-to-fix Failure Path. No "self-healed, probably fine" ambiguity. But the _frequency_ is the on-call tax: a verify-only gate on a busy queue pages on latency, not just real suppression. The 3am question "is this a real suppressed HEAD or just a slow queue?" is answerable only from the poll log, and the operator must decide whether to re-run or wait. Higher cognitive load per page than A's typed verdict.
- **Author leaves:** Lower tribal-knowledge load on the _gate_ (no discriminator subtlety) but higher on the **static CI-presence probe** — whoever inherits it must understand the YAML-trigger-event parsing, which is exactly the fragile knowledge #261 exists to eliminate. Net bus-factor: worse, because the fragile part moved from a self-documenting empty-commit experiment to an opaque static parse.

**Risk-mitigation guidance (fold on):**

- If B is chosen, do NOT statically parse workflow YAML for CI-presence. Detect no-CI the same way A does (clean re-trigger dispatches nothing) — but make it a _one-shot diagnostic_ re-trigger emitted only on the Failure Path, framed as "auto-diagnosing whether this repo has CI for this event" rather than a silent heal. This keeps the loud signal while avoiding the brittle static probe.
- Tune the poll budget _longer_ than A (there is no self-heal safety net), and document that B trades CI minutes for alert precision.

## Approach C — "Outcome gate + EC-2 abort-leaves-last-validated-HEAD + EC-1 push-suppressed idempotency, as one unified branch/PR + CI-dispatch contract" (close the whole EC-1→EC-2 chain, not just the gate)

**Summary:** Land Approach A's gate _and_ close the two edge cases that actually produce the observed pain, treated as one contract aligned across build/debug/ship: (EC-2) on Failure Path, if the branch has an open PR, do **not** push the `[skip ci]` abort commit onto it — leave the last validated HEAD intact (commit locally / stash the handover, push only to non-PR branches); (EC-1) give build debug's PR-exists detection so a re-run does not blind-`gh pr create`→error→Failure-Path, using a **push-suppressed** detection (`gh pr list --head` read-only, no synchronize) and short-circuiting the create-pr step when a PR already exists and HEAD is already pushed — never emitting a mid-build loud `synchronize`.

The operability thesis: the gate alone makes the _symptom_ observable, but EC-1→EC-2 is the _most common path to the symptom_ (issue: "the most likely 'build ends in a PR not running tests'"). Fixing only the gate means on-call still gets paged for the same root cause repeatedly; fixing the chain removes the recurrence.

**Premortems:**

- **10x scale:** EC-1's PR-exists detection is the D2 tripwire. The whole point is that `gh pr list --head` is **read-only** (no push, no synchronize), so detection itself cannot fire the auto-router. The scale risk is the _short-circuit logic_: "PR exists AND HEAD already pushed → skip create-pr." If "HEAD already pushed" is computed wrong (local HEAD ahead of remote after a resume), the workflow either (a) skips a push it needed → no CI → the exact bug, or (b) re-pushes a clean HEAD mid-build → premature synchronize → the D2 defect. Blast radius at scale: a mis-computed "already pushed" predicate regresses D2 across every concurrent build. _Observability:_ the predicate must log `local HEAD <sha> vs remote <sha> → {push|skip}`. _Recovery:_ the outcome gate is the backstop — even if the short-circuit wrongly skips, the gate at the _intended_ final push catches "no dispatch" and self-heals/pages.
- **6 months later:** This approach aligns build/debug/ship on "one branch/PR + CI-dispatch contract" — high value, but the alignment is also the drift risk. Three workflows now share the create-pr-vs-detect-PR logic; a future edit to one (say, debug's local-mode) that does not re-align the other two re-opens EC-1 on the unaligned workflow. The authoring rule "align shared lines across ALL workflows" must be enforced by a render-sweep / grep check, or drift is inevitable. _Recovery:_ a CI lint that greps the three workflows for divergent create-pr blocks.
- **On-call at 3am:** Best outcome-per-page: EC-2 means a _failed build never leaves a CI-suppressed HEAD on a live PR_ — so the next ship of that PR is not poisoned, and the human who picks it up sees the last _validated_ HEAD, not a silent skip. The diagnosability win is large: "build aborted, PR untouched, last green HEAD intact" is a clean recovery state. The risk: EC-2's "leave last validated HEAD" semantics are subtle — the handover doc still needs to land _somewhere_ (it currently rides the abort commit at `bkit-build.md:95-96`). If the handover is dropped to preserve HEAD, on-call loses the abort context. _Recovery:_ push the handover to a non-PR ref (e.g. commit on a `bkit-abort/{FID}` branch or attach to the issue comment, which the Failure Path already does at `:97-101`) so HEAD stays clean _and_ context survives.
- **Author leaves:** Highest tribal-knowledge concentration of the three approaches — the EC-1 short-circuit, the EC-2 PR-aware abort, and the gate all encode D2 invariants that are invisible without the issue history. This is the approach most likely to be "simplified" into a regression. _Mitigation:_ the D2 record in `deployments.md` must enumerate all three (gate / EC-1 read-only-detect / EC-2 preserve-HEAD) as a single named contract with the "why" for each, and the `workflows.md` § must carry the branch/PR decision table (PR-exists × HEAD-pushed → action) so the logic is not reverse-engineered from bash.

**Risk-mitigation guidance (fold on):**

- Scope EC-1 to **read-only detection + push-suppressed short-circuit only**; the moment detection would require a push to a PR branch, defer to the existing final loud push — never add an interim synchronize. This is the line that keeps EC-1 D2-safe.
- For EC-2, decouple "preserve last validated HEAD" from "preserve abort context": keep the issue-comment handover (already in the Failure Path) as the durable context sink, so leaving HEAD untouched costs no diagnosability.
- Gate the whole contract behind the outcome gate as backstop — EC-1/EC-2 reduce _recurrence_, the gate guarantees _detection_ even if they have a bug.

## Cross-Approach Risks

- **Queue latency vs suppression is the universal ambiguity.** Every approach polls a signal that GitHub surfaces _asynchronously_. The poll budget is the single tuning knob that decides false-positive rate, and it is the same magic-number risk in all three. The design's `Risks & Open Questions` must state the invariant: _budget must exceed observed dispatch-surfacing p99, and must NOT wait for run completion_. (Surface for final doc.)
- **The re-trigger / `bkit [auto route]` interaction is unresolved in the issue.** Any self-heal commit on the final HEAD must inherit close-workflow's exact marker treatment (suffix sourced from the pre-commit `bkit:auto` read, `bkit-build.md:1168`), or a self-heal can either _drop_ a needed auto-route (build never routes) or _double-fire_ one. Applies to A and C; B avoids it by not self-healing on the success path but must still handle it on the diagnostic re-trigger.
- **Composition with #81 ship-side gate must be a layered backstop, not a duplicate.** #261's gate fires at the _final feat-branch push_ (catches suppression before ship); #81 Change C fires at _ship pre-merge_ (empty rollup → Failure Path, `bkit-ship.md:291`) and post-merge on `dev` (`:543-546`, `:930-938`). They must not both try to self-heal the same HEAD — ship's gate stays a hard fail-fast (a suppressed HEAD reaching ship is a real anomaly worth a human), while build/debug's gate self-heals earlier. The design must state the division of labor explicitly so a future maintainer does not add self-heal to ship (which would mask the very signal #81 was built to surface).
- **Documentation lockstep is a correctness requirement, not hygiene.** KN-11 (`deployments.md:317-319`) currently describes only the symptom (empty rollup) — it must gain the outcome-gate + discriminator + named poll budget. The shared § in `workflows.md:938` is titled "HEAD-Subject Assertion" but the gate is now _two_ clauses (typed-string + outcome); the section must be renamed/expanded (e.g. § "CI-Dispatch Gate") so the inlined-per-workflow bash has one canonical rationale home. The D2 record in `deployments.md` must record the discriminator-by-construction invariant or it will be "simplified" into a regression.
- **Authoring-constraint risk: the gate is inlined ×3 and must stay byte-aligned.** Instructions-only, no cross-refs, reuse closest existing phrasing (`grep .bkit/workflows/` first — the inline HEAD clause at `bkit-build.md:1180-1185` is the reuse template), align shared lines across build/debug/ship, then re-render `.claude`/`.cursor`/`.opencode` mirrors. Three divergent copies of a poll loop is itself an operability risk (a fix applied to one, not all) — the final design should mandate a render-sweep / grep-equality check across the three inlined gates as an acceptance criterion.
