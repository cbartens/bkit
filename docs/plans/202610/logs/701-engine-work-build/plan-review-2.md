## CRITICAL

1. **The `fixable: null` / `verdict: null` seam is unspecified at the verifier boundary.** Task 1 has the engine emit `fixable: null` and `verdict: null` (Open Questions row 6, option A); the prompt edits say the verifier reads `verdict` from the report and appends the report's `logLine` "verbatim". Three contradictions: (a) the verify artifact's header `Verdict:` accepts only `PASS | CONCERNS | FAIL` — `steps finish` refuses any other value (`steps.ts:177-183`, via `promptHeader` at `steps.ts:111-135`), so a copied `null` verdict fails the step; (b) the prompt's own log contract requires every gap line to end `— Fixable: true` or `— Fixable: false` (`bkit-build-plan-verify.md:117`), which a verbatim `Fixable: null` line violates; (c) `bkit-build-plan-gaps-remediate.md:83` skips only lines ending `— Fixable: false` on a `fixable only` scope, so a `null` line is _attempted_ — re-creating the futile-fix loop #656 eliminated. Plan edit needed: state that for the four diff-read gaps the verifier logs the line with its _decided_ `Fixable: true|false` substituted for the engine's `null`, and that the header `Verdict:` is the post-judgement roll-up (any false → `FAIL`; else any true → `CONCERNS`; else `PASS`), never the report's `null`.

2. **The `no-red` "already landed" exception is silently dropped.** Today `bkit-build-plan-verify.md:73` clears a `no-red` gap when the plan-currency report classifies the task `Broken` and the execute log records `DONE — TASK {N}: already landed` (a line `bkit-build-plan-execute.md:93` writes). The plan's engine mapping marks every `no-red` `fixable: false`, and the prompt keeps only the four diff reads — no row preserves this exception. A build whose task's work already landed (resume, or dev landed the same change) regresses from "no gap, build proceeds" to `FAIL` → Decision Pause → a human-written TEST EXCEPTION, and neither the issue nor Breaking Changes names the change. Fix: keep the exception in the prompt as a verifier override of the engine's `no-red` `fixable: false`, or teach `green` to suppress `no-red` when the execute log records the `already landed` line for the task.

3. **The holistic verify loses its tick path.** Process 9 ("tick its `- [ ] **TASK {N}:**` line") is mode-agnostic: today the holistic pass at build Step 9 ticks tasks it judges satisfied across every group, and ship's summary FAILs on unticked tasks (`summary.ts:174,266,308`). The plan wires `bkit tasks tick` only into Step 7, and `tick --group=` exits 2 on a task outside the group (Task 2 spec), so a holistic artifact's cross-group `Tasks:` has no consumer — tasks newly satisfied at holistic stay unticked and the ship summary blocks. Fix: wire Step 9's finish the same way (per-group `tick` calls over the held numbers, or relax `tick`'s group constraint when `--tasks` is given), or declare the drop and its ship-gate consequence in Breaking Changes.
