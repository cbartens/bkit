## CRITICAL

1. **Debug Steps 9 and 10 still push all of local `dev`, before Step 11 ever runs.** `.bkit/core/workflows/bkit-debug.md:552` (Step 9 Push Remediation) and `:576` (Step 10 Summary) run `bkit branches push --mode=feature`. On `dev`, `pushBranch` (`branches.ts:602-624`) treats the branch as shared and runs a plain `git push origin dev`, which sends every local-only commit. T12 changes only `mode === "dev"` with a record, and T14 only Step 11 (L593-738). So the foreign commit `abc1234` in the Concrete Example reaches `origin/dev` at Step 9, and the Outcome line "`abc1234` still unpushed" is false. Q1.2 ("pushes only its own commits") is not met. Fix: in the engine, a shared branch with a shared-checkout record routes every `pushBranch` mode through the own-commit push (or refuses `--mode=feature` / `--mode=abort` there); in prose, Steps 9 and 10 skip the push on `dev`; add a `workflow-shape.test.ts` row (no `--mode=feature` push reachable on `dev`) and a `shared-checkout.integration.test.ts` row (`--mode=feature` on `dev` with a record never pushes the foreign commit).
2. **The close commit still uses `git add -A`.** Debug Step 11 commits through `workflows close --message=…` (`bkit-debug.md:624`), and `closeWorkflow` stages with `runGit(where.tree, ["add", "-A"])` (`workflows.ts:991`) and then `commit --allow-empty`. T11 converts `writeStepRow` (`steps.ts:405`) and `stageTrackedUpdates` (`ledgers.ts:315`) only. The plan cites `workflows.ts` L982-996 only as the place where the record is removed. Q1.1 names `workflows close` explicitly ("Its commits (`steps finish`, `workflows close`) then leave those paths out"). So `notes.md` from the Concrete Example goes into `chore(dev-ci-failures): close-workflow` and is pushed. Fix: add `closeWorkflow`'s commit to T11 (same own-set / temp-index rule as `writeStepRow`), list it under Architecture `[MODIFY] workflows.ts`, and add a Test-first row (`workflows.test.ts` `close with a shared-checkout record never commits a recorded path`) plus an integration assertion that the close commit's tree excludes the foreign files.

3. **The record lifecycle does not match the order Step 11 runs in.** (a) T11 removes the record in `workflows close` (`workflows.ts` L982-996), but debug Step 11 runs `workflows close` at `bkit-debug.md:624` and the push at `:626`, after it. With no record, T12's "no record → unchanged" path does a plain push of all of local `dev`. (b) On the Failure Path from `dev`, `workflows fail` / `handover --push` (`bkit-debug.md:60-93`, L88) take the shared-branch branch of `handoverVerb` (`workflows.ts:568-642`) into `landFailedRecord` / `handBack`, not the L600-604 non-shared branch the plan cites. So the record is never removed on failure. (c) Because "Same-FID re-run keeps the original record", a later run of the same FID reuses the stale `startSha` and dirty-path set. `startSha..HEAD` then includes the human's commits made between the runs, which get pushed. Fix: remove the record only after the own-commit push and the dev CI wait succeed (or in the push verb itself); remove it in the `landFailedRecord` / hand-back path; tell a resume from a fresh run by the workflow-started row (reuse on resume, rewrite on a new run). Add `workflows.test.ts` rows: record present after close and before push; record removed after a failed handover from `dev`; a re-run after a close rewrites `startSha`.
4. **The `runs context` refusal of issue-less FIDs has no code behind it, and T2 removes the thing that gave it.** Today `runs context` (`runs.ts:1792-1805`) refuses only because `fromMarker` / `fromBranch` return null for a slug FID (`if (!parsed) → EXIT_NO_FID`). The plan says `runs context` "keeps its current refusal" and its pins stay "green before and after", but `runs.ts` is not a `[MODIFY]` for this and there is no red-first row.
