## Findings Log

1. **HIGH** · `class: mechanical` · `.bkit/core/engine/commands/workflow/branches.ts:733-756` (`pushOwnCommits`, plain-push branch)
   - **Scenario:** local `dev` is behind `origin/dev`: someone pushed to `dev` since the user last pulled, which is normal on a busy `dev` with red CI. The run's commits are the only ones ahead, so `ahead` equals `pending` and the code takes the plain `git push origin dev` path. Because `origin/dev` is not an ancestor of local `HEAD`, the server rejects the push as non-fast-forward → `EXIT_PUSH_FAILED` → debug Step 11 sub-step 2 routes exit 8 to **Failure Path**. The replay path, which handles a moved `origin/dev`, is never tried. Success criterion 1 (the fix lands on `dev`) fails in this common case. No test covers it: `shared-checkout.integration.test.ts` and `docs/testing.md:600` cover only a level or ahead local `dev`.
   - **Fix:** take the plain push only when `git merge-base --is-ancestor origin/dev HEAD` also holds. Otherwise, or on a non-fast-forward rejection, fall through to the `pushToDev` replay. Push the explicit SHA (`git push origin {lastPending}:refs/heads/dev`) rather than the branch name, so a commit made between the check and the push can't ride along. Add an integration row: local `dev` one remote commit behind `origin/dev` → the run's commits land via replay.
2. **MEDIUM** · `class: mechanical` · `.bkit/core/workflows/bkit-debug.md:697-710` (Step 11 sub-step 7, `dev` branch) with `.bkit/core/engine/commands/workflow/runs.ts:434-449` (`ciDispatchGate` re-trigger)
   - **Scenario:** on `dev`, the first poll finds no CI run at `{DEV_SHA}`. `runs dispatch` then makes a re-trigger commit and pushes it through `pushBranch`, often as a replayed copy with a new SHA, and reports that new SHA as `head`. The prose never re-holds it, so `runs wait --head="{DEV_SHA}"` and `runs gate --head="{DEV_SHA}"` still target the original SHA. That SHA has no CI run by definition → `result` != `found` → **Failure Path**, after the re-trigger has already started a real run. The hand-off path has the same gap. The CI wait turn-loop polls `--head="{DEV_SHA}"`, and the re-run block passes `--sha="{DEV_SHA}"`, while the engine's own hint (`runs.ts:1401-1404`) says to use `--head=${r.head}` / `--sha=${r.head}`. The stale `--sha` is also what gets recorded as `ciDispatch.head`.
   - **Fix:** after `runs dispatch` exits 0 on `dev`, hold the printed `head` as `{DEV_SHA}` before `runs wait` / `runs gate`. In the turn-loop and in the `{CI_REENTRY}` re-run after a `repoll` phase, use the printed `head` too (re-hold `{DEV_SHA}`). Add a `ci-dispatch-gate-alignment` / `workflow-shape` row that pins the re-hold.
3. **MEDIUM** · `class: mechanical` · `.bkit/core/engine/commands/workflow/steps.ts:410-424` (`writeStepRow`) with `.bkit/core/workflows/bkit-debug.md:27` (**Foreign path** rule)
   - **Scenario:** `steps finish` appends the `step-done` row to `status.jsonl` first. Then `ownPathCommit` throws `EXIT_FOREIGN_PATH` → exit 10, with the row left uncommitted. The workflow says to have the human commit or revert the file, "then re-run the block". The re-run appends a second `step-done` row for the same step. The fold de-dups on `(workflow, step, parentSha, at)` (`.bkit/core/engine/ledgers/status.ts:52-55`), and `at` always differs, so both rows count. At Step 8, `--count-field=soakAttempt=debug-failure-soak:next:...` counts the orphan row, so `soakAttempt` skips a number and the soak cap is reached one attempt early. Other steps get duplicate rows in the compliance grade and the run report.
   - **Fix:** in an in-place run, call `ownSet(cwd, rec)` (which throws `EXIT_FOREIGN_PATH`) before `fs.appendFileSync`, so a refused commit writes nothing and "re-run the block" stays exactly-once. Update the `EXIT_FOREIGN_PATH` exit-code text ("the row was written but…") to match. Add a `steps.test.ts` row: a refused commit leaves `status.jsonl` unchanged.
4. **MEDIUM** · `class: mechanical` · `.bkit/core/engine/commands/workflow/workflows.ts:898-899,961,1013-1015` (`closeWorkflow`)
   - **Scenario:** the same exit-10 ordering gap as finding 3, at the close. `closeWorkflow` first appends the `workflow-done` row to `status.jsonl` and the counter + `outcome` rows to `.bkit/stats.jsonl`. Only then does `ownPathCommit` throw `EXIT_FOREIGN_PATH`. Following the documented recovery ("re-run the block", `bkit-debug.md:27`) gives the run a second `workflow-done` row and a second pair of telemetry rows. Debug-run counts and outcome baselines in `.bkit/stats.jsonl` are then double-counted for that run, and the fold sees two closes.
   - **Fix:** when `activeRecord` is non-null, call `ownSet(where.tree, rec)` before any append in `closeWorkflow`, so a foreign-path refusal writes nothing. Add a `workflows.test.ts` row: exit 10 leaves `status.jsonl` and `.bkit/stats.jsonl` byte-identical.
5. **MEDIUM** · `class: architectural` · `.bkit/core/workflows/bkit-{design,plan,build,debug,ship}.md` Step 1 sub-step 2 (e.g. `bkit-debug.md:115`) and sub-step 4.2, with `.bkit/core/engine/commands/workflow/fids.ts:202-215` (`fromBranch`)
   - **Scenario:** no issue in the prompt, github tracker, and the session is on a hand-named feature branch whose name has an all-digit word that isn't a leading issue id, e.g. `feat/upgrade-react-19` or `feat/node-22-fix`. Sub-step 2 runs `fids parse --branch=feat/upgrade-react-19`. `fromBranch` finds no issue id, and `ISSUE_LESS_FID` rejects the `19` word → exit 3 (`EXIT_NO_FID`). The prose gives that exit no `Route:`, so the header **Commands** rule sends it to **Failure Path**. Even if the agent reads it as "no issue", sub-step 4.2 then takes FID `upgrade-react-19` from the branch, and `fids check --issue=""` rejects it. There is no re-mint here (the re-mint covers only sub-step 4.4) → **Failure Path**. Success criterion 2 ("no issue → warning → run continues") fails for every branch name of this kind. Uppercase or underscore branch names (`feat/Fix_CI`) fail the same way.
   - **Fix:** this needs a rule for issue-less runs on a `feat/` branch whose suffix is not an issue-less FID. Either mint a FID that differs from the branch and say how `worktrees setup` then adopts the branch instead of looking for `feat/{FID}`, or relax the issue-less rule for FIDs taken verbatim from an existing branch. Either way, add an explicit `Route:` for `fids parse` exit 3 → issue-less, and cover it in `workflow-shape.test.ts`.
6. **MEDIUM** · `class: architectural` · `.bkit/core/.bkit/workflows.md:1373` / `.bkit/wording.md:1040` (issue-less mint `{branch-suffix}-{slug}`) with `.bkit/core/.bkit/workflows.md:398,920` (`DEBUG_ATTEMPT` = all-runs index)
   - **Scenario:** the headline use, `/bkit-debug ci failures on dev` on `dev`, mints `dev-ci-failures` every time, including for unrelated incidents on different days. The month bucket is "the feature's existing bucket", so the FID's `status.jsonl` keeps collecting runs across months. `counters run` counts every earlier debug run of that FID. Once `MAX_DEBUG_ATTEMPT` unrelated incidents have used the same wording, every later run starts in SOAK mode (`counters route` exit 1) with no history of its own. The same FID also shares `debug-summary.md`, its `.bkit/issues.jsonl` roadmap rows and its log folder across unrelated incidents. § Best-effort runs documents only the opposite case (a reworded prompt restarts the counter).
   - **Fix:** this needs a mint-rule decision. When a _minted_ (not prompt-named) issue-less FID already has a log folder whose last run is not `IN_PROGRESS`, mint a distinct FID. Options: a disambiguator that isn't all digits, such as `dev-ci-failures-b`, or a letter-prefixed date word like `d1022`; `ISSUE_LESS_FID` accepts both. Keep naming the FID in the prompt as the only way to continue an earlier run. Document this in § Best-effort runs and add a mint test.
7. **MEDIUM** · `class: mechanical` · `.bkit/core/engine/commands/workflow/fids.ts:58-75` (`fidProblem`, non-empty `issue` branch) vs `.bkit/core/.bkit/workflows.md:152`
   - **Scenario:** the doc says that with `--issue` set, "the FID's embedded id must match it", and Gate 1 ticks "FID shape" on that basis. The code checks only that the issue id has the tracker's id shape and that the FID has the tracker's FID shape; it never compares the two. `fids check --fid=123-foo --issue=456` and `steps gate --fid=123-foo --issue=456` both exit 0. A real path: the prompt names `#456` while the session is on `feat/123-foo`, and Step 1 sub-step 4.2 takes the FID from the branch. The run then labels and comments on #456 and logs under `123-foo`. `prs open` writes `<!-- bkit:issue=#456 bkit:fid=123-foo -->`, whose two halves name different issues: `fromMarker` returns 456, `fromBranch` returns 123. `prMarker` (`prs.ts:175-185`) has the same gap.
   - **Fix:** in `fidProblem`, when `issue` is non-empty and `tracker` != `any`, require `issueIdOf(fid, tracker) === issue` (strip `#` first; compare linear / jira uppercased) and name both ids in the problem text. Add `fids.test.ts` / `steps.test.ts` / `prs.test.ts` rows for a mismatched pair.
8. **LOW** · `class: mechanical` · `.bkit/core/engine/commands/workflow/runs.ts:1283-1284` (`runDispatch --sha`) with `runs.ts:164`
   - **Scenario:** `--sha` accepts 7 to 40 hex digits, but the run lookup compares `r.headSha === target.head` exactly against GitHub's 40-character `headSha`. A short SHA, from a hand re-run or an agent abbreviating `{DEV_SHA}`, never matches. The poll times out, a needless re-trigger commit is pushed to `dev`, and the gate times out again → **Failure Path**.
   - **Fix:** resolve `--sha` to the full SHA (`git rev-parse --verify {sha}^{commit}` after `fetchLanded`), or require exactly 40 hex digits, and use the full SHA as `landed`.
9. **LOW** · `class: mechanical` · `.bkit/core/engine/commands/workflow/ledgers.ts:300-310` (`recordOnBranch`) with `.bkit/core/engine/commands/workflow/worktrees.ts:125-145` (`openSharedRecord`)
   - **Scenario:** `branches push` and the `runs dispatch` re-trigger aren't told the FID; they take the most recently written record on `dev`. `openSharedRecord` checks for a live record and then writes its own, with no lock around the two steps. Two debug sessions on the same clone (parallel bkit runs per clone are supported) that pass `worktrees setup` at the same moment both write records. Every `appendRecordCommit` refreshes the file's mtime, so run A's `branches push --mode=dev` can pick run B's record. It then pushes B's commits (or reports "nothing to push") and returns B's SHA as `{DEV_SHA}`.
   - **Fix:** pass `--fid` to `branches push` and `runs dispatch` and select the record with `activeRecord(cwd, fid)`. Create the record with an exclusive create (`fs.openSync(file, "wx")`, or a lock file in the same git dir), so the busy check and the write happen as one step.
10. **LOW** · `class: mechanical` · `.bkit/core/engine/commands/workflow/ledgers.ts:408-416` (`ownSet` ledger prefix hash) vs `ledgers.ts:327-334` (`hashOf`)
    - **Scenario:** the recorded hash comes from `git hash-object -- {rel}`, which applies the path's clean / eol filters. The prefix hash is `git hash-object --stdin` with no path, so it applies no filters. In a clone with `core.autocrlf=true`, or with a `.gitattributes` clean filter on `*.jsonl`, the two hashes never match for a ledger that was dirty before the run. Every append the run makes to that ledger is then refused with `EXIT_FOREIGN_PATH`, even though only the run added rows.
    - **Fix:** hash the prefix with `hash-object --stdin --path={rel}` (or use `--no-filters` on both sides), and add a unit row with an eol attribute.
11. **LOW** · `class: mechanical` · `.bkit/core/engine/commands/workflow/ledgers.ts:505-513` (`commitOwnSet`, temp-index branch, real-index resync)
    - **Scenario:** take a recorded ledger the user had _staged_ before the run, e.g. `docs/failures.jsonl` with their own rows `git add`-ed. It is in `stagedBefore`, so the post-commit `git reset` skips it. The real index keeps the user's blob (old HEAD plus the user's rows), which lacks the run's rows that the new HEAD holds. The user's next plain `git commit` silently deletes the run's committed ledger rows.
    - **Fix:** for a staged recorded ledger, rebuild the real index entry as the new HEAD blob plus the user's staged rows (the same row diff the commit uses), or refuse with `EXIT_FOREIGN_PATH` and name the staged ledger.
