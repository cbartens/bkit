# Design Brainstorm & Ideas

Lens: Optimal-tradeoff — best long-term shape ignoring legacy constraints.

Scope read: `.bkit/core/engine/checks/status-holes.ts`, `commands/lib.ts` (`runCommand`, `EXIT`, `statusLocation`), `commands/registry.ts`, `cli.ts` `main()`, `ledgers/status.ts` (`fold`, `appendLine`, `recordAction`), `commands/workflow/workflows.ts` (`start` / `fail` / `close`), `.bkit/jsonl.md`, `.bkit/workflows.md` § `status.jsonl`, `docs/decisions.jsonl` `384-tier3-promotion`, `docs/deferrals.jsonl` `442-status-hole-detector-beyond-ship`.

## Approach A — Single dispatch seam + one generalised contract deriver ⭐ Recommended

Journal every invocation at the one funnel all `bkit <noun> <verb>` calls already pass through (`runCommand` in `commands/lib.ts`), generalise `status-holes.ts` into one pure deriver + checker that reads any `bkit-{workflow}.md`, and keep every row in the run's own `status.jsonl` — the settled envelope, built with the three parts separable. `Complexity` `MEDIUM`.

- **Shape.** Three parts, each pure and independently testable. (1) _Journal seam_ — `runCommand` resolves the active run (Q12: explicit `--file`, else `--fid` + `--month`, else the single `IN_PROGRESS` run from the cwd's git toplevel, else skip) and appends one `engine-call` row (Q11) on entry; on a non-OK return it writes the `tool-failure` friction row (Q2 / Q5) excluding the routing exits. (2) _Contract deriver_ — one module generalising `deriveExpectedStepSetFromSource`: `## … Step N` headings + `step:"{workflow}-*"` literals give the step universe; every `"{BKIT}"` literal inside a step's section gives that step's required calls (noun, verb, flag names) (Q10). `SHIP_STEP_ORDER` and its four path sets become one _data_ entry in a per-workflow path model. (3) _Checker_ — pure `check(rows, contract, pathModel) → verdict`; `bkit completeness check --workflow= --file=` is a thin CommandSpec (Q13); `workflows close` appends the `completeness` row (Q6); `workflows start` / resume prints the warning (Q14).
- **Extensibility.** A new workflow (`audit`, `auto`) needs a markdown file plus one path-model entry — deriver and checker are workflow-agnostic. A new required command needs no code while it uses the `"{BKIT}"` literal. A new hole _class_ ("command ran but exited non-zero", "step DONE with no journaled call") is one field on the verdict. Five workflows ship behind one mechanism (Q3).
- **Risk.** The seam is the hot path of every invocation: a throw, a slow run resolve, or a wrong attribution there breaks unrelated commands. Mitigation is resolve-or-skip plus a fail-safe write, but that is exactly the code that must never be wrong, and it runs on `install`, `doctor`, `check` too. Second failure mode: the per-workflow path models rot — a workflow gains a branch and the model still expects the old set, so the check reports holes that are not there (the `442-status-hole-detector-beyond-ship` cost).
- **Maintenance.** Five path models must track five markdown files' routing (debug's NORMAL / SOAK ladder, build's verify / challenge loops, plan's SPLIT, design's SPIKE / MILESTONE). `status-holes.ts`'s canonical cross-check (`SHIP_STEP_ORDER`) either generalises to a per-workflow frozen key list or becomes ship-only drift. The routing-exit exclusion set is coarse: exit 3 alone spans eight unrelated commands' refusals (`branches`, `fids`, `issues`, `ledgers`, `prs`, `repo`, `runs`, `status`), so a genuine engine failure that exits 3 is never recorded.
- **Friction vs ideal.** No new artifact, no schema, no migration, no install-path machinery — it reuses `status.jsonl` and `.bkit/friction.jsonl` and satisfies Q4, Q6, Q8, Q10 unchanged. Ideal-shape friction: the journal bloats `status.jsonl` (build names 103 `"{BKIT}"` calls, so ~100 extra rows per run) in a file whose contract is "workflow state SoT; agents must not read / write", and `steps finish` commits it every step. The engine writing `friction` also needs `KIND_WRITERS` in `ledgers/telemetry.ts` plus its `.bkit/jsonl.md` row and `telemetry.test.ts` to gain the engine as a writer — a contract change, not an additive one. And "journaled" means _attempted_, not _succeeded_: a failed required command still counts as present unless the verdict adds a success axis.

## Approach B — Split the engine's run-observability stream out of `status.jsonl`

Give the engine its own append-only run-observability record — journal, unexpected exits, completeness verdict — and let the workflow's step state stay in `status.jsonl`, with `close` appending one pointer row. `Complexity` `HIGH`.

- **Shape.** A dedicated store (one file per run, or one per repo keyed by run) written by the seam and the exit handler, read by `completeness check` and by `bkit stats` / harvest. The checker becomes a reader of that stream plus the workflow contract, so it never folds a status log to find its evidence.
- **Extensibility.** Best of the three: a new observation kind is a new row type in one stream with one reader, touching neither the resume fold, the status-holes audit, nor the per-step commits. A repo-level stream lets engine friction aggregate across FIDs without folding every status log — the shape `bkit stats` wants and cannot get from per-FID logs.
- **Risk.** Two artifacts describing one run can disagree, and the run's own artifacts stop carrying the verdict (departs Q6) unless the pointer row lands. A hard-killed process leaves the stream behind but not the pointer, so a closed run can carry a pointer to nothing.
- **Maintenance.** One schema, one writer, one reader — but a new store to gitignore, land, prune and document: a `.bkit/jsonl.md` kind, a `.agents/docs.md` row, a `harvest` rule, and a decision on whether it rides the PR (losing `merge=union`'s landing story) or stays local (losing the verdict from the run's committed artifacts).
- **Friction vs ideal.** Departs Q6 (verdict in the run's `status.jsonl`) and Q8 (journal as `engine-call` rows in `status.jsonl`) — needs the human to re-confirm. The seam and checker from A are unchanged, so B is A plus a store, not a replacement for A's structure.

## Approach C — Compile each workflow into a drift-gated contract

Generate a machine-readable contract per workflow at `bkit install` / `upgrade`, fail `bkit check` when it is stale, and have the checker compare the journal against the contract instead of re-parsing prose per run. `Complexity` `HIGH`.

- **Shape.** One compile step turns `bkit-{workflow}.md` into a contract artifact (step universe, per-step required calls, path conditions) under `.bkit/`. `bkit check` gates its freshness exactly as it gates a rendered mirror, so the contract cannot silently describe a workflow that no longer exists. The runtime checker reads the contract; the per-workflow path model becomes declarative data a test can pin per workflow.
- **Extensibility.** Best for expectations: a new routing branch is a contract field, not a new code path; the per-workflow fail-open → gate promotion policy of deferral `442` attaches to a contract version; the frozen ship key list stops being hand-held and becomes a contract assertion. Adding a workflow is one markdown file plus a regenerated contract.
- **Risk.** A generated artifact is a third thing that can be wrong, and the failure mode is worse than no check: a stale contract reports false holes on a run that was complete. The drift gate must be airtight in both directions — a consumer editing their own `.bkit/core/workflows/*.md` without re-running install must trip `bkit check`, or the contract lies. Compilation must also express the path conditions the prose expresses in `Route:` / `Failure Path` arms.
- **Maintenance.** A build step in the install / upgrade path, a drift gate, a new artifact family (install manifest, drift check, `.agents/docs.md` row), and every workflow edit becomes a two-file change caught only by CI. Build steps are never added unasked (`.agents/rules.md` § Migrations spirit), so this needs explicit owner buy-in.
- **Friction vs ideal.** Moves derivation from runtime to build time — a flagged departure from Q4's "deriving expectations from the workflow markdown at runtime", though it stays clear of Q10's "no new prose marker" (the contract is generated, never authored). Shares A's seam, checker and wiring, so it is A plus a compile step and a gate.

| Lead with A — one dispatch seam, one generalised deriver, one checker, rows in `status.jsonl` | B's separate observability store; C's compiled contract | A satisfies every settled grill answer (Q4, Q6, Q8, Q10) with no new artifact, no schema, no migration and no install-path machinery; Q3 and the "no new parallel detector where `status-holes.ts` can be generalised" constraint both point at one mechanism |
| Build A's three parts as separable pure modules (deriver takes markdown text, checker takes rows + contract, seam behind one resolve-or-skip interface) | one monolithic `completeness.ts` | Keeps B and C landable later without rewriting the checker — the deriver's purity is what lets C swap runtime parsing for a compiled contract, and the seam's single interface is what lets B swap the store |
| Write the `engine-call` row at dispatch entry | write it on exit with the exit code | A hard-killed command still leaves attempt evidence; the exit path is the separate friction write, so the two rows carry attempt and outcome respectively |
| Record engine friction through the existing ledger idiom | direct `fs.appendFileSync` to `.bkit/friction.jsonl` | One write path and one validation surface; costs a contract change — the engine must join `KIND_WRITERS` in `ledgers/telemetry.ts`, its `.bkit/jsonl.md` § Ledgers & Writers row and `telemetry.test.ts` |
| Verdict as a new `completeness` row type in the run's `status.jsonl` | verdict in a new stream (B) | Settled (Q6); `fold` already ignores row types it does not know, so the row is additive and safe, and it rides the close commit into the run's own artifacts |
| Exclude routing exits by code only (`3`, `8`, `9`, `80`, `81`) | exclude by (code, command) pair, or by whether the step's prose has a `Route:` for that code | Settled (Q5). Flagged: exit 3 is eight commands' refusal code, so an unexpected exit-3 failure is invisible; a per-command exclusion would need the workflow step in scope at the seam |
| Report every hole on every run, no watermark or baseline | the pinned-watermark delta in decision `384-tier3-promotion` | Settled (Q15). Flagged departure: 384 chose a watermark precisely because a full report on a 25-65% holey corpus is the noise that gets a gate muted; a full report per run is that noise unless the report is read-only, which Q1 keeps it |
| Keep the detector advisory / fail-open and record promotion criteria against `384-tier3-promotion` | flip to a blocking gate in this cycle | Settled (constraint + deferral `384-promote-status-hole-detector-from-advisory-to-gate`); the check must never change an exit code, block, or fail a workflow (draft acceptance criteria 4) |
