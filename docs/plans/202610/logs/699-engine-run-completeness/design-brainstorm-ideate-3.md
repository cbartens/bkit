# Design Brainstorm & Ideas

Lens: Risk premortem — failure modes, scale, time, handover.

Settled context all approaches honor (grill Q1-Q17): an always-on journal of `engine-call` rows `{type, workflow, at, noun, verb, flags:[names only]}`; a new `bkit completeness check` verb; `workflows close` records a `completeness` row in the run's `status.jsonl`; `workflows start` / resume prints a warning when the previous run was holey, never an interruption; unexpected non-zero exits append one `friction` row (`category: "tool-failure"`), deduped by key; everything advisory, fail-open, swallowed on error. Approaches differ in where the journal lives, where expectations come from, and which readers break.

## Approach A — Chokepoint journal in the run's own log, runtime structural derivation ⭐ Recommended

One journal hook inside `runCommand` (`.bkit/core/engine/commands/lib.ts`, the single dispatch point every `bkit <noun> <verb>` flows through) appends the `engine-call` row to the attributed run's `status.jsonl` after the command returns; the same hook records the `friction` row on an unexpected exit; the check generalises `checks/status-holes.ts` to all five workflows, deriving steps from `## Step N` headings and required calls from `"{BKIT}"` literals per step section, parsing the workflow markdown at check time.

**Premortem — 10x scale.** What breaks: a full build run invokes 200-400 commands, so `status.jsonl` grows 5-10x per run; every `readStatusEvents` (start, `steps finish`, counters, close, resume) parses every line, so hot-path cost grows linearly with run length — measurable, not fatal. The real blast radius is the hook itself: it sits on the shared dispatch path of every command in every consumer repo, so a journal bug that escapes the swallow is a total CLI outage, not a workflow-only one. Expectation derivation re-parses a few KB of markdown per check — never the bottleneck. Observability: swallowed journal writes are invisible by design; a run whose journal silently broke reads later as a run full of holes, so the detector cries wolf exactly when it is itself hurt — needs a one-line stderr log per swallow and a heartbeat invariant (a run under a journaling engine with zero `engine-call` rows = journal broken, not run holey). Recovery: verdicts are recomputable any time via the standalone verb; lost journal rows are unrecoverable evidence, so the verdict must name the gap, not report holes.

**Premortem — 6 months later.** What breaks: workflow prose edits silently redefine expectations — a step renamed or a `"{BKIT}"` literal moved between sections changes what old runs "should have done", and the stored `completeness` row (computed against close-time prose) disagrees with any re-run of the check (undocumented invariant: a verdict is only meaningful against the markdown at close time). The friction exclusion set (Q5's literal 3, 8, 9, 80, 81) is a magic-number list that drifts the day a command adds a routing exit — false `tool-failure` rows until someone edits the set. New readers of `status.jsonl` written later must know to skip `engine-call` / `completeness` rows (tribal invariant). Observability: prose-vs-verdict drift is invisible unless the check re-runs; fixture tests pinning one run per workflow per path are the tripwire. Recovery: expectations derive from a tracked file, so a verdict is reproducible against the run's own commit (`git show {parentSha}:.bkit/core/workflows/bkit-{workflow}.md`) — document this as the replay procedure.

**Premortem — on-call at 3am.** Page shape: nothing pages (advisory, exit 0 always); the 3am event is a maintainer facing a "previous run was holey" warning on resume, needing to classify each hole as real / conditional-arm-not-taken / journal-gap in under a minute. Diagnosability: only possible if the `completeness` row carries per-hole evidence (step, the missing literals, journal row count, evidence class), never a bare boolean. Recovery path: re-run `bkit completeness check --workflow= --file=` by hand, read the named holes, proceed either way — never blocked. The friction handler's own 3am trap: a crash-looping command appends one deduped row per key (bounded), but if the dedup read-fold-append itself throws, the handler must not mask the original exit code — nested try/finally is the load-bearing detail.

**Premortem — author leaves.** Knowledge concentration: the path-classification knowledge (which steps a MERGED-on-entry run skips, retry-loop steps never mandatory, group loops run once per group, aborted runs expect only the pre-abort prefix) lives today in `status-holes.ts` comments cross-referencing `bkit-ship.md` sub-steps; generalising moves it into prose-structure conventions (`Route:` arms, `Failure Path` blocks, `Group Loop` headings) that only the detector author fully understands — a brittle parser-to-prose-style coupling. Bus factor mitigation: those conventions must become written authoring rules (`.bkit/authoring.md` § Workflows Only) so prose edits stay parseable, and the detector corpus must hold one fixture per workflow per path so a prose-style break fails a test, not a run.

**Risk-mitigation guidance (fold into whichever approach is picked).** (1) Add `engine-call` and `completeness` to `MARK_ROWS` in `run-facts.ts` and audit every `status.jsonl` reader (`stepsBlock` timing, `ciList`, harvest `run` scan's `afterEnd` / `lastActivity` / byRun window) — an `engine-call` row between two `step-done` rows otherwise chops step minutes and shifts run-attribution windows. (2) Derive the friction exclusion set from each verb's declared `exitCodes` spec plus the shared exit table instead of a static list — self-maintaining as commands add codes. (3) Wrap unexpected (non-`CommandError`) throws in the same chokepoint — today they escape `runCommand` to `main().catch` and would never produce friction rows. (4) Gate command-completeness on evidence availability: a run with zero `engine-call` rows predates journaling → steps-only verdict, named as such, so the first resume after upgrade does not flag every historical run holey. (5) Ordering: `workflows close` journals its own calls before computing the verdict, and the check self-excludes the `completeness` verb from expectations. (6) One stderr line per swallowed write; never silent.

## Approach B — Sidecar journal file: `engine-calls.jsonl` beside `status.jsonl`

Same chokepoint hook and same runtime derivation as A, but the journal lives in a sibling per-run file in the run's log folder; only the small `completeness` verdict row lands in `status.jsonl`.

**Premortem — 10x scale.** What breaks: two files per run instead of one — the carry / land / hand-back machinery already globs `*.jsonl` in the log folder (`carryOwnBook`), so mechanics exist, but the append and union-merge surface doubles and every lifecycle verb must know the sidecar exists. Blast radius shrinks where it matters: status-log readers never see journal rows, so step timing, harvest windows, and fold semantics are structurally immune to journal volume; the hook can only corrupt the sidecar. The chokepoint-outage risk is identical to A. Observability: sidecar absence per run is an unambiguous journal-broken signal (A needs a heuristic); the check reads two files, both small. Recovery: sidecar loss (worktree removed pre-close, raced flush) costs only command evidence — the check must define a degraded steps-only verdict explicitly rather than flagging every command as missing.

**Premortem — 6 months later.** What breaks: a new artifact kind joins the lifecycle matrix — future prune / archive / migrate work must discover it; if the artifact indexes (`.bkit/jsonl.md`, `.agents/docs.md`, workflow telemetry docs) do not name it at birth it becomes invisible tribal state. Two union-merged files per run doubles the line-interleaving assumptions the check's `at`-ordering relies on. Observability: schema drift between sidecar and check surfaces as parse skips — the check must count and report skipped lines, not silently tolerate them. Recovery: sidecar is regenerable for the command dimension only from prose + step rows (partial); treat it as expendable evidence and say so in its doc row.

**Premortem — on-call at 3am.** Same warning surface as A, slightly better ergonomics: two small files to eyeball instead of one interleaved log, and "sidecar missing, status intact" has exactly one cause class (carry / disk), easier to reason about than interleaved-row anomalies. Diagnosability of the verdict row is identical to A (evidence-carrying or useless). Recovery: recompute degraded verdict from `status.jsonl` alone.

**Premortem — author leaves.** The sidecar schema is trivial, so less parser knowledge concentrates than in A's in-log typing (where every future reader must know to skip the new types). The risk is the reverse: the next maintainer sees a redundant-looking second file and folds it back into `status.jsonl`, reintroducing the reader-drift bug A must fix by hand. Mitigation: the "why a second file" rationale must land in `docs/decisions.jsonl` and the file's own doc row at birth.

**Risk-mitigation guidance.** (1) Register the sidecar in `.agents/docs.md` and `.bkit/jsonl.md` in the same change that creates it — an unindexed artifact is a future orphan. (2) Reuse the exact `engine-action`-row helpers pattern (`appendLine`, parse-skip-malformed) so the read path carries no new conventions. (3) Define the degraded verdict (sidecar absent) as a first-class output of the check, tested with a fixture. (4) Keep the attribution rule identical to A (`--file` maps to its sibling sidecar; toplevel discovery otherwise) so switching between A and B later is a storage diff, not a contract diff. (5) Fold mitigations 2, 3, 4, 6 from Approach A in unchanged — they are approach-independent.

## Approach C — Frozen expectations manifest at install time

Same journal and hook as A, but expectations are derived once per workflow at `bkit install` / `bkit upgrade` into a generated, hash-stamped manifest (like `dist/` with its `bkit:check:dist` drift gate); the check reads the manifest and never parses markdown at run time.

**Premortem — 10x scale.** What breaks: nothing at runtime — the check reads a small JSON; CI gains a generation + drift-gate step. The blast radius moves to the worst possible place: the generator runs inside `bkit install` / `bkit upgrade` for every consumer, so a generator bug ships broken expectations to every consumer at once (provider-parity surface), where A/B's failures stay advisory and local to one run's verdict. A bad manifest flags every run of every consumer holey; harvested telemetry shows a friction spike with no real cause. Observability: prose-vs-manifest skew is a CI failure before merge (loud, earlier than A/B's silent drift). Recovery: regenerate via re-render — the well-trodden install path.

**Premortem — 6 months later.** What breaks: the manifest is a second artifact of the prose — the "no hand-maintained table" constraint survives only if generation is fully automatic and drift-gated with no manual escape hatch (a hand-edit path recreates the Finding-7 parallel-table failure that decision `384-tier3-promotion` rejected). Mid-run prose edits (routine in bkit's own dogfooding) make the manifest reflect start-of-run prose while A reflects close-time prose — arguably more correct, but a documented semantic difference either way. Observability: the verdict must carry the manifest's source hash so a disagreement is diffable, not mystical. Recovery: idempotent regeneration.

**Premortem — on-call at 3am.** Best diagnosability of the three: the verdict reproduces offline from a pinned artifact, and "the check expects a call the workflow no longer names" resolves by diffing the manifest hash against the prose. Recovery: regenerate the manifest or hand-check against prose; never blocked.

**Premortem — author leaves.** The generator concentrates the same prose-convention knowledge as A's parser, plus build-pipeline knowledge (where generation hooks into install / upgrade, how the drift hash is computed) — two subsystems to understand before touching either. Mitigation: the generator and the runtime parser must be one module with two entry points (parse vs parse-and-freeze), so C is A plus a freeze step and the knowledge transfers.

**Risk-mitigation guidance.** (1) One parser module, two entry points — never a second derivation implementation. (2) Drift gate in the same lane as `bkit check`, failing on prose-newer-than-manifest. (3) Manifest rows carry the source workflow's content hash; the verdict prints it. (4) Record the departure explicitly: decision `384-tier3-promotion` mandates runtime derivation with no table; a generated gated manifest is not hand-maintained but is not runtime-derived — this approach needs an owner-confirmed decision amendment before design, which is why it is not the recommendation despite the best 3am ergonomics.

## Cross-Approach Risks

- **Always-holey verdict noise (settled Q10 + Q15, flagged for the design's open questions).** Conditional, fallback and retry calls count as required and every hole is reported every run, so a clean run's verdict lists each conditional arm it did not take (ship: 85 `"{BKIT}"` literals, build: 102, debug: 82), and the resume warning fires on nearly every run. A warning that always fires gets ignored within a release — the signal dies of fatigue, not of bugs. Mitigation to put to the owner: keep the full hole list in the `completeness` row (Q15 honored) but split holes into evidence-holes (a step recorded `DONE` without its required journal evidence — success criterion 1's wording) versus unexercised-conditional calls, and key the start warning on the first class only.
- **New row types ripple through `status.jsonl` readers.** `runStatusRows` filters by the `workflow` field, so `engine-call` rows enter it: `stepsBlock` computes step minutes from the previous row and would chop every step's timing; the harvest `run` scan's `afterEnd`, `lastActivity` and chat-attribution windows shift on post-close journal rows. Reader fixes are one-time and test-pinnable, but any missed reader is silent telemetry corruption that outlives the feature.
- **Writer-contract change.** The engine as a friction writer touches `KIND_WRITERS` (`telemetry.ts`), the writers table in `.bkit/jsonl.md`, and `telemetry.test.ts`; `by.step` for an engine-written row needs a sanctioned value (the engine is not a workflow step). The contract-change rule applies: grep across workflows / prompts / templates and trace resume and remediation paths before editing.
- **Journal self-reference and ordering.** The check is itself a bkit command run while a run is active, so it journals itself; older consumer prose never names `completeness check`, so internal invocations read as unexpected calls. Define: close journals its own calls before computing the verdict, and the check verb self-excludes from expectations.
- **Swallow must be total.** The fail-safe guarantee (journal and check never change an exit code, never block) needs nested try/finally around every telemetry write plus a test that forces a journal throw and asserts exit-code passthrough — a partial swallow on the shared dispatch path is a CLI-wide outage, the worst blast radius available to this feature.
- **Attribution discovery cost and correctness.** Toplevel discovery of "the single `IN_PROGRESS` run" by scanning `docs/plans/*/logs/*/status.jsonl` grows with repo history; lock files (`workflowLockPath`) already name active runs and are the cheaper discovery path — decide in design, never misattribute (Q12).
- **Warning referent ambiguity.** "Previous run" is unpinned for the resume case (the resumed run is the current run; its verdict is not yet written): recommend the immediately preceding closed / failed / abandoned run of the same workflow in the same `status.jsonl` — resolve in the design's open questions.
