# Design Review

Lens: Operability — failure modes, observability, on-call ergonomics.

## Failure-Mode Enumeration

Subject is maintainer-run tooling (repo-side runner + throwaway repos + bkit-in-a-consumer-repo), not a hosted service. "On-call" = the maintainer running the demo/benchmark; the applicable detection surface is CLI stdout/stderr (`[bkit-*]` prefixes), GitHub Checks, and `[bkit-runs]` gate exit codes — not a paging stack (`docs/observability.md` § Scope: no telemetry pipeline).

| #   | Component / flow    | What fails                                                                                                     | How detected                                                                                                                  | Blast radius                                                        |
| --- | ------------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 1   | Setup runner        | `gh` missing / `gh auth` unauthenticated / Node < 20 / pnpm unresolvable                                       | Preflight stops loudly, before any write                                                                                      | One maintainer; no side effects                                     |
| 2   | Setup runner        | `gh repo create`, fixture copy, `pnpm install`, or `bkit install` fails mid-sequence **after** the repo exists | Runner exit code + stderr; partial state = orphan / half-seeded private repo                                                  | One orphan private repo; re-run idempotency and cleanup unspecified |

## Operational Dependencies

New maintainer-side surfaces this design introduces (no dashboards, alerts, pages, or metrics — consistent with the project's CLI/GitHub-only observability scope):

| New surface                                        | Type                  | Burden                                                                                                                                                                              |
| -------------------------------------------------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scripts/example/new-run.mjs`                      | Repo-side runner      | New tooling to maintain; supplies measurement _inputs_ only; owns setup, never gates                                                                                                |
| Source-side smoke job in bkit's own CI (if Q3 = A) | CI job on bkit's repo | Adds a run to bkit's own CI; edits `.github/workflows/*` require explicit human confirmation (`.agents/rules.md` § CI edits)                                                        |
| `examples/README.md` contract table                | De facto runbook      | Must carry gate stubs, capstone name, tracker flag, plain-script rule, trap inventory, harvest/median procedure; must stay **outside** the copied fixture (else it leaks the traps) |

| Per-release canary + `data.js` owner-check         | Manual release step   | Owns version-pin bump and content-staleness detection                                                                                                                               |

## Verdict Reasoning

`CONCERNS`. The design is operable within its chosen stack: the destructive/blocking paths that already have infrastructure behind them — CI red, ship-gate refusals (codes 10-17), capstone states — carry strong, self-explanatory observability (named exit codes, `required head:` block, run URL). Pass/fail is robustly separated from measurement, and no server-side dependency is introduced, so nothing here is un-operable in the current monitoring model.

It is not a `PASS` because three severe failure modes have **no observability at the point of failure**, and each is guarded only by a convention, an optional/default-off job, or prose:

- Gate-chain growth is silent at use; the sole guard is a source-side smoke job that is an open question whose **default is off**.
- The dual-load contract can break the demo off-disk while `node --test` stays green; the guard is prose in three places, with no signal.
- Evidence loss on teardown is an **unrecoverable** path guarded by a documented procedure rather than an assertion.

None of these makes the design un-operable — all three are addressable with bounded effort — so `FAIL` is not warranted. The remaining gaps (tracker read-back, runner transition logs, quota surfacing, sweep scoping) are improvements rather than blockers.

## CRITICAL

1. **Gate-chain growth has no observability at the failure point.** A bkit release that adds or renames a script in the seeded `bkit:gate:*` chain breaks every run on the affected version, silently at use (`gate-missing-called-scripts` fires only on _missing_ names). The design names this risk but the only guard — the source-side smoke job — is open question Q3, whose `Default if unanswered` is **B (no source-side guard)**. Resolution: either escalate Q3's default to A, or add a detection the runner performs at setup (e.g. read the seeded chain and assert every called script exists after `bkit install`), so the failure is loud where it happens rather than deferred to a user report.
2. **The dual-load contract is silent when it breaks.** Adding `"type": "module"` to the fixture `package.json` (or a `type="module"` script tag) blanks the off-disk page while `node --test` stays green — the deliverable is broken and CI is green. The design guards this only with prose (feature request, fixture, README). Resolution: add one deterministic check to the smoke job — a static assertion over `index.html`/`package.json` for the classic-script form — so the break reds at the source.
3. **Evidence loss on teardown is an unrecoverable path held by convention.** Deleting a failed/red throwaway repo before harvest destroys the only diagnosis surface, and the design admits a run may mistime. The mitigation ("harvest before any teardown") is a documented procedure with no assertion. Resolution: encode it structurally — have the runner refuse teardown (or require an explicit `--discard-unharvested`) while unharvested ledger rows remain in a repo — so the guard is a boundary, matching the design's own stated preference for structural over remembered seams.

## OPTIONAL

- **Runner observability (failure modes 1-2).** Specify the runner's `[Context]` log prefix per convention (a new bkit-side module needs its own noun/prefix) plus key transition lines — repo-created, fixture-copied, install-done, start-command-printed — so a mid-sequence stall is attributable to a step, not just an exit code. Naming the orphan repo in the failure output makes cleanup mechanical.
- **Tracker read-back assertion (failure mode 3).** The design calls tracker-`none` the highest-severity silent failure and mitigates it with the flag plus the `package.json` `bkit.issueTracker` value, but never verifies the value took. Add a post-install read-back that fails loudly when the written config is not `github`.
- **Retention sweep safety (failure mode 14).** Pin the throwaway repo-name prefix the runner creates to the documented sweep pattern (`bkit-example-run-*`) so the sweep can't miss repos, and scope the delete to the authenticated owner with a dry-run/confirm, since it is a destructive bulk delete.
- **Actions-minutes surfacing (failure mode 13).** README prose is the only cost signal; a pre-sweep read of remaining quota (or a printed per-run estimate × N) would turn a mid-sweep stall into a decision made up front.
- **Smoke-job noise tuning (if Q3 = A).** Keep the smoke job deterministic and free of pinned third-party downloads (as designed), and consider the design's own option C (non-blocking report job first) so a transient registry flake on `pnpm install` cannot false-red bkit's own CI.
- **`data.js` owner-check (failure mode 11).** Adopt Q7's recommended A (the per-release canary owner checks the phase list); the default C leaves content drift undetected, and `data.js` slowly lying is exactly the kind of silent regression this lens exists to catch.
- **`[skip ci]` runbook line (failure mode 6).** The code-10 refusal is legible, but the recovery (remove the inherited suppression token, re-push without it) belongs in the `examples/README.md` contract table next to the KN-11 reference.

## OUT OF SCOPE

- **Cost/token observability.** No source exists (`.bkit/stats.jsonl` carries no usage rows); deferring per Q1 is correct — measuring-only, never gating, is the right design, and building a source is a substrate problem, not an operability gap.
- **Metrics / traces / dashboards / alerts.** The project operates with no telemetry pipeline (`docs/observability.md` § Scope); applying service-grade metric/trace expectations here would be out-of-stack.
- **AI non-determinism of trap-catching.** Measured, never gated (per #232's flaky-grader rule); it is not an alert, and the demo must not promise a catch — correctly designed.
- **Human hard stops.** Inherent to the pipeline; they bound automation but are not an operability defect.
- **`bkit install`/`doctor` tracker-`none` advisory (Q6).** A bkit-side behaviour change, deferred to `docs/deferrals.jsonl`; not part of this example.
- **The nine later ideas from #504.** Deferred by the design; out of this cycle.
