## #505 — Root README sells bkit for the public launch (closed)

## Why

The repo is going public, and the root `README.md` is the first thing a visitor sees. It was 588 lines, mostly install and auth reference. The first thing after the pitch was a large warning about a GitHub token. It told an engineer how bkit is built, but never told anyone what they get.

## What changed

**`README.md` is now a 164-line pitch**, written for people who use AI agents but aren't engineers, with engineering detail in a collapsed section. Top to bottom:

1. Banner: "From vibe coding to production code." / "A senior engineering team's process. Run by AI agents. Signed off by you."
2. The problem and the promise, in two short paragraphs.
3. "What's in the box" image: 16 tiles in four groups.
4. "A ready-made workflow for every job": one row per command, plus audits and housekeeping.
5. Pipeline diagram: five steps, agents shown as dots, the three sign-off points, the debug loop, and the four tools (Claude Code, Cursor, Codex, opencode).
6. Benefits in four groups:
   - **You stay in control:** sign-off points, guardrails.
   - **The quality is real:** independent review, self-fixing builds, honest CI.
   - **It fits how you work:** switching tools when limits run out, laptop to cloud, parallel features, issue tracker as the control panel, skills per feature.
   - **Engineering know-how, built in:** best model per job, docs that keep themselves current, project memory ledgers, work stats, audits.
7. Templates ready to adopt: CI, quality checks, cloud agents, dependency updates, secrets sync, Serena, graphify.

## How we got here: the README discussion

This records the conversation that led to the rewrite above: the questions asked, the answers, and the ideas that did and didn't make it in. The issue body says what changed. This comment says why.

### 1. What a repo front page should do

The old README told an engineer how bkit is built but never said what anyone gets. A front page that sells usually goes in this order:

1. Banner: name, a one-line promise, 3–4 badges.
2. The problem, in two sentences.
3. One picture of how it works.
4. 5–7 benefits, each saying what you get rather than how it's built.
5. Quick start in 3–4 commands.
6. Links to reference docs, then the license.

Images are SVGs with a light and a dark version, swapped by a `<picture>` tag so they match the visitor's GitHub theme. A screen recording of a real run would convince people more than any diagram, but it needs a real run, so it's still an open item.

**Decision:** move the reference material out to `.bkit/install.md` and keep the README as the pitch. Done in 56282734.

### 2. The benefits, strongest first

1. **Independent review.** Several reviewers work on each step at once, each with a different job (one hunts bugs, one hunts security holes), and they can't read each other's notes.
2. **You stay in charge.** The pipeline stops for your sign-off after design, after plan, and before merge. It never merges by itself.
3. **A green CI run means the tests really ran.** A final check fails the build if any planned test lane was skipped.
4. **A crash costs nothing.** Progress is saved in files in the repo (`status.jsonl`, `docs/plans/`), not in a chat, so a run picks up where it stopped.
5. **Not locked to one tool** (see section 4).
6. **Skills come and go with the feature.** At build time, `@bkit-build-install-skills` spots technologies the feature needs that no installed skill covers and installs one skill per gap with `npx skills add`, up to 10 (`.bkit/prompts/bkit-build-install-skills.md`). At ship time, any skill not listed in `.agents/skills.md` is removed (`.bkit/workflows/bkit-ship.md:818`). The old README didn't mention this at all.
7. **The issue tracker stays the source of truth.** bkit reads the issue, posts progress, moves its status and links the PR, on GitHub Issues or Linear. The old first line said only "Linear-integrated".
8. **Optional hands-off mode.** When CI finishes, a cloud agent ships if it passed or debugs if it failed, with no laptop open.
9. **34 audit templates** whose findings feed straight into `/bkit-plan`.

**Correction made after the discussion.** During the conversation I said every reviewer pair on Claude runs on two different models. That's wrong. Only the design brainstorm, design review and plan scope-check groups mix Opus and Sonnet. Plan review and the build bug/security pair are all Opus, on purpose. The README says "several review groups mix models", and `.bkit/comparison.md` names the groups.

### 3. "Google agentic engineering": matched or exceeded?

Half right, and the wording matters.

- **It isn't Google's.** The benchmark is Antonio Gulli's book _Agentic Design Patterns_. Gulli works at Google, but it's his book, not a Google framework. Writing "Google's agentic engineering" in a public README would be inaccurate, and Google could object to its name being used that way.
- **What we can honestly claim** (`.bkit/comparison.md:290`): of the book's 22 patterns, bkit fully implements 12, partly implements 8 (deliberately limited to shipping code), and leaves out 2 on purpose. It goes beyond the book in 7 specific ways (`.bkit/comparison.md:318`).
- **"Exceeds" would be an overclaim.** It isn't a superset of the book.
- **The assessment is our own**, not an outside reviewer's.

**Decision:** use the "12 of 22, beyond the book in 7 places" wording, credited to Gulli by name. It's in the README's "For engineers" section.

### 4. Switching tools when a weekly limit runs out

Yes, and it's one of the best things to sell. bkit installs into four tools at once, and each feature's progress lives in the repo, not in one tool's chat, so you can start a feature in one tool and finish it in another.

| Tool        | Paid through                                                             |
| ----------- | ------------------------------------------------------------------------ |
| Claude Code | Claude subscription                                                      |
| Cursor      | Cursor subscription                                                      |
| Codex       | ChatGPT subscription                                                     |
| opencode    | OpenRouter, opencode Zen/Go, or Ollama (free models on your own machine) |

The old README never mentioned Codex, although it's a supported host (`bkit install --codex`, `.bkit/providers.md:24`). Someone paying for two or three subscriptions gets the full use of all of them.

**Caveat, for the reference docs rather than the pitch:** on Codex, a command that would normally pause to ask permission runs anyway, with only a warning (`.bkit/providers.md:51`). Flat-out banned commands are still blocked, and bkit's own workflows never use the ask-first commands.

### 5. What a non-engineer using AI agents would value

These are outcomes someone can judge without reading code:

- **You approve plain documents, not code.** A design, then a step-by-step plan. You're reviewing decisions, which you can judge.
- **A review team you wouldn't know to hire.** Separate agents look for bugs and security holes and argue for alternative designs.
- **It can't ship without your OK.** Force-pushing and deleting history are blocked.
- **It fixes its own failed builds.** `/bkit-debug` reads the logs, finds the cause and retries.
- **It learns from its mistakes.** Fixes and their causes go into `docs/knowledge.jsonl`, which the debugger reads first.
- **The right expertise per feature, cleaned up afterwards** (skills, section 2).
- **Progress shows up where you already look**, on the GitHub or Linear issue.
- **It can work while you sleep** (cloud mode).
- **Its docs keep up with its code.** Shipping also updates the project docs.
- **Expert checkups on demand** (the 34 audits).
- **Setup by pasting one message into your AI.**

To be honest with this audience: they still need a GitHub repo, Node and pnpm. The README's quick start and FAQ say so.

**Decision:** write the headline benefits as outcomes for this reader, and put the engineering depth (separate worktrees, resuming from saved state, the pattern mapping) in a collapsed "For engineers" section.

### 6. Problems found in the old README

- **It contradicted itself on parallel features.** One bullet said you can design one feature while building another; another said "one feature in flight, enforced". The answer: features run in parallel, each in its own worktree. Fixed (see the issue body).
- **No `LICENSE` file**, although `package.json` says MIT. Still open, in the checklist above.
- **Installing needs a GitHub token**, because bkit is on GitHub Packages. Publishing to the public npm registry would cut the quick start to `pnpm add -D` plus `bkit install`. Still open, in the checklist.
- **No proof it works on itself.** bkit is built through its own pipeline, so linking one real design → plan → PR chain would be strong evidence. Still open: nothing under `docs/plans/` is tracked yet.
- **GitHub repo description, topics and social preview image are empty.** Still open, in the checklist.

### 7. Ideas raised but not yet tracked anywhere

- **Expected time and cost per feature.** Not written down anywhere. If `.bkit/stats.jsonl` has real numbers, one line like "a typical feature takes about N minutes" would help. The README's FAQ covers cost only in general terms ("uses more of your quota than a single chat").
- **A plain "who it's not for" note.** Engineers trust tools that admit their trade-offs. The FAQ covers the requirements and the quota cost, but there's no explicit "this is heavier than a single prompt; skip it for one-off scripts" line.

### 4. Features that are undersold or missing from the front page

4. **Hard bugs get their own mode.** For failures it can't pin down, or that only show up when the code runs, soak mode adds instrumentation, gathers evidence, makes the smallest fix the evidence supports, then removes the instrumentation. The README only says "finds the cause".
5. **Every agent's output is checked by code, not just by another agent.** `steps finish` refuses a step whose verdict or artifacts are malformed, the verifier ticks a task only when it can see the result, and deferred-sweep fails the merge on a silent TODO or a skipped test. 8. **Big features get split up.** The complexity check and split break an oversized plan into a sequence of sub-plans that can each be built. The plan is also re-checked against the current code right before the build (plan-current).
9. **Agents look before they edit.** The GateGuard hook makes an agent investigate before changing code, on all four tools. Not mentioned anywhere outside the reference docs.
10. **Context fetch, with names.** 13 ready-made templates: GitHub, Sentry, Vercel, Supabase, Stripe, Expo, Playwright, Maestro, Inngest, Resend, Cloud Run, Tavily and Serena. Listing the names is far more convincing than "and more". A row of logos or a single line would work.
11. **It tells you what to work on next.** `bkit-utility-update-roadmap` ranks the next best items from the board and the ledgers. Non-engineers would value this, but the README hides it under "housekeeping".
12. **It improves itself.** `friction.jsonl` records rework and pauses for confirmation and feeds human-reviewed prompt improvements. The README talks about lessons from fixes but not about the process improving.
13. **Setup that checks itself.** `bkit check` and the advisories say exactly what's misconfigured or out of date after install or upgrade.
