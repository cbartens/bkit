# Design Brainstorm & Ideas

Lens: Pragmatic — existing code, minimal new infra, ship fastest.

Scope read: this is a **scoped revision**, not a fresh design. The fixture/app/traps/capstone-CI and the pass/fail-vs-measurement split are settled and unchanged. The only open ground is the **new run model**: one persistent public repo, per-run folder reset, where results live and how they are read, the privacy check, and bootstrap. All approaches below respect the binding decisions (`design-input-2.md` § Session Prompt A/ALSO SETTLED). No greenfield; every approach reuses the existing runner pattern, `bkit install`, and `.bkit/stats.jsonl`.

Grounded facts (verified in-repo, not assumed):

- `.bkit/stats.jsonl` is written by `bkit workflows close` in **any** consumer repo, every row carries `bkitVersion`, and the file is `merge=union` (`.bkit/workflows.md:136,729`). So accumulation across runs on `dev` is free.
- `outcome` is **one row per workflow run**, not per end-to-end run (`.bkit/jsonl.md:37`). A design→plan→build→ship run = 4 `outcome` rows, correlated by `parentSha`; `repo` is constant across runs. "Group by version" needs `parentSha` to separate runs within a version.
- Correcting the input's placeholder example: `.bkit/stats.jsonl` `outcome` rows already carry `durationSeconds`, `taskCount`, `deferrals`, `failures` (`design-input-2.md` § Issue cites only `compliance`/`counter`/`outcome` — the fields are there; the gap is that `durationSeconds` is per-workflow, not per-run).

## Approach A — Folder-scoped reset on the run branch; results accumulate beside it ⭐ Recommended

Public repo root is a bootstrap-once, bkit-installed consumer (`package.json`, `.github/workflows/bkit-ci.yml`, ledger scaffolding); the app lives in one constant subfolder (`example/`). Each run: runner fetches latest, cuts `feat/{FID}` off `dev`, **resets only `example/`** to the fixture (delete tracked files + re-copy from bkit's `examples/bkit-explainer/`) as one commit, then the pipeline builds in `example/`; the PR squash-merges into `dev`. `main` keeps the canonical fixture (the reproducible start). `.bkit/stats.jsonl` / `status.jsonl` live at root, **outside the reset surface**, and grow via `merge=union`. Benchmark = read `dev:.bkit/stats.jsonl` raw, group by `bkitVersion` (+ `parentSha` per run); no report code. Bootstrap = `--bootstrap` mode of the same runner. Privacy = runner diff scan for secret/PII shapes before any push, plus a documented manual review before first publish.

- **Complexity:** `LOW` — one runner gains a reset step + a bootstrap mode; zero bkit-core change; the whole model rides existing `merge=union` semantics.
- **Extensibility:** New example = sibling folder + same runner; new phase = `data.js` edit; a second host (#45) = same folder, different install flag. Version grouping absorbs release-straddling sweeps.
- **Risk:** Reset scoping — the delete is the one destructive filesystem op; a bug that widens the path (`rm` at root or `.bkit/`) destroys the accumulated benchmark history. Mitigation: scope the delete to the app folder and assert the resolved path before deleting; history loss is the failure to guard.
- **Maintenance:** One runner + one frozen fixture; the root `bkit-ci.yml` capstone name is the only drift surface (unchanged from v3).
- **Reuse vs new:** Reuses `.bkit/stats.jsonl` (union, `bkitVersion` present), the existing runner/`gh`/`bkit install --claude --tracker=github`, and the v3 fixture; new = reset step, bootstrap mode, privacy scan only.

## Approach B — Cut the run branch from `main`; reset is implicit, union-merge carries results

Same persistent public repo, but the runner does **not** delete anything: the run branch `feat/{FID}` is cut from `main` (which holds the full fixture state — root scaffolding _and_ the near-empty app folder), so every run starts byte-identical by construction; the PR targets `dev`, and `merge=union` unions the branch's empty `.bkit/stats.jsonl` with `dev`'s accumulated one. The "reset" becomes a property of the branch base rather than a filesystem step.

- **Complexity:** `LOW`–`MEDIUM` — no destructive step, but `main` must stay install-complete and runnable, and the divergence between branch base (`main`) and PR base (`dev`) means every run's diff to `dev` shows prior runs' output reverted, which is correct but needs stating.
- **Extensibility:** Same as A; the fixture-as-`main` makes "what a run starts from" a browsable branch.
- **Risk:** Reliance on `merge=union` for _every_ accumulating file — any tracked file `main` and `dev` diverged on (a config, a docs file) silently reverts on merge; and the reset is only as good as `main` staying pristine, which nothing enforces.
- **Maintenance:** `main` is now load-bearing (must stay fixture-clean) — one more invariant to keep, versus A's explicit reset path.
- **Reuse vs new:** Reuses union-merge and the runner; new = branch-base change only. Fewer moving parts than A, one more invariant.

## Approach C — Reset as in A, but execute in a scratch clone and push only the branch/PR

Runner clones the public repo to a scratch dir, resets `example/` there, runs the pipeline in the clone, then pushes `feat/{FID}` + PR; the maintainer's main checkout never churns. Buys isolation from the shared checkout's branch switches and cross-FID `dev`-lock contention (`.bkit/workflows.md:249`).

- **Complexity:** `MEDIUM` — a second working copy, a clone/push lifecycle, and a fixture path that now has two homes (bkit `examples/` and the clone).
- **Extensibility:** Fine, but the clone lifecycle grows any time a host-specific step is added.
- **Risk:** Split-brain — two checkouts of the same repo invite edits landing in the wrong one; and the workflows already isolate themselves with git worktrees, so the clone mostly duplicates that.
- **Maintenance:** Two surfaces (clone management + the reset) where A has one.
- **Reuse vs new:** Reuses A's reset; new = clone/scratch infrastructure that the existing worktree mechanism already provides. YAGNI unless checkout contention is observed.
