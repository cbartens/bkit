Caveat discovered while a consumer (gether-life/app-gether-life) wired `figma` into its MCP list: the host-side grants this feature writes are only half the path — the MCP server itself can still refuse the client.

**Finding.** Figma's remote MCP server (`https://mcp.figma.com/mcp`) allowlists OAuth Dynamic Client Registration by exact `client_name` at `https://api.figma.com/v1/oauth/mcp/register`. Clients outside the Figma MCP Catalog get a bare `403 Forbidden` (OpenCode reports "Dynamic client registration failed: HTTP 403"). Figma confirms this is intentional while in beta; new-client onboarding is paused behind the catalog waitlist.

**What this means here:**

- A bkit-listed server is pre-approved on the host, not guaranteed connectable. `figma` connects from Claude Code and Cursor (allowlisted → browser OAuth; the tokenless `{type, url}` config is correct as-is) and fails from OpenCode with identical files.
- No token fallback exists to document: the endpoint rejects PATs, and `mcp:connect` is OAuth-only — self-registered Figma OAuth apps get "Invalid scopes for app".
- Supported path on unlisted hosts: Figma's desktop-app server `http://127.0.0.1:3845/mcp` (Dev/Full seat, no write-to-canvas).

Recorded in `docs/knowledge.jsonl` here (`495-figma-remote-mcp-dcr-403-host-grant-does-not-bypass-upstream-client-allowlist`) and in the consumer's ledger. Upstream tracking: [sst/opencode#3875](https://github.com/sst/opencode/issues/3875) (OpenCode feature request) and [anomalyco/opencode#38360](https://github.com/anomalyco/opencode/pull/38360) (registered-client fix, closed unmerged pending Figma approval).

Suggested doc tweak (not landed): one line in `.bkit/providers.md` § MCP servers and the context template — listing a server pre-approves it on the host; the server may impose its own upstream client gate.
