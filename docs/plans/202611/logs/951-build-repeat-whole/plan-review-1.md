## CRITICAL

1. **(plan edit) No task can commit a change to bkit's own `bkit.workflows` config: `steps finish` refuses it with exit 13.** `steps finish` (default `--commit=auto`) refuses any step commit that changes a `bkit.workflows` key in `package.json` (`EXIT_WORKFLOWS_CHANGED`, `.bkit/core/engine/commands/workflow/steps.ts:1366-1378`, tested at `steps.test.ts:2177-2191`: "A run never changes its own limits"). The build's code-step commit runs through it (`bkit-build.md:670`). The runbook writes such a change three ways:
   - Task 1 `UPDATE: package.json: bkit.workflows.build.verify.maxAttempts 5 → 2` (plan line 499), with `package.json holds maxAttempts: 2` in its `DONE WHEN`. Task 1's commit is refused every time, and the refusal message tells the agent to restore HEAD's value.
   - Task 1 adds `build.holistic` to `CONFIG_DEFAULTS.asks`, so `seedBkitDefaults` (`.bkit/core/engine/install/modules/core.ts:586-703`, `askBlocks` at 636) adds `bkit.workflows.build.holistic` to `package.json` on every `bkit upgrade`. `pnpm bkit:generate` runs `pnpm bkit upgrade` (`package.json:67`), and Tasks 3, 4, 7, 8 and 12 name `pnpm bkit:generate` in their `DONE WHEN`. Each of those commits then carries a `bkit.workflows` change and is refused.
   - Task 9's `lowerVerifyMaxAttempts` runs during the same upgrade and lowers bkit's own `verify.maxAttempts` 5 → 2, which is another `bkit.workflows` change.
   
   This is a missing prerequisite: the plan needs a committed `package.json` with verify 2 and a `build.holistic` block, and the build's own commit guard does not let any task produce it. Fix: remove the `package.json` UPDATE line and its `DONE WHEN` clause from Task 1. Add a Pre-Flight item (Core or Conditional) so the owner commits bkit's `package.json` `bkit.workflows.build.verify.maxAttempts: 2` and `bkit.workflows.build.holistic: { "ask": true, "maxAttempts": 2 }` on the branch before `/bkit-build` starts. Unknown ask keys are ignored before Task 1 lands (`invalidAskSettings` and `askSettings` iterate only `ASK_POINTS`, `.bkit/core/engine/shared/settings.ts:305-335`), so the early commit is safe. The later upgrade's seed and migration then find nothing to write. Also state that this build's own verify limit becomes 2 when it starts, because `workflow-started.limits` freezes it then. Keep the `Breaking Changes` row "bkit's own `package.json` `build.verify.maxAttempts` 5 → 2", and point it at the Pre-Flight commit.
