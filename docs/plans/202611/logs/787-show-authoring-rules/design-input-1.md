## Issue description — oldest

### Problem

GateGuard (the hook that shows a per-file checklist and the matching `.bkit/authoring.md` rules before an edit) only fires on each host's edit tools. An agent that edits through the shell never sees it, for example with a Python script, `python3 - <<EOF`, `node -e`, `tee` or `cp`. On 2026-10-31 an agent edited several audit templates through Python scripts. It said it had not seen the authoring rules, because GateGuard never fired.

The rules already required those reads, but nothing put them in front of the agent at the moment of the edit. Every layer that could have done so has a gap:

### Outcome

Every edit to an agent-read file gets the matching authoring rules before it happens, whether it goes through the edit tools or the shell. This holds on every host and in every consumer install, with no check that runs after the edit.

### Success criteria

**Hooks** (the owner's chosen items, 2026-11-01):

1. **The shell check spots edits made by scripts.** Inline `python` and `node` code that writes a file, a script file named on the command line, and `tee`, `cp`, `mv`, `git apply`, `patch` or `ruby -i` onto a source file are all detected before the command runs. A script whose target files cannot be worked out gets a warning saying GateGuard cannot see what it will touch, and that the authoring reads still apply to each file it edits.
2. **The shell warning carries what GateGuard would have shown.** When the target file is known, the warning names it, gives the same per-file checklist, and quotes the `authoring.md` sections for that kind of file. It counts toward GateGuard's once-per-file record, so the agent is not warned twice for the same file. It works the same way on every host.
3. **Every host's hook fires on all of that host's edit tools.** Claude's matcher includes `NotebookEdit`. The Cursor, Codex and OpenCode matchers are checked against each host's documented tool list, and widened where a tool that edits files is missing. Any host left with a gap carries a sourced note saying that host has no way to hook it.

**Rules and headers:**

- `.agents/rules.md` § Authoring names § Doc Templates for templates.
- § Edit tools says an exception does not waive the authoring reads.
- Every template's opening note points an editor at `authoring.md`.
- `lite.md` carries the header pointer.

### Constraints and non-goals

- Everything ships to consumers: the shared hook parts in `.bkit/core/hooks/`, the `bkit:start` / `bkit:end` block of `.agents/rules.md`, the shipped templates and the shipped docs. None of it goes in bkit-repo-only code.
- Before the edit only. No after-the-command hook (PostToolUse) and no git-diff check.
- Every host that runs GateGuard and the Bash guard gets the same behaviour.
- Advisory stays the default, and the fail-open contract in the hook headers stays.
- Out of scope: pointers in prompt and workflow headers. `.agents/rules.md` § Repo Authoring and bkit's own GateGuard already cover those files in this repo, consumers do not edit them, and every subagent would read the extra line on every run.
- Out of scope: bkit's own project rules. `.agents/rules.md` § Repo Authoring § Authoring sections and `.bkit/authoring.md` § Which Sections Apply cover those (e1b72a7b0).

### Decisions already made

- Harden before the edit only; checks after the edit were rejected (owner, 2026-10-31).
- Every change must ship to consumers (owner, 2026-10-31).

  - **The edit-tool advisory picking sections by file kind.** The shipped `docAuthoringAdvisory` would stop naming the same two sections for every file.

### Draft Acceptance Scenario

> **DRAFT only:** reviewed in the design interview. Starting point for the design's Acceptance Scenario, not a fixed contract: the design may change any part, and records each change as a Decisions row.

#### Narrative

When an agent edits an agent-read file, I want the authoring reminder to appear before the edit, including edits made through shell commands or scripts. I want one general advisory across edit methods and supported hosts, keeping this change focused on reliable detection.

#### Success Criteria

1. The shell check detects the script and command edit forms listed in the issue before execution.
2. Known targets receive the existing per-file checklist and the same general authoring advisory used by edit tools, sharing the once-per-file record.
3. Scripts that might write to unknown targets receive a warning that their targets cannot be determined and authoring reads still apply. Clearly read-only commands are excluded.
4. Every supported host's edit tools are covered where hooks allow it; unavoidable gaps are documented with sources.
5. Consumer installs receive the hook improvements and requested rules/header pointers. File-type-specific advisories are recorded as future work.

#### Key Edge Cases

- Computed script targets cannot always be determined before execution.
- A file touched through both shell and edit tools should not receive duplicate first-touch advice.
- Hook failures retain the existing fail-open behavior: they do not stop the command.
- This change adds no shell blocking, after-edit checks, or file-type-specific rule selection.

#### Process Sketch

- WHEN an edit tool first touches a file → THEN show its checklist and the general advisory before the edit.
- WHEN a shell edit has known targets → THEN show the same advice for each target not already recorded.
- WHEN a script might write but its targets are unknown → THEN warn about that uncertainty and the required authoring reads.
- WHEN a command is clearly read-only → THEN omit the shell-edit warning.
- WHEN a host cannot intercept an edit method → THEN document the supported boundary.
