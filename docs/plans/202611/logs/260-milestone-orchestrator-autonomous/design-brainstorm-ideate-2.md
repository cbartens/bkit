# Design Brainstorm & Ideas

Lens: Optimal trade-off — best long-term shape, legacy constraints set aside.

Fixed by the owner and not re-opened here (design-input-1.md § Grill decisions): the manager is a Claude desktop session on Fable at `high` effort; every piece with one right answer is a `bkit manage <verb>` command; the manager's instructions hold only judgement; Claude desktop app only; local runtime only; the hard limits are enforced by permissions or engine checks; reports are new comments on the parent issue. The approaches below differ on the choices the owner left to the design: where the run state lives, how the manager learns what is due, and how much of the existing workflow skeleton is reused.

## Approach A — Private event ledger plus one "what is due" command ⭐ Recommended

The run state is an append-only event file kept in Git's common directory (untracked, shared by every worktree), and one command, `bkit manage tick`, folds it together with live probes (tracker, worktrees, the running builds' changed files, machine load) and prints a short typed list of what is due now, so the manager's prompt only says how to judge each kind of due item.

How the pieces fit:

- **State home.** `bkit-outbox/manage/{FID}/events.jsonl` under Git's common directory, next to the outbox that already carries cross-worktree private state (`docs/architecture.md` § Tracker reporting boundary). It must stay out of `docs/` and out of any commit: the v6.3 run learned that touching `docs/` in the main checkout while the push hook's tests run breaks the run, and a state file that changes every few minutes would do exactly that. Events are append-only (`run-started`, `permission-granted`, `worker-registered`, `worker-cleared`, `brief-sent`, `question-parked`, `assumption-made`, `landed`, `pushed`, `report-posted`, `issue-parked`). The current slots, queue, open questions and items owed before a landing are a fold of these, never stored.
- **Re-reading after a reset.** `bkit manage resume` prints the folded state in one screen. A `SessionStart` hook for the `compact` and `resume` sources runs it and injects the output, but only for a session id the run registered as the manager. The re-read is a check, not a sentence in the prompt asking the manager to remember (`Checks over instructions`). The hook's behaviour on the app needs a live check; if the app does not fire it, `tick` prints the same block first, and every manager turn starts with `tick`.
- **What `tick` prints.** One line per due item, in the fixed one-line form the learnings ask for: `ASK-WORKERS clean=1 slots=3` (the count of clean workers fell below the number of test slots), `START #812 lane=build overlap=none`, `GO-GATE worker-02`, `ANSWER worker-03 q-7 options=[A->step 9, B->step 4]`, `LAND #790 review=missing:summary,ledger-rows`, `PUSH reason=batch(5)`, `REPORT reason=question-batch`, `ENGINE-DIFF landing=a1b2 affects=worker-01@step6`. The manager reads it and judges. Nothing in `tick` acts on its own; the verbs it names do the chores.
- **Verbs** (each one right answer): `preflight`, `kickoff` (the "settled without asking" table plus the count of questions left; starts the issues with nothing to ask), `propose` (next issues from blocked-by links, priority, size and file overlap), `slots`, `brief` (renders the brief with commit to cut from, files allowed and forbidden, report points), `answer` (the third answerer, below), `review-checklist` (paths filled in; says when the manager's own read is the only bug review), `land` (trial merge, rebuild, checks, squash onto `dev`, checks again, stops at the first red), `push` (cheap blockers first, then the long hook, taken as a test slot), `mention` (issue title and URL printed from the tracker), `report`, `estimate`, `close-run`.
- **Third answerer in `/bkit-build`.** The pause step records `answerer` as one of `owner`, `headless`, `manager`. The engine prints each pause option with the step it leads to (`Stop -> parks the run`, `Try again -> repeats step N`), so the manager cannot override a Stop with a Try again without seeing it. `bkit manage answer` writes `Decision: Accept (assumed, by the manager)` and refuses to do it for a HIGH review finding or a MEDIUM one that cannot be fixed (engine check, not prompt text). This touches `/bkit-build` and the decision-row grammar; the exact file and row shape must be checked against `.bkit/core/workflows/bkit-build.md` in the design doc.
- **Limits enforced.** A `PreToolUse` guard, active only for the session id registered as manager (and workers the manager registered), refuses: anything touching `main` or a release, force push, `--no-verify`, forced removal of a worktree or branch, reads or prints of credentials, and any edit that is not an append to a ledger. This is the one place the "brief text alone did not hold" lesson is answered. Host hook text lives under `.bkit/core/hooks/`; this is the Claude-only exception to `Provider parity`.
- **Estimate.** `estimate` returns a range, not a date. Before any landing: for each open issue take the size's measured low and high hours (seed table from the v6.3 numbers: S about 2h, the largest 21h+ over two runs), divide the sum by the slot count, and floor it at the longest blocked-by chain. It prints the range labelled `seed`. After each landing the table is blended with the run's own measured hours per size (weight grows with the number landed), and the range narrows. The progress line counts issues: `Run: ████░░░░░░ 40% · 8/19 landed · 2 parked · est. finish 18:30-22:10`.
- **Reports.** `report` builds the text from the fold: landed, parked and why, questions with options, issues filed, every assumption, plus a fenced state digest. The manager posts it as a new comment on the parent issue and pastes the link in chat. If the Git-common state is ever lost, `resume --from-tracker` rebuilds the fold from the last digest. This is the only copy of run state that leaves the machine.
- **Landing.** `bkit manage land` is a thin adapter over the landing contract `/bkit-ship` is assumed to expose once #938 lands: input an issue, output `{sha, checks}` or the first failure. Until #938 exists the adapter holds the chores itself behind the same contract, so nothing waits and nothing is built twice.

`Complexity`: HIGH. A fold, about a dozen verbs, a guard hook, a resume hook and a small change to `/bkit-build`.
Extensibility: strong. A new due-item kind is a new event type plus one `tick` rule; the manager prompt gains one line only when a new kind needs a new kind of judgement. The later cloud-trigger idea (#324, out of scope now) could call the same verbs.
Risk: `tick` becomes a second place that quietly encodes policy and drifts from the prompt; or the app does not fire the resume hook, and the manager works from a stale picture after a reset. Mitigation: policy lives only in `tick` rules (one home), and every turn starts with `tick`.
Maintenance: moderate. One fold schema to version, and each new event type needs a test; the verbs are individually small and testable on a scratch repo. The prompt stays short, which is the cheapest part for `Fewer tokens`.
Friction vs ideal: touches `.bkit/core/engine/commands/` (a new `manage` noun and registry entry), `.bkit/core/hooks/`, `/bkit-build` pause step and decision rows, `.bkit/providers.md` (records the Claude-only exception and each host's gap), `bkit install` (writes `/bkit-manage` only for Claude), root `DETAILS.md` (limitations), `.bkit/workflows.md`, `.bkit/prompts.md`, `.bkit/cli.md`, `docs/capabilities.md`. `.bkit/core/engine/commands/land.ts` states that local `dev` commits are never pushed as they stand (a caller replays exactly its own commits), while the v6.3 model batches landings on local `dev` and pushes them together: `push` must either replay the landed commits through `land.ts` or the design must change that rule, and this is the largest open friction. Nothing existing breaks if the new noun is additive; the build change must keep `owner` and `headless` behaviour byte-identical.

## Approach B — Tracked per-run ledger, toolbox verbs, loop in the prompt

The state is a committed `docs/plans/{YYYYMM}/logs/{FID}/manage.jsonl` that looks like `status.jsonl`, the engine offers independent chore verbs (preflight, propose, land, push, report, mention), and the manager's prompt carries the loop and the rules for when to ask for workers, push or report.

- `Complexity`: MEDIUM. The ledger machinery already exists; there is no `tick`, no resume hook, no folded due-list.
- Extensibility: moderate. Every new rule is a new sentence in the manager's prompt, which grows with each lesson (the v6.3 run produced dozens), and every sentence is read again on every request.
- Risk: sentences that must hold (when to ask for workers, when a gate is red only on known-flaky tests, how an engine diff maps to running builds) are exactly the ones the learnings say did not hold as brief text. The manager can skip a rule without anything failing. The committed file also churns `docs/` in the main checkout every few minutes, which collides with the rule that `docs/` must not change while the push hook's tests run, so appends would need queuing.
- Maintenance: low engine cost, high prompt cost; the prompt becomes the thing that drifts.
- Friction vs ideal: fits `Decisions go to ledgers` and the "engine facts go in status.jsonl" doctrine, and the run is reviewable in git and resumable from another clone. Against that, it breaks `Engine over agents` for the decision of what is due, adds commit noise, and still needs the guard hook and the `/bkit-build` change from A. Surfaces touched are a subset of A's, minus `tick` and the resume hook.

## Approach C — Manager as a sixth numbered workflow

`/bkit-manage` is written like the other five: numbered steps with gates, a lock, `status.jsonl` rows, `bkit status resume`, `progressLine`, and the comment lifecycle, with each pass of the loop being one numbered round.

- `Complexity`: MEDIUM at the start, HIGH once the loop is bent into the shape. Locks, status rows, stats, `comply`, resume and comment dedupe come for free.
- Extensibility: poor where it matters. The 14 duties are concurrent, not a sequence, so steps become "rounds" with the real work in a sub-list, and `Progress Lines` (a position inside one workflow, computed from a fixed step count) cannot express "8 of 19 issues landed, est. finish 18:30". A second progress format is needed anyway.
- Risk: `bkit status resume` assumes a linear position; after a reset the manager would resume "at round 31" without knowing which workers are alive. The per-FID lock and the 30 minute staleness rule assume one workflow per issue and would collide with the sub-issues' own locks if the manager used the parent's FID.
- Maintenance: lower new code, but every change to the shared workflow skeleton now has to keep the manager working, and the manager is the odd one out.
- Friction vs ideal: it reuses the most existing machinery, and it is the shortest path to something runnable. It forces the manager into a pipeline shape it does not have, and the compliance grader, stats and `workflows.md` catalog all gain a special case. It would be the better choice only if the owner wanted the manager to be one more workflow among six rather than a control loop over them.
