## Notes

- Task 1 evidence: `gh` 2.102.0 `pr list --help` says `--limit` defaults to 30 and `--head` does not support `<owner>:<branch>`. `GH_DEBUG=api gh pr list --head ...` shows the GraphQL query filters `headRefName: $headBranch` on the server, orders `CREATED_AT DESC` and sends `limit: 30`. On a page of 30 fork entries, the hook's new filter `map(select(.isCrossRepository | not)) | .[0] | select(. != null) | ...` prints nothing and exits 0, so `PR_LOOKUP=ok` and `OPEN_PR` stays empty. The old guard filter `.[0].number` printed the fork PR's number on the same page, so the CI-suppressor guard failed closed before this diff and fails open after it. GitHub allows one PR per head and base pair, so one fork can open the 30 PRs against 30 existing branches of the base repo; the attacker needs no access to the repo. The merge gate (`bkit runs gate --validated=`) stays the authority on what merges, which keeps this MEDIUM rather than HIGH. `docs/security.md` § CI Auto-Route Trust already makes the same point for CI: a lookup that can return fork PRs must filter its own results, and the filter must see every result.
- Task 2 evidence: in a scratch repo on macOS `/bin/sh` (GNU bash 3.2.57, POSIX mode), the base renamed `f.txt` to a name holding ESC `[2J` and edited it, while the branch edited `f.txt`. `git merge-tree --write-tree --name-only` exited 1 and quoted the path as `"x\033[2Jy.txt"`. The hook's exact `echo "$PR_MERGE_OUT" | sed ...` line wrote a raw byte 033 to stderr. Debian and Ubuntu `/bin/sh` is dash, whose `echo` also expands `\033`. Only someone who can push to a same-repo base branch can stage this, so it stays LOW, collaborator against collaborator. The `sed '/^$/,$d'` step already drops git's own unquoted `Auto-merging` lines, which carry the raw byte too.
