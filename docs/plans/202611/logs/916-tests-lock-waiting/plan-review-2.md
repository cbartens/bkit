## CRITICAL

1. **(plan edit) Backwards-compat break: the exit-81 short-call loop loses its place in line on every re-run, so 60 s hosts starve behind any longer waiter.** `.bkit/core/.bkit/providers.md:853-856` sets Codex, Antigravity, Cursor and OpenCode to a 60 s wait, then exit 81 and a re-run, and `:858` promises that this "costs a re-run per minute of waiting and nothing else". `docs/testing.md:326` adds `--lock-wait-s=0` (try once) and Claude's 1200 s cap. Under TASK 1 a give-up unlinks the ticket (plan `:299`, `:405`), and the re-run takes a new ticket at the end of the line (plan `:75`). Every run that started waiting during the last 60 s is therefore ahead of the re-run, and so is any run that takes the lock in the gap between give-up and re-run. While longer-wait runs keep arriving, a short-call looper is always last; a `--lock-wait-s=0` caller is never first unless the line is empty. Today it wins about 1 in k at each release. This is the issue's starvation turned around onto exactly the waiters bkit's own verbs create. No Open Question, Edge Case, `Derived Test Matrix` row or task covers it, and TASK 4 leaves `providers.md:858` stating a cost that is no longer true.
   - Fix: add an Open Question on how a re-run keeps its place. For example, `bkit tests run`, `bkit tests changed` and `bkit branches push` pass the run's first-wait time (for example `LOCAL_STACK_LOCK_SINCE`), and the helper uses it as the ticket time, so a re-run sorts at its original place. Another option is to accept the cost and document it.
   - Then add an Edge Case row and a `Derived Test Matrix` row ("a waiter that gives up with exit 75 and asks again within its re-run window stays ahead of a run that arrived in between"), with its task.
   - Then add `.bkit/core/.bkit/providers.md` § Long-running shell commands to TASK 4 and to `Documentation Updates`.

## OPTIONAL

1. **Flagged high-risk surfaces with no rule above making them `CRITICAL`:**

   - Each is covered by the existing suites plus the planned rows. They are listed so the build treats them as shared surfaces.
2. **When the queue folder is created is ambiguous.** Breaking Changes (plan `:126`) says it is "created on first wait". Architecture (`:295-296`) creates the folder and a ticket on every wait-mode take, contended or not, and TASK 1's 73 test red (`:421`) only works under the second reading.
   - State that the folder and ticket are created on every wait-mode take.
   - State whether `try` creates the folder or treats a missing folder as an empty queue, so a `try` never starts failing with 73 because of a path it only reads.
3. **Pid source contradiction.** Breaking Changes (plan `:127`) says "tests read the pid from" the ticket file. The ticket file holds only `<who> — <checkout>` (`:264`), and the runbook reads the pid from the ticket name (`:396`). Align `:127` with `:396`.

Under random order the re-asker comes last about 1 time in 6. Assert the full order file instead (five waiters in arrival order, then the re-asker), which brings chance passes down to 1 in 720.

The post-acquire handler at `scripts/ci/bkit-machine-lock.sh:254` only sets `$stopping`, and a builder could install it before the loop. Add a row that sends `SIGTERM` to a waiting helper (pid from its ticket name) and asserts the ticket is gone at once and the runs behind move up.

## OUT OF SCOPE

1. **Possible existing cancellation gap: unverified, a probe is worth doing.** The helper installs `$SIG{INT}` / `$SIG{HUP}` after acquiring (`scripts/ci/bkit-machine-lock.sh:254`). Perl installs that handler even when Bash started the helper with SIGINT ignored. If so, a terminal Ctrl-C reaches the helper through the process group and makes it release the lock, while the `run` wrapper defers its own cancellation until the gate ends. That would leave the gate running unlocked, which is the case knowledge `machine-lock-wrapper-cancellation-keeps-foreground-owner-alive` guards for TERM to the wrapper. It exists today and is outside this plan.
2. **Detect-only `bkit check` advisory for an adopted lock copy without the queue.** This is already in the plan's Suggested Scope Expansion. Once every supported release ships the queue, an un-recopied consumer copy is the only way a run can still jump the line.
