## CRITICAL

### R2-1 — Coordinate the existing journal writer with managed ledger target locks (plan edit)

- **Plan evidence:** Task 4 (`plan-v1-draft.md:357`) changes only `ledgers/status.ts`, workflow `locks.ts` and workflow `ledgers.ts` for operation locking. Its architecture promises that concurrent engine appenders cannot interleave and that prepared offsets remain valid. The inventory treats the append helper as the write boundary but omits the independent journal writer.
- **Source evidence:** `ledgers/journal.ts:228` exports `appendFrictionRow`; at lines 233–245 it reads `APPEND_LEDGERS.friction.file`, computes recurrence from current contents and directly calls `fs.appendFileSync`. `commands/lib.ts:549` invokes this writer for command failures; workflow status owner-pause also uses it. This is an existing engine writer, not an unsupported editor bypassing the CLI. The supplied closed deferral `699-engine-run-completeness-challenge-low-bkit-core-engine-ledgers-journal-ts-174` documents why its append-only recurrence behavior must be retained.
- **Regression vector:** A managed friction operation holds its proposed lock and prepares an exact offset, while an ordinary command failure appends through `appendFrictionRow` without that lock. The managed write can then append at a different offset, or a prepared recovery becomes uncertain because another engine writer changed the expected length. Same-key recurrence/lineage reads can also race. A guarantee for all supported APPEND_LEDGERS targets cannot be proved by testing only `appendLedgerRows`, compact and union.
- **Required plan edit:** Add the direct journal writer and its callers to the reuse/surface inventory. Extend the existing cycle-free target-lock primitive to every engine write path to a managed ledger target, explicitly including `appendFrictionRow`, or explicitly block that competing writer while a prepared operation owns the target. Preserve its append-only history fix and optional telemetry error policy; do not import command modules into the leaf journal. Audit other direct target writers as part of Task 4's scope.
- **Acceptance/test:** Extend Task 4's Integration matrix row and DONE WHEN with a real two-process friction case: pause a managed append after preparation, trigger the real journal/owner-pause writer through another dispatcher process, release/resume and inspect actual ledger bytes, folded recurrence and receipts. The competing write must wait or return a visible non-success result, never invalidate a claimed completed receipt; recovery must yield exactly the intended rows and a correct recorded offset. Include same-key recurrence and distinct-key cases. This can remain in `ledgers/journal.integration.test.ts` within the existing task caps.

### R2-2 — Prove retrigger idempotence at the Git effect, not only the handoff receipt (plan edit)

- **Plan evidence:** Task 7 (`plan-v1-draft.md:419`) requires uncertain retriggers to reconcile before another dispatch, but its Integration TEST FIRST fails on “recording a second retrigger for the same intent.” The matrix describes real local persistence; it does not require observing the commit/push that the receipt represents.
- **Source evidence:** `commands/workflow/runs.ts:861` reads the old HEAD, `runs.ts:862` creates an actual empty commit and `runs.ts:867` calls `pushCurrentBranch`. The shared-checkout branch at `runs.ts:878` calls `retriggerCommit` and then `pushBranch`. `res.retrigger = true` is set only at `runs.ts:895`, after these effects. A process may lose its result between a successful push and this recorded outcome.
- **Regression vector:** A resumed dispatch can create/push two retrigger commits while deduplicating the status event to one. The proposed receipt-only assertion would still pass. Failure to reconcile a commit made before an interrupted push can also leave an orphan or push the wrong head. These are the effects the accepted durable handoff requirement is intended to control.
- **Required plan edit:** Make Task 7's Integration test and DONE WHEN require real commit/push reconciliation evidence. Persist/compare the original and retrigger commit identities, including the shared-checkout ownership branch, and distinguish commit-created, push-completed and receipt-completed checkpoints. Keep unavailable/conflicting evidence blocking the affected retrigger.
- **Acceptance/test:** Use temporary repositories with a local bare Git remote and the real dispatcher/Git helpers. Interrupt after commit creation and after the remote accepts the push but before completion recording; restart a fresh process with the same invocation/intent. Assert the remote branch SHA, reachable retrigger commit count and owned tree contents, plus the durable receipt. There must be exactly one intended retrigger commit and no unrelated staged content published. Inject conflicting remote movement and assert no second commit/push until resolved. Provider polling fixtures may remain outside this Git boundary. This is an Integration test under `docs/testing.md:574`; it needs no external network or new @live lane.
