# Design Brainstorm & Ideas

Lens: Pragmatic — existing code, minimal new infrastructure, fastest to ship.

Evidence read for this lens: `.bkit/core/engine/ledgers/telemetry.ts` (`APPEND_LEDGERS` :386, `KIND_WRITERS` :412, `identity()` :844, `fold()` :1909, `foldFrom()` :2012), `.bkit/core/engine/ledgers/migrate.ts` (`SCHEMA_LEDGERS`, `migrateLedgerText` drops a union-resurrected copy of a rewritten row), `.bkit/core/engine/ledgers/compact.ts` (`COMPACT_LEDGERS`), `.bkit/core/engine/commands/workflow/ledgers.ts` (`ledgersCommand` :671; an existing `check` verb with a required `--plan`), `.bkit/core/engine/commands/workflow/context.ts` (`ledgerScan` :666, `ledger-scan` verb :1342 with clamp + artifact plumbing), `.bkit/core/engine/install/modules/core.ts:408` (where `migrateLedgers` runs on install / upgrade), `.bkit/core/.bkit/workflows.md:250` (close squash: `-X ours` plus re-append of dropped `.jsonl` rows, exit 18 when a branch-added `.jsonl` line is missing on `origin/dev`), `.gitattributes:17-21`, `.bkit/jsonl.md` § Write Idiom, § Ledgers & Writers, § Key & References, § Updating a Row, § Compaction, § Identity / Dedup, § Versioning. Surface count: the four old paths appear 494 times across 109 files under `.bkit/core/` (about 10 engine source files, the rest prompts, workflows, `.bkit/*.md` docs and 40-odd `bkit-audit-*` templates).

## Approach A — Brain as one more ledger inside the existing engine ⭐ Recommended

`docs/brain.jsonl` becomes one `APPEND_LEDGERS` entry taking the six brain kinds; every settled answer is built by extending `telemetry.ts`, `migrate.ts`, `compact.ts`, `ledgers.ts` and `context.ts` in place, with brain-only logic (links, transitions, context selection, check) in one new file `.bkit/core/engine/ledgers/brain.ts` that imports the existing fold / validate / lineage primitives. `Complexity`: `HIGH` (five plans; each one is an extension of a working path, but the whole program touches the engine, the install path, about 100 agent-read files and four prompts). Extensibility: a new kind is one `APPEND_LEDGERS` kinds entry, one `KIND_WRITERS` entry and one transition-list line; `.bkit/issues.jsonl` `feature` rows can join later the same way (Q14). Risk: the legacy-file handling on open branches; the main failure mode is a stale branch's append to an old file being lost, resurrected or clobbering a newer brain row (mitigations below). Maintenance: one codec, one fold, one updater prompt instead of four; the 109-file path sweep is a one-time cost, then lower than today because `Cross-Ledger Impact` bookkeeping disappears. Reuse vs new: reuses `foldFrom(paths)` (already merges several files), `normalize()`, `lineage()` / `withLineage()`, `validate()`, the `KIND_WRITERS` check in `append`, `migrateLedgerText`'s drop-the-resurrected-copy rule, `compactLedgerText`, `clampFile` with the `ledger` profile, `ledgerScan`, the `package.json` `bkit.*.ask` settings reader in `.bkit/core/engine/shared/settings.ts`, and the cron shape of `.bkit/templates/.github/workflows/bkit-trivy.yml`; net-new is `brain.ts`, the `brain` `CommandSpec`, the merge migration, the FTS5 index builder, one prompt `bkit-utility-update-brain`, and a small committed rejection log.

How each settled piece lands, smallest change first:

- **One file, same codec (Q2, Q11, Q12).**
  - `APPEND_LEDGERS`: drop the four entries, add `brain: { file: "docs/brain.jsonl", kinds: ["knowledge", "decision", "deferral", "failure", "assumption", "summary"] }`.
  - `identity()`: the six brain kinds return `brain ${repo} ${key}` instead of `${kind} ${repo} ${key}`. No key exists in two of the four old files today, so fold winners are unchanged (Success Criterion 2).
  - `COMPACT_LEDGERS` becomes `brain` + `issues`; `SCHEMA_LEDGERS` gains `docs/brain.jsonl` and keeps the four old paths.
  - The `.gitattributes` managed block gains `docs/brain.jsonl merge=union` and keeps the four old lines.
- **Envelope without a schema bump (Q13).**
  - The envelope is the existing top section plus `summary` (required on new brain rows), `status` and one optional `links: {supersedes?, dependsOn?, relatedTo?}`.
  - Per-kind fields stay flat, as today: `rationale`, `severity`, `reason` and the rest stay where every current reader (`bkit stats`, `bkit ledgers triage`, `bkit decisions pending`, the roadmap render) already reads them. A nested `body` object would force a rewrite of every one of those readers for no new capability, because a generic reader only needs the envelope fields and ignores the rest.
  - `schema` stays `3`: `links` is an optional addition, and § Versioning already makes readers tolerate missing fields.
  - `assumption` adds `falsifiedBy` (required; refused without it, like a `deferral` without `reason`) and `validUntil?`. Its `status` is `ACTIVE` / `FALSIFIED` / `SUPERSEDED`.
- **Kind changes (Q12).** `KIND_TRANSITIONS` sits beside `KIND_WRITERS` and is checked in the same `append` pass. Each allowed pair carries its status mapping, e.g. `failure` `CLOSED` → `knowledge` `ACTIVE`, `deferral` `needs-decision` → `decision` `ACTIVE`, `assumption` `ACTIVE` → `knowledge` `ACTIVE`. Any other kind change exits 8, as a refused writer does today.
- **Merge migration (Q2, Q6, Q13).**
  - A new `mergeIntoBrain(root, dryRun)` in `migrate.ts` is called from `.bkit/core/engine/install/modules/core.ts` right after `migrateLedgers`.
  - It copies every line of the four old files into `docs/brain.jsonl` (no row lost; fold order is by `ts`, so line order is free). It fills `links` on each row from `references` entries that exactly equal an existing key. It fills a missing `summary` from the first sentence of `description` (deterministic, capped length). It leaves `references` untouched.
  - It then truncates each old file to zero bytes instead of deleting it.
  - It is idempotent: an old-file line whose `(key, ts)` already exists in the brain is dropped, which is the same rule `migrateLedgerText` uses for union-resurrected copies.
  - Same key in two old files (none today): the row with the earlier `firstTs` keeps the key, and the other becomes `{key}-{kind}`. This rule is fixed and gives the same result on every run.
  - Q6 says the links come from appended same-`key` rows, while Q13 says the migration rewrites every old row once. This design reads Q13 as the governing answer and puts the links in the rewritten rows, which avoids adding about 650 extra lines.
- **Why truncate, not delete.** A stale branch that appended to `docs/knowledge.jsonl` hits a modify/delete conflict when `dev` has deleted the file. `merge=union` does not resolve that conflict, and `-X ours` in the close squash does not either, so `bkit branches land` stops with a non-zero squash (`.bkit/core/.bkit/workflows.md:250`). With a zero-byte file the merge is a content merge, and the union driver keeps the branch's rows. It may also bring back the old lines. Readers fold `[brain, ...old files]` through `foldFrom`, and the `(key, ts)` drop rule makes a resurrected copy invisible. The next brain update moves any genuinely new rows into the brain and truncates the file again. Not verified: the exact union result of "ours emptied, theirs appended". It must be proven with a real `git merge` in a test before the plan relies on it.
- **Typed links and the dead-premise check (Q4, Q5, Q10).**
  - `brain.ts` builds a reverse index from the fold. `bkit brain append` prints the current rows whose `links.dependsOn` names a key the append turned `SUPERSEDED` / `CLOSED` / `FALSIFIED`, and always exits 0 for this reason.
  - `bkit brain check` lists every dead premise, every dangling link key, every `dependsOn` cycle (a DFS with a visited set, which never recurses without bound), every passed `validUntil`, and every fork (see concurrency). It exits 0. Existing `bkit ledgers check --plan` becomes `bkit brain check --plan` and keeps its exit code `EXIT_ROWS_MISSING`.
  - A successor is found by searching for rows whose `links.supersedes` names the key. The 45 old `SUPERSEDED` rows with no exact-key reference stay unlinked after the migration, and brain update proposes those links.
- **Loading rows by file (Q8, Q7).**
  - `bkit brain context --files=<list|->` folds, keeps current rows (not `SUPERSEDED` / `CLOSED` / `FALSIFIED`) where a `references` path equals a file or is a folder above it at any depth, and appends the always-loaded summary. It writes through `clampFile(..., "ledger", ...)`, the plumbing `bkit context ledger-scan` already uses, and emits `tokensEst` (characters / 4) so before / after measurement is one number per task.
  - The six prompts and `.bkit/core/.agents/rules.md` that carry "Check gotchas first" switch to this command.
- **Keyword search (#793).**
  - `bkit brain search "<text>"` builds a `node:sqlite` FTS5 table over the fold winners under gitignored `tmp/` (already `tmp/**` in `.gitignore`). The index is rebuilt when the brain file's size + mtime + line count no longer match the values it was built from, and results are ranked by `bm25`.
  - Not verified: whether `node:sqlite` prints an `ExperimentalWarning` on Node 24. If it does, the command must keep stderr clean for `--json` callers.
  - Fallback when `node:sqlite` cannot open: existing `ledgerScan` term overlap over the fold winners. That is pure JS and already tested.
- **Brain update (Q15-Q23).**
  - `bkit brain update` is the deterministic half. It compacts, moves old-file stragglers, rolls up the recall log, lists fade candidates and runs the check. It then writes a candidate packet for the agent.
  - One new prompt `bkit-utility-update-brain` does the inference. It merges the per-kind steps of the four `bkit-utility-update-*` prompts (one sweep, no `Cross-Ledger Impact` section) and adds the contradiction, pattern, link and summary steps.
  - With `bkit.brain.update.ask: true` (default) the prompt writes a report with a `Suggested Changes` table, and only approved rows go through `bkit brain append`. With `false` it appends directly.
  - The scheduled run is opt-in: a copy-and-own cron recipe in the shape of `bkit-trivy.yml` for the deterministic half. The agent half needs an agent host, and nothing in the engine schedules one today (Open).
- **Concurrency without a lock (Q28).**
  - Every row brain update appends carries `basedOn: <ts>`, the `ts` of the row it copied.
  - `bkit brain append` skips a suggested row whose target's current winner `ts` is not its `basedOn` ("stale, re-offered next run"), which is a compare-before-write check with no lock.
  - Across branches, `bkit brain check` reports a fork when an entry's winner has `basedOn` older than another row of the same key. That is the concrete failure where a brain-update copy made on `dev` outranks a content change landed from a feature branch. The next brain update re-appends the newer content.
  - Report files are named per run (time + random suffix), so two runs never overwrite each other's report.
- **Shared recall (Q24, Q25).**
  - `context` / `search` append the keys they return to a gitignored recall log in the main checkout's `tmp/`, resolved through `git rev-parse --git-common-dir`. Most reads happen inside `.worktrees/{FID}`, and a worktree-local `tmp/` is deleted with the worktree, so its recalls would be lost.
  - Brain update writes `lastRecalled` onto the entry only when the stored date is older than half the fade window. This keeps line churn and the fork surface small. Readers take the newest `lastRecalled` across all of an entry's rows, as Q25 says.
- **Rejections (Q20).** These go in a committed, `merge=union`, append-only `.bkit/brain-rejections.jsonl`, one row per rejection, keyed by a hash of (action, target keys, each target's winner `ts`). A change to any target row changes the hash, so the suggestion comes back by itself, with no expiry logic.

## Approach B — Virtual brain: fold across the old files, write new rows only to `docs/brain.jsonl`

The four old files are frozen as history and never rewritten. All new appends go to `docs/brain.jsonl`, and every reader folds `[brain, knowledge, decisions, deferrals, failures]` through `foldFrom`, with `normalize()` presenting old rows in the envelope. Links are backfilled as appended same-`key` rows in the brain, which is Q6's original wording. `Complexity`: `MEDIUM`. It drops the rewrite migration, the zero-byte stub question and the summary-filling rewrite, and keeps everything else in Approach A. Extensibility: same as A for new kinds. Old-shape rows stay a permanent second input shape, so every future envelope change has to be mapped in `normalize()` as well as written. Risk: departs from Q2 and Q13 (the four files never become one, and no row is rewritten into the envelope), so it needs the owner's confirmation. It also leaves the 109 files that name the old paths with two truths: grep-based audit templates and prompts still have to know about five files, or a reader that greps only the brain misses about 655 rows. Maintenance: higher than A over time. `normalize()` carries the old-to-envelope mapping forever, and any human skimming or grepping sees two layouts. Reuse vs new: reuses everything A reuses, and needs no merge migration at all. The `bkit upgrade` step shrinks to "append link rows for exact-key references", and the stale-branch case disappears because nothing is deleted or truncated. Net-new is the same `brain.ts`, commands and prompt as A, minus `mergeIntoBrain`.

## Approach C — Dedicated brain module with its own codec

A new `.bkit/core/engine/brain/` module owns the envelope types, a fold keyed by `(repo, key)`, link resolution, transitions, the migration and every `bkit brain` verb. `telemetry.ts` keeps only stats, friction and `feature` rows, and the brain module does not call `identity()`, `validate()` or `KIND_WRITERS` from it. `Complexity`: `HIGH`. Extensibility: the cleanest boundary for later brain-only features (for example `feature` rows moving in under Q14), and `telemetry.ts` (over 2,000 lines) stops growing. Risk: two codecs drift. `lineage()`, `validate()` totals, the whole-second `ts` rule and the writer check would exist twice. `bkit stats` (`outcome.ledgers.deferrals` / `failures` counts) and `bkit ledgers triage` / `bkit decisions pending` would also have to switch codecs in the same change, which puts Success Criterion 2 ("fold winners, `bkit stats` figures and the `docs/roadmap.md` render are unchanged") at the most risk of the three approaches. Maintenance: highest. Every rule in `.bkit/jsonl.md` that applies to both families (minted `ts`, `merge=union`, writers are exhaustive) must be enforced in two places, and `telemetry.test.ts`'s doc-table parity test needs a twin. Reuse vs new: reuses only `clampFile`, `ledgerScan` and the settings reader. The codec, fold, validation, migration and writer table are net-new, against `.agents/rules.md` § Improve over duplicate.
