# Design Brainstorm & Ideas

Lens: Optimal-tradeoff — best long-term shape ignoring legacy constraints.

## Approach A — Build-time canonical partial, stamped into every rendered surface ⭐ Recommended

A single source-of-truth snippet (e.g. `.bkit/templates/partials/untrusted-input.md`, or a constant in `.bkit/src/bkit-modules.ts` alongside the existing tracker-marker machinery) is injected at build/install time into every workflow header and every leaf-prompt header — not hand-copied per file. The render step already exists for the analogous problem: `.bkit/workflows/*.md` carry `<!-- bkit:tracker github start/end -->` marker pairs that `bkit-modules.ts` strips/selects per-provider at install time. Extend that same marker-substitution model with an unconditional `<!-- bkit:untrusted-input -->` marker that the renderer expands to the canonical bullet in every `.bkit/prompts/*.md` and `.bkit/workflows/*.md` at generation time (into `.claude/.cursor/.opencode` mirrors), and a companion `bkit-templates-content.test.ts`-style test asserts the marker is present in every source file (so drift is a build failure, not a doc-review catch). `rules.md` keeps its own copy (already covered by the existing `bkit-rules-sync.test.ts` byte-equality gate) as the mechanics-pointer layer; the leaf/workflow copies are the actually-reached layer per the audit's decisive fact.

- **Complexity:** MEDIUM — one new marker type + one renderer code path + one enforcement test; no new file format, reuses proven marker infra.
- **Extensibility:** Best of the three — future wording changes (e.g. adding a new content class beyond PR/comment/issue) are a one-line edit to the partial; propagates to all 46+ files automatically on next `bkit install`/render, zero per-file edits.
- **Risk:** Renderer bug silently fails to expand the marker in one provider mirror (e.g. opencode's different assembly path) → false sense of coverage. Mitigate with the enforcement test asserting the _expanded_ text (not just the marker) in rendered output, not just source.
- **Maintenance:** LOW ongoing — wording lives in exactly one place; no per-prompt bullet to keep in sync ever again.
- **Friction vs ideal:** Touches the renderer (`bkit-modules.ts` / install pipeline) which is more surface than a pure content edit — this is new machinery, not a docs change, so it needs its own tests and is a bigger PR than P0–P4 as scoped in the issue. It also diverges from the issue's stated plan (P1–P4 = per-file bullet edits) — would need to be reframed as "P4.3 enforcement test becomes P0: build a partial-expansion mechanism instead of copy-paste + drift test." Existing 9 prompts' hand-copied bullets become redundant/replaced, a one-time migration.

## Approach B — Per-file copy-paste rollout + presence-only enforcement test (as scoped in design-input.md)

Follow the issue's literal plan: upgrade the canonical text in `rules.md` + `.bkit/templates/.agents/rules.md` (already gated by `bkit-rules-sync.test.ts`), hand-add the identical bullet to all 8 workflow headers and all 46 leaf prompts (P0–P4 rollout order), and write one new enforcement test that asserts every `.bkit/prompts/*.md` and `.bkit/workflows/*.md` file contains the exact upgraded bullet string (grep-style, mirroring `bkit-modules.integration.test.ts`'s parity-assert pattern).

- **Complexity:** LOW — no new machinery, pure content edits across ~54 files + one straightforward string-presence test.
- **Extensibility:** WORST of the three — every future wording tweak is 54+ manual edits again; the enforcement test only catches _drift after the fact_ (a file missing the string), it doesn't prevent the copy-paste burden that caused drift in the first place. New leaf prompts added later require the author to remember to copy the bullet — the enforcement test is the only backstop, and it's easy to word a "close enough" variant that string-matching either wrongly flags or wrongly passes.
- **Risk:** Enforcement test becomes brittle (any wording refinement breaks 54 files at once) or is written loosely (substring match) and degrades to security theatre — it can pass while individual files carry stale pre-upgrade text if the match is too permissive, defeating P4.1's whole point.
- **Maintenance:** MEDIUM-HIGH ongoing — this is exactly the "per-file copies drift" failure mode the design-input calls out as the current defect; Approach B _reproduces_ it rather than fixing it, just with a wider net this time.
- **Friction vs ideal:** LOWEST short-term friction — matches the issue's task list exactly, no renderer changes, ships in one pass with git-diff-reviewable content-only edits. This is the "already have X" default the process instructs to not default to, but it is a legitimate low-risk choice given #342 explicitly frames itself as "minimal, additive" (non-goal: not a rewrite of call sites) and the real controls are token-scope/structural gates per §5a, making the prose layer's long-term shape lower-stakes to get perfectly DRY.

## Approach C — Trust-tier classification + scoped bullets (only act-leg leaves get the strong clause; read-only leaves get a lighter one)

Instead of one universal bullet, classify surfaces into tiers per the audit's own P0–P3 structure (ingest+act orchestrators, act-leaf, edit-leaf, read/judge-leaf) and ship a _different_ bullet per tier — full ingest+act+flag clause for P0/P1, lighter "data not instructions" clause for P2/P3 reviewers that never touch git. Reasoning: a reviewer prompt that only emits a verdict block has no act-leg to close, so forcing the full "never let it steer git/merge/token" clause into every one of the 37 P2/P3 files is dead weight that also risks the same civilisational drift problem in miniature (two canonical strings instead of one).

- **Complexity:** MEDIUM — two (or three) canonical variants instead of one, tier-lookup table to classify each of the 46 prompts, still needs per-file placement (copy-paste or partial).
- **Extensibility:** MEDIUM — tier boundaries need re-litigating whenever a leaf's capability changes (e.g. a P3 reviewer later gains Edit/Bash and must be promoted to P1 wording) — an extra classification-maintenance axis the other two approaches don't have.
- **Risk:** Classification drift — a leaf's tool grant changes (tools array edited) without anyone re-checking whether its untrusted-input bullet still matches its actual capability; the two-tier split can silently under-cover a promoted leaf.
- **Maintenance:** MEDIUM — two strings to keep in sync (each still needs its own drift guard), plus the tier map itself is a maintained artifact.
- **Friction vs ideal:** Contradicts the design-input's own recommended end-state ("make the bullet a universal header element... zero-gap, no per-leaf classification debt") — introduces exactly the classification debt that quote explicitly warns against, for a complexity saving (skip 37 files) that's marginal once a partial-expansion mechanism (Approach A) makes the per-file cost near-zero anyway.
