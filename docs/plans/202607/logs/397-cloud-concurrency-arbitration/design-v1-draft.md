# Design: bkit-cloud Concurrency Arbitration

## Related Issues

- #363 — Route post-merge CI failure to `/bkit-debug`, widen `bkit-cloud` trigger (open, `bkit:build`) — hard landing-order dependency; edits the same four lines of the same Tier-1 byte-equal file. Its plan v4 ships `branches: ['feat/**','fix/**','dev']` (`main` deliberately dropped, recorded as a reversal + deferral row) and `cancel-in-progress: ${{ github.event.workflow_run.head_branch != 'dev' }}`.
- #59 — Auto-route build PRs to ship/debug after CI (closed, completed) — origin of the group expression. Its "`cancel-in-progress: true` is safe for ship because squash-merge is GitHub-atomic" rationale, and its parked escalation "consider per-stage concurrency groups", are both directly addressed here.
- #260 — Milestone Orchestrator autonomous PM loop (open) — downstream consumer. Wants capacity-1 + single-flight + **idempotent dispatch** + reconciliation; GHA concurrency supplies the first two only.
- #324 — Recurring self-healing audit loop (open) — third dispatch producer on the same `workflow_run` substrate; must be able to slot into whatever lane policy lands here.

## Acceptance Scenario

### Narrative

As a maintainer running several `bkit:auto` issues in parallel, I want the cloud router to run at most one ship at a time across the whole repo, and never let two cloud sessions work the same issue at once — so two agents never race on one branch and a merge never lands against a `dev` that moved underneath it. When my work has to wait its turn I want to see it waiting in the Actions list rather than watch it boot and burn minutes. When it is displaced instead of queued, I want to be able to find it, not discover weeks later that a green PR quietly never merged.

### Success Criteria

1. At most one cloud run executes a ship repo-wide at any moment; a second concurrent ship waits without booting, and neither cancels the other.
2. A dispatched run for issue N and a CI-triggered run for issue N never execute concurrently, whichever payload shape carried the id.
3. Green CI on a post-merge branch (`dev` today, `main` if re-added) never enters the ship lane and never displaces a waiting ship.
4. Per-FID isolation for design / plan / build and `feat/**` / `fix/**` debug is preserved, and no run is cancelled mid-flight by a newer arrival.
5. Every wait, yield or displacement is identifiable from the GitHub Actions run list alone; a run that yields or is displaced never produces a `bkit:failed` label.

### Key Edge Cases

- **Three or more concurrent ships.** GHA holds exactly one pending run per group; a third arrival displaces the pending second. That PR stays green, open and merge-ready but never ships, and the displaced run never executes a step so it cannot report anything. Caps requirement 1 at N=2 and forces an explicit recovery answer.
- **Both agent secrets set.** One run launches the `claude` and `opencode` jobs on the same PR. Workflow-level concurrency cannot separate them — they are one run. A ship-global lane therefore delivers "one ship **run** at a time", not "one ship **agent** at a time".
- **A waiting ship dequeues onto a moved `dev`.** Its PR is behind and its green CI is stale; it must re-derive branch/PR/CI state and re-gate at merge time rather than merge on trust.
- **Two id shapes for one issue.** `363` (dispatch payload) vs `feat/363-route-post-merge` (`workflow_run` payload). Nothing evaluated from trigger payload alone can equate them, so the cross-surface case is unsolvable at workflow level by construction.
- **Post-merge branches in the trigger filter.** Under #363 a green `dev` is a no-op, not a ship. Treating CI conclusion alone as the ship signal turns every successful merge — the most frequent event in the repo — into ship-lane contention, and each such run displaces a pending ship.
- **No shared filesystem between cloud runs.** `.bkit/.dev.lock` and `docs/plans/*/logs/{FID}/.lock` are gitignored and created on a fresh runner per run; they arbitrate nothing between two cloud runs. There is no lock-based backstop to fall back on.

### Process Sketch

```
WHEN a run is a ship (dispatched phase=ship, or CI success on feat/** or fix/**) → THEN it holds the single repo-wide ship lane; a second ship waits without booting and never cancels the one in flight
WHEN a third ship arrives while one is already waiting → THEN the waiting one is displaced; its PR stays green, open and unshipped, and is identifiable from the Actions run list
WHEN a run resolves to issue N → THEN it holds the issue-N lane; any other cloud run for N waits, whichever payload shape carried the id
WHEN a waiting run finally starts → THEN it re-derives branch / PR / CI state and re-checks the merge target; a stale gate routes it back to re-validate instead of merging
WHEN CI goes green on dev or any other post-merge branch → THEN it is a no-op and never enters the ship lane
WHEN a run yields the issue lane instead of waiting → THEN it exits successfully with a stated reason and no bkit:failed label
```

### Two-lane model

Two orthogonal concurrency lanes on one workflow file. They are separable decisions and can land in either order.

**Lane 1 — phase lane (workflow-level `concurrency`). Closes Gap 1.**
Evaluated from trigger payload before any runner boots — cheap, and the only place that can stop a second ship from booting at all.

```yaml
concurrency:
  group: >-
    ${{ ( inputs.phase == 'ship'
          || ( github.event_name == 'workflow_run'
               && github.event.workflow_run.conclusion == 'success'
               && ( startsWith(github.event.workflow_run.head_branch, 'feat/')
                    || startsWith(github.event.workflow_run.head_branch, 'fix/') ) ) )
        && 'bkit-ship-global'
        || format('bkit-auto-{0}', inputs.issue || github.event.workflow_run.head_branch) }}
  cancel-in-progress: false
```

The discriminator is an **allowlist** of ship-routing branch prefixes, not a denylist. A denylist (`success && head_branch != 'dev'`) passes today's matrix and silently mis-routes the moment `main` returns — and `main` is explicitly parked as revisitable by #363. The allowlist is correct by construction against a branch filter that is still moving. `startsWith()` exists in GHA expressions; the "no expression can normalise the tokens" comment in the file is about `replace`/regex/split, and does not block prefix tests.

**Lane 2 — FID lane (job-level `concurrency` on a resolver output). Closes Gap 2.**
Evaluated after a step has run, so it can key on a value computed by real shell rather than by expression functions. This is the one path that closes the cross-payload-shape gap inside GHA.

```yaml
jobs:
  resolve: # no `concurrency:` block — it must never queue behind the jobs it gates
    outputs: { skip, phase, arg, issue, fid, lane }
  run: # claude
    needs: resolve
    concurrency: { group: "${{ needs.resolve.outputs.lane }}-claude", cancel-in-progress: false }
  opencode:
    needs: resolve
    concurrency: { group: "${{ needs.resolve.outputs.lane }}-opencode", cancel-in-progress: false }
```

`lane` is `bkit-fid-{FID}` on the normal path and `bkit-noop-{github.run_id}` whenever `skip=true`, so no-op and gated-out runs can never contend for a shared group (and the design does not have to rely on unverified behaviour of skipped jobs holding a group).

The per-agent suffix is deliberate: the two agent jobs are **additive by design** (both run when both secrets are set). Putting them in one group would convert a documented shipped contract into a queue with its own eviction hazard. The dual-agent same-FID collision is a real, pre-existing concern and is recorded as out of scope (§ Risks R-4).

Why the two lanes are complementary rather than redundant: the phase lane stops a second ship **before a runner boots** (cheap, but blind to payload shape); the FID lane stops a same-FID collision **after resolution** (correct, but costs one resolver job). A ship run sits in both — `bkit-ship-global` at run level and `bkit-fid-{FID}-{agent}` at job level — which is exactly requirement 1 and requirement 2 simultaneously.

Cell 7 is the cell the issue's proposed expression gets wrong, and it is the highest-frequency event in an active repo. Under the issue's discriminator it enters `bkit-ship-global`, occupies the ship slot, and — because arrival displaces the pending run — makes green-dev-CI events into ship-queue poison in a self-inflicted loop (ship A merges → dev CI goes green → the dev-success run displaces pending ship B → B never runs). **The allowlist discriminator eliminates this entire eviction source**, which is why it is the single highest-value line in the change.

Cell 7 still contends in `bkit-auto-dev` and can displace a pending dev-debug. That is intentional and must be written down as intentional: a later green `dev` means the earlier red `dev` was fixed, so the queued debug is moot.

### Boundaries and integration points

- **Shipped surface:** `.github/workflows/bkit-cloud.yml` is Tier-1 `byte-equal-text` and must stay byte-identical to `.bkit/templates/.github/workflows/bkit-cloud.yml`. Every change is a two-file change plus a mirror regeneration in the same commit.
- **Consumer blast radius:** install and upgrade force-overwrite this file. Consumers on older versions keep the old model until they upgrade; a consumer who hand-edited loses it silently. A postinstall advisory (precedent: the existing `bkit-cloud.yml` always-true-gate detector in `.bkit/src/bkit-postinstall.ts`) is the mitigation.
- **Permissions:** the current `permissions:` block grants `actions: read`, not `write`. Job-level concurrency needs nothing extra; the contingency probe (§ Components) needs only `actions: read`; any re-dispatch / baton / sweeper approach needs an `actions: write` bump and is therefore out of scope this cycle.
- **Landing order:** strictly after #363. Both edit the same four lines in a file where "take one side" is not a safe conflict resolution, and #363 is already at `bkit:build`.
- **Downstream:** #260 and #324 consume this as a _policy_ (routed phase → lane), not as an ad-hoc expression. The resolver job is the seam a third dispatch producer plugs into.

## Data Model

**No new persistent state surface.** No cache entry, no lock branch/ref, no label mutex, no new ledger file. Everything below is either an existing GHA-native value or an in-run output.

### Lane keys

| Key                         | Scope                      | Derived from                                            | Cardinality                                  |
| --------------------------- | -------------------------- | ------------------------------------------------------- | -------------------------------------------- |
| `bkit-ship-global`          | repo-wide                  | literal string, selected by the allowlist discriminator | 1                                            |
| `bkit-auto-{inputs.issue}`  | one dispatched issue       | `workflow_dispatch` payload                             | 1 per issue                                  |
| `bkit-auto-{head_branch}`   | one branch                 | `workflow_run` payload                                  | 1 per branch (incl. `bkit-auto-dev`)         |
| `bkit-fid-{FID}-{agent}`    | one issue x one agent lane | `resolve` job output                                    | 1 per (FID, agent)                           |
| `bkit-noop-{github.run_id}` | one run                    | `github.run_id`                                         | unique per run — deliberately non-contending |

`{FID}` is the canonical feature id already derived by the existing `shared-deriv` block: `bkit:fid=` / `bkit:issue=` markers in the PR body first, branch-name extraction as fallback, fail-safe no-op when neither resolves.

| Output  | Type                                   | Meaning                                                                                                         |
| ------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `skip`  | `'true'`/`'false'`                     | no work to do (non-terminal conclusion, no open PR, `bkit:auto` revoked, unresolvable FID, no agent secret set) |
| `phase` | `ship`/`debug`/`design`/`plan`/`build` | routed phase                                                                                                    |
| `arg`   | string                                 | PR number (ship/debug) or issue id (design/plan/build) — same sanitisation guard as today                       |
| `issue` | string                                 | tracker issue id                                                                                                |
| `fid`   | string                                 | canonical feature id                                                                                            |
| `lane`  | string                                 | `bkit-fid-{FID}` or `bkit-noop-{run_id}` — the job-level concurrency group                                      |

### Existing state, correctly scoped

| Artefact                                                                    | Scope it actually has                                      | Scope it does NOT have                                                                                           |
| --------------------------------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `.bkit/.dev.lock` (gitignored, `set -C`, 600s deadline)                     | one filesystem — LOCAL clone, persistent `CLOUD_CURSOR` VM | anything across two GHA runners                                                                                  |
| `docs/plans/{YYYYMM}/logs/{FID}/.lock` (gitignored, 30-min-idle stale rule) | same                                                       | same                                                                                                             |

Both file locks stay exactly as they are. They are not modified, demoted, or re-scoped by this change — the change is that the documentation stops claiming they arbitrate cloud runs.

### `resolve` job

- Runs before both agent jobs. Carries the same `bkit:start auto-route-gate` `if:` block so the free-tier gate still costs zero runner minutes.
- **No `concurrency:` block of its own** — a resolver inside the group it computes would deadlock behind the job it is meant to gate.
- No `actions/checkout`. The existing ctx logic uses only `gh pr list` / `gh pr view` / `gh issue view` and shell, so it does not need the repo. This keeps the added job cheap.
- First step checks whether _either_ agent secret is set; if neither, emits `skip=true` immediately so the "no secrets configured" path stays near-instant, as today.
- Permissions: `contents: read`, `issues: read`, `pull-requests: read`, `actions: read`.
- Emits a single `::notice::` naming the resolved phase, FID and lane. This is the diagnostic anchor: every run that boots leaves one line saying what it is and what it will contend for.

### Agent jobs (`run` / `opencode`)

- `needs: resolve`; `if:` keeps the existing secret gate and adds `needs.resolve.outputs.skip != 'true'`.
- Job-level `concurrency: { group: '${{ needs.resolve.outputs.lane }}-{agent}', cancel-in-progress: false }`.
- The duplicated `Resolve phase + brief context` step and its `bkit:start shared-deriv` block collapse into `resolve` — roughly 55 duplicated lines and their standing drift risk disappear. The `shared-deriv` / `auto-route-gate` marker blocks move with the code, and the marker-presence tests must follow them.
- The `/bkit-auto <phase> <arg>` dispatch prompt is unchanged; `arg` now comes from `needs.resolve.outputs.arg`. The existing `^[0-9A-Za-z._/-]+$` sanitisation guard moves into `resolve` and must not be dropped (prompt-injection guard).

### Contingency flow — if job-level `concurrency` cannot read `needs`

The `resolve` job exists in both variants; only what consumes its output changes.

- **Primary (job-level group):** GHA queues the second same-FID job natively. Requirement 5's "visible with a reason" is free.
- **Contingency (in-run yield):** `resolve` additionally queries `gh api /repos/{owner}/{repo}/actions/workflows/bkit-cloud.yml/runs?status=in_progress`, extracts each peer's FID from `head_branch` + `display_title` (the existing `run-name` already renders `bkit auto ship(363)`), and if a peer with the same FID and a **lower run id** exists, emits `skip=true` + `::notice::` and exits 0. Lowest-run-id-wins is a deterministic tiebreak read from shared state, so two simultaneous checks can never both yield (deadlock) nor both proceed (race). An unparseable peer is treated as "no collision" — fail-open, preserving today's behaviour. Needs only the already-granted `actions: read`.
- The contingency **yields rather than queues**, so it satisfies requirement 2's "does not boot-then-fail" but not its "queues". If the contingency is taken, requirement 2 must be recorded as partially met.

### Test rewrite (T3.1)

Today two tests locate the group by `line.includes("group: bkit-auto-")` and assert one line contains both `inputs.issue` and `head_branch`. A folded `>-` group expression makes that line vanish and both tests fail on a _correct_ change. The tests encode a formatting assumption as an expectation and must follow the change, not constrain it:

- Assert **rendered semantics** by parsing the YAML (a YAML parser is not currently a dependency of `.bkit/src`; adding one as a devDependency is the doctrine-aligned move — validate shipped config with a real parser, not string presence), not by line-shape.
- Assert the routing **matrix**: for each cell of the table above, the group expression selects the stated lane. This is the test that stops the discriminator drifting away from the ctx-step routing `case`.
- Keep the byte-equality test between the canonical and the rendered template unchanged.
- `actionlint` (already in `package.json`) is the real-tool validator for the expression syntax itself — including operator precedence in the `&&`/`||` ternary idiom, where the ship condition must be parenthesised as one group because `&&` binds tighter than `||`.

| ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

The allowlist is correct by construction against a branch filter that is still moving.                                                                                                                                                                                  |

## Trade-offs Accepted

**Gained**

- Ship becomes genuinely capacity-1 repo-wide before a second runner boots, replacing an unserialised concurrent-merge race whose only backstop was a server-side head check.
- The cross-payload-shape same-FID collision is closed inside GHA for the first time — it has never been arbitrated in the cloud, in either direction.
- The highest-frequency mis-routing (green `dev` into the ship lane) is eliminated by construction, and stays eliminated when `main` returns.
- No agent is ever cancelled mid-flight, so no run ends with a stuck `bkit:shipping` label, a missing close row, or a missing `outcome` telemetry row.
- ~55 lines of duplicated `shared-deriv` collapse to one implementation, removing a standing drift risk that predates this issue.
- No new state surface, no new lock protocol, no new file to garbage-collect, no leaked-lock recovery problem.

**Sacrificed vs the alternatives**

- **vs the reconciler/sweeper approach:** requirement 1 is met for N=2 only. A third concurrent ship displaces the pending second, and the displaced run never executes a step so it cannot report anything. Recovery is a manual `/bkit-ship` re-dispatch, findable but not automatic. Accepted because the allowlist discriminator removes the dominant eviction source, leaving only genuinely-concurrent triple ships, and because the automated fix needs `actions: write` plus a capped sweeper that belongs to #260's substrate.
- **vs the router/executor split:** the lane policy stays encoded in a YAML expression plus a shell resolver rather than in one normalised dispatch surface. Each new _policy_ (e.g. "audit runs never collide with ship") means editing the expression again. Accepted on YAGNI: two of the three future producers do not exist yet.
- **vs the external CAS lock:** the primary shape depends on a platform behaviour that must be verified before the plan commits (§ Risks R-2). Accepted because the contingency is fully specified and cheap.
- **Throughput:** capacity-1 ship is the _stated target_, but a queued ship that dequeues will need `update-branch` and a fresh CI cycle before its gate passes. Serialising ships converts a merge race into a serial CI-cycle chain, which becomes the practical throughput ceiling of the whole pipeline at multi-FID scale. Accepted deliberately rather than discovered in production.
- **Cost:** one extra job per admitted event (`gh` calls only, no checkout) plus GitHub's per-job billing minimum. Accepted for the duplication it deletes and the log line it guarantees.
- **Scope:** the dual-agent double-ship (both secrets set → two agents on one PR) is left exactly as today. This design does not make it worse, and does not fix it.
- **Consumer churn:** a Tier-1 force-overwrite of `bkit-cloud.yml` that consumers cannot see the benefit of, and that silently destroys any hand-edit. Mitigated by a postinstall advisory, not eliminated.

### Risks

- **R-1 — The GHA queue is depth 1 and lossy.** With three concurrent ships, the middle one is displaced, its PR stays green and merge-ready, and it never ships. The displaced run executes no step, so no bkit-authored notice, comment, label or ledger row can exist for it — nothing in `status.jsonl` records "I was evicted". Detection is an after-the-fact Actions API query (a `bkit-cloud` run with `conclusion: cancelled` and zero started jobs, whose `run-name` names the phase and issue). **Mitigations layered on:** the allowlist discriminator removes the dominant eviction source; `.bkit/cloud.md` must carry the eviction hypothesis and the recovery query so a 3am page has something to test; a capped reconciler is deferred to a follow-up.
- **R-2 — Double queuing.** A ship run can be pending at workflow level _and_, once started, pending again at job level. Two eviction surfaces per run, not one. Needs an explicit look during Plan for whether the job-level lane should be skipped for ship-lane runs.
- **R-3 — Discriminator/routing drift.** The allowlist branch-prefix set in the group expression and the routing `case` in the resolver are two encodings of one truth, with nothing binding them. The branch filter has already moved twice in #363 and `main` is parked as a scheduled future change to exactly this input. When someone adds `hotfix/**`, the allowlist quietly declines to treat it as a ship and the cell falls into a _plausible-looking_ `bkit-auto-hotfix/...` group — the bug looks like correct behaviour. **Mitigation:** the matrix test in T3.1 must parse both out of the YAML and assert set-equality; a comment alone is not enough.
- **R-4 — Dual-agent same-run double-ship.** With both secrets set, one run launches two agents that both dispatch `/bkit-auto ship` against the same PR. Workflow-level concurrency cannot separate them by construction. The header documents this as additive by design; it is simultaneously an unarbitrated same-FID collision. Pre-existing, not introduced here, deliberately not changed here, deferred.
- **R-5 — Knowledge concentration.** Four non-obvious facts become load-bearing: the depth-1 eviction semantics, the `needs`-in-job-`concurrency` capability, why the discriminator is an allowlist and not a denylist, and why the resolver exists at all. The last is the sharpest: the file's own long comment says cross-surface normalisation is impossible, so a future reader will "simplify" the resolver away and silently reintroduce Gap 2. **Mitigation:** the comment must be rewritten to say _impossible at workflow level, which is why the resolver exists_, and a test must fail on the resolver's removal.
- **R-6 — Shipped-surface blast radius.** Tier-1 byte-equal, force-overwritten by install and upgrade. Consumers on older versions keep the old model; hand-edits are destroyed with no merge and no prompt. Advisory is the mitigation, not a fix.
- **R-7 — Test coupling.** A folded multi-line `group:` breaks two string-matching tests on a correct change, and the byte-equality test fails unless the canonical mirror is regenerated in the same commit. Cheap if anticipated, confusing if not.
- **R-8 — Adjacent defect discovered, out of scope.** `.bkit/workflows/bkit-ship.md` runs `gh workflow run ci.yml`, which requires `actions: write`; the cloud jobs grant `actions: read`, so that call is a 403 under the cloud token today. Not this issue's remit — route to `docs/failures.jsonl` during Plan rather than folding it in.

### Open questions for the Plan phase

1. Should ship-lane runs skip the job-level FID lane to avoid double queuing (R-2), or is same-FID exclusion for ships worth the second eviction surface?
2. Does the resolver's `::notice::` need to become a durable row (e.g. a `status.jsonl` append), or is the Actions run record sufficient evidence for the recovery query? A durable row means a cloud run writing to `dev` per event — noisy, and the run record already carries the same facts.
3. Which YAML parser dependency for the matrix test, and does adding a devDependency to `.bkit/src` conflict with the packed-tarball dogfood discipline?
4. Does the postinstall advisory check the concurrency block's _semantics_ (parsed) or its _presence_ (string)? Precedent in `bkit-postinstall.ts` is string-based; semantics is the doctrine-aligned choice.
5. Confirm #363's final landed shape at rebase time — its plan v4 is the baseline, but `main` inclusion and the `cancel-in-progress` expression are both explicitly still moving.
