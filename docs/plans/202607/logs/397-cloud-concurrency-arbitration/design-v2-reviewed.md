## Acceptance Scenario

### Narrative

As a maintainer running several `bkit:auto` issues in parallel, I want the cloud router to run at most one ship at a time across the whole repo, and never let two cloud sessions work the same issue at once — so two agents never race on one branch and a merge never lands against a `dev` that moved underneath it. When my work has to wait its turn I want to see it waiting in the Actions list rather than watch it boot and burn minutes. When it is displaced instead of queued, I want to be able to find it, not discover weeks later that a green PR quietly never merged.

### Success Criteria

1. At most one cloud run executes a ship repo-wide at any moment; every other concurrent ship waits without booting, and none cancels another. Under the adopted `concurrency.queue: max` arm this holds for **all N up to 100 pending, FIFO**; under the deferred arm (`queue` key absent → GHA default `single`) it holds for N=2 only and the middle ship is displaced (§ Decisions, § Risks R-1).
2. A dispatched run for issue N and a CI-triggered run for issue N never execute concurrently, whichever payload shape carried the id.
3. Green CI on a post-merge branch (`dev` today, `main` if re-added) never enters the ship lane and never displaces a waiting ship.
4. Per-FID isolation for design / plan / build and `feat/**` / `fix/**` debug is preserved, and no run is cancelled mid-flight by a newer arrival.
5. Every wait, yield or displacement is identifiable from the GitHub Actions run list alone; a run that yields or is displaced never produces a `bkit:failed` label.

### Key Edge Cases

- **Three or more concurrent ships.** Behaviour depends on `concurrency.queue`, which is a **choice, not a platform limit** (V-2). Under the GHA default `queue: single` GHA holds exactly one pending run per group and a third arrival displaces the pending second: that PR stays green, open and merge-ready but never ships, the displaced run never executes a step so it cannot report anything, **and its tracker issue is left carrying whatever prior-phase label it already had** — no `bkit:failed`, no `bkit:shipping`, nothing that says a ship attempt was lost. Under `queue: max` (up to 100 pending, FIFO, at both workflow and job level) the third ship simply waits its turn and the whole class disappears.
- **A ship pending at job level while holding the global lane.** A ship run occupies `bkit-ship-global` at workflow level for its entire wall-clock duration — including time its agent job spends _pending_ on `bkit-fid-{N}-{agent}` behind an unrelated long-running dispatched phase for the same FID. The ship lane is therefore held by a run that is executing nothing. This is the one interaction where the two lanes make each other worse; see § Risks R-9.
- **Both agent secrets set.** One run launches the `claude` and `opencode` jobs on the same PR. Workflow-level concurrency cannot separate them — they are one run. A ship-global lane therefore delivers "one ship **run** at a time", not "one ship **agent** at a time".
- **A waiting ship dequeues onto a moved `dev`.** Its PR is behind and its green CI is stale; it must re-derive branch/PR/CI state and re-gate at merge time rather than merge on trust.
- **Two id shapes for one issue.** `363` (dispatch payload) vs `feat/363-route-post-merge` (`workflow_run` payload). Nothing evaluated from trigger payload alone can equate them, so the cross-surface case is unsolvable at workflow level by construction.
- **Post-merge branches in the trigger filter.** Under #363 a green `dev` is a no-op, not a ship. Treating CI conclusion alone as the ship signal turns every successful merge — the most frequent event in the repo — into ship-lane contention, and each such run displaces a pending ship.
- **No shared filesystem between cloud runs.** `.bkit/.dev.lock` and `docs/plans/*/logs/{FID}/.lock` are gitignored and created on a fresh runner per run; they arbitrate nothing between two cloud runs. There is no lock-based backstop to fall back on.

### Process Sketch

```
WHEN a run is a ship (dispatched phase=ship, or CI success on feat/** or fix/**) → THEN it holds the single repo-wide ship lane; a second ship waits without booting and never cancels the one in flight
WHEN a third ship arrives while one is already waiting → THEN under `queue: max` it joins the FIFO queue and eventually runs; under the deferred `queue: single` arm the waiting one is displaced, its PR stays green, open and unshipped, and is identifiable only from the Actions run list
WHEN a run resolves to issue N → THEN it holds the issue-N lane; any other cloud run for N waits, whichever payload shape carried the id
WHEN a waiting run finally starts → THEN it re-derives branch / PR / CI state and re-checks the merge target; a stale gate routes it back to re-validate instead of merging
WHEN CI goes green on dev or any other post-merge branch → THEN it is a no-op and never enters the ship lane
WHEN a run yields the issue lane instead of waiting → THEN it exits successfully with a stated reason and no bkit:failed label
```

### Two-lane model

Two orthogonal concurrency lanes on one workflow file. They are separable decisions and can land in either order.

**Lane 1 — phase lane (workflow-level `concurrency`). Closes Gap 1.**
Evaluated from trigger payload before any runner boots — cheap, and the only place that can stop a second ship from booting at all.

```yaml
concurrency:
  group: >-
    ${{ ( inputs.phase == 'ship'
          || ( github.event_name == 'workflow_run'
               && github.event.workflow_run.conclusion == 'success'
               && ( startsWith(github.event.workflow_run.head_branch, 'feat/')
                    || startsWith(github.event.workflow_run.head_branch, 'fix/') ) ) )
        && 'bkit-ship-global'
        || format('bkit-auto-{0}', inputs.issue || github.event.workflow_run.head_branch) }}
  cancel-in-progress: false
  queue: max # gated on the actionlint decision — see § Decisions; omitted under the deferred arm
```

The whole expression is verified valid: run verbatim through actionlint 1.7.12 (the version `ci.yml:399` downloads) inside a workflow carrying `workflow_run` (`branches: ['feat/**','fix/**','dev']`) plus `workflow_dispatch` → exit 0. The `&&`/`||` ternary parenthesisation is accepted, `startsWith()` is a valid GHA function, and `inputs.phase` is accepted in a `concurrency` block on a workflow whose `inputs` are populated for only one of its two triggers — a behaviour the shipped file already relies on in production (`run-name` at `.bkit/templates/.github/workflows/bkit-cloud.yml:53-56` uses the same `inputs.phase && … || …` fall-through). `github.event.workflow_run.*` being null on dispatch is guarded twice: the `github.event_name == 'workflow_run'` conjunct short-circuits, and GHA coerces null to `''` for `startsWith`.

The discriminator is an **allowlist** of ship-routing branch prefixes, not a denylist. A denylist (`success && head_branch != 'dev'`) passes today's matrix and silently mis-routes the moment `main` returns — and `main` is explicitly parked as revisitable by #363. The allowlist is correct by construction against a branch filter that is still moving. `startsWith()` exists in GHA expressions; the "no expression can normalise the tokens" comment in the file is about `replace`/regex/split, and does not block prefix tests.

**The allowlist is also the design's consumer-visible limit, and it fails _silently_.** A consumer whose branch convention is not `feat/**` / `fix/**` (say `feature/**`, `story/**`, or ticket-id branches) keeps working with no error — their CI-triggered ship traffic simply falls through the ternary into the per-branch `bkit-auto-{head_branch}` group and **never acquires `bkit-ship-global` at all**, so they lose the entire repo-wide ship-exclusivity guarantee this design exists to deliver, for an unknown fraction of the consumer base, with no way to discover it short of reading the group expression. This is not acceptable as an invisible limitation; it is acceptable as a documented one. Two mitigations, both in scope this cycle: (a) an explicit callout in `.bkit/cloud.md` naming the exact prefixes the guarantee depends on and what to change if a repo uses others, and (b) extending the planned `bkit-postinstall.ts` advisory to flag an installed `bkit-cloud.yml` whose ship-lane prefixes do not match the consumer's observed branch naming. (a) is mandatory; (b) is the stronger form and is preferred if the advisory is parsed rather than string-matched (§ Open questions 4).

**Lane 2 — FID lane (job-level `concurrency` on a resolver output). Closes Gap 2.**
Evaluated after a step has run, so it can key on a value computed by real shell rather than by expression functions. This is the one path that closes the cross-payload-shape gap inside GHA.

```yaml
jobs:
  resolve: # no `concurrency:` block — it must never queue behind the jobs it gates
    env: { GH_REPO: "${{ github.repository }}" } # MANDATORY — no checkout, see § resolve job
    outputs: { skip, phase, arg, issue, fid, lane }
  run: # claude
    needs: resolve
    concurrency:
      { group: "${{ needs.resolve.outputs.lane }}-claude", cancel-in-progress: false, queue: max }
  opencode:
    needs: resolve
    concurrency:
      { group: "${{ needs.resolve.outputs.lane }}-opencode", cancel-in-progress: false, queue: max }
```

**V-1 — that job-level `concurrency.group` may read `needs` — is VERIFIED, not inferred**, from two independent sources: GitHub's context-availability table (`jobs.<job_id>.concurrency` → `github, needs, strategy, matrix, inputs, vars`, versus workflow-level `concurrency` → `github, inputs, vars`), and the repo's own pinned validator. actionlint 1.7.12 was probed on a scratch workflow shaped exactly like this block: `needs.resolve.outputs.lane` inside `jobs.run.concurrency.group` → exit 0; the same expression at workflow level → `context "needs" is not allowed here. available contexts are "github", "inputs", "vars"`; and a deliberate typo (`…outputs.laneTYPO`) at job level → `property "lanetypo" is not defined in object type {lane: string; skip: string}`. The negative control proves the checker is active for this key, and the typo control proves it is type-resolving the `resolve` job's declared outputs rather than merely tolerating the string. Lane 2 stands on verified ground; the peer-run-probe contingency this design previously carried is retired (§ Recorded alternative).

`lane` is `bkit-fid-{FID}` on the normal path and `bkit-noop-{github.run_id}` whenever `skip=true`, so no-op and gated-out runs can never contend for a shared group (and the design does not have to rely on unverified behaviour of skipped jobs holding a group).

The per-agent suffix is deliberate: the two agent jobs are **additive by design** (both run when both secrets are set). Putting them in one group would convert a documented shipped contract into a queue with its own eviction hazard. The dual-agent same-FID collision is a real, pre-existing concern and is recorded as out of scope (§ Risks R-4).

Why the two lanes are complementary rather than redundant: the phase lane stops a second ship **before a runner boots** (cheap, but blind to payload shape); the FID lane stops a same-FID collision **after resolution** (correct, but costs one resolver job). A ship run sits in both — `bkit-ship-global` at run level and `bkit-fid-{FID}-{agent}` at job level — which is exactly requirement 1 and requirement 2 simultaneously.

**Where the two lanes make each other worse (answered, not deferred).** Because a run holds its workflow-level group for its whole wall-clock life, a ship whose agent job is _pending_ on `bkit-fid-{N}-{agent}` keeps `bkit-ship-global` occupied while executing nothing — head-of-line blocking of the repo-global lane by an unrelated FID's long-running phase. Open question 1 asked whether ship-lane runs should therefore skip the FID lane. **Decision: they must not.** Skipping it reopens Gap 2 for precisely the pair the issue names (a CI-triggered ship for N racing a dispatched phase for N), which is requirement 2's entire content. The stall is accepted and documented instead (§ Risks R-9); it is bounded by the blocking run's own workflow timeout, and under `queue: max` its cost is pure latency — under the deferred `queue: single` arm it is additionally an eviction hazard, because ships arriving during the stall cancel-replace each other in the pending slot.

Cell 7 is the cell the issue's proposed expression gets wrong, and it is the highest-frequency event in an active repo. Under the issue's discriminator it enters `bkit-ship-global`, occupies the ship slot, and — because arrival displaces the pending run — makes green-dev-CI events into ship-queue poison in a self-inflicted loop (ship A merges → dev CI goes green → the dev-success run displaces pending ship B → B never runs). **The allowlist discriminator eliminates this entire eviction source**, which is why it is the single highest-value line in the change.

Cell 7 still contends in `bkit-auto-dev`. Under the deferred `queue: single` arm it can displace a pending dev-debug, and that displacement is intentional and must be written down as intentional: a later green `dev` means the earlier red `dev` was fixed, so the queued debug is moot. **Under `queue: max` the displacement does not happen** — the dev-debug waits and then boots onto a now-green `dev`, where its own Step 1 re-derivation finds nothing to fix and it exits as a no-op. That is a slightly wasteful but strictly safe outcome, and it is the arm the design prefers; the "intentional displacement" reasoning survives only as the rationale for the deferred arm, not as a standing design property.

### Boundaries and integration points

- **Shipped surface:** `.github/workflows/bkit-cloud.yml` is Tier-1 `byte-equal-text` (registered at `bkit-manifest.ts:344` and `:350`, in both `CLOUD_MANIFEST_CLAUDE` and `CLOUD_MANIFEST_OPENCODE`). **The two files are NOT byte-identical and must not be made so** — the template carries `runs-on: {{CLOUD_RUNNER}}` where the canonical carries `runs-on: ubuntu-latest` (19529 vs 19523 bytes). The enforced invariant is **render-then-compare**: `bkit-modules.integration.test.ts:1133-1146` asserts `canonical === renderCloudWorkflow(rawTemplate, "github").replace(/\{\{CLOUD_RUNNER\}\}/g, "ubuntu-latest")`. A builder acting on "byte-identical" would try to equalise the files and destroy the `{{CLOUD_RUNNER}}` token (#362). Every change is still a two-file change plus a mirror regeneration in the same commit — the comparison is just render-then-compare, not `diff`.
- **Consumer blast radius:** install and upgrade force-overwrite this file. Consumers on older versions keep the old model until they upgrade; a consumer who hand-edited loses it silently. A postinstall advisory (precedent: the existing `bkit-cloud.yml` always-true-gate detector in `.bkit/src/bkit-postinstall.ts:361-395`) is the mitigation. **Second, distinct blast radius:** consumers whose branch convention is not `feat/**` / `fix/**` lose the `bkit-ship-global` guarantee entirely and silently (§ Two-lane model, Lane 1). That needs its own doc callout, and preferably its own advisory clause — it is not covered by the drift detector, which compares against the shipped contract and would see a correctly-shipped file.
- **Permissions:** there is **no workflow-level `permissions:` block** — permissions are declared per job (`run`: `contents: write, pull-requests: write, issues: write, actions: read, id-token: write`; `opencode`: the same minus `id-token`). The new `resolve` job therefore inherits nothing and must declare its own. Job-level concurrency needs no extra scope; any re-dispatch / baton / sweeper approach needs an `actions: write` bump and is therefore out of scope this cycle.
- **Landing order:** strictly after #363. Both edit the same four lines in a file where "take one side" is not a safe conflict resolution, and #363 is already at `bkit:build`. **Stall fallback (the wait is currently unbounded):** #363's plan v4 is committed to `dev`, but branch `feat/363-widen-bkit-cloud-trigger` carries only worktree-setup / branch-sync / install-skills commits — **no workflow edits yet** — and has no open PR. If #363 has not opened a PR by the time #397 reaches Build, #397 rebases onto whatever is on `dev` and ships against the **current** trigger filter (`branches: ['feat/**']` only, `bkit-cloud.yml:31`), which the allowlist discriminator already handles correctly — `dev` simply never reaches the workflow, so cell 7 and cell 8 are unreachable rather than mis-routed. #397 must not widen the trigger filter itself; that stays #363's change.
- **Downstream:** #260 and #324 consume this as a _policy_ (routed phase → lane), not as an ad-hoc expression. The resolver job is the seam a third dispatch producer plugs into.

## Data Model

**No new persistent state surface.** No cache entry, no lock branch/ref, no label mutex, no new ledger file. Everything below is either an existing GHA-native value or an in-run output.

### Lane keys

| Key                         | Scope                      | Derived from                                            | Cardinality                                  |
| --------------------------- | -------------------------- | ------------------------------------------------------- | -------------------------------------------- |
| `bkit-ship-global`          | repo-wide                  | literal string, selected by the allowlist discriminator | 1                                            |
| `bkit-auto-{inputs.issue}`  | one dispatched issue       | `workflow_dispatch` payload                             | 1 per issue                                  |
| `bkit-auto-{head_branch}`   | one branch                 | `workflow_run` payload                                  | 1 per branch (incl. `bkit-auto-dev`)         |
| `bkit-fid-{FID}-{agent}`    | one issue x one agent lane | `resolve` job output                                    | 1 per (FID, agent)                           |
| `bkit-noop-{github.run_id}` | one run                    | `github.run_id`                                         | unique per run — deliberately non-contending |

`{FID}` is the canonical feature id already derived by the existing `shared-deriv` block: `bkit:fid=` / `bkit:issue=` markers in the PR body first, branch-name extraction as fallback, fail-safe no-op when neither resolves.

### `resolve` job output contract

| Output  | Type                                   | Meaning                                                                                                         |

### `resolve` job

- Runs before both agent jobs, and **must be emitted before them in the file** — see the ordering invariant below.
- Carries the same `bkit:start auto-route-gate` `if:` block so the free-tier gate still costs zero runner minutes.
- **No `concurrency:` block of its own** — a resolver inside the group it computes would deadlock behind the job it is meant to gate.
- No `actions/checkout` — the ctx logic uses only `gh pr list` / `gh pr view` / `gh issue view` and shell. **But "no checkout" alone breaks it:** `gh pr list` in a non-git directory fails with `failed to run git: fatal: not a git repository`, and `gh` recovers only from a git remote, an explicit `-R`, or `GH_REPO`. The job **must** therefore set `env: { GH_REPO: '${{ github.repository }}' }` alongside the existing `GH_TOKEN`. Verified both ways by direct probe: bare `gh pr list` fails in a non-repo directory; `GH_REPO=<owner>/<repo> gh pr list` returns results with no checkout. Without this line the resolver dies at its first `gh` call on **every** run and both lanes are inert.
- First step checks whether _either_ agent secret is set; if neither, emits `skip=true` immediately so the "no secrets configured" path stays near-instant, as today.
- Permissions: declared on the job (there is no workflow-level block to inherit from): `contents: read`, `issues: read`, `pull-requests: read`, `actions: read`.
- Emits a single `::notice::` naming the resolved phase, FID and lane. This is the diagnostic anchor: every run that boots leaves one line saying what it is and what it will contend for.
- **Ordering invariant (new, and currently only satisfied by luck):** the surviving marker-block tests T2.7 (c) (`bkit-modules.integration.test.ts:1195-1232`) and Challenge Finding 1 (`:2279`, tests at `:2321/:2326/:2331/:2383`) use `indexOf` — the **first** `# bkit:start shared-deriv` / `auto-route-gate` pair in the file. After the refactor that first pair lives in `resolve`. The layout must assert this ordering rather than inherit it: `resolve` is emitted first and still carries the `auto-route-gate` marker around its `if:` and the `shared-deriv` marker around the relocated derivation.

### Runbook deliverables — `.bkit/cloud.md`, same cycle, not deferred

These are build deliverables with acceptance criteria, not documentation intentions. The eviction failure mode is the only CRITICAL-severity outcome in this design with **zero** automated signal, and "documented in `cloud.md`" is not a runbook until it is a command a 3am reader can paste.

1. **Eviction recovery, verbatim command.** Under the deferred `queue: single` arm, the recovery path for a lost ship must be a literal invocation, e.g. the shape `gh run list --workflow bkit-cloud.yml --status cancelled --json databaseId,displayTitle,headBranch,createdAt` followed by a per-run job check (`gh run view <id> --json jobs`) to confirm **zero started jobs** — that pair is the eviction signature. Alongside it: what to do next (re-dispatch `/bkit-ship` for the named PR) and the explicit warning that under sustained load the re-dispatch can itself be evicted. The exact flags are a Build-time detail; the acceptance criterion is that the doc contains a runnable command, not a description of one.
2. **The tracker-state consequence, stated plainly.** An evicted run never executes a step, so it applies no label and writes no `status.jsonl` row — the tracker issue is left carrying whatever **prior-phase** label it already had. There is no `bkit:failed`, no `bkit:shipping`, nothing anomalous to notice. This is arguably worse than today's behaviour, where a cancelled mid-flight run at least leaves an explicit-but-wrong stuck label that a human eventually queries. The doc must say so, because "the tracker looks fine" is exactly the observation that ends an investigation early.
3. **Waiting vs hung vs evicted triage, with a threshold.** `queued` = waiting (normal, self-resolving); `in_progress` past its expected duration = hung (bounded by the workflow's own 3600s timeout, nothing pages); `cancelled` **with zero started jobs** = evicted. The dangerous read is the third: `cancelled` looks routine — a human cancel, a redeployed workflow file, a GHA-side infra cancel — but for this one shape it means "nobody will retry this," and nothing re-fires CI on an already-green unchanged PR. Include a concrete queued-duration trigger ("if a dispatched ship shows `queued` for more than N minutes, check whether the running ship has exceeded its own internal timeout") so on-call has an actionable threshold rather than intuition.
4. **The branch-prefix callout.** Name the exact prefixes (`feat/**`, `fix/**`) the `bkit-ship-global` guarantee depends on, state that other conventions fall through to the per-branch group and get **no** repo-wide ship exclusivity, and say what to change. A consumer auditing their own setup must be able to self-diagnose (§ Two-lane model, Lane 1).

**Under the adopted `queue: max` arm, items 1 and 2 shrink to a historical note** — there is no eviction to recover from — but items 3 and 4 stand regardless, and item 1's command remains useful for any cancellation. If the `queue` arm is deferred, all four are mandatory before Build closes.

### Recorded alternative (not active) — in-run peer-run probe

Retained as a documented alternative, not as a live contingency: **V-1 is verified** (§ Two-lane model), so the pivot this branch existed to cover cannot be triggered by the capability question. Kept because it is the cheapest known mechanism if the job-level lane ever has to be withdrawn, and because its machinery is reused by one conditional deliverable below.

- **Shape:** `resolve` queries `gh api /repos/{owner}/{repo}/actions/workflows/bkit-cloud.yml/runs?status=in_progress`, extracts each peer's FID from `head_branch` + `display_title` (the existing `run-name` already renders `bkit auto ship(363)`), and if a peer with the same FID and a **lower run id** exists, emits `skip=true` + `::notice::` and exits 0. Lowest-run-id-wins is a deterministic tiebreak read from shared state, so two simultaneous checks can never both yield (deadlock) nor both proceed (race). An unparseable peer is treated as "no collision" — fail-open. Needs only the already-granted `actions: read`.
- **Why it is not the primary:** it **yields rather than queues**, so the losing work never happens; it would satisfy requirement 2's "does not boot-then-fail" but not its "queues".
- **One conditional use survives:** if the `queue: max` arm is deferred, the same read-only Actions-API call in `resolve` can additionally look for a recent same-lane run with `conclusion: cancelled` and zero started jobs and surface it in its own `::notice::` — turning a silent eviction into "surfaced on the next run that boots for this repo," at zero new permissions cost. Under the adopted `queue: max` arm this is unnecessary and must not be built; there is nothing to surface.

## Trade-offs Accepted

**Gained**

- Ship becomes genuinely capacity-1 repo-wide before a second runner boots, replacing an unserialised concurrent-merge race whose only backstop was a server-side head check.
- The cross-payload-shape same-FID collision is closed inside GHA for the first time — it has never been arbitrated in the cloud, in either direction.
- The highest-frequency mis-routing (green `dev` into the ship lane) is eliminated by construction, and stays eliminated when `main` returns.
- No agent is ever cancelled mid-flight, so no run ends with a stuck `bkit:shipping` label, a missing close row, or a missing `outcome` telemetry row.
- ~55 lines of duplicated `shared-deriv` collapse to one implementation, removing a standing drift risk that predates this issue.
- No new state surface, no new lock protocol, no new file to garbage-collect, no leaked-lock recovery problem.
- Every booting run leaves exactly one `::notice::` naming phase / FID / lane — a single anchor line that today's duplicated per-job ctx steps do not provide, and the fastest way during incident review to answer "which lane did this run occupy".
- Under the adopted `queue: max` arm: no ship is ever lost to eviction, at any N up to 100, without a reconciler, an `actions: write` bump or any new state surface.

**Sacrificed vs the alternatives**

- **vs the reconciler/sweeper approach:** only under the deferred `queue` arm — there, requirement 1 is met for N=2 only, a third concurrent ship displaces the pending second, the displaced run never executes a step so it cannot report anything, and its tracker issue keeps a stale prior-phase label. Recovery is a manual `/bkit-ship` re-dispatch, findable but not automatic. Accepted because the allowlist discriminator removes the dominant eviction source, because the four runbook deliverables make it findable, and because the automated fix needs `actions: write` plus a capped sweeper that belongs to #260's substrate. Under the adopted arm this sacrifice does not apply.
- **vs the router/executor split:** the lane policy stays encoded in a YAML expression plus a shell resolver rather than in one normalised dispatch surface. Each new _policy_ (e.g. "audit runs never collide with ship") means editing the expression again. Accepted on YAGNI: two of the three future producers do not exist yet.
- **vs the external CAS lock:** the primary shape depends on GHA platform behaviour rather than on state the repo owns. Accepted, and the dependence is now **verified rather than assumed** — job-level `concurrency` reading `needs` is confirmed by GitHub's context table and by the pinned actionlint's type-checker (V-1), and `queue` semantics are confirmed from the workflow-syntax reference (V-2).
- **Liveness:** a ship can hold `bkit-ship-global` while its own agent job is pending on the FID lane, blocking unrelated ships for the duration of an unrelated same-FID phase (§ Risks R-9). Accepted rather than engineered around, because the alternative reopens Gap 2.
- **Consumer reach:** the ship-global guarantee only applies to repos using `feat/**` / `fix/**` branches. Accepted as a documented limitation (§ Two-lane model, § Runbook deliverables item 4), not as an invisible one.
- **Throughput:** capacity-1 ship is the _stated target_, but a queued ship that dequeues will need `update-branch` and a fresh CI cycle before its gate passes. Serialising ships converts a merge race into a serial CI-cycle chain, which becomes the practical throughput ceiling of the whole pipeline at multi-FID scale. Accepted deliberately rather than discovered in production.
- **Cost:** one extra job per admitted event (`gh` calls only, no checkout) plus GitHub's per-job billing minimum. Accepted for the duplication it deletes and the log line it guarantees.
- **Scope:** the dual-agent double-ship (both secrets set → two agents on one PR) is left exactly as today. This design does not make it worse, and does not fix it.
- **Consumer churn:** a Tier-1 force-overwrite of `bkit-cloud.yml` that consumers cannot see the benefit of, and that silently destroys any hand-edit. Mitigated by a postinstall advisory, not eliminated.
- **Alerting:** nothing here pages. Every signal is pull-based — the state of a run in the Actions UI plus a runbook. That matches bkit's stated observability scope (`docs/observability.md`: no server-side telemetry pipeline, log drains or tracing) and is a low-noise, low-detectability trade. It is accepted explicitly rather than left implicit, because the one failure mode with CRITICAL severity under the deferred arm (eviction) also has zero automated signal.

### Risks

- **R-1 — Eviction under the deferred `queue` arm (does not apply under `queue: max`).** With `queue: single`, three concurrent ships displace the middle one: its PR stays green and merge-ready and never ships. The displaced run executes no step, so no bkit-authored notice, comment, label or ledger row can exist for it — nothing in `status.jsonl` records "I was evicted", **and the tracker issue is left on whatever prior-phase label it already carried**, so the tracker looks unremarkable rather than wrong. That is arguably worse than today's failure shape, where a mid-flight cancel at least leaves an explicit-but-incorrect stuck label that eventually gets queried. Detection is an after-the-fact Actions API query (a `bkit-cloud` run with `conclusion: cancelled` and **zero started jobs**, whose `run-name` names the phase and issue), and `cancelled` is visually indistinguishable from a human cancel, a redeployed workflow file, or a GHA-side infra cancel. **Mitigations, in order:** adopt `queue: max` and the whole risk disappears; failing that, the allowlist discriminator removes the dominant eviction source, the four § Runbook deliverables make the residue findable with a real command rather than a paraphrase, and the recorded alternative's next-run breadcrumb probe turns "silent" into "surfaced on the next run that boots". A capped reconciler stays deferred to #260's substrate.
- **R-2 — Double queuing.** A ship run can be pending at workflow level _and_, once started, pending again at job level: two waiting surfaces per run, not one. **Answered, not deferred** (§ Two-lane model, § Decisions): the FID lane is kept for ship runs, because skipping it reopens Gap 2 for exactly the pair requirement 2 names. Under `queue: max` the cost is latency; under the deferred arm each surface is also an eviction surface. See R-9 for the liveness half of this risk.
- **R-3 — Discriminator/routing drift.** The allowlist branch-prefix set in the group expression and the routing `case` in the resolver are two encodings of one truth, with nothing binding them. The branch filter has already moved twice in #363 and `main` is parked as a scheduled future change to exactly this input. When someone adds `hotfix/**`, the allowlist quietly declines to treat it as a ship and the cell falls into a _plausible-looking_ `bkit-auto-hotfix/...` group — the bug looks like correct behaviour. **Mitigation:** the matrix test in T3.1 must parse both out of the YAML and assert set-equality; a comment alone is not enough.
- **R-4 — Dual-agent same-run double-ship.** With both secrets set, one run launches two agents that both dispatch `/bkit-auto ship` against the same PR. Workflow-level concurrency cannot separate them by construction. The header documents this as additive by design; it is simultaneously an unarbitrated same-FID collision. Pre-existing, not introduced here, deliberately not changed here, deferred.
- **R-5 — Knowledge concentration.** Five non-obvious facts become load-bearing: that queue depth is `concurrency.queue`-dependent rather than fixed, the `needs`-in-job-`concurrency` capability, that the `resolve` job needs `GH_REPO` because it has no checkout, why the discriminator is an allowlist and not a denylist, and why the resolver exists at all. The last is the sharpest: the file's own long comment says cross-surface normalisation is impossible, so a future reader will "simplify" the resolver away and silently reintroduce Gap 2. **Mitigation:** the comment must be rewritten to say _impossible at workflow level, which is why the resolver exists_; a test must fail on the resolver's removal; and the `GH_REPO` line carries an inline comment naming what breaks without it.
- **R-6 — Shipped-surface blast radius.** Tier-1, render-compared, force-overwritten by install and upgrade. Consumers on older versions keep the old model; hand-edits are destroyed with no merge and no prompt. Advisory is the mitigation, not a fix.
- **R-7 — Test coupling.** A folded multi-line `group:` breaks the two string-matching tests in T3.1, the ctx-step relocation breaks both assertions in T2.7 (b), and the render-then-compare test fails unless the canonical mirror is regenerated in the same commit. The marker tests survive only because `indexOf` finds the first block — which the new layout must guarantee, not inherit. Cheap if anticipated, confusing if not.
- **R-8 — Adjacent defect discovered, out of scope.** `.bkit/workflows/bkit-ship.md:545` runs `gh workflow run ci.yml --ref "feat/{FID}"` (and `:228` preflights the scope), which requires `actions: write`; the cloud jobs grant `actions: read`, so that call is a 403 under the cloud token today. Not this issue's remit — route to `docs/failures.jsonl` during Plan rather than folding it in.
- **R-9 — Head-of-line blocking of `bkit-ship-global` by the FID lane (liveness).** A run holds its workflow-level group for its entire wall-clock life, including time its agent job spends _pending_ at job level. So a ship for FID N that is queued behind a long-running dispatched build for FID N occupies the repo-global ship slot **while executing nothing**, blocking ships for every other FID. Under `queue: max` the consequence is bounded latency: the blocked ships wait FIFO and all eventually run. Under the deferred `queue: single` arm it is worse — every ship arriving during the stall cancel-replaces the previously pending one, so a single slow same-FID build can silently consume an unbounded number of unrelated ship attempts. The stall is bounded by the blocking run's own workflow timeout (3600s for ship; `bkit-ship.md` header `Timeouts` rule). **Accepted, not engineered around** (§ Decisions): the alternative — exempting ship runs from the FID lane — reopens Gap 2 for the exact pair requirement 2 exists to exclude. This is a second, independent argument for the `queue: max` arm.
- **R-10 — Silent scope-narrowing for consumers outside the branch-prefix allowlist.** A consumer whose branches are not `feat/**` / `fix/**` keeps working with no error but never enters `bkit-ship-global`, losing the repo-wide ship-exclusivity guarantee entirely — for an unknown fraction of the consumer base, with no run output, advisory or doc line telling them so. **Mitigation:** the mandatory `.bkit/cloud.md` callout (§ Runbook deliverables item 4) and, preferably, a postinstall advisory clause. A documented limitation is acceptable; an invisible one is not.

### Resolved risks — closed with evidence, do not re-litigate at Plan

- **Queued-run staleness — CLEARED.** The concern was that a ship dequeuing minutes or hours late would act on a trigger-time snapshot: a moved `dev`, a stale green CI, a PR that changed or already merged. Traced line by line against `.bkit/workflows/bkit-ship.md`: Step 1 resolves `BOOK_ROOT`/lock fresh at boot; Step 2 sub-step 4 re-lists the PR (`gh pr list --head …`); sub-step 5 explicitly handles "PR merged while I was waiting" (`state = MERGED` → resume marker → skip to Step 9) as a named, tested path; sub-step 6 re-reads `ENTRY_HEAD`/`MERGEABLE`; sub-step 7 re-reads `statusCheckRollup` and Failure-Paths on any failed check; Step 3 re-checks whether `origin/dev` is now an ancestor of `ENTRY_HEAD` and routes a moved `dev` to Step 4 integration + Step 5 CI re-validation (`gh workflow run ci.yml` + poll, `SHIP_CI_WAIT_TIMEOUT_S`) before Step 6's `gh pr merge --match-head-commit` gate. **The workflow acts on the boot-time snapshot, never the trigger-time snapshot, by construction** — a property that predates #397 and is unaffected by it. Queueing is therefore **strictly better** than today's `cancel-in-progress: true`, not merely different: today's cancel can kill a run after it has pushed commits and applied labels, leaving a stuck `bkit:shipping`, no close row and no `outcome` row; the new model never does that. The cost is latency, not correctness, and it is bounded by the in-flight run's 3600s workflow timeout plus its Failure-Path exit — order of an hour, not unbounded. No freshness guard is needed and none should be added.
- **V-1 (`needs` in job-level `concurrency`) and V-4 (repository-scoped groups) — CLOSED.** See the verification-gates table. The peer-run-probe contingency they justified is retired.
