# Design Brainstorm & Ideas

Lens: Pragmatic — existing code, minimal new infra, ship fastest.

## Constraints read from the repo (not from the issue text)

Three facts change what "cheapest" means here, and two of them contradict the issue body:

1. **Workflow markdown is already machine-tested.** The issue states `tests/` is five `.bats` files and "no test references `bkit-ship` or parses workflow markdown". False: `.bkit/src/` carries a vitest suite that greps the five workflow files for structural invariants — `bkit-counter-prose-audit.test.ts` (fence-aware prose scan for bare `MAX_*` comparisons), `bkit-telemetry-workflow-writers.test.ts` (every telemetry append block stamps all A2 envelope fields), `bkit-ci-dispatch-gate-alignment.test.ts`, `bkit-comply-gate-wiring.test.ts`, `bkit-workflow-lock-snippet.integration.test.ts`. Prose **does** have CI; the harness for "assert a rule about `bkit-ship.md`" exists and costs one new `*.test.ts` file. This makes every approach below cheaper and removes "write a test framework" from scope.
2. **#341 has not landed.** `RUNTIME_DEVPUSHES` appears nowhere in the tree; #341 is `OPEN`, labelled `bkit:build`. Any design that writes "when `RUNTIME_DEVPUSHES = true`" is writing against a flag that does not exist, so 384 either blocks on 341 or defines the seam itself.
3. **The capstone gate is already written.** Step 13 sub-step 2 already selects `bkit-tests-check` and falls back to every `bkit-tests*` lane. The Path A/B merge gate is that block, re-pointed from the squash SHA to the PR head — copy, not invent.

Also relevant: `.bkit/scripts/` already ships seven installed helper scripts (`bkit-status-fold.sh`, `bkit-counter-bus.sh`, `bkit-status-route.sh`, …) sourced by workflow prose, and `tests/*.bats` already covers them. A ship-specific helper script is a well-trodden path, not new infrastructure — which is what makes Approach C viable rather than fanciful.

## Approach A — Rewrite `bkit-ship.md` around two variables: `BOOK_ROOT` and a frozen head ⭐ Recommended

**Summary.** Restructure `bkit-ship.md` into the agreed verify → base-check → integrate → re-validate → merge → dev-side shape, and make the two unwritten conventions into two named shell variables that every later step reads: `BOOK_ROOT` (the one tree bookkeeping is written to, resolved once in Step 1) and `BOOK_PATHS` (the path-scoped staging allow-list). Every `git add -A` and every `$(git rev-parse --show-toplevel)/…/status.jsonl` in the file collapses onto those two. Finding 2's missing `touch` and the Failure Path's append-before-abort ordering ride along as two- and one-line fixes in the same pass. New vitest file asserts the invariants that the prose can no longer state loosely.

The `BOOK_ROOT` resolver is the load-bearing choice: rather than blocking on #341, Step 1 probes what the runtime can actually do — main checkout present, not bare, `dev` checkout-able, push credentials present — and sets `BOOK_ROOT` to the dev tree or to the worktree accordingly. That is precisely the seam `RUNTIME_DEVPUSHES` will set when 341 lands; 341 then replaces the probe body with a flag read and touches nothing else. It also dissolves Finding 4 for free, because a single variable cannot resolve to two trees.

- **Complexity: MEDIUM.** One 1244-line markdown file rewritten (roughly 13 steps → 10, with three deletions: ship's unconditional rebase, Step 3's prior-run diffing, Step 8's `Update: Source files.`), one new test file, one `workflows.md` step-table section, then `bkit install` to regenerate the Claude/Cursor/opencode mirrors and refresh the content snapshot. No TypeScript changes required.
- **Extensibility: good.** The push contract becomes a variable rather than a convention, so future runtimes (cloud, GH Actions) change one resolver. Adding a phase-specific bookkeeping target elsewhere follows the same pattern. Downside: the contract lives in prose plus a test, so a future editor can still write a non-conforming block and only learn at CI.
- **Risk: a half-applied rewrite.** Mid-edit, the file would carry both the old head-mutating model and the new frozen-head model, and any ship run against that state is worse than either. Mitigate by treating the rewrite as one atomic task with the invariant test written first. Secondary risk: renaming or renumbering steps breaks `counter_next`/`counter_current` keys and makes historical consumer `status.jsonl` folds discontinuous — so step **keys** (`ship-merge-pr`, `ship-deferred-sweep`, …) must be preserved even where step **numbers** move.
- **Maintenance: low-to-moderate.** Smaller file, fewer branches, one status tree. The recurring cost is that `bkit-ship.md` and its three rendered mirrors plus the snapshot must stay in lockstep — already true today and already enforced by `bkit check`.
- **Reuse vs new.** Reuse: the shared worktree block, `bkit-status-fold.sh`, `bkit-counter-bus.sh`, the dev-lock idiom, the Step 13 capstone selection logic, the whole markdown-invariant test harness. New: one resolver snippet, one `touch` line, one test file, one canonical step-set constant.

## Approach B — Surgical patch: keep the 13-step skeleton, fix the five mechanisms in place

**Summary.** Do not restructure. Delete the unconditional rebase from ship's Step 2 (the four other phases keep theirs), delete Step 3 entirely, move `gh pr update-branch` out of Step 6 into an explicit integrate block guarded by the `merge-base --is-ancestor` check, add unconditional dispatch plus a capstone assertion after any head move, and retarget every bookkeeping write to `BOOK_ROOT`. Step numbers and names stay exactly where they are; the A/B routing lives inside the existing steps rather than as a top-level route.

- **Complexity: LOW.** The smallest diff that closes the reported defects. No renumbering, no mirror churn beyond the edited regions, no step-key risk, and the review surface is a handful of fenced blocks rather than a whole file.
- **Extensibility: poor.** The step numbering would no longer describe what the workflow does — a "Regression Guard" slot that is really a base check, a "Merge PR" step that also integrates and re-validates. Every later reader has to reconstruct the A/B model from scattered conditionals, which is the exact failure mode that produced this issue: a correctness property that depends on reading several steps together and holding them in your head.
- **Risk: the ordering defect survives.** Comment 1's independently-logged finding is that the guard evaluates a head Step 4 is about to discard. Keeping the step order means fixing that with a conditional rather than by construction, and conditionals in prose are what consumer agents improvise around (Finding 7). Also leaves the "is the head frozen right now?" question answerable only by tracing control flow.
- **Maintenance: higher than A over time.** Each future ship change has to re-derive which steps may move the head. The rule "bookkeeping never moves the head" is stated but not structurally enforced.
- **Reuse vs new.** Almost entirely reuse — this is the option that adds the least net-new anything. That is also its problem: it preserves the structure whose under-specification is the root cause.

## Approach C — Extract ship's git/CI mechanics into `.bkit/scripts/bkit-ship-gate.sh`

**Summary.** Move the executable content of the new shape out of markdown and into an installed helper script beside the existing seven: `ship_resolve_book_root`, `ship_base_is_current`, `ship_integrate`, `ship_revalidate`, `ship_assert_capstone`, `ship_book_commit`. `bkit-ship.md` shrinks to orchestration — source the script, call the function, route on its exit code. The push contract stops being prose an agent interprets and becomes a function an agent invokes.

- **Complexity: HIGH.** New script, new `.bats` suite, install-manifest wiring, uninstall wiring, mirror rendering, and a consumer upgrade path. It also splits the change across two review surfaces (script and markdown) that must land together.
- **Extensibility: best of the three.** Behaviour becomes unit-testable against fixtures instead of asserted about prose, and the same functions could later serve debug or build if head-match gating spreads. The canonical step set could live in the script rather than in a comment.
- **Risk: version skew between an installed script and rendered markdown.** A consumer on an older `.bkit/scripts/` with a newer rendered `bkit-ship.md` (or the reverse) gets a workflow calling a function that does not exist or behaves differently — a failure mode the existing scripts already have but which matters far more when the function is the merge gate. Second risk: agents route around shell they cannot read as easily as prose, so a script that exits non-zero for a reason the markdown does not explain invites the same improvisation as today.
- **Maintenance: two surfaces instead of one,** but each is smaller and the shell half has real tests. Net cost probably lower after two or three ship changes; higher immediately.
- **Reuse vs new.** Reuse: the installed-script pattern, `.bats` harness, source-and-call idiom already used five times in `bkit-ship.md`. New: an entire script module plus its install/uninstall surface.

**Why not C now:** it is the right end state, and Approach A is a strict subset of the path toward it — A names the functions as variables and blocks; C promotes those blocks into functions. Doing A first means the contract is defined before it is extracted, and the extraction becomes mechanical. Doing C first means designing the function boundaries against a workflow whose semantics are still being decided in the same change.
