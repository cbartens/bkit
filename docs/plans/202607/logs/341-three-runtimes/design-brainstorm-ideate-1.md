## Approach A — Sourced runtime shim in `.bkit/scripts/` + thin header pointers ⭐ Recommended

**Summary.** Add one `.bkit/scripts/bkit-runtime.sh` that workflows `source` — exactly the pattern `bkit-counter-bus.sh` / `bkit-counter-bus-config.sh` already use (`bkit-build.md:573-574`, `bkit-ship.md:591-592`) and that header rules already point at ("**Limits:** `MAX_MERGE_ATTEMPT` is defined in `.bkit/scripts/bkit-counter-bus-config.sh`", `bkit-ship.md:49`) — exposing `bkit_runtime_detect` (sets `BKIT_RUNTIME` + `GH_OK`), `bkit_wait_ci` (sleepless bounded poll), `bkit_branch_setup` (adopt-or-mint), and `bkit_close_phase`. Header rules shrink to one-line pointers instead of carrying behaviour.

- **Complexity:** MEDIUM. One new file, ~4 sourcing lines per workflow, 7 sleep sites collapse into one function, three duplicated "shared kernel" copies (S2) become an actually-shared kernel.
- **Extensibility:** Best of the three. A mode 4 (Cursor background agent — `CURSOR_REMOTE_AGENT` is already probed at `bkit-preflight.ts:1135`, and `providers.md:281` documents its detection) is a branch inside one function, not five prose edits x six workflows.
- **Risk (named honestly):** **MCP fallback cannot live in bash.** MCP calls are agent tool invocations, not shell commands — `bkit_gh()` can detect and report "gh unavailable", but it cannot _itself_ call `mcp__github__merge_pull_request`. So change 2 stays prose no matter what; this approach is a **hybrid** (bash owns detect/wait/branch/close; prose owns the gh→MCP substitution). Anyone expecting the shim to solve change 2 will be disappointed. Secondary risk: the shim must exist in worktrees and in consumer repos — it rides `bkit install` like its siblings, but adds a version-drift surface.
- **Maintenance:** Lowest ongoing. It is unit-testable in the existing vitest suite (`.bkit/src/*.test.ts`), so `bkit check` can actually assert behaviour — which no prose rule can. F1/F2 get implemented once inside `bkit_close_phase` rather than re-argued per workflow.
- **Reuse vs new:** High reuse. Zero new infra concepts — the sourcing pattern, the scripts dir, the header-pointer idiom, and the test harness all exist. Net-new is one file.

## Approach B — Pure additive prose header rules (the seed, literally)

**Summary.** Exactly the six changes as written: ~5 additive `>` blockquote rules in each workflow header gated on one runtime flag (renamed per S1), the §6c map as a reference table, FID hoist per S3, and the three localized §4 fixes. No new files.

- **Complexity:** LOW. Smallest possible diff; mode 1 is untouched **by construction** (every rule is gated), which is the single strongest argument for it.
- **Extensibility:** Poor and sublinear. Each new rule is copied into six workflow headers; the headers are already ~30 dense bullets (`bkit-ship.md:10-50`). Rule N+1 costs the same as rule N, forever.
- **Risk:** **Prose rules are advisory, and D1/D2 are the proof.** The incident chain was an agent improvising a merge _despite_ an existing header protocol that says "No Improv" and "**If** any step/tool/command fails → **Failure Path**". Adding more prose to the same header asks the same failure mode not to recur. The seed's own framing concedes it: "the only gh-outage branch today is `gh-error → abort`" — that branch is _code_ (`bkit-build.md:1303`), and it held; the prose around it did not. Also: nothing mechanically enforces the seven sleep sites, so drift is silent.
- **Maintenance:** Deceptively cheap up front, expensive later — rules live far from the call sites they govern, and there is no test that can fail when they diverge.
- **Reuse vs new:** Maximum reuse, zero new. Also zero new leverage.

## Approach C — Capability normalisation + single uniform path

**Summary.** Reject the mode enum. Probe three orthogonal capabilities once (`GH_OK`, `CAN_WORKTREE`, `CAN_PUSH_DEV`) and let every phase degrade on capability, not identity. Then **converge**: make PR-based phase-close the only close path in all three runtimes and delete the local squash-merge entirely (`bkit-design.md:795-815`, `bkit-plan.md:786-792`).

- **Complexity:** HIGH up front, LOW steady-state. It deletes a path instead of adding one — the only approach here whose end state is _smaller_ than today's.
- **Extensibility:** Excellent on the axis that actually bites. Modes are not orthogonal to capability: a mode-2 runner with an expired `GH_BKIT_TOKEN` is `GH_OK=false` while `MODE=2`, and a mode-flag design will confidently take the gh path and fail. KN-CORE-1 (401 after rotation) is exactly this class. Capability probing handles it for free; a mode enum needs a special case per intersection.
- **Risk:** **Directly contradicts two hard constraints** — "additive rules gated on a single MODE flag" and "must not regress mode 1". Uniform PR-close changes the everyday laptop path: design close would require network + an open PR + CI, and collides head-on with F1 (`[skip ci]` docs-only economics). Mode 1's local squash is fast and offline-capable; taking that away is a real regression, not a cosmetic one.
- **Maintenance:** Lowest of all _if_ it lands, because dual paths rot — the mode-3 close path would otherwise be exercised only in the runtime nobody debugs interactively. But it is the highest-variance bet.
- **Reuse vs new:** Reuses the ship close machinery (`bkit-ship.md:545-561`) as the single close primitive; net-new is mostly deletion plus the F2 guard re-implementation.

**Why C is worth keeping on the table despite the constraint conflict:** the capability-vs-mode insight is separable from the uniform-path bet. A synthesiser can take capability probing (which strictly dominates the mode flag, and costs the same) while keeping A's or B's dual close path. That decomposition is the most valuable thing in this brief.
