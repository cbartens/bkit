# Design Brainstorm & Ideas

Lens: Optimal-tradeoff — best long-term shape ignoring legacy constraints, with the divergence deliberately concentrated on the **failure / control-flow seam**: how a bash-gated workflow (`|| Failure Path`) branches on an MCP call that returns neither exit code nor stderr — and, per the live incident in `related-issues.md` (`mcp__github__search_issues` returning a clean `total_count: 0` on a private repo where `gh search issues` found 3 hits), how it detects a call that succeeded _and lied_.

Verified against live source before drafting: `bkit-design.md:10-31` (header rule-block + Worktree/Git/Status-branch rules), `:216-233` (adopt-worktree-or-mint-`feat/{FID}` at Step 2), `:795-810` (Close Workflow local squash-merge + `git push origin dev`); `bkit-auto.md:82-99` (`OWNER_REPO` via `gh repo view`, `FID="${BRANCH#feat/}"` hard-coupling); `bkit-ship.md:545-563` (`sleep 30` CI poll); `bkit-build.md:1260-1342` (existing **CI-Dispatch Gate** kernel — a `poll_decide()` bash function that already translates a `gh` call's exit code into a tri-state `found|none|err` + a `GH_ALL_ERRORED` accumulator, feeding a `case` statement — this is bkit's one existing precedent for "detect tool-unavailable, don't just abort"); `.claude/hooks/cloud-bootstrap.sh:56-64` (silent `gh auth login --with-token` with `|| log`, non-blocking by hook-type constraint).

## Approach A — Sentinel-bridge: materialize MCP outcomes into bash-readable files, mechanize the wait not the judgment ⭐ Recommended

**Summary:** Keep MCP calls exactly where they already live — invoked in-conversation by the orchestrator (as trackers already are today, e.g. `bkit-auto.md:96` `mcp__github__pull_request_read`) — but make the header fallback rule (seed change 2) require the orchestrator to immediately write the call's outcome to a small JSON sentinel (`{tool, status: ok|error|timeout, count, corroborated: true|false}`) at a fixed path before the next bash step runs. Every existing `|| Failure Path` / `[ -f ... ]` / `jq` gate then reads the sentinel exactly the way it already reads `status.jsonl` or subagent artifacts — no new gate idiom, just a new artifact type. Retry/backoff is split deliberately: the _decision_ to retry (was this error transient?) stays a judgment call by the orchestrator reading the tool's own error payload, but the _wait_ between attempts is a real `sleep N` bash call the orchestrator issues between two tool invocations — so backoff timing is mechanical even though the retry trigger isn't. The result-plausibility gap from the live incident is closed structurally, not by an extra rule: the sentinel schema _always_ carries `count` + `corroborated`, and the header rule defines "corroborated" once (e.g. a second independent signal — cross-check against a `list_*` call, or against the PR/issue metadata already in context — before a `0`/empty result is trusted enough to write `None.` instead of `Search unavailable.`).

- **Complexity:** MEDIUM — one new artifact convention (sentinel JSON) + one schema, but it reuses the file-based gate idiom bkit already leans on everywhere (subagent-writes / orchestrator-reads-and-commits); no new binaries, no new stack coupling.
- **Extensibility:** Good — a new gh-covered call site just adds "call the mapped MCP tool, write the sentinel" to its existing step text; the `§6c` map stays the single source of truth for tool names, the sentinel schema is call-site-agnostic. Also generalizes past this issue: the same sentinel shape is the natural home for future MCP result-plausibility rules bkit will need elsewhere (e.g. Linear reads), so it pays down #342's adjacent scope too.
- **Risk:** The sentinel is only as honest as the orchestrator's self-report — an orchestrator that misreads a tool's own return object can still write `status: ok` for a call that actually errored (same trust root as today, just made visible/auditable instead of invisible). Mitigation is procedural, not mechanical: the header rule must say "write the sentinel from the tool's raw return, not from your interpretation of it" and gates must fail loud if the sentinel is malformed/missing rather than defaulting to a pass.
- **Maintenance:** One schema + one map table (§6c) to keep in sync; marginal cost per new call site is a couple of lines, not a new mechanism.
- **Friction vs ideal / existing-codebase friction:** Low — this is additive on top of the existing "orchestrator calls tool, bash step reads the derived value" pattern already present at `bkit-auto.md:96-99` (parse PR body → extract `ISSUE_ID`/`FID`); it formalizes an implicit convention rather than introducing a foreign one.

## Approach B — Shell-native MCP shim: give MCP calls a real exit code

**Summary:** Go one step further toward the ideal and eliminate orchestrator self-report from the control-flow path entirely — wrap the `§6c`-mapped MCP calls behind a thin CLI bridge (a small local script that speaks to the same MCP server config in `.mcp.json` headlessly and returns a real process exit code + JSON on stdout / error text on stderr), so the fallback branch becomes a genuine subprocess exactly like `gh` is today, and existing `|| Failure Path` / retry-with-backoff bash loops (the same `poll_decide()` shape already proven at `bkit-build.md:1285-1299`) work on it completely unmodified, no orchestrator judgment involved at all — including for detecting a silently-empty-but-wrong result, since the shim can encode "0 results" vs "call failed" as genuinely distinct exit codes.

- **Complexity:** HIGH — requires building and shipping a new stack-agnostic CLI/binary that authenticates to and calls MCP servers headlessly (not the same thing as Claude Code's in-conversation MCP client), plus keeping it in lockstep with `.mcp.json` server config and the `§6c` tool map. This is real new tooling, not an "additive header rule."
- **Extensibility:** Excellent once built — new call sites are pure bash, identical to `gh` call sites; the whole fallback surface becomes mechanically testable outside a live agent session (a real win for CI/regression-testing the fallback itself, which today can only be exercised by an actual model run).
- **Risk:** Main failure mode moves from "orchestrator misjudges a tool result" to "the shim itself drifts from or duplicates the MCP client's auth/session semantics" — a second implementation of MCP-calling logic to keep correct, with its own token-scoping and injection-surface questions (stacks on top of §5a, doesn't remove it).
- **Maintenance:** Ongoing — a bespoke CLI is a new artifact with its own release/versioning inside bkit's stack-agnostic shipped surface, contradicting the "additive header rules … not a rewrite" framing from the primary seed; every future MCP tool bkit wants to fall back onto needs a shim entry.
- **Friction vs ideal / existing-codebase friction:** HIGH — this is explicitly the kind of new-tooling investment the issue's guiding principle (minimal, additive, no rewrite) was written to rule out; flagging it because it is the actually-correct long-term shape if the constraint "don't build new tooling" didn't apply — the sentinel-bridge (Approach A) is a deliberate, named compromise against this ideal, not an accident.

## Approach C — Prose-only judgment fallback (status-quo-adjacent, formalized)

**Summary:** The cheapest read of the primary seed: a single header rule states the `§6b` fallback + the result-plausibility caveat in prose only ("when `GH_OK=false`, use the mapped MCP tool; treat a `0`-count or empty MCP read as inconclusive unless corroborated by a second signal") and stops there — no sentinel file, no shim, no new artifact. Retry/backoff and the "was this call actually trustworthy" judgment are left entirely to the orchestrating model reading its own tool-call history in-context, exactly as it does today for every other prose rule in the header block (e.g. the existing Comments/Tracker rules already work this way with no mechanical enforcement).

- **Complexity:** LOW — literally the rule text from the primary seed's change 2, no build, no schema, no new gate idiom.
- **Extensibility:** Poor for this specific seam — every future "was this MCP result trustworthy" question is re-litigated per call site by the orchestrator's judgment in the moment, with no durable artifact to audit after the fact (this design run itself only caught the `search_issues` bug because a human/agent happened to cross-check with `gh search issues` — under this approach that cross-check is optional, not structural).
- **Risk:** Highest, and not hypothetical — this is functionally the control-flow shape that was already in effect when D1 (the `[skip ci]` leak) and the live `search_issues`-returns-zero incident both occurred; formalizing the wording does not change the underlying trust root that already produced two silent-wrong-result failures in this issue's own history.
- **Maintenance:** Lowest authoring cost, but shifts cost downstream into incident response/audit (per `related-issues.md`, this exact failure class already required a `docs/failures.jsonl` + `.bkit/friction.jsonl` entry to even notice) — cheap to write, expensive to debug when it silently misfires again.
- **Friction vs ideal / existing-codebase friction:** Lowest of the three to ship, but is included primarily as the calibration baseline the other two approaches are justified against — it is viable (many bkit header rules already work exactly this way) but reintroduces the specific risk category the issue exists to close.

## Decisions

| Decided                                                                                                      | Alternatives                                                       | Why                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Recommend Approach A (sentinel-bridge) as the shape for seed change 2's fallback mechanism                   | B (shell-native shim), C (prose-only)                              | A is the only option that both stays inside the "additive header rule, no new tooling" constraint (unlike B) and gives the fallback path a durable, gate-readable artifact instead of pure orchestrator self-report (unlike C) — directly closing the class of failure (`search_issues` silent-zero, D1's silent `[skip ci]`) surfaced during this very design run. |
| Retry/backoff should be split: mechanical `sleep` between attempts, judgment-based retry trigger             | Fully mechanical retry (requires B), fully prose retry (C)         | A real `sleep N` is cheap and available today without new tooling; the retry _decision_ cannot be mechanized without B's shim, so splitting the two gets the achievable half of "mechanical" without the build cost of the whole.                                                                                                                                   |
| Result-plausibility ("corroborated" flag) belongs in the sentinel schema itself, not a bolt-on separate rule | Standalone "0-hits-needs-corroboration" prose clause (closer to C) | Baking it into the schema makes every fallback call site carry the check by construction, rather than relying on each call site's author remembering a separate prose caveat — same reasoning bkit already applies to `status.jsonl`'s `verdict`/`failures` fields (`bkit-design.md:25`).                                                                           |
| Flag Approach B explicitly as the "ideal-if-unconstrained" shape rather than silently dropping it            | Omitting it since it clearly violates the additive-only constraint | The brief asks to reason from first principles ignoring constraints, then name the friction each approach creates against the existing codebase — B is the honest answer to "what's actually best long-term," it's just not this issue's minimum change-set.                                                                                                        |
