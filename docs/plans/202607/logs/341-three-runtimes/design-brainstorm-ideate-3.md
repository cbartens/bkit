# Design Brainstorm & Ideas

Lens: Risk premortem — failure modes, scale, time, handover.

> **Verdict rationale (CONCERNS, not FAIL):** the six-change seed is directionally right and buildable, but three repo facts contradict it as written and must be resolved in the design, not the build:
>
> 1. **`MODE` is already taken.** `bkit-auto.md:70-80` sets `MODE=CI|BRIEF` (phase routing). Change 0's "set `MODE` once at workflow start" collides head-on in the one workflow that most needs the flag. Rename required (`RUNTIME` below).
> 2. **The blocked op is not just the push — the `checkout` is destructive first.** Close Workflow does `cd "$REPO_ROOT"` then `git checkout dev` (`bkit-design.md:797-799`, `bkit-plan.md:785`, `bkit-ship.md:736-738`). In mode 3 `REPO_ROOT` **is** the session working tree, so `git checkout dev` yanks the live session off `claude/…` **before** the push fails. The issue names only `git push origin dev` (D4). Call this **D6**; it changes the fix shape (guard the checkout, not just the push).
> 3. **Two workflow files are unowned by the seed.** `bkit-worktree-prune.md` (18 worktree refs) and `bkit-worktree-sync.md` (16) are worktree-native utilities. "Six workflows" misses them; under adopt-or-mint they are meaningless in mode 3 and need an explicit disposition (self-skip vs out-of-scope).

## Approach A — Capability table derived from one detection (defends against identity drift) ⭐ Recommended

**Summary:** One detection block sets `RUNTIME` (1|2|3|unknown) **once**, immediately derives four named capability flags (`CAN_WORKTREE`, `CAN_PUSH_DEV`, `CAN_SLEEP`, `GH_OK`), and every header rule and call site branches on the **capability**, never on the runtime identity — so the identity is an input to one inference table instead of a predicate scattered across six files.

**Why this shape:** the seed already mixes paradigms and doesn't notice. Change 1 makes `GH_OK` a **probed capability** (`gh auth status` → `true|false`); changes 3/4/5 make worktree/push/sleep **inferred from identity**. That inconsistency is the design smell. If gh-auth deserves a probe because "mode 3 usually can't but sometimes can," the exact same logic applies to `CAN_PUSH_DEV` (a mode-2 runner with a read-only `GITHUB_TOKEN` also cannot push dev — §1 says `GITHUB_TOKEN` is "read-only + won't fire CI", so `MODE=2 => CAN_PUSH_DEV` is **already false** in the default GH-Actions config). An identity-keyed rule encodes a claim that is wrong today, not in six months.

`RUNTIME` is retained (not discarded) as the **default source** for the three non-probed flags — this is not a 16-state lattice, it is a 3-row table with named outputs plus one probe. Rules read `CAN_*`; only the table reads `RUNTIME`.

Naming: **`RUNTIME`, never `MODE`** (collides with `bkit-auto.md:70-80`). `WORKTREE_PATH` becomes the indirection: adopt mode sets `WORKTREE_PATH="$REPO_ROOT"`, and all **49** `{WORKTREE_PATH}` sites keep working untouched.

**Premortems**

- **10x scale (more phases, more repos, more runtimes):** breaks when runtime #4/#5 lands (Cursor background agents are **already here** — `providers.md:281`; devcontainers, Codespaces next). Under A the blast radius is one table row (`unknown => probe or conservative default`), not a grep for `MODE=3` across 6 files x N call sites. Fan-out: subagents inherit `WORKTREE_PATH` via `Context` cwd (49 sites) — because A only changes what the variable _holds_, subagent fan-out is unaffected at 1x or 10x. Hotspot: the detection block itself becomes load-bearing for all six workflows — it must be dead simple and side-effect-free. Observability: emit the resolved table (`RUNTIME=3 CAN_WORKTREE=false CAN_PUSH_DEV=false CAN_SLEEP=false GH_OK=true`) as one narrated line **and** one `status.jsonl` row at Step 1.
- **6 months later:** the drift risk is a **capability flag that is set but read nowhere** (or a call site that grew a `sleep` and never asked `CAN_SLEEP`). Magic-number risk: backoff/timeout constants in the CI-wait rule get copy-pasted per site and drift. Undocumented invariant to name **now**: _"merge body must be skip-token-free"_ — currently implicit in one `--body ""` (`ship:551-553`); under A it becomes a named rule that both transports inherit. Mitigation: a `bkit check` assertion that every `CAN_*` flag has >=1 reader and every `sleep` in `.bkit/workflows/` sits under the CI-wait rule.
- **On-call at 3am:** the page shape is _"phase closed but dev has no commit"_ or _"CI never ran on dev"_ (D1's actual signature). Diagnosability under A is the best of the three: the Step-1 capability line in `status.jsonl` tells you in one read whether the run **thought** it could push dev. Recovery path: re-run the close step only — `RUNTIME` is re-derived, no state is carried. Worst 3am case for A: detection **misfires** (env var absent on a resumed session) and a mode-3 run believes `CAN_PUSH_DEV=true` → hits D6 (`git checkout dev` on the live session). Recovery is `git checkout claude/…` + re-run; the _narrated_ capability line is what makes this a 2-minute fix instead of an hour.
- **Author leaves:** best bus-factor of the three. `CAN_PUSH_DEV=false` is self-documenting at the call site; `MODE=3` requires knowing the §1 table by heart. The concentrated knowledge is the **inference table** — one block, one place to read, and it is the natural home for a comment explaining _why_ mode 2 can't push dev. Risk: the person who leaves is the only one who knew the table was a **default**, not a truth, and that `GH_OK` is probed while the rest are assumed.

**Risk-mitigation guidance (layer onto A):**

- Rename `MODE` → `RUNTIME` **first**, as its own workstream, before any rule lands. Grep-verify zero collision with `bkit-auto.md`'s `MODE=CI|BRIEF`.
- Rewrite the `**Worktree:**` header rule (`bkit-design.md:30` and 5 peers) to `pwd != WORKTREE_PATH => Failure Path` **in the same commit** as adopt-or-mint. Shipping adopt-or-mint without it = every mode-3 step fails.
- Add a **D6 guard**: never `git checkout dev` when `CAN_PUSH_DEV=false`. Guard the checkout, not just the push.
- Make `CAN_PUSH_DEV` **probeable, not only inferred**: `git push --dry-run origin dev` is cheap and non-destructive; use the probe when `RUNTIME=unknown`, and keep the table as the fast path.
- Give `bkit-worktree-{prune,sync}.md` an explicit disposition: self-skip loudly when `CAN_WORKTREE=false` (do not leave them to fail obscurely).
- Bound the fallback: **max 1 gh->MCP transition per workflow run**, recorded in `status.jsonl`. An unbounded per-call fallback is how D2 became D1.

## Approach B — Literal seed, minimally corrected (defends against over-abstraction)

**Summary:** Build exactly the six changes as written — one `RUNTIME` flag (renamed), five additive header rules duplicated per workflow file, adopt-or-mint gated on `RUNTIME=3` — accepting identity-keyed branching as the honest cost of a 3-value enum you can actually enumerate and test.

**The case against A, stated fairly:** capabilities are a lattice; identities are a list. Three identities = three test scenarios, and bkit can plausibly run all three end-to-end. Four booleans = 16 states, of which ~13 are unreachable and **none** will ever be tested — and untested states in a strict-procedure workflow file are worse than an honest `if RUNTIME=3`. A capability that is only ever set from the identity table is **identity with extra indirection**: it adds a hop for a future that may never arrive. bkit's own doctrine (memory: "bkit shipped surface must be stack-independent"; "minimal, additive") points at the smaller change.

**Premortems**

- **10x scale:** the `MODE=3` predicate is copied into ~5 rules x 6 files = ~30 sites. At runtime #4 (Cursor background agents, **already shipped**), every one is silently wrong — the flag falls through to the mode-1 branch and the runner tries `git worktree add` on a session it can't worktree. Blast radius: silent, per-phase, discovered only by the user. This is B's defining weakness and it is **not hypothetical** — `providers.md:281` documents runtime #4 today, and its detection isn't even an env var (stdin JSON), so `RUNTIME` detection can't see it from bash at all.
- **6 months later:** header rules drift **between files**. There is no shared include, so six copies of the CI-wait rule diverge the first time someone fixes a bug in one. Precedent risk is real: the tracker blocks are duplicated inline across 6 files today (78-111 markers/file) and only stay in sync because a **generator** owns them — the new rules would have no generator. Undocumented invariant: "rule text in bkit-ship.md is authoritative; the other five are copies" — pure tribal knowledge.
- **On-call at 3am:** page shape identical to A, diagnosability worse. `RUNTIME=3` in the log tells you the identity but not the **decision** — you still have to read the rule text to know what it implied. Recovery path is the same (re-run close step). B's specific 3am failure: the six copies have drifted, so the phase that failed follows a rule that differs from the one you're reading in the other file.
- **Author leaves:** worst bus factor. The §1 runtime table lives in an issue, not the repo; `MODE=3` at a call site means nothing without it. Load-bearing tribal knowledge: _which_ of the six files is the template others were copied from.

**Risk-mitigation guidance (layer onto B):**

- If B is chosen, **put the five rules in `.agents/rules.md`'s bkit block, not in six headers.** It is already `**Read in full:**` by every workflow header, already has a `bkit:start/end` managed block, and mirrors to exactly one template file. This turns B's central weakness (6-way drift) into a 2-file edit and costs nothing. Counter-consideration to resolve in design: `rules.md` is read by **all** agents including subagents, so runtime-branching there has a wider blast radius than a workflow header, and rules.md is doctrine-prose while workflow headers are strict executable protocol — the two have different registers. Compromise: **invariants** (merge-body skip-free, never-foreground-sleep) go in `rules.md`; **procedure** (adopt-or-mint steps) stays in headers.
- Add a drift gate: a test asserting the five rule blocks are byte-identical across the six workflow sources. Without a generator, only a test keeps copies honest. (Note: mirrors are force-rendered and **not** drift-gated by `bkit check` — per repo memory — so the gate must target `.bkit/` sources.)
- Detect `RUNTIME=unknown` explicitly and **fail loud** rather than defaulting to mode 1. Defaulting to mode 1 is what makes runtime #4 silent.

## Approach C — One close path: PR-based phase-close always; worktree demoted to a local accelerator (defends against the untested-second-path rot)

**Summary:** Reject the premise that two branch models must coexist — make **PR-based phase-close the single path in all three runtimes** (open `feat/{FID}`->dev PR at close, merge via gh primary / MCP fallback), and demote the worktree to a mode-1 performance/isolation detail that **no workflow step depends on**, so the laptop path and the cloud path are the same code exercised on every run.

**The failure mode it targets:** "two models coexist" means mode 1 devs (99% of runs) never execute the mode-3 close path. The mode-3 path rots between uses and breaks silently — which is **exactly how D1 happened**: the merge invariant lived only in the gh path (`--body ""`), the fallback path was improvised on first contact, and nobody noticed until CI went dark on dev. A and B both **institutionalise** that asymmetry: they add a second close transport that mode 1 will never run. C makes the risky path the everyday path, so the laptop is the mode-3 test suite.

Note this is a smaller delta than it sounds: comment 2 already concluded design/plan close becomes _"structurally identical to build/ship close"_ in mode 3. C says: make it identical in **all** modes, and delete the local-squash-merge transport rather than keeping it as a mode-1 special case. Fewer transports, not more.

**Premortems**

- **10x scale:** 5 PRs per feature instead of 1 (design/plan/build/debug/ship each close via PR). At 10x features that is a lot of PR/CI churn — each phase-close PR is a `[skip ci]` docs commit that must **not** fire full CI, so the CI-Dispatch Gate interplay (repo memory KN-11: "skip-ci must not be HEAD when PR is created") becomes load-bearing and hostile. Real hotspot: PR-merge is a **network round-trip + branch-protection evaluation** per phase close, vs a local `git merge --squash`. Blast radius of a GitHub outage grows: today mode 1 can close design offline; under C it cannot. Rate budget (§6g N2, deferred) arrives sooner. **This is C's strongest objection.**
- **6 months later:** best drift profile of the three. There is one close path, so there is no second copy to rot and no "mode 3 close" that only one person has ever seen work. The invariant (skip-free merge body) has exactly one enforcement point. Drift risk moves to **infrastructure**: C hard-depends on dev branch protection permitting autonomous merge and on "Automatically delete head branches" (§7) — both are repo _settings_, invisible in the codebase, changeable by anyone with admin, and silently breaking. That is undocumented-invariant risk of a nastier kind than rule drift: it isn't in git.
- **On-call at 3am:** best page shape. Failures surface as a **PR that didn't merge** — a durable, inspectable artifact with a URL, checks, and a merge button — rather than a local `git push origin dev` that failed inside a bash block and left a worktree mid-state. Recovery path is "look at the PR, merge it" and is available to a human with no bkit knowledge. Counter: C's 3am failure is _"branch protection changed and every phase close is now blocked"_ — total, immediate, all-runtimes. A/B degrade to "mode 3 is broken"; C degrades to "everything is broken." Blast radius vs diagnosability is the real trade.
- **Author leaves:** best bus factor on the workflow code (one path, self-evident artifacts), worst on **infra**. The knowledge "dev branch protection must allow the bkit app to merge without review, and auto-delete-head-branches must be on" is tribal and lives in a settings UI. Must be written into `docs/deployments.md` (its stated scope: "branch protection") and ideally asserted by a preflight probe.

**Risk-mitigation guidance (layer onto C):**

- Add a **preflight assertion** that dev branch protection permits the autonomous merge and auto-delete-head-branches is on — fail loud at Step 1, not at close. This converts C's worst 3am page into a startup error. (Resolves §8 item 3 by making it self-checking rather than a one-time manual confirm.)
- Keep `git push origin dev` as a **fast path** only where `CAN_PUSH_DEV=true` **and** the PR path is unavailable — but do **not** make it the default, or C degenerates into B with extra steps. Prefer deleting it outright; a fast path nobody debugs is a slow path with a landmine.
- Resolve the `[skip ci]` interaction **in design, not build**: 5 phase-close PRs whose HEAD is a `[skip ci]` docs commit collide with KN-11. §6d's "consider dropping `[skip ci]` from intermediate status-commit subjects" is not a nice-to-have under C — it is a prerequisite.
- Demote, don't delete, the worktree: keep `git worktree add` in mode 1 for isolation, but assert that **no step reads worktree-ness** — only `WORKTREE_PATH`, which resolves to the repo root when absent. Same indirection as A; C just makes it the only consumer.

## Cross-Approach Risks

_Surface these in the final design's `Risks & Open Questions`._

1. **`MODE` name collision (`bkit-auto.md:70-80`)** — applies to all three; blocks change 0. Rename to `RUNTIME` before any rule lands.
2. **D6 — `git checkout dev` is destructive in mode 3, and fires before the push.** Named nowhere in the issue. All approaches must guard the checkout, not just the push.
3. **The `pwd`-outside-worktree header rule kills adopt-or-mint on step 1.** Hard sequencing coupling in every approach; cannot be a follow-up.
4. **Runtime #4 already exists.** Cursor background agents (`providers.md:281`) detect via stdin JSON, **not** an env var — so no bash-visible primitive exists for them. Any `RUNTIME` detection block must define `unknown` behaviour explicitly (fail loud, or conservative "assume least capable"). Silent fallthrough to mode 1 is the worst option and is B's default.
5. **Fallback must be bounded and recorded.** D2->D1 was an _unbounded, unrecorded_ improvisation. Cap at 1 gh->MCP transition per run, emit a `status.jsonl` row. Applies to A/B/C alike. Reinforced by §5a (injection): every extra MCP call widens the lethal-trifecta surface (#342).
6. **MCP failures have no exit code** (§5c) — bkit's control flow is bash `|| Failure Path` gates. Every mapped fallback needs an explicit success assertion (re-read the PR state after `merge_pull_request`), because "the tool returned something" is not "it worked". This is the mechanism gap behind §8 item 1 and it is unsolved in all three approaches.
7. **`[skip ci]` vs phase-close PRs (KN-11).** Any PR-based close whose HEAD is a `[skip ci]` docs commit collides with the CI-Dispatch Gate. Acute in C (5 PRs/feature), present in A/B's mode-3 close. §6d's "drop `[skip ci]` from intermediate status commits" may be a prerequisite, not an option.
8. **Branch protection + auto-delete-head-branches are repo settings, not code** (§7, §8 item 3). Invisible to git, changeable by any admin, silently break every autonomous merge. Should be preflight-asserted and written into `docs/deployments.md` (whose stated scope is branch protection) rather than confirmed once by hand.
9. **`core.bare` flip appears in the close path** (`bkit-design.md:798`, `bkit-ship.md:737`) — a laptop-specific workaround (repo memory: `bkit install` flips `core.bare=true`) that is meaningless in modes 2/3. It rides along in the exact block being rewritten; decide whether it moves behind `CAN_WORKTREE` or stays unconditional.
10. **Mode 1 non-regression needs a real test, not review.** Repo memory ("Validate shipped config with the real tool, not string-presence tests"; "Verify install AND upgrade live") applies directly: a test asserting rule text is present will pass while shipping a broken close path. The mode-1 close path must be exercised end-to-end.
