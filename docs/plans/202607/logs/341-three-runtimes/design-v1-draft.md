## Acceptance Scenario

### Narrative

A developer runs any bkit phase — from their laptop, from a GitHub-Actions runner, or from a claude.ai cloud session — and the phase behaves the same way in all three: it starts without aborting on step 1, never yanks the session onto another branch, and reliably lands its work on `dev`. When `gh` is unavailable in the cloud session, the phase still completes through a sanctioned, bounded fallback rather than an improvised one. Afterwards the developer can read the run's status trail and see which runtime was detected, what it was judged capable of, and which transport actually carried the close.

### Success Criteria

1. All five phases + `bkit-auto` complete end-to-end in each of the three runtimes; the mode-1 laptop path is verified non-regressed by a real end-to-end run (not a rule-text-presence test).
2. No run ever mutates the session's checked-out branch in a runtime that cannot restore it — zero `git checkout dev` when dev-push capability is absent (D6).
3. Every phase-close lands on `dev` with a commit/merge body free of CI-suppression tokens, and the resulting CI-dispatch outcome on `dev` is asserted rather than assumed (D1 closed on both transports).
4. Any gh→MCP transition is bounded (max 1 per run), recorded in `status.jsonl`, and confirmed by an independent re-read that asserts the intended effect actually happened.
5. An MCP read returning empty/zero is never recorded as authoritative absence — it is corroborated or reported as unavailable.

### Key Edge Cases

- **Unknown runtime / runtime #4 already ships.** Cursor background agents (`providers.md:281`) detect via stdin JSON — no bash-visible primitive exists. Silent fallthrough to the mode-1 branch is the worst outcome; `unknown` must resolve to least-capable + loud.
- **Identity says capable, reality says not.** A mode-2 runner with the default read-only `GITHUB_TOKEN` cannot push dev; a rotated `GH_TOKEN` 401s (KN-CORE-1). Any identity-keyed capability claim is wrong today, not in six months.
- **MCP up but silently wrong.** The live `search_issues` incident: a clean `0` on the one surface (trackers, §6i) that has no fallback by design. gh fails loudly with an exit code; MCP failed quietly and wrongly.
- **Adopt mode collapses worktree isolation.** `WORKTREE_PATH == REPO_ROOT` means two phases on one session tree share a working tree; the existing `.lock` becomes the only concurrency guard (repo doctrine already forbids concurrent workflows on one clone).
- **Repo settings are invisible to git.** Branch protection on `dev` and auto-delete-head-branches are UI settings, changeable by any admin, and silently break every autonomous close.
- **`pwd` outside worktree fires on every step in adopt mode** (`bkit-design.md:30`) — adopt-or-mint is dead on arrival unless this rule changes in the same commit.

## Architecture

Four layers, split by **register** — what can be mechanised in bash, what must stay agent-prose, and what is a durable invariant.

```
Layer 0  RESOLUTION      .bkit/scripts/bkit-runtime.sh (sourced, unit-tested)
         bkit_runtime_detect -> RUNTIME + CAN_WORKTREE/CAN_PUSH_DEV/CAN_SLEEP/GH_OK
                             -> WORKTREE_PATH (the indirection point)
         Emits 1 narrated line + 1 status.jsonl row at Step 1.

Layer 1  MECHANISM       .bkit/scripts/bkit-runtime.sh
         bkit_wait_ci    -> bounded poll; wait primitive selected by CAN_SLEEP
         Replaces 7 sleeps / 4 poll constructs / 3 copy-pasted "shared kernel" blocks.

Layer 2  PROCEDURE       workflow headers (.bkit/workflows/bkit-*.md), gated on CAN_*
         Branch model (adopt-or-mint) · Worktree rule rewrite · Close model (3 shapes)

Layer 3  INVARIANTS      .agents/rules.md (bkit:start/end block)
         Merge/commit body MUST be skip-token-free · Never foreground-sleep
         Fallback bounded + recorded + success-asserted · Empty MCP read is inconclusive
```

**Why the split.** `.agents/rules.md` is already `**Read in full:**` by every workflow header, already has a managed `bkit:start/end` block, and mirrors to exactly one template file — 2 files reach all 6 workflows. But it is doctrine-prose read by _all_ agents including subagents, so adopt-or-mint _procedure_ does not belong there. Invariants (universal, register-appropriate) go to `rules.md`; procedure stays in headers; mechanism goes to the shim.

**Why a shim is not new infra.** `.bkit/scripts/bkit-counter-bus.sh` / `bkit-counter-bus-config.sh` are already sourced by workflows (`bkit-build.md:573-574`, `bkit-ship.md:591-592`) and already pointed at from a header rule — verbatim: "**Limits:** `MAX_MERGE_ATTEMPT` is defined in `.bkit/scripts/bkit-counter-bus-config.sh`" (`bkit-ship.md:49`). The shim reuses that idiom 1:1. Net-new is one file that rides `bkit install` like its siblings.

**Boundaries.**

- The shim owns detect / capability table / CI-wait / close-guard helpers. It is unit-testable in the existing vitest suite, so `bkit check` can assert behaviour — which no prose rule can.
- The shim **cannot** own the gh→MCP substitution. MCP calls are agent tool invocations, not shell commands: bash can detect `GH_OK=false` and report it, but cannot invoke `mcp__github__merge_pull_request`. Change 2 stays prose in every approach. Any design claiming otherwise is wrong.
- Mirrors (`.claude/`, `.cursor/`, `.opencode/`) are force-rendered from `.bkit/` and are not drift-gated — true edit cost is 6 sources (+templates), not 18 files.

**Integration points:** `bkit-auto.md` Step 1 (FID resolution reorder), Step 2 of all five phases (branch model), Close Workflow of design/plan/ship (transport + D6 guard), `bkit-cloud.yml` (already marker-primary/branch-fallback — no change needed), `cloud-bootstrap.sh` (gh hardening).

## Data Model

### Capability table — one detection, four named flags

Identity is an **input to one table**, never a predicate at a call site. This is a 4-row table with named outputs plus two probes — not a 16-state lattice.

| RUNTIME       | Detected by                         | CAN_WORKTREE | CAN_PUSH_DEV                           | CAN_SLEEP | GH_OK |
| ------------- | ----------------------------------- | ------------ | -------------------------------------- | --------- | ----- |
| 1 (local)     | neither var set                     | true         | probe                                  | true      | probe |
| 2 (gh-action) | `GITHUB_ACTIONS`/`CI`               | true         | **probe** (default token is read-only) | true      | probe |
| 3 (claude.ai) | `CLAUDE_CODE_REMOTE=true`           | false        | false                                  | false     | probe |
| unknown       | no primitive (e.g. Cursor bg agent) | false        | false                                  | false     | probe |

- **`GH_OK` is probed** (`gh auth status`, loud, once) — the seed already concedes this.
- **`CAN_PUSH_DEV` is probed** where the table says `true` (`git push --dry-run origin dev`, non-destructive). The seed makes `GH_OK` a probe _because_ "mode 3 usually can't but sometimes can" — the identical logic applies here, and `RUNTIME=2 => CAN_PUSH_DEV=true` is **already false** in the default GH-Actions config (§1: `GITHUB_TOKEN` is read-only). An identity-keyed rule encodes a claim that is wrong today.
- **`unknown` is least-capable + loud.** Never a silent fallthrough to mode 1.
- Rules read `CAN_*`. Only the table reads `RUNTIME`.

### `WORKTREE_PATH` — the indirection point

Measured: **31** structural `git worktree add|remove|prune|list` ops vs **49** `{WORKTREE_PATH}` refs (mostly subagent `Context` cwd) across 7 files — not "208 mentions".

- Mint mode: `WORKTREE_PATH="$REPO_ROOT/.worktrees/{FID}"` (today's behaviour, unchanged).
- Adopt mode: `WORKTREE_PATH="$REPO_ROOT"`.

All 49 path refs keep working untouched because only the variable's _contents_ change. The seed's "not a rewrite of call sites" is only true **via** this indirection. Real edit surface is the 31, concentrated in Step 2 + Close Workflow.

### FID resolution order — a reorder, not an invention

`bkit-auto.md:93-112` **already** parses `<!-- bkit:issue=#{ISSUE_ID} bkit:fid={FID} -->` from the PR body as the preferred source, and `bkit-cloud.yml:190-198` already does marker-primary / branch-fallback. The blocker is pure **ordering**: step 7 (`BRANCH` must start with `feat/`) and step 8 (`FID="${BRANCH#feat/}"`) abort before step 10 ever runs.

```
1. PR-body marker  <!-- bkit:issue=… bkit:fid={FID} -->   (preferred — already exists)
2. Branch-name derive  ${BRANCH#feat/}                     (fallback)
3. Neither -> Failure Path
```

The `feat/`-prefix hard-reject at `:86-87` is deleted, not relaxed. Cheapest item in the seed, mis-sized as part of "the biggest one".

### `status.jsonl` rows — the fallback audit trail (existing artifact, no new type)

| Row                  | When                     | Carries                                             |
| -------------------- | ------------------------ | --------------------------------------------------- |
| `runtime-resolved`   | Step 1                   | `RUNTIME`, four `CAN_*`, `WORKTREE_PATH`, `GH_OK`   |
| `transport-fallback` | on any gh→MCP transition | `from`, `to` (mapped tool), `reason`, `assertedBy`  |
| `close-transport`    | at phase close           | which of the 3 close shapes ran, and the landed SHA |

### §6c gh→MCP map (reference table, prose-owned)

Unchanged from the issue, with one correction: the `git push origin dev` tail resolves to `push_files` for docs-only closes (see Decision D5), NOT to a PR. Trackers are **absent** from this map by design (§6i).

## Components / Flows

### Flow 1 — Step 1 resolution (all phases)

`source .bkit/scripts/bkit-runtime.sh` → `bkit_runtime_detect` → narrate one line (`RUNTIME=3 CAN_WORKTREE=false CAN_PUSH_DEV=false CAN_SLEEP=false GH_OK=true`) → append `runtime-resolved` to `status.jsonl`. Load-bearing for all six workflows, so it must be dead simple and side-effect-free.

### Flow 2 — Branch model (Step 2, all five phases)

```
CAN_WORKTREE=true  -> mint feat/{FID} + git worktree add   (today's path, untouched)
CAN_WORKTREE=false -> adopt current branch in place; WORKTREE_PATH="$REPO_ROOT"
                      Assert current branch != dev -> else Failure Path
```

**Coupled, same commit:** the header rule `**Worktree:** ... If step ever finds pwd outside worktree → Failure Path` (`bkit-design.md:30` + 5 peers) becomes `pwd != WORKTREE_PATH => Failure Path`. In adopt mode `pwd` == repo root == "outside worktree" → guaranteed Failure Path on **every step**. This cannot be a follow-up; shipping adopt-or-mint without it ships a workflow that cannot take one step.

### Flow 3 — Close model: three shapes, not one

The seed's "PR-based phase-close" is a blanket over three structurally different closes. Separating them is what dissolves F1.

| Shape                                         | Phases       | Today                                                                                         | Mode-3 status                                                                                                            |
| --------------------------------------------- | ------------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **A — docs-only land on dev**                 | design, plan | `checkout dev` + `merge --squash` + `push origin dev`                                         | **Blocked** (D4 push + D6 checkout) — needs a transport                                                                  |
| **B — commits on the persistent PR branch**   | build, debug | push to `feat/`/`fix/` branch + PR ops                                                        | **Already works** (current branch is pushable)                                                                           |
| **C — server-side PR merge + local dev sync** | ship         | `gh pr merge` (server-side, works) then `checkout dev` + `pull` + `pnpm install` (`:733-751`) | Merge works; the **sync block is destructive** (D6) and is pure local housekeeping → **skip it**, do not re-transport it |

Shape C is the clearest correction to the seed: ship's merge is _already_ server-side. The `cd "$REPO_ROOT"` / `git checkout dev` block that follows exists only to refresh the local dev checkout and reinstall deps. In mode 3 nothing local needs dev — the right answer is to skip the block when `CAN_PUSH_DEV=false`, not to build a fallback transport for it.

### Flow 4 — Shape A transport (the D6 + F1 core)

```
Compute the docs file set explicitly (allowlist, not denylist)
  -> STRAY guard: assert set matches ^docs/plans/|^\.bkit/friction\.md$   [preserved from :802-803]
CAN_PUSH_DEV=true  -> today's local path: checkout dev, merge --squash, commit, push   [mode 1/2 unchanged]
CAN_PUSH_DEV=false -> NO checkout. Land the docs set server-side via mapped MCP
                      push_files with an explicit, skip-token-controlled message.
  -> Canonical-doc assert: re-read dev:docs/plans/{YYYYMM}/{FID}-design.md    [preserved from :807]
  -> Branch cleanup: skip in adopt mode (you are standing on the branch)
```

`push_files` is **the exact server-side equivalent of the `git push origin dev` that mode 1 already performs** — same write, different transport, no new capability requirement. Contrast a PR-close, which introduces a _new_ infra dependency (branch protection permitting autonomous merge), collides with F1, and drops both F2 guards.

### Flow 5 — CI-wait (`bkit_wait_ci`)

Measured: **7 `sleep` statements in 4 poll constructs** — 6 inside already-bounded loops (`bkit-build.md:1298,1320`; `bkit-debug.md:1018,1040,1137,1159`), 1 bare `sleep 30` (`bkit-ship.md:556`). D5 is **2 shapes, not 3 sites**. Six live in three copy-pasted blocks each labelled `# --- CI-Dispatch Gate shared kernel ---` — "shared" in comment only, physically duplicated.

```
bkit_wait_ci: bounded poll (attempt cap + elapsed cap, recorded)
  CAN_SLEEP=true  -> sleep "$POLL_INTERVAL_S" between attempts
  CAN_SLEEP=false -> yield: one check per orchestrator turn, bounded attempts
ship:556 `sleep 30` -> deleted, replaced by the bounded poll for RUN_ID
```

Deleting the blind `sleep 30` is a **mode-1 improvement, not a regression**: 30s is an unbounded guess that can be both too short (false "CI did not trigger") and wasteful.

### Flow 6 — gh→MCP fallback (prose, Layer 3)

```
GH_OK=false -> use the §6c-mapped MCP tool
            -> bounded: max 1 gh->MCP transition per workflow run
            -> recorded: `transport-fallback` row in status.jsonl
            -> success-asserted: independent re-read confirming the intended effect
               ("the tool returned something" != "it worked" — MCP has no exit code)
            -> retry: mechanical wait between attempts; the retry *decision* stays judgment
            -> request minimal output
Empty/zero MCP read -> INCONCLUSIVE, never authoritative absence.
                       Corroborate with a second MCP signal (e.g. a list_* call) or report unavailable.
```

D2→D1 was an _unbounded, unrecorded_ improvisation. Bounding and recording it is what makes the fallback a controlled path rather than a licence to improvise. Every extra MCP call also widens the lethal-trifecta surface (§5a/#342).

### Flow 7 — localized §4 fixes

- **Debug egress blindness** — allowlist + loudness; a self-skip `exit 0` must never read as "no runtime errors".
- **Playwright artifact seam** — no MCP artifact-download tool exists; failure signal lives in job logs (`get_job_logs`), only the rich report is lost. Open decision (see Risks).
- **Hard-coded macOS paths** — reframed: this is **not a mode-3 issue**. `.bkit/templates/docs/plans/template.md:195` leaks `/Users/christian/Documents/GitHub/create-t3-turbo` **to every consumer** in all three modes (plus repo copies at `:191`, `:575` and `.agents/skills/using-git-worktrees/SKILL.md:191`). Keep the fix in scope, but scope it as the shipped user-path coupling bug it is — bundling it behind a mode-3 milestone hides a consumer-facing defect.
- **`bkit-worktree-{prune,sync}.md` disposition** — 18 + 16 worktree refs, unowned by "the six workflows", meaningless under adopt. Explicit disposition: **loud self-skip when `CAN_WORKTREE=false`**. Silent omission = obscure mode-3 failures in a workflow nobody scoped.

## Trade-offs Accepted

**Choosing the shim (D3) over pure prose:**

- **Gain:** testability (`bkit check` can assert real behaviour), one shared CI-wait kernel instead of three copy-pasted ones, F1/F2 guards implemented once instead of re-argued per workflow, best bus factor (`CAN_PUSH_DEV=false` is self-documenting; `RUNTIME=3` requires knowing the §1 table by heart).
- **Sacrifice:** one more file in the shipped surface and a version-drift seam (it must exist in worktrees and consumer repos — it rides `bkit install` like its siblings). A hair further from the literal "additive header rules" framing, justified by the header-pointer precedent at `bkit-ship.md:49`.

**Choosing capability flags (D2) over identity:**

- **Gain:** correct today (mode 2's read-only token), correct for runtime #4 which already ships, and correct after a token rotation (KN-CORE-1).
- **Sacrifice:** one hop of indirection, and a real risk the next maintainer does not know the table is a **default, not a truth** — that `GH_OK`/`CAN_PUSH_DEV` are probed while the rest are assumed. Mitigation: the table is one block with that fact in a comment, plus a `bkit check` assertion that every `CAN_*` flag has >= 1 reader.

**Choosing `push_files` (D5) over PR-close:**

- **Gain:** F1, F2, D1 and D6 all dissolve at once rather than each needing a guard; no new infra dependency; `[skip ci]` docs economics preserved (design closes stay CI-free, as today).
- **Sacrifice:** design/plan close is no longer structurally identical to build/ship close — the convergence comment 2 hoped for does not happen. Shape A's mode-3 transport is exercised only in mode 3 (the rot risk ideate-1 C and ideate-3 C name). Depends on the token being permitted to write `dev` directly — the same permission mode 1 already exercises, but on a different credential.

**Choosing two close transports over one:**

- **Gain:** mode 1 stays offline-capable and instant; no 5-PRs-per-feature churn; a GitHub outage does not block a local design close.
- **Sacrifice:** the mode-3 transport is the path nobody debugs interactively. This is the design's **biggest accepted risk** and it is D1's exact aetiology. Mitigations layered on: the invariant (skip-token-free body) is _named and shared_ rather than living in one transport (D10); the fallback is bounded, recorded and re-asserted (D13); mode-1 non-regression gets a real end-to-end test, not a rule-text-presence test.

## Risks & Open Questions

**Risks**

1. **Detection misfire is the worst 3am page.** An env var absent on a resumed session → a mode-3 run believes `CAN_PUSH_DEV=true` → hits D6 (`git checkout dev` on the live session). Recovery is `git checkout claude/…` + re-run the close step (no state carried, `RUNTIME` re-derived) — the _narrated_ capability line is what makes this a 2-minute fix instead of an hour. This is why `unknown` must be least-capable + loud.
2. **The detection block becomes load-bearing for all six workflows.** It must be side-effect-free and dead simple.
3. **`git push --dry-run origin dev` may not be a reliable probe behind the mode-3 proxy** — it may fail for reasons unrelated to dev-push permission. Needs a spike before it is trusted; the table remains the fast path.
4. **Repo settings are not in git.** Branch protection on `dev` (and auto-delete-head-branches for shape C) are UI settings, changeable by any admin, silently breaking every autonomous close. Should be **preflight-asserted at Step 1** rather than confirmed once by hand, and written into `docs/deployments.md` (whose stated scope is branch protection). Under D5, `push_files` also depends on `dev` accepting a direct write from the bkit token.
5. **Capability flags that are set but read nowhere**, and backoff/timeout magic numbers copy-pasted per site. Mitigation: `bkit check` asserts every `CAN_*` has >= 1 reader and every `sleep` in `.bkit/workflows/` sits under the CI-wait rule.
6. **Every extra MCP call widens the lethal-trifecta surface** (§5a). Adjacent to #342 — do not duplicate its scope, but the bounded-fallback cap (D13) is a real mitigation and should be attributed as such.
7. **Mode-1 non-regression needs a real end-to-end test, not review.** A test asserting rule text is present will pass while shipping a broken close path.
8. **`core.bare` flip rides along in the close block** (`bkit-design.md:798`, `bkit-ship.md:737`) — a laptop-specific workaround, meaningless in modes 2/3, sitting inside the exact block being rewritten. Decide: move behind `CAN_WORKTREE` or leave unconditional.

**Open questions**

1. **Does `dev` accept a direct `push_files` write from the bkit token?** D5 hinges on this. If branch protection forbids it, fall back to D5(a) — PR-close + drop `[skip ci]` from close subjects — which then makes §6d's "consider dropping `[skip ci]` from intermediate status-commit subjects" a **prerequisite, not an option**. Resolve before build.
2. **Artifact seam (§8.2):** job-logs-only for cloud e2e, or one sanctioned `gh api`/`curl` exception? No MCP artifact-download tool exists; only the rich Playwright report is lost, not the failure signal.
3. **Should §6i admit a narrow read-path corroboration outside MCP on private repos?** D12 says no (doctrine forbids `gh` for tracker ops) and corroborates within MCP instead. If MCP-internal corroboration proves unreliable, this needs revisiting — deferred.
4. **Is the `search_issues` zero-on-private-repo failure a bkit-side scope/config issue or an upstream MCP bug?** Not diagnosed. It is logged (`docs/failures.jsonl`, `.bkit/friction.jsonl`) but the root cause is unknown, and D12 mitigates the symptom, not the cause.
5. **Which of the 4 `CAN_*` flags actually earn their keep?** `CAN_SLEEP` is the weakest — if foreground `sleep` is truly blocked in mode 3, the turn-yield alternative needs validation that it can bound a poll without degenerating into rate-limited tight-looping.

**Assumptions**

- Mode-3's proxy restricts `git push` to the current branch (infrastructure, not policy) — from §1, not re-verified here.
- `push_files`/`create_or_update_file` accept an explicit commit message and an explicit file list (the basis of D5's D1/F2 closure).
- The five phases' Step 2 branch logic is uniform enough that one adopt-or-mint rule covers all five (`bkit-design.md:216-229`, `bkit-plan.md:220-233` verified; build/debug/ship spot-checked only).
