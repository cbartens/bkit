# Design Review

Lens: Operability — failure modes, observability, on-call ergonomics.

Subject: `docs/plans/202607/logs/341-three-runtimes/design-v1-draft.md` (v1), cross-checked against `design-input.md`, `related-issues.md`, and live source (`bkit-design.md`, `bkit-ship.md`, `bkit-auto.md`).

## Failure-Mode Enumeration

Per new mechanism, "wrong but not erroring" behaviour:

1. **Layer 0 detection (`bkit_runtime_detect`, design-v1-draft.md:41-46, 124-126).** Fails if `.bkit/scripts/bkit-runtime.sh` is missing/stale in a worktree that predates this ship (mixed-version consumer). Design does not say what happens if `source` itself errors — an unset `CAN_*` var and an explicitly-`false` one are bash-indistinguishable downstream (`[ "$CAN_PUSH_DEV" = true ]` is false either way). **This is exactly the silent-failure class the issue is about, one layer earlier than anything the design names**: a broken shim degrades to "looks like a legitimate least-capable runtime" instead of a loud "detection itself failed." Detected by: nothing named. Blast radius: whole run, every phase, indistinguishable from a correct `unknown` row.
2. **`CAN_PUSH_DEV` probe (`git push --dry-run origin dev`, design-v1-draft.md:79-85, Risk 3).** Design's own Risk 3 flags this as unvalidated behind the mode-3 proxy but only discusses "may fail for unrelated reasons" (i.e. false-negative → falls back to `push_files`, a cost/complexity hit, not a safety hit). It does **not** discuss the dangerous direction: false-**positive** (dry-run says pushable, real push isn't, or proxy semantics differ from a real push in some corner). Detected by: nothing — Flow 4 (design-v1-draft.md:150-160) branches purely on `CAN_PUSH_DEV`, not `CAN_WORKTREE`/`RUNTIME`. Blast radius: in mode 3, a false-positive on `CAN_PUSH_DEV` sends the run down "today's local path: checkout dev, merge --squash... push" — **which includes `git checkout dev` on the live session**, i.e. exactly D6, the hazard the whole design exists to close. Risk 1 names this scenario ("env var absent... believes CAN_PUSH_DEV=true → hits D6") as the design's own worst 3am page, but the mitigation offered is post-hoc recovery narration, not a structural double-guard (see CRITICAL-1).
3. **`GH_OK` probe (`gh auth status`, design-v1-draft.md:84).** Flagged "loud, once" — good; but only the boolean is recorded per Flow 1's narration, not the probe's raw exit/stderr. An operator debugging a misfire cannot tell "gh genuinely unauthed" from "probe itself errored oddly and defaulted false" (see On-Call Ergonomics).
4. **`CAN_SLEEP` (design-v1-draft.md:280, Risk 5 — "the weakest flag").** Design frames the risk as one-directional: turn-yield "needs validation that it can bound a poll without degenerating into rate-limited tight-looping." It does not address the opposite, more dangerous misfire: `CAN_SLEEP` wrongly recorded `true` in mode 3, where the design itself states foreground `sleep` is **blocked** (§2 of design-input.md, mode-3 row). If `bkit_wait_ci` (Flow 5, design-v1-draft.md:164-176) calls `sleep "$POLL_INTERVAL_S"` in an environment that blocks it, the failure mode is not a clean error — it is an indeterminate hang. A hang produces **zero observability**: no `status.jsonl` row (the step never reaches its post-condition), no narrated line, nothing for on-call to read. This is a strictly worse failure than anything D1-D5 named, and the design does not discuss it. Detected by: nothing named. Blast radius: whole run, silent, until an external timeout (session-level, not workflow-level) eventually kills it.
5. **The `push_files` / `merge_pull_request` MCP close transport (Flow 4/6, design-v1-draft.md:150-191).** Per D4, this is a hard prose boundary — bash cannot construct or intercept the tool call, so it cannot grep the commit message for `[skip ci]` **before** the call, unlike the local path where the message is a bash variable. The design's only post-hoc check is the canonical-doc re-read (`git show dev:docs/plans/.../{FID}-design.md`, design-v1-draft.md:158) — this confirms the **write landed**, not that its **message was skip-token-free**. See CRITICAL-2: this is a fully mechanizable bash-side check (`git log -1 --format=%s` / `%B` against the resulting SHA) that the design omits.
6. **D12 corroboration for empty MCP reads (design-v1-draft.md:187-188, 215).** "Corroborate with a second MCP signal (e.g. a `list_*` call)" assumes the corroborating call is failure-independent from the one that returned the wrong zero. The live incident's root cause is explicitly undiagnosed (Open Question 4, design-v1-draft.md:279) — if the defect is systemic to the MCP server's search/list surface on private repos (rather than specific to `search_issues`), the corroborating `list_*` call could return an equally-wrong clean result, and D12's own rule would then legitimately record "corroborated" over a still-false fact. One hop deeper, same class of silent-wrong-result the issue exists to fix.
7. **Adopt-mode `pwd`-outside-worktree coupling (D7, Flow 2, design-v1-draft.md:136).** Correctly identified as same-commit, not a follow-up — good. The one place the design gets "turn silent into loud" unambiguously right: adopt-mode without the rewrite is a guaranteed, loud, first-step Failure Path, not a silent misbehaviour.
8. **Branch-protection / auto-delete-head-branches drift (Risk 4, design-v1-draft.md:268).** Recorded only as a Risk with a recommendation ("should be preflight-asserted... rather than confirmed once by hand"), not committed as a Decision or a Flow step. As written, the design ships without this assertion — an admin flipping a UI setting silently breaks every autonomous close, and nothing in Flow 1-6 checks for it at Step 1 the way `GH_OK`/`CAN_PUSH_DEV` are checked. This is the exact "assumes a human will notice" pattern the review brief asks to flag.

## On-Call Ergonomics

- **Runbook obviousness.** The `runtime-resolved` row gives `RUNTIME`, four `CAN_*`, `WORKTREE_PATH`, `GH_OK` — good raw material, _if written_. But it records only derived booleans, not why a probe returned what it did. An operator seeing `CAN_PUSH_DEV=false` cannot tell "correctly detected read-only token" from "probe threw and defaulted false" without re-running the probe by hand. Recommend the row also carry the probe's raw exit code (and a truncated stderr) for the two probed flags (`GH_OK`, `CAN_PUSH_DEV`) — cheap, and it is the difference between a 2-minute diagnosis and re-deriving state from scratch (which Risk 1 already claims as the recovery story, but only works if the row exists and is legible).
- **Recovery action.** Risk 1's recovery ("`git checkout claude/…` + re-run the close step, no state carried, `RUNTIME` re-derived") is a real, idempotent, human-executable action — good. But it is reactive: it assumes the operator notices the session got yanked off its branch (visible in-session) before anything else happens. If the misfire instead lands on the `CAN_SLEEP` hang (#4), there is no analogous "the session will obviously notice" moment — it just stops. Recommend an explicit outer bound (e.g. `bkit_wait_ci`'s attempt/elapsed cap must be enforced by a mechanism that survives a blocked `sleep`, not one that assumes `sleep` returns).
- **Alert noise.** The bounded-fallback cap (max 1 gh→MCP transition per run, D13) is a good noise control — it turns "how many times did it improvise" into a fixed, reviewable number instead of an open-ended retry storm. No tuning concern here.
- **Diagnosis without the row.** If a mode-3 run misbehaves and the `runtime-resolved`/`transport-fallback`/`close-transport` rows are silently absent (shim-source failure, or a model that skipped both the fallback _and_ the recording rule), on-call has **no way to tell which capability was mis-detected, which transport ran, or why** — they are back to grepping session transcripts, which is exactly the D1/D2 debugging experience the design is trying to eliminate. The design's entire observability story rests on those three rows being written, and two of the three enforcement paths for "were they written" (#1 shim failure, #9 self-referential prose recording) are themselves prose-or-silence, not bash-asserted.

## Operational Dependencies

New on-call burden this design introduces, to be explicitly acknowledged (not blockers, but real):

- A new shipped file (`.bkit/scripts/bkit-runtime.sh`) that must ride every consumer install (D19's "6 sources, not 18 files" framing correctly scopes the edit cost, but it is still a new load-bearing dependency for **every** phase — Risk 2 says as much).
- `status.jsonl` gains three new row kinds (`runtime-resolved`, `transport-fallback`, `close-transport`) that someone/something must actually read. The design names no consumer of these rows beyond ad-hoc human debugging after an incident. Recommend at minimum a `bkit check`/`bkit-analysis` pass that periodically summarises `transport-fallback` frequency and cross-references it against `GH_OK=false` runs, so drift is visible before the next D1-class incident rather than after.
- A `bkit check` assertion (mentioned in Trade-offs, design-v1-draft.md:249, 269) that "every `CAN_*` flag has >= 1 reader" — good, but this is a lint on the _shim_, not on runtime behaviour; it does not catch any of the CRITICAL gaps above (all of which are about what the shim's _output_ is trusted to mean, not whether it's read).
- Branch-protection / auto-delete-head-branches state (Risk 4) becomes an implicit operational dependency of every autonomous close, with no owning preflight check and no doc cross-reference (`docs/deployments.md` is named as the intended home but the design does not commit to writing it there).

## Verdict Reasoning

The architecture is sound and directly answers the two documented incidents (D1's unbounded/unrecorded fallback, and the live `search_issues` silent-zero) with real, load-bearing mechanisms: bounded+recorded+re-asserted fallback (D13), non-authoritative-zero corroboration (D12), and a testable capability shim (D3) instead of unenforceable prose. That is genuine progress over "prose-only," which the design itself correctly rejects as calibration baseline (the direction that produced both incidents).

But held to the bar the review brief sets — _does this turn silent failures loud, or add new silent ones_ — it does both. Four gaps are structural, not stylistic, and each is a plausible 3am page with **no observability at all** as currently specified:

1. The one place a probe misfire has the worst possible consequence (`CAN_PUSH_DEV` false-positive → D6 recurrence) is guarded by the probe alone; the reliable, unprobed signal (`CAN_WORKTREE`/`RUNTIME`) that could catch it for free is not consulted at that call site.
2. `CAN_SLEEP` misfiring in the dangerous direction (foreground sleep blocked, flag says it's fine) produces a hang with zero rows written — worse than any failure mode the design's own risk list names, because a hang precludes the very "narrated line" mechanism the design relies on everywhere else.
3. The MCP close path (Flow 4/6) has no mechanized post-hoc check of the landed commit's actual message/body — only that a canonical file exists. The pre-existing gh-primary path already has a documented, narrower version of this gap (PR-title assertion only, not a post-merge body re-scan — `bkit-ship.md:538-542` vs the actual squash-merge commit at `bkit-ship.md:995-999`), so this is not a new pattern the design introduces so much as one it fails to close on the new transport, despite D1's whole aetiology being "the body scan didn't cover where the token actually leaked."
4. The design's own fallback-recording invariant (`transport-fallback` row) is enforced by the same register (prose) that failed to record D2's original improvisation — there is no bash-side cross-check that a row exists whenever `GH_OK=false` was logged and a close later occurred. This is the design repeating, at one remove, the exact failure shape it was commissioned to fix.

None of these require rearchitecting; each is closable with a modest, concrete addition (a second gate on the checkout, a hang-safe wait primitive, a `git log` grep on the landed SHA, a consistency check between `runtime-resolved` and `transport-fallback` rows). That additive, non-structural nature is why this is CONCERNS rather than FAIL — but they should be resolved (or explicitly deferred with a named owner) before build, not discovered in the next live incident.

## CRITICAL

1. **`CAN_PUSH_DEV` probe misfire is not double-guarded against the reliable `CAN_WORKTREE`/`RUNTIME` signal.** Flow 4 (design-v1-draft.md:150-160) branches the local-checkout path (`checkout dev`) purely on `CAN_PUSH_DEV`. A false-positive probe result in mode 3 reproduces D6 exactly (checkout on the live session) even though `CAN_WORKTREE=false` — a value that is _not_ probed and is high-confidence — is already known at that point and could gate the checkout closed. Add `CAN_WORKTREE=true` (or `RUNTIME != 3`) as a second, unprobed condition before the local-checkout branch fires.
2. **No mechanized post-close check that the landed commit (via any transport) is skip-token-free.** Only a pre-merge PR-title grep exists today (`bkit-ship.md:538-542`); the actual squash-merge body/message is never re-scanned post-hoc, on either the gh path or the new MCP path (`push_files`/`merge_pull_request`, D4/D5). This is a fully bash-expressible, transport-agnostic check (`git log -1 --format=%B` / `%s` against the SHA the close produced) and its absence leaves exactly the vector that produced D1 open for the new transport. Add it as a Flow-4/Flow-6-shared post-condition, independent of which transport ran.
3. **`CAN_SLEEP` misfiring true in an environment that blocks foreground `sleep` produces a silent hang with zero observability** — no `status.jsonl` row, no narrated line, because the step never completes to emit one. The design's Risk 5 only discusses the opposite (safe) misfire direction. Needs either a hang-safe wrapper (e.g. `timeout` around the `sleep` call so a blocked primitive fails loud instead of hanging) or explicit validation, before build, that the platform errors rather than blocks.
4. **Shim-source failure is indistinguishable from a legitimate `unknown`/least-capable detection.** An unset `CAN_*` var and an explicit `false` are bash-equivalent at every call site; nothing asserts the shim actually ran and populated all four flags plus `RUNTIME` before Step 1's narration. Add an explicit post-source assertion (all five variables set, non-empty) that fails loud if the shim didn't execute, distinct from a correctly-detected least-capable row.
5. **The `transport-fallback` audit row is recorded by the same prose register that might skip the fallback rule itself** — there is no bash-side consistency check cross-referencing `runtime-resolved.GH_OK=false` against a later `transport-fallback` row before a `close-transport` row is accepted. Without it, the audit trail this design is built around is only as trustworthy as the compliance layer that produced D1/D2. Add a mechanical assertion at Close Workflow: if `GH_OK=false` was logged at Step 1 and the close used a mapped tool, a `transport-fallback` row MUST exist, else Failure Path.
6. **Branch-protection / auto-delete-head-branches drift is recorded only as a Risk (design-v1-draft.md:268), not committed as a Decision or Step-1 preflight.** As specified, the design ships with no assertion of this precondition, reproducing the "silently breaks every autonomous close" failure Risk 4 itself names. Promote to a committed Step-1 (or pre-close) check, or explicitly defer with a named follow-up issue.

## OPTIONAL

- Record the raw exit code/stderr of the two probed flags (`GH_OK`, `CAN_PUSH_DEV`) in the `runtime-resolved` row, not just the derived boolean — closes the "correctly-false vs probe-malfunctioned" ambiguity for on-call.
- D12's corroboration assumes failure-independence between `search_*` and `list_*` MCP calls that is not established (root cause is undiagnosed, Open Question 4). Log the corroboration attempt and its result as its own distinguishable state (not folded into "corroborated" vs "unavailable") so a later-discovered shared defect is diagnosable from the trail.
- Name an explicit reader/consumer of the new `status.jsonl` row kinds (e.g. a periodic `bkit-analysis` summary of `transport-fallback` frequency vs `GH_OK=false` runs) — an audit trail nobody reads is not operationally an audit trail.
- Consider whether `bkit_wait_ci`'s attempt/elapsed cap should be enforced by a mechanism independent of the primitive being capped (i.e. survives a blocked `sleep` rather than relying on it returning) — same root cause as CRITICAL-3, framed as a general robustness property of the wait primitive.

## OUT OF SCOPE

- The lethal-trifecta prompt-injection surface widened by every extra MCP call (design-v1-draft.md:270) is correctly deferred to #342 and not re-litigated here.
- Whether the live `search_issues` zero-on-private-repo defect is bkit-side or upstream MCP (Open Question 4) is a diagnosis task, not an operability property of this design; D12 mitigates the symptom pragmatically and that trade-off is accepted here, contingent on OPTIONAL item 2 above making a future re-diagnosis possible.
- Artifact seam (Playwright report, Open Question 2) and the `dev`-accepts-`push_files` open question (Open Question 1) are pre-build spikes already named by the design as blocking prerequisites — not additional operability findings.
