# Design Review (re-review 2, operability lens)

Scope: #380 design AS REVISED — body + `## Addendum — Canonical-home revision (post-review, 2026-07-23)`, addendum wins on conflict. Re-assessed against `docs/observability.md`, `docs/deployments.md`, `.agents/rules.md`, and the live `.bkit/workflows/bkit-{design,plan,build,debug,ship}.md` mechanics (dev-lock, worktree, STRAY allowlist, `.bkit/jsonl.md`).

## Failure-Mode Enumeration

Per the four new surfaces named in scope, plus carry-forward from the pre-addendum design:

1. **Reverse tracker-label sync (D)** — fails by: racing a workflow's own in-flight `bkit:*` label MCP write (label flap: sync writes phase X while the workflow is mid-transition to Y); MCP call failure/timeout; a drifted issue with no on-disk FID counterpart (e.g. a Backlog-only issue never designed) that the reconciler can't resolve. Detection today: none named — the addendum states the _requirement_ ("must not fight … reconcile only settled drift") but the design specifies no mechanism (no lease, no `updated_at`/label-generation compare, no cool-down) to actually satisfy it, so a race is not detectable by construction, let alone observable. Blast radius: one tracker issue's label flaps/mismatches the roadmap-canonical phase — visible to any human trusting the tracker label as a proxy for phase, silently wrong until the next cadence pass "fixes" it (possibly by flapping again).

2. **build/debug dev-writes under the dev-lock (C)** — fails by: `DEVLOCK` contention/timeout (`.bkit/.dev.lock`, 600s deadline, 900s staleness reclaim — verified in `bkit-ship.md`); a rejected `git push origin dev` race after lock release; the worktree→`$REPO_ROOT` crossing itself (ship's idiom operates via `git -C "$REPO_ROOT"` from inside `.worktrees/{FID}`, relying on the primary checkout staying parked on `dev` — this precondition is asserted nowhere for build/debug, which today never touches `$REPO_ROOT`/`dev` at all). Detection: unspecified — no `[bkit-roadmap]`-family line is named for _this_ new write path (existing `[bkit-roadmap]` coverage in the design is for the fold's fail-open branches, not for a dev-lock timeout on a workflow that historically has zero dev-lock exposure). Blast radius: potentially the _whole build/debug close_ — the design never says whether a `DEVLOCK` timeout on this new roadmap-status write is fail-open (skip, log, proceed) or fail-closed (abort the close) for build/debug. Ship's own dev-lock sites are inconsistent precedent — one site treats busy-lock as non-fatal ("ship FAILED status left uncommitted on dev; it rides along on the next dev push"), three other sites `exit 1` on deadline. Silently inheriting the fail-closed variant would mean a consumer's otherwise-green build/debug session aborts on a shared-file lock contention that has nothing to do with their code — a new and non-obvious on-call complaint ("my build failed and the error is about `docs/roadmap.md`").

3. **Canonical-source loss / corruption recovery** — `docs/roadmap.md`'s phase sections are claimed regenerable (Reconciliation section: "stays regenerable from … dev-visible on-disk artifacts + each closing workflow's authoritative knowledge of its own FID's phase"), but for an **in-flight build/debug FID** the only durable, dev-visible record of "this FID is currently in Build/Debug" is the row itself — the underlying `status.jsonl` phase-transition history for that FID still lives solely on `feat/{FID}` (unchanged by the addendum; only the row-write is added, not a ledger push). If the row is lost (a bad `-X ours` resolution during the addendum's now-required regenerate-on-conflict-plus-canonical-write, a stray force-op on `dev`, or a mis-scoped `git add`), there is **no passive re-derivation** — nothing re-populates that FID's Build/Debug row until that FID's _own next close_. Detection: none proposed — no reconciliation job cross-checks live `feat/*` branches (or `.worktrees/*`) against the roadmap board's Build/Debug sections for orphaned/missing entries; no alert distinguishes "FID X has no roadmap row because it hasn't started" from "FID X has no roadmap row because its last write was lost." This directly undercuts Addendum A's own invariant ("every item being worked on MUST appear in `docs/roadmap.md` under exactly one phase section") — the invariant is asserted but never checked.

4. **`docs/completed.md` → `docs/completed.jsonl` migration (G)** — fails by: cutover with **no backfill** of historical completed rows. `.agents/docs.md` and `bkit-ship.md:902` (`COMPLETED_HIT=$(grep -c … docs/completed.md)`) confirm `docs/completed.md` is an existing, append-only, read-from artifact with real consumer history. The addendum names "any existing `completed.md` readers migrate together in the same change" (covers the `bkit-ship.md:902` reader) but never mentions a one-time backfill converting pre-cutover markdown rows into `completed.jsonl` rows. Blast radius, concretely tied to finding E: E's "on-disk scan excludes completed FIDs" reads the new ledger to decide what to skip; if `completed.jsonl` starts empty at cutover, **every FID shipped before the migration reappears as active** on the very next roadmap regenerate — this is not a cosmetic bug, it inflates the phase-sectioned board with historical noise and defeats E's stated purpose (bounding per-close cost as `docs/plans/**` grows) on day one of rollout.

5. **Carried-forward, still-relevant from the body** — tracker-read failure/empty (already well-covered: `[bkit-roadmap]`, fail-open, `list_issues`-only); `maxTurns`/context exhaustion on the analysis pass (covered: coverage-stamp + `ROADMAP_SCAN_COVERAGE` counter); mirror-regen staleness (covered: WS-6, batched, dogfooded).

## On-Call Ergonomics

- **build/debug close failing on a `DEVLOCK` timeout** — runbook obviousness is poor as specified: the design gives no error text template for this new failure surface (contrast ship's existing `"dev lock held by: … — serialise this run or use a separate clone"`, which at least tells the operator what to do). If build/debug silently inherits `exit 1`-on-deadline from the ship idiom being reused verbatim, a consumer mid-build sees a roadmap-lock error with no obvious link to their actual work — poor "runbook obviousness from alert payload." Recovery action is not stated as automatic/idempotent/human: does a retry on next build-step re-attempt the write, or is the row permanently skipped for this close? Needs an explicit fail-open decision (recommend: fail-open, log, defer to next close — consistent with the design's own "regenerate-on-conflict … non-event" philosophy) written into the design/plan, not left implicit.
- **Reverse tracker-label sync flapping a label** — no alert exists to notice flapping (a label toggling between two values across successive cadence runs due to an unresolved race). Purely silent unless a human happens to watch tracker notification noise. Recovery is implicitly "next reconcile pass," which is exactly the failure mode repeating if the underlying race condition isn't fixed — noise-prone by construction until the settled-vs-in-flight detection is actually specified.
- **Missing/orphaned canonical row for an in-flight FID** — no alert, no dashboard. Discovery today would be entirely human: someone notices `docs/roadmap.md` doesn't list a FID they know is being worked on. For an artifact the addendum explicitly promotes to "canonical home for issue state," this is the highest-value missing alert in the whole design.
- **`completed.jsonl` post-migration board bloat (finding 4)** — discovery is via a human noticing the roadmap board is suddenly full of long-shipped FIDs after the upgrade that ships G; no automated check flags "on-disk scan count post-migration >> pre-migration count." Cheap to add (a one-time sanity assertion in the ship/upgrade path), currently absent.
- **Good ergonomics carried from body** — the `[bkit-roadmap]` fail-open discipline on the fold, the coverage-stamp + `ROADMAP_SCAN_COVERAGE` counter for maxTurns exhaustion, and the marker-block self-heal (bootstrap vs mangled-marker vs hand-edit, each with a distinct decided behaviour and a stderr line) are genuinely well-specified — noise-tuned (best-effort, never gates) and runbook-obvious (the banner text plus the "reasons for staleness" header stamp double as the runbook).

## Operational Dependencies

- **New shared mutex users** — build and debug now contend on `.bkit/.dev.lock` alongside design/plan/ship. This is not a new mechanism (reuses ship's idiom) but is a new _load_ on an existing mechanism: build/debug closes are historically far more frequent than ship closes (multiple build/debug cycles per ship, especially debug retry loops), and the worktree model exists specifically to let multiple `feat/{FID}` build/debug sessions run in parallel across worktrees of one clone — this design reintroduces a serialization point into what was previously an embarrassingly-parallel close path. Must be acknowledged explicitly in the plan, with a stated fail-open/fail-closed decision (see Failure Mode 2) — not silently inherited from ship's mixed precedent.
- **New CI/bats coverage surface** — the body already mandates a "per-workflow-shape-aware CI/bats assertion" (3 shapes: design/plan STRAY-widen, build/debug `git add -A`, ship's scoped `git add -- docs/`). The addendum adds a **4th shape** (build/debug's new dev-lock-mediated write to `$REPO_ROOT`, distinct from their existing feat-branch `git add -A`) that the Workstream Impact section does not call out as requiring its own assertion — the existing WS-2 rationale text ("three shapes") is now stale and must be updated to five workflows / (at least) four staging+write shapes, or the exact gap the body itself warns against ("a naive grep passes while a build/debug close silently mis-stages") recurs one level up, for the new dev-write instead of the STRAY-allowlist.
- **New machine-readable ledger** — `docs/completed.jsonl` (peer of `deferrals.jsonl`/`failures.jsonl`, `.bkit/jsonl.md` format) is a new consumer-visible file requiring the same care as any other JSONL ledger addition (`.bkit/jsonl.md`'s "Ledgers & Writers" table needs a new row for `@bkit-ship-update-docs`'s write, and — per finding 4 — a backfill step this design doesn't currently name).
- **Board-visibility expectation on maintainers** — Addendum A raises the bar from "convenience view" to "canonical home… every item MUST appear" — this is a new operator expectation (dashboards/triage habits shift to trusting `roadmap.md` over the tracker) that should be acknowledged as a genuine behavior change for on-call/maintainer workflow, not merely a mechanical data-model change.

## Verdict Reasoning

The pre-addendum design's operability posture was strong: regenerate-on-conflict as the core anti-fragility property, consistent `[bkit-roadmap]` fail-open discipline, a first-class coverage counter instead of a Risks-section aside, and well-thought-out marker-block self-heal semantics. The addendum's core _mechanical_ moves (phase-sectioned board, FID-as-key, exclude-completed scoping) are sound extensions of that same regenerate-on-conflict model and do not by themselves break operability.

The gap is that the addendum inverts the authority model (tracker-as-mirror instead of tracker-as-truth) and adds four materially new write/sync surfaces — reverse tracker-label sync, build/debug dev-writes, a promoted canonical-recovery invariant, and a ledger-format migration — **without carrying forward the same observability/fail-open rigor the rest of the design applies everywhere else.** Each of the five failure modes above is a genuine, concrete gap (not speculative): a specified requirement with no specified mechanism (D's "must not fight"), an inherited-but-undecided failure policy (C's dev-lock fail-open/closed), an asserted-but-unverified invariant (A's "every item MUST appear"), and a migration with no backfill (G) that breaks a _different_ addendum item (E) on rollout day. None of these is architecturally irreconcilable — they are each a "the plan must specify X" gap consistent with how the body itself already defers several items to Plan (e.g. exact upsert-vs-regenerate mechanism) — but there are enough of them, several load-bearing for correctness on rollout, that this does not clear PASS as revised. **CONCERNS**: address the CRITICAL items below (at minimum: build/debug dev-lock fail-open decision + error text, `completed.jsonl` backfill, the reverse-sync race-avoidance mechanism, and extending the shape-aware CI assertion to the new dev-write shape) before or during Plan; nothing here requires re-opening Design.

## CRITICAL

- **Build/debug dev-write fail-open/fail-closed is undecided.** The addendum says build/debug now write roadmap status to `dev` "under ship's existing dev-lock idiom," but ship's own dev-lock sites are inconsistent precedent (one non-fatal, three `exit 1`-on-deadline). Must explicitly decide (recommend fail-open, matching the design's own regenerate-on-conflict philosophy) and specify the error text / log line, distinct from the fold's existing `[bkit-roadmap]` fail-open lines, so on-call can tell "roadmap dev-write skipped" from "build/debug actually failed."
- **`docs/completed.md` → `docs/completed.jsonl` has no backfill plan.** Without converting historical `completed.md` rows into `completed.jsonl`, finding E's "exclude completed FIDs from the on-disk scan" silently fails open in the wrong direction on rollout — every pre-migration shipped FID reappears as active on the roadmap board, inflating the board and defeating E's stated cost-bounding purpose immediately.
- **Reverse tracker-label sync (D) states a requirement with no mechanism.** "Must not fight a workflow's own in-flight label write; reconcile only settled drift" needs an actual settled-vs-in-flight detection (e.g. compare label state against a lease/timestamp, or gate the sync to only run when no workflow currently holds `DEVLOCK`/a per-FID lock for that issue) and a dedicated, bracketed-prefix log signature for fire/skip/conflict distinct from the existing `[bkit-analysis]` cadence line.
- **No reconciliation/alert for the canonical-artifact invariant itself.** Addendum A asserts "every item being worked on MUST appear in `docs/roadmap.md` under exactly one phase section" but the design proposes no check (e.g. diff live `feat/*`/`.worktrees/*` against the Build/Debug board sections) that would catch a violation — for an artifact explicitly promoted to canonical, this is the single highest-value missing observability item.
- **The per-workflow-shape-aware CI/bats assertion is stale post-addendum.** It currently covers 3 staging shapes; the addendum's build/debug dev-write is a 4th distinct shape (a `DEVLOCK`-mediated write to `$REPO_ROOT`, not the existing feat-branch `git add -A`) that must get its own assertion or the exact "naive check silently misses a shape" failure the body warns about recurs for the new surface.

## OPTIONAL

- Give the reverse-sync (D) and the build/debug dev-write (C) each a distinct `[bkit-*]`-family prefix (e.g. `[bkit-roadmap-sync]`, reusing `[bkit-roadmap]` for the write side) so a single grep can isolate each new surface's health independently of the existing fold fail-open lines.
- Add a one-time sanity assertion after the `completed.jsonl` cutover ships (e.g. compare on-disk-scan FID count immediately pre/post migration) so a missed or partial backfill is caught mechanically rather than by a human noticing board bloat.
- Consider whether the reverse-sync (D) should log a distinguishable "drift found, corrected" counter (mirroring `ROADMAP_SCAN_COVERAGE`'s pattern) so drift _rate_ is trend-visible rather than only per-event log lines — useful signal for whether the two-way sync is stable or chronically fighting something.
- Document explicitly, in the plan, what happens to a build/debug close's _overall_ success/failure status when only the roadmap dev-write sub-step fails (vs. the primary build/debug work succeeding) — this is implied by "best-effort, never gates" elsewhere in the design but should be stated for this specific new write, not left to precedent-matching against ship's mixed dev-lock handling.

## OUT OF SCOPE

- General reverse-sync design (label-write conflict resolution algorithms, e.g. CRDT-style or vector-clock approaches) — the design correctly scopes D as "MCP-only, best-effort, idempotent" for v1; a more robust conflict-resolution scheme is future work if the flapping failure mode proves real in practice.
- #260's eventual full actuator/contract — explicitly and correctly deferred by the design (fold/leaf boundary preserves the evolution path); not re-litigated here.
- Full dev-lock redesign (e.g. per-resource locking instead of one repo-wide `.bkit/.dev.lock`) to reduce the new build/debug contention — the addendum's choice to reuse the existing singleton lock is reasonable for v1 given no evidence yet of it being the wall-clock pole; revisit only if the cadence-driven parallelism regression (Operational Dependencies, bullet 1) is observed in practice.
