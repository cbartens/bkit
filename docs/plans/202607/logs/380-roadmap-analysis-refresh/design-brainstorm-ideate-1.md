# Design Brainstorm & Ideas

Lens: Pragmatic — existing code, minimal new infra, ship fastest.

Scope anchor: two-tier roadmap model confirmed by owner — (1) cheap mechanical phase-status write on every workflow close, (2) opus-scale analysis refresh on ship-close + on-demand. `docs/roadmap.md` is the sink (file, not tracker issue). Reuse targets already in-repo: ship Step 10's parallel-subagent pattern (`@bkit-ship-update-docs` ‖ `@bkit-ship-summary`), the dev-lock/dev-write idiom, `bkit:*` phase-label transitions done in every workflow's Step 1, `plan-complexity-check` (when-NOT-to-use heuristic), `design-organise` (grouping/dependency seams), the audit prompt family (`bkit-utility-audit-*`), and the shell-helper convention (`.bkit/scripts/bkit-status-fold.sh`).

## Approach A — Reuse-in-place: ship-Step-10 analysis subagent + shared mechanical shell helper ⭐ Recommended

Summary: Add the full-analysis engine as a third parallel subagent (`@bkit-ship-roadmap-refresh`) inside ship's existing Step 10 (Update Docs & Summary), and add the mechanical phase-row write as a tiny deterministic `.bkit/scripts/bkit-roadmap-mechanical.sh` invoked at each workflow's existing phase-label-transition step (piggybacking the dev-lock) — faithfully implementing the owner's confirmed two-tier model with zero net-new orchestration steps.

- Complexity: MEDIUM. Analysis tier is near-free (clone the Step 10 parallel-invocation block + a new prompt file). Cost sits in the mechanical tier touching the label-transition step of all 5 shipped workflows (× cross-provider mirror regen) and reasoning about where the write lands (main-checkout `dev` under dev-lock, since design/plan/build/debug run on `feat/{FID}` worktrees whose commits are invisible to sibling issues until merge).
- Extensibility: HIGH. New phases/columns = edit one shell helper + one prompt. The analysis subagent is a leaf, so promoting it to #260's tick (Approach C's goal) later = re-point an invocation, not a rewrite.
- Risk: Mechanical-write branch visibility. A per-workflow roadmap edit must reach the shared `dev` checkout to serve as a live board other agents read; committing it on the feature worktree defeats the "other agents see status" requirement. Mitigation: reuse ship's exact dev-lock + `git -C "$REPO_ROOT"` dev-commit idiom, but this adds a dev-write to workflows that today never touch dev (design/plan) — the main design decision to resolve.
- Maintenance: LOW-MEDIUM ongoing. One shell helper + one prompt to keep current; mechanical tier is deterministic (no LLM drift). Cross-provider parity assertions already exist for shipped surfaces.
- Reuse vs new: HIGH reuse — parallel-subagent block, dev-lock, tracker-label list, status-fold-style helper. Net-new: one prompt file, one shell helper, one `docs/roadmap.md` row in `.agents/docs.md`.

## Approach B — Ship-close-only + on-demand `/bkit-roadmap` utility; phase board derived from live tracker labels

Summary: Drop the per-workflow mechanical writes entirely; run the analysis subagent only at ship-close (Step 10) and via a new `/bkit-roadmap` utility workflow, and have the refresh regenerate the phase-status board from live `bkit:*` label state (`list_issues` MCP) instead of incremental per-close edits — the design-input's own v1 phasing, minimal-touch.

- Complexity: LOW-MEDIUM. Only ship + a new thin utility workflow (mirror the `bkit-worktree-*` utility shape); no edits to design/plan/build/debug closes, no new dev-writes outside ship, no cross-branch visibility problem.
- Extensibility: MEDIUM. Adding richer per-issue state later still means going back and instrumenting the individual closes (the work Approach A does now).
- Risk: Staleness between ships. Phase board is only current as of the last ship-close or last manual `/bkit-roadmap` run; an in-flight design/plan won't surface until the next ship. Diverges from the owner's explicit "each workflow moves the row" ask — must be re-confirmed as an acceptable v1 simplification.
- Maintenance: LOW. One prompt + one utility workflow; board is a pure projection of tracker truth, so no incremental-write consistency bugs.
- Reuse vs new: HIGH reuse — utility-workflow skeleton, ship Step 10 pattern, tracker `list_issues`. Net-new: one prompt, one utility workflow file, `docs/roadmap.md` index row. Fewer shipped-surface touch-points than A.

## Approach C — Build the #260 sensing primitive once: standalone `@bkit-sense` leaf + roadmap writer

Summary: Factor the "reconstruct the frontier" pass into a standalone sensing subagent (`@bkit-sense`) that emits a structured frontier snapshot, with a thin roadmap-renderer on top; #380 wires it to ship-close + `/bkit-roadmap`, and #260's future tick consumes the identical agent — honouring improve-over-duplicate against the stated evolution path.

- Complexity: HIGH. Requires designing a stable frontier-snapshot contract now (issues × phase × dependency × ledger/audit candidates) that both #380 rendering and an unbuilt #260 actuator can consume.
- Extensibility: HIGH (best). One sensing engine, many consumers; ledger/audit-injection and grouping logic live in the shared primitive, not duplicated per surface.
- Risk: Speculative scope. Designing to #260's unbuilt tick contract violates YAGNI/no-speculative-scope; the snapshot schema is guesswork until #260 is designed, and over-abstraction may need rework anyway.
- Maintenance: MEDIUM-HIGH. A schema contract with two consumers is a coordination surface; snapshot-format changes ripple.
- Reuse vs new: MEDIUM. Reuses grouping/complexity heuristics but introduces a net-new agent + snapshot artifact contract ahead of demand.
