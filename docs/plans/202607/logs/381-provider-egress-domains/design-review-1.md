## Stack Feasibility

Buildable. Verified against source in this worktree, not taken from the draft:

**Import graph — the leaf module plan compiles.** `.bkit/src/bkit-cloud-env.ts` imports only `node:fs`, `node:path`, `type IssueTracker` from `bkit-manifest.js`, `getTemplatesRoot` from `bkit-paths.js`, `applyTokens` from `bkit-tokens.js` — it does **not** import `bkit-modules.js`. `bkit-modules.ts:59-65` imports `writeClaudeCloudDoc`, `writeCursorCloudDoc`, `resolveNetworkAllowlist`, `networkAllowlistBases`, `writeNetworkAllowlistArtifact` from `bkit-cloud-env.js`. Direction is exactly as the draft states; a new import-free `bkit-registry.ts` introduces no cycle, and the draft is right that a `cloud-env -> modules` edge would be a module-init TDZ failure, not a survivable cycle.

**Coverage lane.** `package.json:47` (`test:coverage:unit`) is a literal brace list containing `cloud-env` and not `modules`; `--coverage.thresholds.branches=70`. A new `bkit-registry.ts` is outside `--coverage.include`, so it is unmeasured — which is fine only while it stays branch-free, exactly as designed. `--coverage.include` does not affect test _selection_, so tests over the leaf still run. The reasoning at draft line 103 is correct and matches the recorded precedent at `slop-scan.config.json:157`.

**`slop:delta`.** Verified the two per-symbol exemptions the draft cites: `.bkit/src/bkit-cloud-env.ts` / `structure.pass-through-wrappers` at `slop-scan.config.json:156-157`; `[".bkit/templates/.cursor/hooks/guardrails.cjs", ".cursor/hooks/guardrails.cjs"]` / `defensive.empty-catch` at `:174-175`. Both are **file-scoped**, not symbol-scoped, so new functions in `bkit-cloud-env.ts` inherit the pass-through exemption and no new exemption is needed. Net finding count should fall (a hardcoded array is deleted). The prune path adds no new `catch`: `readBkitVersion`/`writeBkitVersion` are already imported at `bkit-modules.ts:24-25` and `parseBkitVersion`'s catch is pre-existing.

**Node engine.** `package.json:28-30` = `"node": ">=20"`. `URL.canParse` available. Confirmed `new URL(...).hostname` strips the port for free, so the "ports" edge case needs no code.

**Derivation rule is implementable and the table is arithmetically right.** All 10 keys of `OPENCODE_PROVIDER_DEFAULTS` (`bkit-modules.ts:1397-1496`) verified: `integrate.api.nvidia.com`, `api.groq.com`, `api.cerebras.ai`, `openrouter.ai`, `ollama.com`, `api.z.ai`, `api.moonshot.ai` all collapse to the stated bases and pass `base === host || host.endsWith("." + base)`; `ollama-local` is `http://localhost:11434/v1`; `opencode-zen`/`opencode-go` have `baseURL: ""` (`URL.canParse("")` is false). 10 keys, not 11 — draft correct.

**Not implementable as written:** IP-literal rejection. Draft enumerates it as a failure case but gives no detector. `new URL("https://1.2.3.4/v1").hostname` is `"1.2.3.4"`, which passes the `>= 2 labels` gate and collapses to `3.4`; IPv6 yields the bracketed `"[::1]"`, which fails the label gate as CI-red rather than "contributes nothing" as the Process Sketch promises. The two mechanisms (proposer-rejects-silently vs gate-fails-CI) need an explicit split for this case.

## Library / API Evaluation

- **No new dependency proposed, and none is needed.** `psl`/`tldts` correctly rejected — see Ecosystem Search. Keeping the runtime dep set at `picomatch` alone preserves the packed-tarball dogfood posture.
- **`node:crypto`** for the 8-hex fingerprint — already imported by `bkit-version.ts`; `sha256` is exported there (`bkit-version.ts`, `export function sha256`). Reuse rather than a second hasher. Note `bkit-cloud-env.ts` does not currently import `node:crypto` or `bkit-version.js`; importing `bkit-version.js` from `bkit-cloud-env.ts` is cycle-free (`bkit-version.ts` imports only node builtins).
- **`BkitVersion` typing.** `tier3Hashes` and `canonicalHashes` are **required** properties (`bkit-version.ts:37-65`), defaulted inside `parseBkitVersion`. Adding a required `webFetchDerived: string[]` breaks the object-literal construction sites in source (`bkit-modules.ts:926`, `bkit-version.ts` parse return, `bkit-upgrade.ts:477-481`); the `{...bkitVersion, ...}` spreads at `bkit-upgrade.ts:481` and `:528` and `migrateStrayGitattributes` survive untouched. `tsconfig.json` excludes `**/*.test.ts` from `tsc --noEmit`, so the ~48 test-side `tier3Hashes:` literals will **not** break typecheck. Low cost — but the draft should say which shape it means.
- **License/bundle:** N/A (no new package). `check:dist` gate applies: a new `.bkit/src/bkit-registry.ts` produces `dist/bkit-registry.js`, which must be built and committed in the same change or `pnpm check:dist` fails.

## Integration Risk

**Systems touched, verified:**

- `.bkit/src/bkit-cloud-env.ts` (derivation, both cloud renderers, artifact writer) — unit-lane measured, 4 downstream call sites.
- `.bkit/src/bkit-modules.ts` (registry move, enrich+prune, `injectOpencodeNetworkCurlAllows`) — integration-lane only; `OPENCODE_PROVIDER_DEFAULTS` confirmed module-private (`const`, no `export`) with 4 in-file uses (`:1508`, `:1518`, `:1642`, `:1965`) plus the declaration. Grep confirms no external import. Move cost is genuinely one import line.
- `.bkit/src/bkit-version.ts` + `.bkit/src/bkit-upgrade.ts` — new field.
- `.cursor/hooks/guardrails.cjs` + its template twin — `diff` confirms they are **byte-identical today**, so test 6 (hook byte parity) passes as-is and is a pure regression guard.
- `.bkit/templates/.claude/settings.json` — the seed is exactly as claimed: 7 of 13 bases carry only the `*.` form (`githubusercontent.com`, `anthropic.com`, `claude.com`, `linear.app`, `opencode.ai`, `ollama.com`, `nvidia.com`).

**Blast radius — where it is smaller than the draft fears:**

- `.cursor/allowlist.json` is **git-tracked** (`git ls-files` confirms) and appears in no `.gitignore` rule and in no manifest (`CURSOR_MANIFEST`, `bkit-manifest.ts:262-274`, has no entry). So the "fresh clone has the hook but not the artifact" case does not arise by default — deleting `SHIPPED_NETWORK_BASES` is safe at first install, and a crash between the hook write (`bkit-modules.ts:1272-1281`) and the artifact write (`:1332-1341`) degrades to **ask**, i.e. fail-safe, in a partially-completed install. Upgrade parity confirmed at `bkit-install.ts:2594-2604` under `renderModules.has("cursor")`.
- `deepContains` uses **subset** semantics for arrays (`bkit-tiers.ts:69-71`), so emptying the template's `permissions.allow` WebFetch entries strictly relaxes containment — `bkit check` cannot regress from it.
- No test anywhere in the repo asserts a `WebFetch(domain:…)` literal. Repo-wide grep finds hits only at `bkit-modules.ts:1717` (JSDoc) and `:1748` (the generator). **This resolves the draft's open question 5: the answer is no.** The opencode↔claude gate-parity assertion in `bkit-modules.integration.test.ts` covers bash gates, not WebFetch.
- Only two `BKIT_SHIPPED_NETWORK_DOMAINS` assertions exist and both are negative (`bkit-cloud-env.test.ts:406-407`), so switching the constant to a computed value breaks nothing.

**Where it is larger than the draft accounts for:** the `.bkit/version` write path (CRITICAL 1) and the tests that assert the retired Trusted branch (`bkit-cloud-env.test.ts:326-329` and `:399-402` both assert `"Set to **Trusted** (default)"` for `renderCloudNetworkAllowlist`) — those two must be rewritten in the same change, and the draft's Docs table does not list them.

## PoC Approach

Do not build. Minimal proof, ~1 hour, three assertions, no production edit:

1. **Derivation + gate, in a scratch vitest file.** Copy the 10 `baseURL` strings into a fixture array; implement `URL.canParse` -> `hostname` -> reject `""`/`localhost`/`*.localhost`/IP-literal -> last-two-labels; assert the 8 expected bases, that `ollama-local` and both builtins yield nothing, and that `https://1.2.3.4:8080/v1`, `https://[::1]/v1`, `https://api.pages.dev/v1` and `https://x.example.co.uk/v1` each land in the _intended_ rejection channel. This is the only genuinely unproven logic.
2. **Provenance write path.** In a tmp dir, seed `.bkit/version`, write a `webFetchDerived` field from a stub, then run the real `runCoreModule` postDispatch writer and read the file back. Confirms whether the field survives an install (see CRITICAL 1) before any prune code is written.
3. **Fan-out injectability.** One throwaway test file that `vi.mock`s a stub `bkit-registry.js` and imports `bkit-cloud-env.js`, asserting the mocked row reaches `resolveNetworkAllowlist`. Proves test 5 is expressible against a module-init `const`.

If (2) fails, the prune sub-feature is re-scoped before the plan, not during the build.

## Unknowns & Blockers

1. **Does the `.bkit/version` provenance field survive an install?** Not blocked on experimentation — read `bkit-modules.ts:858-930`; it does not. See CRITICAL 1. The plan must name the writer.
2. **Does an opencode built-in gateway session actually contact `models.dev`?** Unresolved. `models.dev` appears only in code comments (`bkit-modules.ts:1405`, `:1480-1483`, `:2013`) and `.bkit/prompts.md` — never as a URL bkit issues. Cheap to settle by running an `opencode-zen` session with the host blocked; low risk either way. Design's "included pending verification" is acceptable.
3. **Dashboard "Allowed domains" field upper bound** (Claude web / Cursor). Unmeasured; at ~19 bases the paste is ~38 lines, far from any plausible cap. Not a blocker now; keep as the deferral the draft records.
4. **Whether `.bkit/version` should carry consumer stack domains.** `webFetchDerived := resolveNetworkAllowlist(cwd)` includes consumer `allowed-domains`, so a consumer's `vercel.com`/`sentry.io` land in a repo file. `.bkit/version` is already consumer-varying (per-consumer `canonicalHashes` paths) and is not shipped (`package.json` files has `"!.bkit/version"`), so this is a note, not a blocker — but it should be a stated consequence, since the design elsewhere leans hard on "no consumer content in bkit-owned artifacts".
5. **`ISSUE_TRACKERS` contains `"none"`** (`bkit-manifest.ts:70`). The completeness test "every key of every registry has a row" needs an explicit answer for it.

## Verdict Reasoning

CONCERNS, not PASS and not FAIL.

Not FAIL: the spine is feasible on the approved stack with zero new dependencies. The import direction, the leaf-module cycle avoidance, the coverage-lane reasoning, the manifest formats, the same-pass Cursor write guarantee, the byte-identical hook twin, the subset semantics of `deepContains`, the absence of any WebFetch test assertion, and all 10 registry derivations were each verified against source and hold. The draft's ground-truth table is unusually accurate — every line-number claim I checked (`bkit-cloud-env.ts:471-485/505-507/546-557/646-669`, `bkit-manifest.ts:239/267`, `guardrails.cjs:110-124/126-145/154-192`, `bkit-modules.ts:59-65/1033/1272-1281/1332-1341/1397/1706-1714/1716-1758`, `bkit-install.ts:2594-2604/2605-2616`, `slop-scan.config.json:156-157/174-175`, `package.json:28-30/47`) resolved correctly, and the six claimed live gaps are all real (`groq.com`/`cerebras.ai`/`openrouter.ai` absent from the shipped 13; `api.githubcopilot.com` at `.bkit/templates/.mcp.json:9`, `.bkit/templates/.cursor/mcp.json:9`, `bkit-modules.ts:1651`; `skills.sh` at `.bkit/templates/.agents/skills.md:17`; `models.dev` per (2) above).

Not PASS: four defects would each surface as rework or a shipped bug if the design proceeded verbatim — one of them (the `.bkit/version` write path) can make `bkit check` never reach 0 writes, which contradicts the design's own Success Criterion 3 and is a release gate. All four are addressable inside this design's shape, so the design proceeds once they are closed.

## CRITICAL

1. **`webFetchDerived` has no viable write path as designed.** `runCoreModule`'s deferred `postDispatch` writer (`bkit-modules.ts:858-930`) writes `.bkit/version` from a **fresh object literal** `{ pinnedVersion, tier3Hashes, canonicalHashes }` — it reads the existing file only for the two hash maps. `enrichClaudeSettingsWebFetch` runs earlier, inside `runClaudeModule` (`:1033`), so anything it records is clobbered before the install ends. Two outcomes, both bad: (a) the field is never persisted, `previous` is always `[]`, and the prune is dead code that passes its own unit tests (which seed `.bkit/version` by hand) while never firing in production; or (b) if enrich also pushes `.bkit/version` into `ws.writes`, every `bkit check` reports a pending write and the CI drift gate is permanently red — directly violating Success Criterion 3. The design must name the writer: thread the derived list into the postDispatch literal, extend the `needsWrite` predicate (`versionChanged || hasNewEntries`) to include "derived set changed", and state the dry-run rule (never record under `dryRun`). Note the upgrade path is already safe — `updateCanonicalHashesAfterUpgrade` uses `{ ...bkitVersion, ... }` (`bkit-upgrade.ts:477-481`) — so install and upgrade currently disagree.
2. **The `EgressSource` type contradicts the populated set it is supposed to hold.** The type declares `id: string` and `base: string` (singular), but three rows in the § Populated set table carry composite ids and multiple bases: `agent-host / claude / cursor / opencode` -> 4 bases; `package-registry / npm / github` -> 3 bases; `opencode-zen / opencode-go` -> 2 bases in one row. As written the data cannot be expressed. Either `base: string` becomes `bases: readonly string[]`, or the table splits to one row per base — and the completeness test ("table-driven over `Object.keys`, so a new registry entry fails until it declares") cannot key on composite ids like `claude / cursor / opencode`. Pick one before the plan; the choice changes the derived-export shapes and every test in § 6.
3. **The fingerprint line, as specified, gets pasted into a vendor dashboard field.** `renderCloudNetworkAllowlist` emits the domains inside a ` ```text ` fence that the doc instructs the consumer to paste verbatim into "Allowed domains" (one per line). A `# bkit-allowlist <8 hex>` line placed "into both cloud paste blocks" lands inside that fence and is submitted as if it were a domain. The fingerprint must be rendered as prose **outside** the fenced block (both `.claude/cloud.md` and `.cursor/cloud.md`), and the design should say so explicitly rather than leave it to the builder.
4. **The prune's safety claim is false as stated, and its recording rule is under-specified.** "`previous \ current` is the only removal set that **provably cannot** delete a consumer's hand-added grant" (§ Remaining decisions) is contradicted by the design's own Trade-offs paragraph ("a consumer who hand-added a domain that later also appears in the derived set ... will be pruned"). Restate the guarantee honestly ("cannot delete a grant bkit never recorded writing"). Separately: `enrichClaudeSettingsWebFetch` has three early returns before it writes anything — file absent, `JSON.parse` failure, `permissions.allow` not an array (`bkit-modules.ts:1737-1747`) — plus `dryRun`. If `webFetchDerived := current` is recorded on any of those paths, bkit claims grants it never wrote, and the _next_ run's `previous \ current` can delete consumer entries. The record must be written only on the path that actually wrote the file.

## OPTIONAL

- **Rows with `hosts: []` and a non-empty `base` silently narrow the Cursor cloud surface.** `kimi-docs` is declared `hosts: []`, `base: "kimi.com"`. `BKIT_SHIPPED_NETWORK_HOSTS` is defined as "sorted unique `hosts`", so `kimi.com` disappears from `renderCursorNetworkAllowlist` — the exact #376 grant the design elsewhere insists on preserving, regressed on one surface. `kimi.com` is a knowable host; give the row `hosts: ["kimi.com"]`, or define `BKIT_SHIPPED_NETWORK_HOSTS` to fall back to `base` when `hosts` is empty.
- **Specify the IP-literal detector.** Cover bracketed IPv6 (`hostname` returns `"[::1]"`) and dotted-quad IPv4 (which otherwise passes the `>= 2 labels` gate as `3.4`), and say which channel each uses — silent "contributes nothing" (per the Process Sketch) or CI-red gate rejection. They currently disagree.
- **Say how test 5 (injected provider) injects.** `BKIT_SHIPPED_NETWORK_DOMAINS` is computed at module init, so injection requires a hoisted `vi.mock("./bkit-registry.js")` that applies to the whole test file — which would also perturb the provider-rendering tests in `bkit-modules.integration.test.ts`. Either put test 5 in its own file, or export a pure `deriveEgressEntries(rows)` and assert each surface against the exported constant rather than a literal.
- **Add the two Trusted-branch tests to the Docs/changes table.** `bkit-cloud-env.test.ts:326-329` and `:399-402` both assert `"Set to **Trusted** (default)"` from `renderCloudNetworkAllowlist`; retiring that branch breaks them. § 5 lists six docs but no test file.
- **Close open question 5 now.** No test in the repo asserts any `WebFetch(domain:…)` string (only `bkit-modules.ts:1717` and `:1748`). Emptying the template array does not touch the gate-parity assertion. The draft's "likely yes" is wrong; leaving it open invites a wasted plan-time investigation.
- **State the `BkitVersion` field shape.** `canonicalHashes` is _required_ on the interface with the default applied in `parseBkitVersion` — "additive exactly like `canonicalHashes`" therefore means required-with-parser-default, touching 3 source construction sites. Test literals are safe (`tsconfig.json` excludes `**/*.test.ts`).
- **Answer `ISSUE_TRACKERS.none` and `DEP_UPDATERS.none`** in the completeness test's contract, so "every key of every registry has a row" is mechanically satisfiable.
- **`json.schemastore.org`** is shipped in `.bkit/templates/.claude/settings.json` (`$schema`) and is the one remaining bkit-configured host outside the populated set. Success Criterion 2 says "no other domain list exists in the repo" — either declare it as a `docs`/`schema` row or record why an editor-fetched `$schema` host is deliberately out.
- **`check:dist`**: the new `dist/bkit-registry.js` must be built and committed in the same change or `pnpm check:dist` fails the CI lane.
- **Fingerprint stability**: derive it over the sorted _derived_ set only, not the consumer union, or every `allowed-domains` edit changes the fingerprint and re-triggers the "your paste is stale" signal for a change the consumer already knows about.

## OUT OF SCOPE

- **Fixing the OpenCode `curl *{base}*` substring-glob weakness.** Correctly bounded by OpenCode's permission schema (no URL-host primitive); the design's decision to document it in `.bkit/providers.md` rather than fix it is the right call. Track as the deferral already named.
- **A unified runtime allowlist artifact read by all three IDE surfaces.** Blocked by Claude `permissions.allow` and OpenCode `permission.bash` requiring literal per-host strings; the draft's rejection with a "do not re-propose without re-discovering this" note is correct.
- **A bootstrap-time cloud reachability probe** to detect a stale dashboard paste. Genuinely the only mechanism that closes the human-transport gap, but it is a new cloud-session capability, not a derivation change. Defer.
- **`developer.mend.io` / `depot.dev` (dep-updater hosts).** Egress is on GitHub Actions runners, not in an agent session; exclusion with a recorded reason is correct.
- **Removing WebFetch grants on `bkit uninstall`.** `.claude/settings.json` uninstall uses `stripTier2JsonScope` against the manifest template; with the seed emptied, enrich-added grants are no longer template-scoped and will survive an uninstall. A real consequence of emptying the seed, but a separate uninstall-hygiene concern — record it, do not solve it here.
