### C1 — CRITICAL · mechanical · `fix/**` CI success routes to `/bkit-ship`, which is structurally `feat/{FID}`-only

- **lens:** R1 (bugs / edge cases)
- **location:** `.bkit/templates/.github/workflows/bkit-cloud.yml:192` (+ mirror `:472`, live `.github/workflows/bkit-cloud.yml:192`/`:472`) → `.bkit/workflows/bkit-auto.md:142`,`:204` → `.bkit/workflows/bkit-ship.md:336-345`,`:368`

Step 2.4 (`:368`) then runs `gh pr list --head "$(git branch --show-current)"` = `feat/{FID}` → no PR → **Failure Path**, which posts a failure comment and sets `bkit:failed`. Net: every opted-in debug fix PR that goes green now **fails the issue** and leaves the green fix PR unmerged — strictly worse than the pre-change silence, and the plan's Breaking-Changes claim "cloud auto-merges the fix PR" cannot occur. Downstream ship steps that do fire act on the wrong ref: `gh workflow run ci.yml --ref feat/{FID}` (`bkit-ship.md:545`), gate `--branch feat/{FID}` (`:668`), cleanup `git push origin --delete "feat/{FID}"` (`:1102`).

Larger (architectural) alternative — teach `bkit-ship.md` Steps 2/5/13 a `feat|fix` branch-prefix variable. Either way correct the routing table in `.bkit/cloud.md`, `docs/deployments.md` and the plan's Breaking-Changes claim. Cross-ref: this also invalidates the "fix-PR green CI now auto-merges" premise R2 relies on in M3 below.
- **agreement:** 1/2 (R2 assumed the ship path functioned and cited it as `/bkit-ship <PR>`; the dispatch is `/bkit-ship {FID}` — R1's reading is the one verified against `bkit-auto.md:204`)

### H1 — HIGH · mechanical · `FID` reaching `bkit_dev_dispatch_guard` on the `fix/**` arm is neither slug-asserted nor slug-normalised (merged R1-F2 + R2-F1)

- **lens:** R1 (bugs / edge cases) + R2 (security) — merged: same call site, same root cause, one fix site
- **location:** `.bkit/templates/.github/workflows/bkit-cloud.yml:329` (marker derive), `:338` (branch fallback), `:366` (guard call) + mirror `:565`,`:569`,`:588`; guard body `:213-224` (mirror `:481-492`); contrast the asserted `dev` arm at `:286`
- **exploit scenario:** two live defects of the same omission — the `dev` arm asserts `^([0-9]+|[a-z]+-[0-9]+)-[a-z0-9-]+$` before use (`:286`), the `feat/**`/`fix/**` arm asserts nothing before passing `$FID` to the guard at `:366`.
  1. _Correctness (R1):_ the fix arm's fallback `sed -E 's#^(feat|fix)/##' | grep -oE '^[0-9]+|^[a-z]+-[0-9]+'` truncates the slug to its leading id (`363`), and per the code's own comment the fix PR body carries no `bkit:fid=` marker so `fix/**` **always** lands here. `find … -path "docs/plans/*/logs/363"` never matches the real `logs/363-widen-bkit-cloud-trigger/`, so `:221` invents `docs/plans/$(date -u +%Y%m)/logs/363/`, `mkdir -p`s it, appends the row and **commits + pushes that orphan directory to `dev`** on every `fix/**` CI failure (repo pollution; the operator-reset notice points at the wrong file). The two surfaces also count against different keys, so the documented invariant — `.bkit/cloud.md` "One budget per FID shared across the `dev` and `fix/**` failure surfaces" — is false: a FID can burn 3 dev **and** 3 fix dispatches, doubling the bound.
  2. _Security (R2):_ when the marker path _is_ taken, `grep -oE 'bkit:fid=[^[:space:]>]+'` (`:329`) admits `/`, `.`, `..` and glob metacharacters straight into `find -path`, `status_dir=`, `mkdir -p`, `git add`, `git commit -m "docs($guard_fid): …"`, `git show "origin/dev:${status_file}"` and `git push origin dev`. A collaborator (or, on a public consumer repo, any fork contributor whose CI runs) authoring a `fix/**` PR body with `bkit:issue=#<any bkit:auto issue>` + `bkit:fid=../../../../.bkit/scripts` and a `bkit [auto route]` head subject gets the privileged `workflow_run` job to `mkdir -p` and append `status.jsonl` outside the log tree and **push it to `dev` as the bot** on the first red CI run; `bkit:fid=*` redirects the write into an unrelated FID's log dir via the `find` pattern. This violates the MUST in `docs/security.md:87` § FID slug allowlist ("every FID resolution site MUST assert a strict slug allowlist before path construction … rejecting `/`, `.`, `..`"), and makes the new `docs/security.md:89` claim true only for the `dev` path.
- **suggested fix:** one change closes both — assert **and** normalise at the guard boundary, fail-closed: at the top of `bkit_dev_dispatch_guard` (both jobs + template) add `[[ "$guard_fid" =~ ^([0-9]+|[a-z]+-[0-9]+)-[a-z0-9-]+$ ]] || { echo "::notice::Invalid FID '$guard_fid' — refusing to write counter."; return 1; }`, and stop truncating on the fix arm so the key matches the `dev` arm's: derive `GUARD_FID=$(echo "$BRANCH" | sed -E 's#^(feat|fix)/##')` (leaving `FID`/`ISSUE` unchanged for the kill switch) and call `bkit_dev_dispatch_guard "$GUARD_FID" "$HEAD_SHA"`. Preferably also apply the allowlist to the marker-derived `FID` at `:329` itself, falling through to the branch fallback on mismatch exactly as `docs/security.md:87` prescribes. Verify the two surfaces then share one counter key (plan T13 currently asserts the truncated value and must be updated).
- **agreement:** 2/2

### M1 — MEDIUM · mechanical · the dispatch cap fails OPEN on any `jq` error over `status.jsonl`

- **lens:** R1 (bugs / edge cases)
- **location:** `.bkit/templates/.github/workflows/bkit-cloud.yml:226-231` (mirror `:494-499`)
- **exploit scenario:** `dev_count=$(jq -s … "$status_file" 2>/dev/null || echo 0)`. `status.jsonl` is a `merge=union` NDJSON file appended by many workflows, subagents and now two concurrent cloud jobs; one truncated line, stray non-JSON line or conflict artefact makes `jq -s` exit non-zero, stderr is discarded and `dev_count` silently becomes `0`. The cap then never trips regardless of how many `dev-dispatch` rows exist, so the cross-session loop it exists to bound (fix pushed → CI red → debug dispatched → fix pushed …) runs unbounded, each iteration burning a paid agent run. Note the asymmetry: the sibling `landed` check was deliberately hardened fail-closed (`:249-259`) while the count that enforces the bound fails open.
- **suggested fix:** distinguish "no rows" from "cannot parse" — drop `|| echo 0`, capture the exit status and treat non-zero `jq` as cap-exceeded: `if ! dev_count=$(jq -s … "$status_file" 2>/dev/null); then echo "::notice::status.jsonl unparseable for $guard_fid — refusing to dispatch uncounted (fail-closed)."; return 1; fi`. Optionally pre-filter with `grep -E '^\{' "$status_file" | jq -s …` so one bad line degrades to a count rather than an unbounded loop.
- **agreement:** 1/2

### M6 — MEDIUM · mechanical · `bkit-auto-dev` is a single concurrency group for all FIDs; superseded FIDs are silently dropped

### L2 — LOW · architectural · the dispatch cap — designated a security control — is enforced from a repo file the controlled principal can rewrite

- **lens:** R2 (security)
- **location:** `.bkit/templates/.github/workflows/bkit-cloud.yml:213-260` + `.bkit/scripts/bkit-counter-bus-config.sh:24`, doc claim `docs/security.md:89`
- **exploit scenario:** `docs/security.md:89` states `MAX_DEV_DISPATCH_ATTEMPTS=3` "is itself a cost/security control: without it, a stuck `dev`/`fix/**` feedback loop could dispatch unbounded paid agent sessions". Enforcement reads `dev-dispatch` rows from `docs/plans/{YYYYMM}/logs/{FID}/status.jsonl` on `origin/dev` — the same file the dispatched `/bkit-debug` session writes with `contents: write` — and the operator reset procedure is literally "delete dev-dispatch rows in status.jsonl" (`:234`). There is no independent counter, so any actor or prompt-injected/malfunctioning agent that can push to `dev` (every dispatched session can) resets the only bound to zero. A session steered by a poisoned failure log or fixture into rewriting `status.jsonl` — a file it legitimately edits every run — silently restores 3 remaining attempts and the failure→debug→push→failure cycle continues indefinitely. The fail-closed push verification (`:249-259`) protects only against under-counting from lost pushes, not against reset.
- **suggested fix:** derive the count from a source the dispatched session cannot rewrite — `gh run list --workflow bkit-cloud.yml` filtered by FID, or an append-only tracker comment/label written with a token the session does not hold — or minimally cross-check the file-derived count against `gh api` run history and take the maximum before dispatching. At the very least document the self-reset property next to the "cost/security control" claim rather than presenting the cap as a hard bound.
- **agreement:** 1/2
