# Plan Review

## CRITICAL

**C-1 — Severity ladder inconsistency in reconciler spec (Architecture § bkit-build-challenge-reconcile.md, Process step 6 and 8)**

The plan specifies the severity tie-break as "max-wins (BLOCK > WARN > PASS / FAIL > CONCERNS > PASS)" — mixing two incompatible severity ladders. The actual `bkit-build-challenge.md` source uses `CRITICAL/HIGH/MEDIUM/LOW` for finding severity and `PASS/CONCERNS/FAIL` for verdict. There is no `BLOCK` or `WARN` severity in the existing prompt. The reconciler spec imports `BLOCK`/`WARN` from the plan-review ladder (used in `bkit-plan-review-*` prompts), which is a different domain. The Acceptance Scenario edge case table also references `R1 PASS / R2 BLOCK` — but a challenge agent never emits `BLOCK`. This inconsistency will produce an incoherent reconciler prompt that cannot operate correctly against its actual inputs. The reconciler Process step 6 must use the correct challenge verdict ladder: `FAIL > CONCERNS > PASS` (max-wins). All references to `BLOCK`/`WARN` in the reconciler spec must be replaced.

**C-2 — Fix 3 gate location conflicts with plan's own Concrete Example (bkit-plan.md Step 3 vs plan-input.md Fix 3)**

The Linear issue § Fix 3 says the gate fires at Step 1 ("after reading `plan-input.md`"). The plan's Concrete Example also says Step 2 writes `plan-input.md` and Step 3 fires the gate. However, the Architecture section § `[MODIFY] bkit-plan.md` inserts the gate at Step 3 sub-step 0 (pre-subagent), which matches the Concrete Example. The source Linear issue says "Step 1", which would be before the worktree is even set up and `plan-input.md` may not yet be written. The plan resolves this discrepancy by placing the gate at Step 3 (correct), but the inconsistency with the Linear issue's wording is unacknowledged. More critically, the grep command `grep -oE 'BAR-[0-9]+' docs/plans/logs/{FID}/plan-input.md | sort -u | wc -l | tr -d ' '` does not account for the case where `plan-input.md` is generated by copy/paste with FID tokens that could include the current issue's own `BAR-N`. If the source Linear issue description mentions the parent BAR-137 or any other `BAR-N` reference, the gate will false-positive on legitimate single-issue inputs. The plan acknowledges this as a known false positive in the edge case table but does NOT prescribe any mitigation other than telling the user to rephrase their input. The runbook Task 9 does not include a verification step for the false-positive scenario. This is incomplete — the gate should at minimum document that the count includes ALL `BAR-N` tokens found in the file (including those in prose) and the runbook should verify the exact grep produces the expected count on the BAR-155 plan-input itself (which contains `BAR-137`, `BAR-141`, `BAR-131`, `BAR-139`, `BAR-142`, `BAR-93`, `BAR-132` — a count of 8, meaning BAR-155's own plan-input.md would trigger this gate).

**C-3 — Step renumbering in bkit-build.md is underspecified and creates a verification gap**

The plan prescribes renumbering former Steps 10–17 to Steps 11–18 in `bkit-build.md` and instructs a `Grep` post-edit on `Step 1[0-7]` to confirm zero refs to old numbers remain. However, the existing workflow at Step 11 (`Build Challenge Tests`) has routing that cross-references Step 9 by number: `6. **If** CHALLENGE_VERDICT = FAIL → **Re-run Step 9**.` After renumbering, Step 9 (parallel challenge) remains Step 9 (unchanged) but Step 10 becomes the new reconcile step. The re-run routing in (former) Step 11 (now Step 12) still says "Re-run Step 9" — which after renumbering would be correct (Step 9 is still the parallel challenge launch). But the plan does not call this out explicitly, leaving ambiguity about whether "Re-run Step 9" stays as-is or needs updating. Additionally, the plan does not specify where `CHALLENGE_REMEDIATE_ATTEMPT` initialisation lives in the new step layout — currently it is set in Step 9 but after the split, the parallel pair (Step 9) and reconcile (Step 10) each touch the same counter. The runbook Task 11 does not include a verification step tracing the `CHALLENGE_REMEDIATE_ATTEMPT` counter lifecycle through the new three-step sequence.

**C-4 — `docs/decisions.md` ADR missing from Derived Test Matrix but present in Runbook (gap = untestable)**

Task 17 in the Runbook appends an ADR to `docs/decisions.md`. The Documentation Updates table lists this as required. However, the Derived Test Matrix has no row covering this task. Per template rule: "Each row → one Agent Execution Runbook task. No row without a target file." Same gap applies to `docs/pending.md` (Task 18). Both are implementation tasks without test matrix coverage.

## OPTIONAL

**O-1 — `REBASE_FAILED` variable scoping across bash heredoc boundaries**

The plan inserts the `REBASE_FAILED=true` flag inside a bash block, then adds a separate sub-step `3a` outside the bash block that tests `REBASE_FAILED`. In bkit workflow files, orchestrator bash blocks are executed as discrete shell invocations — a variable set in one `bash` block is not necessarily visible in subsequent prose instructions or subsequent bash blocks unless the orchestrator explicitly re-evaluates it. The plan should either (a) keep the `REBASE_FAILED` check inside the same bash block with an early-Failure-Path invoke, or (b) use the shell exit code / a temporary sentinel file as the inter-block signal. This matches how `exit 1` worked before, but the new pattern requires the orchestrator to read `REBASE_FAILED` from shell state that may not persist. The plan should clarify the mechanism.

**O-2 — bkit-build-challenge-reconcile model name drift in prompts.md update**

In § `[MODIFY] .agents/prompts.md`, the plan lists `bkit-build-challenge-2` row as `gpt-5.4-high` / `claude-sonnet-4-6` for the "thinking mode" column. The first value `gpt-5.4-high` appears to be a copy-paste error from a different model tier table — all other `-2` slot agents use `claude-sonnet-4-6`. This should be verified against the actual `prompts.md` model table column headings before Task 13 executes.

**O-3 — Reconciler `cp` step conflicts with its own stub-first protocol**

Architecture § `bkit-build-challenge-reconcile.md` Process step 1 says "cp of one input as scaffold" then step 2 "prepend Verdict: PENDING header". A `cp` of an input file (which already has a Verdict line from the challenge agent) means the prepend in step 2 would produce a duplicate Verdict header. The reconciler should instead `Write` a fresh skeleton (matching how `bkit-design-update.md` operates) rather than `cp` an input. The plan's body says "Process step 1: cp of one input as scaffold (or fresh Write of skeleton — match bkit-design-update.md exactly)" — the `or` is ambiguous; the running text should commit to `Write` a fresh skeleton to avoid the duplicate-header defect.

**O-4 — Task count grep pattern mismatch between workflow gate and complexity-check prompt edit**

Architecture § `bkit-plan.md` Change 2 uses `grep -cE '^- \[ \] \*\*Task'` to count tasks. Architecture § `bkit-plan-complexity-check.md` Change says `grep on '^- \[ \] \*\*Task' or equivalent task marker`. The plan-input § Fix 2 says the workflow greps `^### Task `. There are now three different task-marker patterns across the plan. The actual plan template uses `- [ ] **Task N:**` (verified from `docs/plans/template.md` Agent Execution Runbook section). The workflow-side grep pattern `^- \[ \] \*\*Task` is correct for the template. The discrepancy between the Linear issue's `^### Task ` suggestion and the plan's actual pattern should be explicitly resolved in the runbook (Task 9 verification step should confirm the grep pattern produces the correct count on a known plan file before committing the workflow edit).

**O-5 — No Failure Path assertion after Step 9 parallel pair if one file is empty but the other is not**

The plan specifies: "Sub-step 2: assert both files exist and non-empty → Failure Path on empty." The existing workflow Step 9 (single agent) has the same assertion. However, if `build-challenge-1.md` is non-empty and `build-challenge-2.md` is empty, the plan routes to Failure Path. This is correct but means the non-empty `-1` artifact is discarded without any recovery path. The reconciler never gets to run. A CONCERNS-level finding: the plan could note that an alternative is to run the reconciler with one input and a sentinel empty-input, but the plan explicitly prescribes hard Failure Path. This is an acceptable design choice but the runbook should verify the Gate 9 checkbox explicitly covers the two-file partial-empty case.
