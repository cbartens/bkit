### Critical (must-fix before Step 5)

- [C1] **Template skeleton missing 8 mandatory sections.** The plan omits the following sections required by `docs/plans/template.md`: (a) `Breaking Changes & Naming Review` with human-confirmation checkbox — required because P2.T9 (`process.exit(1)` behaviour change), P3 Tier-1→Tier-2 reclass, and `__bkit__` namespace are all explicitly flagged as Major-Changes-bar items in the plan's own Risks table; (b) `Pre-Flight / Dependencies` section (core checklist including prerequisite plans); (c) `Rollback Strategy` table; (d) `Architecture & Component Changes` section (file inventory with `[NEW]`/`[MODIFY]`/`[DELETE]` tags); (e) `Data Schema Integration` (even if "None — no DB"); (f) `Security & Privacy` checklist; (g) `Merge Method` statement; (h) numbered `Agent Execution Runbook` with `[ ]` per-task checkboxes (template mandates checkboxes; the plan uses narrative task descriptions). Missing human-gate checkboxes means a build-phase agent cannot confirm Gate 1 is cleared before starting implementation. **Suggested fix:** add each missing section verbatim from the template with the bkit-specific content filled in; move breaking-change items to the Breaking Changes section and add the confirmation checkbox.

- [C2] **`migrateTier1JsonToTier2` (P3.T6) has no source-of-truth for previous defaults.** The task says "identify keys matching previous bkit defaults, lift into `__bkit__` envelope" but no task builds or references a lookup table of what bkit's canonical default values were at each prior version. Without that table, the migration function cannot distinguish consumer-added content from bkit-shipped defaults in old Tier-1 files. On the `app-gether-life` scenario (three upgrades, manual re-merges), incorrect identification of consumer keys as bkit defaults would silently destroy them — exactly the failure the plan is trying to prevent. **Suggested fix:** add a sub-task to P3.T6 to define and ship a `BKIT_TIER1_DEFAULTS` versioned constant or extract it from the `bkit-modules.ts` manifest built in P2.T1; make P3.T6 depend on that artifact explicitly.

Suggested fix: decide on one flag style and remove the other from the P2.T6 scope; note the choice explicitly.
