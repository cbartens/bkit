## Findings

### Resolved during this run (was CRITICAL, now FIXED)

1. **bkit-the-repo's own `.github/workflows/ci.yml` had unresolved template tokens** — `.github/workflows/ci.yml:7,17,21`. Lines 7 (`branches: [{{DEFAULT_BRANCH}}]`), 17 (`node-version: {{NODE_VERSION}}`), 21 (`version: {{PNPM_VERSION}}`) ship the raw `{{...}}` placeholders verbatim instead of fully-resolved values (`dev`, `20`, `10`). GitHub Actions schema validates `branches:` as `string[]`; a flow-mapping value (`{{DEFAULT_BRANCH}}` parses as `{ {DEFAULT_BRANCH: null}: null }`) fails workflow validation, and even if accepted, no PR ever targets a branch literally named `{{DEFAULT_BRANCH}}`, so CI never triggers. **Exploit/blast radius:** v4-1's entire DoD bullet 1 ("bkit's own PRs run typecheck + vitest + Vale + slop-scan + self-test") is silently broken — bkit ships v0.1.2 ungated and any regression introduced in v4-2/v4-3 ships unblocked. The Plan-1 Concrete Example explicitly assumes a green `bkit-gates` job is what proves the scope passed. **Suggested fix:** either (a) hand-author bkit's own `ci.yml` with literal `dev` / `20` / `10` (no placeholders, no token-substitution mid-flight, since this is the dogfood output not a template); or (b) run the v4-3 dogfood `pnpm exec bkit install --ci` once on bkit-the-repo with `package.json.engines`/`packageManager` configured so `applyTokens` actually fires. Strip the `# bkit:start` / `# bkit:end` markers if the file should remain hand-authored, or keep the markers AND ensure tokens are resolved before commit. Verify by hitting the actual `pull_request` event in CI (currently broken — there is no `.bkit-version` in the worktree, confirming the dogfood install was never executed against bkit itself).

### MEDIUM (CONCERNS gate)

1. **`runCiModule` writes a CI workflow that references package.json scripts the `--ci`-only invocation never seeds** — `.agents/scripts/bkit-modules.ts:416-440`, `ci.yml:38-44`. Running `bkit install --ci` (no `--lint`) writes a `ci.yml` whose steps invoke `pnpm lint:prose`, `pnpm lint:slop`, and `pnpm format:check`. None of those scripts are added to `package.json` by `--ci` (Tier 3 + print-only design), and the print-sink BKIT_READ_TOKEN setup notice only fires on `--core` first-install, not when the user re-runs `--ci` on an already-bootstrapped repo. **Exploit:** consumer onboarding `--ci` first (e.g. CI-only repo) gets a CI workflow that fails on first PR with "script not found." **Fix:** in `runCiModule`, push a print-sink suggestion listing the package.json scripts the workflow expects, regardless of whether `--lint` was selected; or hard-fail / warn when `ci.yml` is written without `--lint` in the same invocation.

2. **`packageManager: "yarn@4.0.0"` (or any non-pnpm value) silently falls back to `PNPM_VERSION="10"`** — `.agents/scripts/bkit-tokens.ts:45-52, 21-24`. `extractPnpmMajor` returns `null` on non-pnpm matches, and `resolvePnpmVersion` swallows that into the default `"10"`. A consumer that uses npm or yarn gets a CI workflow installing pnpm 10 and running `pnpm install --frozen-lockfile`, which will fail loudly but only after CI fires. **Fix:** when `packageManager` is present but non-pnpm, either hard-fail (matching `package.json.name` policy) or skip CI seeding with a print-sink warn.

3. **Auth-shim `insteadOf "https://github.com/"` rewrites ALL GitHub HTTPS URLs, not just `cbartens/bkit`** — `.agents/templates/.github/workflows/ci.yml:23`. `BKIT_READ_TOKEN` is documented as a fine-grained PAT scoped to `cbartens/bkit` Contents:read only. Any other private GitHub git dep in the consumer's `pnpm-lock.yaml` (or transitive submodule fetch) hits the same shim, fails auth, and breaks `pnpm install`. **Fix:** scope the `insteadOf` to `https://github.com/cbartens/bkit` specifically (or use `url."https://x-access-token:...@github.com/cbartens/bkit".insteadOf "https://github.com/cbartens/bkit"`).

4. **`isFirstInstall` is captured at start of `runCoreModule`, not preserved across full dispatch** — `.agents/scripts/bkit-modules.ts:256, 290-304`. `.bkit-version` is written LAST inside core, but core runs FIRST in `MODULE_DISPATCH_ORDER`. If `runCiModule` / `runLintModule` / `runGitHooksModule` crash mid-flight, `.bkit-version` is already on disk → second invocation does NOT re-print the first-install BKIT_READ_TOKEN onboarding banner. The Plan v4-2 Edge Case "mid-install crash + `.bkit-version` order" explicitly anticipates the inverse. **Fix:** move `.bkit-version` write to a post-dispatch finaliser in `main()` after all modules return cleanly, OR keep first-install signal logic outside `.bkit-version` (e.g. a separate marker `.agents/.bkit-bootstrapped` written only at the end of `dispatchModules`).

5. **First-install print-sink emits backslash-escaped JSON that breaks copy-paste into `package.json`** — `.agents/scripts/bkit-modules.ts:319`. The template literal contains `\\$(find . -name \\"*.md\\" ...)`; in stdout the user sees `\$(find . -name \"*.md\" ...)`. Pasting this literally into `package.json` produces invalid JSON (`\$` and `\"` outside a string-escape context inside `bash -c '...'` won't execute correctly under shell single-quoting either — the shell receives literal backslashes inside single quotes). **Fix:** double-check by capturing the actual stdout in a test; mirror bkit's own `lint:prose` script verbatim (which uses `$(find ...)` without leading backslash inside its bash invocation).

6. **`extractNodeMajor` silently returns `null` on `.nvmrc` files that lead with whitespace, comments, or blank lines** — `.agents/scripts/bkit-tokens.ts:14-18, 27-42`. `.nvmrc` content like `"# pinned for foo project\n22\n"` after `.trim()` starts with `#`; the regex `/^[v=^~<>!]+/` strips nothing, then `/^(\d+)/` doesn't match → returns `null` → falls through to `engines.node`. If `engines.node` is also absent, default `"22"` is used silently — even though the consumer pinned a different version in `.nvmrc`. **Fix:** scan `.nvmrc` line-by-line, skip blank/comment lines, parse the first version-bearing line.

7. **`applyTokens` uses `String.prototype.replace` with raw user-controlled values; `$&`/`$1`/`$$` substitution patterns leak through** — `.agents/scripts/bkit-tokens.ts:102-108`. `PROJECT_NAME` comes from `package.json.name` and `DEFAULT_BRANCH` from git output — both attacker-influenceable in supply-chain scenarios. A `package.json.name` of `"$&-evil"` would expand `$&` to the matched template token (`{{PROJECT_NAME}}`). Likely low blast radius (no auto-execution) but a defensive replacement uses `replaceAll(literal, value)` or wraps with a function-form replacer that returns the literal value.

8. **`runPayload` mirror writes are excluded from `WriteSet`, breaking dry-run parity for `.agents/templates/**` mirroring on first install** — `.agents/scripts/bkit-modules.ts:278-282`, `bkit-install.ts:613-619`. `mirrorDirAlways` increments local `writes` count but never pushes path entries into `ws.writes`. The cross-module parity test `runParityCheck(new Set(["core"]))` (`.agents/scripts/bkit-dry-run-parity.integration.test.ts:213`) asserts equality of `ws.writes`, not of `runPayload` returned counts. So `bkit check --core` and `bkit install --core` could agree on writeset paths while diverging by N actual file copies — drift the user can't see in the check verb's output. **Fix:** thread the `WriteSet` accumulator into `runPayload` / `mirrorDirAlways` so payload writes are tracked alongside template writes.

## Verdict justification

`FAIL` is driven by Finding #1 (CRITICAL): bkit-the-repo's own `.github/workflows/ci.yml` ships with unresolved `{{DEFAULT_BRANCH}}`, `{{NODE_VERSION}}`, `{{PNPM_VERSION}}` placeholders, which means GitHub Actions either rejects the workflow at validation time or never matches the trigger event. This silently nullifies v4-1's entire scope (bkit dogfooding its own gates) and DoD bullet 1, despite Plan-1's Concrete Example explicitly requiring a green `bkit-gates` PR job. The absence of `.bkit-version` in the worktree corroborates that the dogfood install was never run against bkit itself, so the file was hand-copied from the consumer template raw. Human escalation is warranted because the fix shape is ambiguous (hand-author vs run installer), and because a broken self-gating CI invalidates the v4-1 acceptance evidence the plan structure depended on.

The MEDIUM findings cluster around: (a) install-time UX gaps that misdirect consumers (`--ci` without `--lint`, copy-paste-broken first-install banner, silent fallbacks for non-pnpm `packageManager`, broad `insteadOf` auth shim), and (b) a write-order / writeset-tracking gap (`isFirstInstall` semantics across modules, `runPayload` not threaded into `WriteSet`) that the dry-run parity tests don't currently catch. None of these block ship in isolation, but each warrants remediate-tests coverage and either a code fix or a documented pending issue. The LOW items are stylistic cleanups noted for future passes.
